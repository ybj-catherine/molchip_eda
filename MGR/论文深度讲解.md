# MGR（Mutation-Guided Refinement）论文深度讲解

> **Closing the Loop on LLM-Generated RTL Assertions with Quality-Aware Formal Verification**
> 作者：Ramesh Krishnamurthy, Danial Chitnis, Themis Prodromakis
> 机构：University of Southampton
> arXiv: 2606.21451 v1 · 2026-06-19 · cs.AR
> 原文：<https://arxiv.org/abs/2606.21451>
> 代码：开源（论文描述为"lightweight, open-source framework"）

---

## 1. 一句话定位

**MGR（Mutation-Guided Refinement）是一个"test-the-test"框架，把 LLM 生成的 RTL assertions 喂入 formal verification 流水线，通过注入 synthetic RTL mutants 看哪些断言"对的原因不对"（vacuous / weak / wrong-reason-pass），把 surviving mutants 作为反馈迭代让 LLM 强化 assertion set；在 7 个 RTL 设计上达到 90-100% effective kill rate（SDRAM 除外），配合 Architecture-Aware Solver Selection 把 assertion-solving 延迟降低 49%，用 Causal Narrative Synthesis（CNS）生成可解释的失败叙述。**

这句话里的 6 个技术承重点，下文逐一拆解：

1. **Mutation-Guided Refinement（MGR）核心循环** — 注入 RTL mutants → formal verify 现有 assertions → surviving mutants → feedback 给 LLM → 强化 assertions
2. **Effective kill rate $\rho_{\text{eff}}$** = Killed / (Total − Invalid)，过滤掉无效 mutants 的归一化指标
3. **Architecture-Aware Solver Selection** — 根据 RTL 结构（control/data path、深度、并行度）选最适合的 SMT solver，匹配 oracle 100%，延迟降低 49%
4. **Causal Narrative Synthesis（CNS）** — LLM 生成失败叙述（"为什么这个 assertion 失败"），faithfulness 从 37% 提到 ≥75%（带 hint 可到 100%）
5. **"对的原因不对" 检测** — vacuous assertions（恒真/恒假）、wrong-reason-pass（mutation 没 kill 但 RTL 行为变了）
6. **闭环而非一次性生成** — 把 formal verification 变成 adversarial refinement loop

## 3. 输入 / 输出

### 3.1 输入

- **RTL 设计**：7 个 benchmark design
- **LLM-generated assertion set**：由某个 LLM（如 GPT-4）生成的 SVA 断言
- **Formal verification tool**：Yices 或 SymbiYosys（从描述看是开源形式化工具）
- **可调用的 LLM**：用于 refinement + CNS

具体例子（简化 ALU 的 SVA）：

```systemverilog
module alu(input logic [3:0] a, b, input logic [1:0] op, output logic [7:0] y);
  always_comb begin
    case (op)
      2'b00: y = a + b;
      2'b01: y = a - b;
      2'b10: y = a & b;
      2'b11: y = a | b;
    endcase
  end
endmodule

// LLM-generated assertion (可能有问题：vacuous)
property p_overflow;
  @(posedge clk) (op == 2'b00) |-> (y == a + b);  // 恒真！
endproperty
assert property (p_overflow);  // vacuous: y 确实是 a+b, 但断言没验证 add 的正确性
```

### 3.2 中间产物

- **Mutants**：注入的 RTL faults
- **Mutant classification**：KILLED / SURVIVED / INVALID / TIMEOUT / INCONCLUSIVE
- **Effective kill rate $\rho_{\text{eff}}$**
- **Causal Narrative**：失败叙述（自然语言 + 引用具体信号）

### 3.3 输出

- **Refined assertion set**：经过 MGR 迭代强化后的 SVA
- **Quality report**：每个 assertion 的 quality metric
- **Solver selection**：选定的 SMT solver

### 4.1 整体 Pipeline

```
│  │  (SVA)        │   │  (RTL faults)│   │  (Yices等)   │             │
│  └──────────────�   └──────────────┘   └──────┬───────┘             │
│                                                  │                   │
│                                                  ▼                   │
│                                          ┌──────────────┐           │
│                                          │  Mutant      │           │
│                                          │  Classifier  │           │

│       ┌────────────────┐                                              │
│       │  Causal        │                                              │
│       │  Narrative     │                                              │
│       │  Synthesis     │                                              │
│       └────────────────┘                                              │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 核心模块详解

**Module 1: Mutation Injector**

- 做什么：在 RTL 设计中注入 synthetic faults
- 实现：mutation operator set（类似 Mantra 但针对 formal 验证场景）
- 输出：mutant RTL 集合

**Module 2: Formal Verifier + Solver Selector**

- 做什么：用 formal tool 验证 assertion set 在 mutant 上的行为
- 关键：Solver selection 不是 always Yices，而是按 architecture 选最合适的
- Architecture-Aware：识别 control flow depth、data path width、并发度等

**Module 3: Mutant Classifier**

- 做什么：每个 mutant 分类为 KILLED / SURVIVED / INVALID / TIMEOUT / INCONCLUSIVE
- 分类规则：
  - KILLED：assertion 在 mutant 上 fail
  - SURVIVED：assertion 在 mutant 上仍 pass（漏洞）
  - INVALID：mutation 编辑后 RTL 不再是有效硬件变体
  - TIMEOUT：proof 超时（深度不够）
  - INCONCLUSIVE：边界情况

**Module 4: Effective Kill Rate 计算器**

- 做什么：算 $\rho_{\text{eff}}$ = Killed / (Total − Invalid)
- 关键：过滤 INVALID 后才算有效命中率

**Module 5: LLM Refinement**

- 做什么：用 surviving mutants 作为 feedback 喂给 LLM，让 LLM 强化 assertion
- 实现：prompt = `现有 assertion + surviving mutants + RTL context` → response = `refined assertions`
- 关键意义：把 formal verification 变成 adversarial loop

**Module 6: Causal Narrative Synthesis（CNS）**

- 做什么：为失败的 assertion 生成可解释叙述
- 实现：zero-shot LLM → faithfulness 100% 识别正确信号（无幻觉）
- 改进：用 case-specific hints 后 faithfulness 从 37% 提到 ≥75%（100% with hints）

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的工具/模型 | 是否需训练 |
|------|------|------|---------------|:---:|
| Mutation Injector | RTL | mutants | mutation operators | 否 |
| Formal Verifier | mutants + assertions | PASS/FAIL | Yices / SymbiYosys | 否 |
| Solver Selector | RTL architecture | solver choice | rule-based | 否 |
| Mutant Classifier | verifier output | K/S/I/T labels | 自研 | 否 |
| LLM Refinement | surviving mutants | refined assertions | LLM | 否 |
| CNS | failed assertions | causal narrative | LLM | 否 |

## 5. 关键公式

### 5.1 Effective Kill Rate

$$
\rho_{\text{eff}} = \frac{\#\text{Killed}}{\#\text{Total} - \#\text{Invalid}}
$$

- $\#\text{Killed}$：被 assertion kill 的 mutant 数
- $\#\text{Total}$：注入的 mutant 总数
- $\#\text{Invalid}$：INVALID 类别（不构成有效硬件变体）
- $\rho_{\text{eff}}$：有效 kill rate，refinement trigger 阈值 = 85%

**工程直觉**：过滤掉 INVALID 后，剩下的 mutants 才是 "assertion 是否真的强" 的有效信号。

**为什么这么设计**：如果不剔除 INVALID，会低估 assertion 强度（因为有些 mutant 不是有效设计）。Refinement trigger 阈值 85% 是经验值，"robust harnesses typically converge to 90-100%"。

### 5.2 Refinement Trigger

$$
\text{Refine} \iff \rho_{\text{eff}} < \tau = 0.85
$$

- $\tau = 0.85$：refinement trigger 阈值
- 触发条件：effective kill rate 低于 85%

**Refinement Loop**：
$$
\text{Assertions}_{k+1} = \text{LLM}(\text{Assertions}_k, \text{SurvivedMutants}_k, \text{RTL})
$$

- 每轮迭代把 surviving mutants 反馈给 LLM
- 循环直到 $\rho_{\text{eff}} \geq 0.85$ 或达到 max iteration

### 5.3 Solver Selection 的延迟节省

论文报告：
- **Mean assertion-solving latency**：always Yices vs rule-based selector
- **Reduction**：约 49%（具体数字待论文补充）

直觉：不是所有 RTL 都适合 Yices，按 architecture 选更高效的 solver 可显著降低 formal proof 时间。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练**。整个框架是 formal verification + LLM prompt 的组合，所有组件都是预训练的或规则引擎。

### 6.2 实验设置

- **Benchmark**：7 个 RTL 设计（具体名称待论文补充；提到 SDRAM 是 outlier）
- **Assertion 来源**：LLM-generated（GPT-4 级）
- **Mutant set**：synthetic，design-specific tuning 可能需要
- **评估指标**：
  - $\rho_{\text{eff}}$（effective kill rate）
  - Solver selection 的 oracle match rate（100%）
  - Solver selection 的 latency reduction（49%）
  - CNS faithfulness（37% → ≥75% with hints）

### 6.3 关键实验结果

| 设计 | $\rho_{\text{eff}}$ | 备注 |
|------|:---:|------|
| Design 1-6（6 个设计） | **90-100%** | robust |
| **SDRAM** | **plateau** | structural limit：timing-oriented mutations 在 proof depth 内不可观察 |

| Solver Selector 指标 | 数值 |
|--------------------|:---:|
| Oracle match rate | **100%** |
| Mean latency reduction vs always-Yices | **~49%** |

| CNS 指标 | 数值 |
|---------|:---:|
| Faithfulness (zero-shot) | **100%** (correct signals identified, no hallucination) |
| Overall faithfulness (refined prompt) | **37% → ≥75%** |

## 7. 创新点

### 创新点 1：Mutation-Guided Refinement 闭环

- **已有做法**：
  - Krishnamurthy 2026（survivor feedback）
  - Yu DVCon 2024（mutant feedback）
  - 单次 LLM assertion 生成
- **本论文**：把 mutation + formal verification + LLM refinement 构成 adversarial loop
- **关键差异**：loop 的关键是 effective kill rate（不是 raw kill rate），过滤 INVALID 是方法论贡献

### 创新点 2：Architecture-Aware Solver Selection

- **已有做法**：always 用 Yices / 默认 solver
- **本论文**：按 RTL architecture 选最合适的 SMT solver
- **关键数据**：oracle match 100%、latency reduction 49%
- **意义**：formal verification 的工程优化，不是 ML novelty

### 创新点 3：Causal Narrative Synthesis

- **已有做法**：formal verification 失败时给 raw counterexample（工程师自己读）
- **本论文**：LLM 生成自然语言失败叙述
- **关键数据**：faithfulness 37% → 75-100%
- **意义**：让 assertion 失败可解释，降低使用门槛

## 10. 讨论与局限

### 10.1 论文自述的局限

- SDRAM 的 plateau（timing mutations 在 proof depth 内不可观察）
- $\rho_{\text{eff}}$ 依赖 mutation set 选择（可能需要 design-specific tuning）
- CNS 评估限于 failed counterexamples 子集

### 10.2 代码/复现层面的问题

- **"lightweight, open-source"** 但具体 GitHub 链接待论文补充
- **7 designs benchmark 来源**：是公开 IP 还是自研？
- **Mutation operator set**：和 Mantra 的 19 种有何区别？
- **Solver selection rule**：rule-based 是怎么定义的？

### 10.3 本资料包的批判性分析

1. **"Mutation-Guided Refinement" 不是新概念**：Krishnamurthy 2026、Yu DVCon 2024 都有类似工作。MGR 的贡献是把 $\rho_{\text{eff}}$ 形式化并加 architecture-aware solver selection。学术 novelty 在于形式化 + 工程优化。
4. **CNS 的 faithfulness 提升到 75% 仍不算高**：100% with hints 是 overfit 的体现；without hints 75% 说明 LLM 在 1/4 案例上 hallucinate。工业部署可能不可靠。
5. **Solver selection 的 oracle match 100%**：意味着 rule-based 完美预测了 oracle 选择的 solver。这本身是 overfit 风险——如果换一批 RTL，rule 是否仍 100%？
6. **和 HierSVA、AssertLLM 等 LLM assertion synthesis 的对比缺位**：MGR 的 baseline 应包括这些工作，但论文只说"LLM-generated"未明确对比对象。
