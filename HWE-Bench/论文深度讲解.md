## 1. 一句话定位

**HWE-Bench 是第一个大规模、仓库级真实硬件 bug 修复 benchmark，包含从 6 个知名开源硬件项目（OpenTitan、XiangShan、Ibex、CVA6、Rocket Chip、Caliptra-RTL）提取的 417 个真实 bug-fix 案例，每个案例在 Docker 容器中提供 buggy/fixed 代码对和验证测试，评估 7 种 LLM + 4 种 Agent 框架后发现最佳方案仅解决 70.7% 的任务，揭示了硬件语义推理和跨文件协调是 LLM Agent 的核心瓶颈。**

---

## 2. EDA 阶段映射（①-⑰）

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ✅ **核心** | Bug 定位在 RTL 代码中 |
| ② 功能仿真 | ✅ **核心** | 用仿真/回归测试验证修复是否正确 |
| ③-⑰ | ❌ | 不涉及综合、物理设计等后端流程 |

**覆盖率：2/17。** 和 BugGen 一样，专注 RTL 前端的 bug 发现和修复。

> ⚠️ HWE-Bench 是 benchmark 不是方法——它提供数据和评估框架，不提出新的 bug 修复算法。它对标的是 SWE-Bench（软件工程领域的真实 bug benchmark）。

## 3. 数据构成

### 3.1 项目分布（完整 417 个任务）

| 项目 | Bug 数 | 占比 | 项目说明 | 语言 |
|------|:------:|:----:|----------|------|
| **OpenTitan** | **245** | 58.8% | Google 开源安全芯片 Root of Trust | SystemVerilog |
| **XiangShan** | 54 | 12.9% | 中科院高性能 RISC-V 处理器 | Verilog/Chisel |
| **Ibex** | 35 | 8.4% | lowRISC 小型 RISC-V CPU 核 | SystemVerilog |
| **CVA6** | 35 | 8.4% | 6 级流水线应用级 RISC-V 核 | SystemVerilog |
| **Rocket Chip** | 32 | 7.7% | RISC-V SoC 生成器 | Chisel |
| **Caliptra-RTL** | 16 | 3.8% | 安全 Root of Trust 模块 | SystemVerilog |

### 3.2 每个任务包含什么

```
每个 task 实例：
  ├── buggy_code/        ← 含 bug 的原始 RTL 代码（整个仓库的快照）
  ├── fixed_code/        ← 修复后的 RTL 代码
  ├── test/              ← 验证测试（仿真/回归测试脚本）
  ├── bug_description    ← bug 描述（来自 commit message / issue）
  ├── diff               ← buggy→fixed 的 unified diff
  └── Dockerfile         ← 可复现的 Docker 环境（含 EDA 工具）
```

### 3.3 为什么 OpenTitan 占这么多（58.8%）

1. OpenTitan 是最大的公开硬件项目之一（31,359 commits）
2. Google 的工程实践好——每条 bug fix 都有清晰的 commit message 和关联 issue
3. 包含了从简单（单文件语法错误）到复杂（跨多模块 CDC 时序问题）的全谱系 bug

## 4. 实验设计

### 4.1 评估的模型与框架

**7 种 LLM**：Claude Sonnet 4、GPT-4o、GPT-4.1、DeepSeek-Coder-V2、Qwen 3 Coder、Gemini 2.5 Pro、Kimi Code

**4 种 Agent 框架**：
- Claude Code（Anthropic 的 coding agent）
- Codex CLI（OpenAI 的 coding agent）
- Kimi Code（Moonshot 的 coding agent）
- OpenHands（开源 agent 框架）

### 4.2 评估流程

```
给定一个 task：
  1. Agent 获得 bug_description + 可访问的代码仓库
  2. Agent 自行定位 bug、生成修复 patch
  3. 在 Docker 容器中运行 test 验证修复
  4. test 全部通过 = SUCCESS
  5. test 有失败 = FAIL

指标：
  - Pass@1：一次尝试的修复成功率
  - Pass@K：K 次尝试中至少一次成功的概率
  - 成本：每次任务的 LLM API 费用
```

## 5. 关键结果

### 5.1 整体表现

| 方案 | 整体 Pass@1 | 小核心 (Ibex) | 复杂 SoC (OpenTitan) |
|------|:----------:|:------------:|:-------------------:|
| Claude Code | **70.7%** | >90% | <65% |
| Kimi Code | ~68% | >88% | <62% |
| Codex CLI | ~62% | ~85% | <55% |
| OpenHands + GPT-4o | ~45% | ~70% | <35% |

### 5.2 为什么复杂项目上表现差？

**三类失败根因**：

| 失败类型 | 占比 | 含义 | 例子 |
|----------|:----:|------|------|
| **Fault Localization** | 35% | 找不到 bug 在哪 | Agent 在错误的模块中搜索 |
| **Hardware-Semantic Reasoning** | 40% | 不理解硬件语义 | 不懂 CDC、不懂流水线时序 |
| **Cross-Artifact Coordination** | 25% | 跨文件协调失败 | bug 涉及 RTL + 配置 + 验证文件 |

### 5.3 成本

- 平均 **$0.10/task**（Claude Code）
- 复杂任务可达 $0.50-1.00
- 417 个任务全跑约 **$40-100**

## 6. 创新点

### 创新点 1：首个真实硬件 bug 修复 benchmark

之前的所有 benchmark（VerilogEval、RTLLM）都是 LLM 生成 RTL 的功能正确性测试，不是真实 bug 修复。

### 创新点 2：仓库级评估

不是给一个独立的 Verilog 文件让 LLM 修，而是给整个仓库——包含上百个文件、复杂的模块依赖、配置文件和验证环境。更接近真实硬件工程师的工作场景。

### 创新点 3：Docker 可复现

每个 task 都有完整的 Docker 环境，保证评估的一致性和可复现性。

---

## 7. 与相关公开工作的关系

本文与同方向工作的关系仅按公开任务定义比较：它聚焦 LLM 生成 RTL 缺陷及其检测能力，不能直接代表真实项目中的缺陷分布。与其他方法对照时，应统一数据来源、缺陷注入方式、检测指标和划分协议。

## 8. EDA 缩写表

| 缩写 | 全称 | 解释 |
|------|------|------|
| RTL | Register Transfer Level | 寄存器传输级，Verilog/VHDL 描述的电路抽象层级 |
| CDC | Clock Domain Crossing | 跨时钟域，信号在不同时钟域间传递 |
| SoC | System on Chip | 片上系统 |
| RoT | Root of Trust | 安全根，芯片安全的基础模块 |
| IP | Intellectual Property | 知识产权模块，可复用的设计单元 |

## 9. 讨论与局限

### 9.1 论文自述的局限

- 数据偏向 OpenTitan（58.8%），可能存在项目特异性
- 仅包含 Verilog/SystemVerilog/Chisel，不包含 VHDL
- Docker 镜像较大，下载和存储成本高
- 不评估 bug 检测（只评估修复），没有 detection 子任务


- **评估框架可以扩展**：可以基于 HWE-Bench 的 Docker 框架构建 bug detection 评估

## 10. 一分钟复述版

1. HWE-Bench 是第一个大规模真实硬件 bug 修复 benchmark
2. 417 个 bug 来自 6 个知名开源硬件项目
3. 最佳 LLM Agent 仅解决 70.7% 的任务，复杂项目 <65%
4. 3 类失败根因：找不到 bug、不懂硬件语义、跨文件协调失败
6. 每个 task 提供 buggy/fixed code、test 和 description，便于独立复核修复结果
