## 1. 一句话定位

**Encarsia 是一个「自动 bug 注入 + 形式化可观测性证明」的 CPU fuzzer 评测平台：通过对 1,672 个 PR 中 177 个真实软件可观测 bug 做归类，归纳出两种最常见的 RTL 源码结构缺陷（信号错连 Signal Mix-ups、条件错写 Broken Conditionals），并在 Yosys 的 RTLIL 中间表示上自动注入近 1000 + 1000 个可控 bug；接着用 JasperGold 或 Yosys 形式化证明每个被注入 bug 的体系结构可观测性，得到可复现的 EnCorpus bug 集；最后在 Ibex、Rocket、BOOM 三个 RISC-V CPU 上对比 DifuzzRTL / ProcessorFuzz / Cascade，三家最佳检测率均不超过 41.67%，证明现有硬件 fuzzer 的「指令级差分粒度」「结构覆盖率」「种子选取」三大宣传点并不提升 bug 检出。**

这句话里的五个承重点，后面逐一拆解：

1. **177 个真实 bug 的调查与二元分类** — Encarsia 不依赖人工编写少量「典型 bug」玩具集，而是对 Ibex、CVA6、Rocket、BOOM 四个开源 RISC-V CPU 项目的 1,672 个 PR 做完整人工审计，筛出 177 个软件可观测 bug，并把它们全部归入「信号错连 / 条件错写」两类。这一实证基础使后续自动注入的 bug 在统计意义上逼近真实 bug 的分布。
2. **Yosys RTLIL 上的可重复注入** — 论文选择 Yosys 综合工具的中间表示 RTLIL 作为注入靶点：条件赋值在 RTLIL 中被规整为多路选择器树、信号赋值被规整为「wire-driver」连接。这两类结构与调查得出的两类 bug 一一对应，使注入变换既可程序化批量生成，又能保证 bug 形态贴近真实错误（论文实验报告每个 CPU 上约 1000 个 Signal Mix-ups + 1000 个 Broken Conditionals）。
3. **形式化可观测性证明（assume-guarantee 验证）** — 仅修改 RTL 是不够的：很多「注入的 bug」会被综合器优化掉或被前置逻辑屏蔽，永远不会出现在体系结构可见状态上。Encarsia 用 JasperGold（商用）或 Yosys（开源）对每个被注入的 DUT 单独证明「存在一段程序，能让该 bug 的影响出现在某个体系结构可见的寄存器/信号/内存位置」，即「architectural observability」。这是 EnCorpus bug 集「确定可触发、可观测」的基石，也是与传统「随机注入 + 跑 fuzz 看结果」评测方法的根本区别。
4. **三大核心反直觉发现** — (a) DifuzzRTL（指令级粒度差分）与 ProcessorFuzz（指令块级粒度差分）检出 bug **完全相同**——更细粒度的差分并不带来更多 bug；(b) DifuzzRTL/ProcessorFuzz 在有无覆盖率反馈下检出 bug **也完全相同**——结构覆盖率指标（CSR 翻转、控制寄存器、MUX 选择端等）不提升 bug 检出；(c) **种子程序**（seed）才是 bug 检出的决定性因素——不同种子找到的 bug 子集差异巨大，而覆盖率反馈反而会丢失部分 bug。
5. **可扩展评测框架 + 标准化基线** — Encarsia 提供 `EncarsiaConfig` 类对任意新 CPU 进行扩展；论文同时在 Cascade、DifuzzRTL、ProcessorFuzz 上交叉评测。它不是「再做一个 fuzzer」，而是「给所有 fuzzer 一份可重复的考卷」。

## 2. EDA 阶段映射（①-⑰）

Encarsia 不生成 RTL、不做综合后仿真、不评估时序/PPA。它是**对 RTL 进行可控扰动 + 在功能仿真阶段验证 bug 可观测性**的工具。整篇论文的核心工作落在 ① 的 RTL 内部表示变换，以及 ② 的功能仿真（含形式化验证器充当的「无限覆盖差分测试」）。

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | Encarsia 直接修改 RTL 设计：在 Yosys RTLIL 中间表示上做信号错连和条件错写变换；这是它能注入「可重复 bug」的物质基础。但 Encarsia 不是为了改设计，而是为了评测别人改的设计 |
| **② RTL 功能仿真** | ✅ **核心** | 形式化验证（JasperGold / Yosys SMT）在本阶段充当「穷举所有可能的指令序列」的功能仿真；同时，被注入 bug 的 DUT 也由 Verilator/Questasim 跑实际 testcase 验证 fuzzer 行为。两者均属于功能仿真阶段的验证活动 |
| ③ 逻辑综合 | ⚠️ 间接 | Encarsia 不评估综合质量，但它的注入操作是在 Yosys 综合流程内部（RTLIL 层）完成的。综合本身不是它的优化目标，但是它的「编辑平台」 |
| ④ 门级仿真 | ❌ | Encarsia 的 bug 注入输出仍是 RTL 级，未下到门级网表；它的形式化验证也跑在 RTL 抽象层而非 SDF 标注的门级 |
| ⑤ STA | ❌ | 不计算路径延迟、不关注时序违例 |
| ⑥ 形式验证 | ✅ **关键依赖** | Encarsia 用 JasperGold 或 Yosys SMT 在 RTL 抽象层做「bug 可观测性证明」——这正是形式验证的典型应用（数学证明存在一条路径让 bug 影响传播到体系结构可见状态）。需要强调：Encarsia 不是 ⑥ 形式验证本身，而是 **使用形式验证作为子工具** 来给它的 bug 集背书 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SDF/SPEF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17（①+②，含 ⑥ 作为子工具）。** Encarsia 是「RTL 阶段的扰动器 + RTL 阶段的可观测性证明器 + CPU fuzzer 评测平台」，与本资料包中 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md) 同属「② RTL 功能仿真」专题，但侧重完全相反：ChipFuzzer 是「用 LLM 生成更好的 testcase」来发现 DUT 的真 bug，Encarsia 是「用自动注入假 bug + 形式证明可观测」来评测别人发现真 bug 的能力。

> ⚠️ **最容易误读的边界：Encarsia 是评测工具，不是验证工具。** 它不试图证明「DUT 没有 bug」，而是回答「这个 fuzzer 的 bug 检出能力有多强」。它的可观测性证明只针对**注入的 bug**——用形式化方法确认注入的扰动确实能产生体系结构后果，并非给原始 DUT 出具无 bug 证明。

## 3. 输入 / 输出

### 3.1 输入

| 输入项 | 数据类型/格式 | 具体说明 |
|--------|--------------|---------|
| **目标 CPU RTL** | Verilog / SystemVerilog / Chisel（→Verilog） | 论文实验用三个开源 RISC-V CPU：Ibex（lowRISC，2 级顺序，RV32IMC）、Rocket（Berkeley，5 级顺序，RV64GC）、BOOM（Berkeley，6/7 级乱序，RV64GC）。三者覆盖最小整数核到 Linux 应用级乱序核的微架构光谱 |
| **Yosys 综合环境** | RTLIL 中间表示 | Encarsia 在 RTLIL 上做注入：条件赋值被规整为多路选择器树 `$mux` 节点；信号赋值被规整为 wire-driver 连接 `connect` 操作。这是注入变换「自动、可重复、贴近真实」的物理基础 |
| **Bug 注入参数** | 命令行参数（`-n` 注入次数、`--category` 选择 Signal Mix-ups 或 Broken Conditionals、`--seed` 随机种子） | 通过 `encarsia.py -d out/EnCorpus -H ibex rocket boom -p 30` 一次性在三个 CPU 上各注入 30 个 bug（论文主表规模）；不带 `-p` 时每个 CPU 默认约 1000 + 1000 个注入 |
| **形式化验证器** | JasperGold 商用 / Yosys 开源 | 提供「bug 是否可观测」的数学证明；JasperGold 含闭源引擎（`-V`），Yosys 用 SMT 求解器实现等价的 assume-guarantee 验证（`-Y`） |
| **CPU 行为模型** | Spike（golden ISA model） | 差分 fuzzer 在探测注入 DUT 时使用：把同一段程序跑在被注入的 RTL 与 Spike 上，发现不一致即认定为潜在 bug |
| **实验预算** | 30 分钟 fuzzing（论文 Docker 复现环境）；24 小时 fuzzing（论文原始实验环境） | 两者并存：Docker 镜像（`make pull` + `make run`）将 fuzzing 缩短到 30 分钟以便复现，原始实验维持 24 小时以贴近正式实验设置 |
| **要评测的 fuzzer** | 三个：DifuzzRTL（含/不含 coverage feedback 两档）、ProcessorFuzz（含/不含 coverage feedback 两档）、Cascade | 所有 fuzzer 均在统一被注入的 DUT 上跑同一时长的 fuzzing；论文附录详细列出每个 fuzzer 在 Docker 中如何配置 |

### 3.2 中间产物

**(a) RTLIL 注入变换的语义示例（论文 §3 思想的可视化）**

Encarsia 注入 Signal Mix-up 的核心操作可表达为：

```
原始 RTLIL：$mux 输入端 A 驱动来自 wire1
原始 RTLIL：$mux 输入端 B 驱动来自 wire2

Encarsia 注入：
  随机选取两个 wire 的驱动关系进行交换
  → $mux 输入端 A 驱动来自 wire2
  → $mux 输入端 B 驱动来自 wire1

并按 Verilog 隐式规则处理位宽差异（截断或符号扩展）。
```

论文中给出的真实示例（来自 Ibex PR #399）：在调试 CSR 访问控制中，设计师把「部分访问检查结果」误用为「最终访问检查结果」——这正是一个 Signal Mix-up：用错了 wire。Encarsia 把这种 bug 抽象为「驱动关系被错误交换」。

**(b) Broken Conditional 的表化注入**

```
原始 RTLIL：case (sel) 2'b00: out = a; 2'b01: out = b; 2'b10: out = c; 2'b11: out = d;
                   ↓ 规整为多路选择器树
           $mux(sel[1],
                $mux(sel[0], a, b),
                $mux(sel[0], c, d))

Encarsia 注入选项：
  - 删去一个 case（等价于「漏掉某些输入组合的处理」）
  - 把某个 case 的输入组合改成 don't-care（X 值变得过于宽松）
  - 改变 case 的优先级（多路选择器树的拓扑重排）
```

**(c) EnCorpus bug 集合（论文核心交付物之一）**

Docker 镜像内含三个 tar 包：`EnCorpus_ibex.tar.gz`、`EnCorpus_rocket.tar.gz`、`EnCorpus_boom.tar.gz`，每个 tar 包对应一个被注入 bug 的 CPU 设计及其可观测性证明。

**(1) EnCorpus bug 集**

- 元信息：注入类型（Signal Mix-up / Broken Conditional）、注入位置（行号 + RTLIL 节点 ID）、CPU 设计 ID

**(3) 八条实验洞察（论文核心反直觉发现）**

1. 指令级差分粒度（DifuzzRTL）与指令块级差分粒度（ProcessorFuzz）检出 bug **完全相同**——更细粒度的差分机制不带来更多 bug。
2. DifuzzRTL/ProcessorFuzz 在有/无 coverage feedback 下检出 bug **也完全相同**——结构覆盖率指标不提升 bug 检出。
3. 种子程序（seed）才是 bug 检出的决定性因素——不同种子找到的 bug 子集差异巨大；coverage feedback 反而会丢失部分 bug（在 time-bounded 预算下）。
4. Cascade（无覆盖率反馈的纯黑盒 fuzzer）检出 bug 显著更快；覆盖率反馈的开销既拖慢发现速度，也会因时间预算限制而漏报。
5. 与特定指令/ISA 扩展绑定的 bug 会被遗漏——fuzzer 没有覆盖到所有指令。
6. 已知 bug 的过滤机制（已知 buggy pattern 排除）会丢掉部分可揭示新 bug 的输入。
7. 同一指令的 ISA 等价源操作数可能来自 CPU 不同内部路径；不覆盖所有指令的 fuzzer 会漏 bug。
8. 微架构 corner case（如 buffer 已满时丢弃数据）会被遗漏——需要系统化的微架构执行路径覆盖。

### 4.2 核心模块逐个详解

**（1）真实 bug 调查器（Bug Survey）**

人工审计 1,672 个 PR，筛出 177 个软件可观测 bug（即「bug 的影响能传播到 CPU 程序员可见的寄存器、内存、CSR 或异常行为」）。这 177 个 bug 经过反复归类发现可以全部装入两个语义类别：
- **Signal Mix-ups（驱动类）**：相似名字/类型/用途的信号被错误替换；操作符误用；驱动关系接错。
- **Broken Conditionals（多路选择器类）**：条件判断出错；漏掉 edge case；`case` 缺少 `default`；算法错误。

这一调查结果从实证上回答了「自动注入什么 bug 才有意义」——它告诉 Encarsia 的设计者两类注入变换就足以覆盖真实 bug 的主要分布。

**（2）RTLIL 信号错连注入器（Signal Mix-up Injector）**

操作对象是 Yosys RTLIL 中的 wire-driver 连接。算法逻辑：
1. 在 RTLIL 中识别所有 `connect` 操作（即 Verilog 中的 `assign`）；
2. 随机选取两个 `connect` 操作（要求 LHS 线宽匹配，否则按 Verilog 隐式规则截断/符号扩展）；
3. 交换它们的驱动关系；
4. 对逻辑表达式（不直接是 wire 赋值的组合逻辑），Encarsia 在逻辑单元端口与输入之间插入中间线，使同样的交换程序可工作。

这一步对应真实 bug 的「用错 wire」现象。

**（3）RTLIL 条件错写注入器（Broken Conditional Injector）**

Yosys 综合后的 RTLIL 把所有条件赋值（`case`、`if` 链、三元运算符）规整为多路选择器树 `$mux` 节点。Encarsia 利用这一规整化做注入：
1. 找到 `$mux` 节点；
2. 抽象其真值表（行 = 输入组合，列 = 输出选择）；
3. 注入选项：(a) 删除一个 case；(b) 把某个 case 的输入组合改成 don't-care X 值（即条件过宽，原本不该命中的输入也命中了）；(c) 改变 case 优先级（重排多路选择器树的拓扑）。

这一步对应真实 bug 的「条件判断错」现象。

**（4）预过滤器（Prefilter, `-P`）**

并非所有注入的 bug 都会让 CPU 仍可启动。某些信号交换可能直接让 CPU 卡死在复位阶段。预过滤器跑一段简单引导程序（如 `addi x1, x0, 1; ...`），过滤掉无法到达基本指令完成的注入，节省后续形式化验证的时间。

**（5）形式化可观测性证明器（Architectural Observability Prover）**

这是 EnCarSIA 最核心、最具方法学意义的模块。它对每个注入的 bug 单独证明：
- **存在性（assume）**：假设输入/寄存器初始条件存在某个特定值；
- **保证（guarantee）**：在该假设下，能通过一段有限指令序列，让注入 bug 的影响出现在某个体系结构可见位置（寄存器、CSR、内存或异常）。

证明输出是触发序列或 VCD 波形。两条实现路径：
- **JasperGold**（`-V`，闭源）：商用形式化验证引擎，速度快、稳定性高。
- **Yosys SMT**（`-Y`，开源）：基于 Yosys 内置的 SMT 求解器实现等价验证，让不购买 JasperGold 的研究者也能复现。

这个模块是 Encarsia 区别于「随机注入 + 看运气」的评测方法的关键——它保证了 EnCorpus 里的每一个 bug 都是**确定可触发且可观测**的。

**（6）fuzzer 评测协调器（Fuzzer Evaluation Driver）**

固定三个变量（DUT、fuzzer、fuzzing 时长），变化三个变量（fuzzer 种类、coverage feedback 开/关、种子），用 4 张表（Tables 7–10）汇报每个 fuzzer 在每个 CPU 上检出 bug 的占比、漏报 bug、误报 bug、时间分布。

## 5. 关键公式

Encarsia 没有显式的论文编号公式（搜索摘要与 README 均未给出公式）。本节给出**对其 bug 注入变换的形式化表达**，所有公式均为「论文未给出编号公式，以下是对其算法行为的形式化」。

### 5.1 Signal Mix-up 注入的形式化

$$
\text{Mixup}(w_1, w_2) = (w_1 \leftrightarrow w_2) \mid_{\text{RTLIL}}
$$

- $w_1, w_2$：RTLIL 中两个等宽（必要时 Verilog 截断/符号扩展）wire 的 driver
- $\leftrightarrow$：交换两个 wire 的驱动关系

**工程直觉**：在 RTLIL 层面，所有 wire 的 driver 是一个简单的 `connect` 列表。交换两个 driver 就是交换它们各自的目标信号——这等价于在原始 Verilog 里把两条 `assign` 语句的目标写反。

**为什么这么设计**：RTLIL 抽象剥离了 Verilog 语法糖（命名习惯、always 块、`case` 语句），让注入变换只关注「数据流的连接关系」。这比直接在 Verilog 文本上做注入更稳定（Verilog 文本受注释、缩进、风格影响大），也避开了「某些 driver 隐藏在 always 块内」的扫描难题。

### 5.2 Broken Conditional 注入的形式化

$$
\text{MuxTruthTable}(M) = \{(c_i, v_i)\}_{i=1}^{k}
$$

$$
\text{Break}(M) = \begin{cases}
\text{MuxTruthTable}(M) \setminus \{(c_k, v_k)\} & \text{「删除 case」模式} \\
\{(c_k, X), \ldots\} & \text{「don't-care 放宽」模式} \\
\text{permute}(\text{MuxTruthTable}(M)) & \text{「优先级重排」模式}
\end{cases}
$$

- $M$：RTLIL 中的一个 `$mux` 节点（即一段条件赋值的综合结果）
- $c_i, v_i$：第 $i$ 个 case 的「条件组合」「输出值」
- $X$：don't-care 值，使原本不该命中的条件也命中
- $\setminus$：集合删除
- $\text{permute}$：重排 case 优先级

**工程直觉**：把多路选择器抽象成真值表后，注入方式有三种语义化的「人类错误」：漏写一个分支、写条件时图省事用了过宽的判断、把 if-else 顺序写反了。RTLIL 的 `$mux` 树结构让这三种变换都能用统一算法实现。

### 5.3 Bug 检测率（论文 Tables 7–10 的形式化）

$$
\text{Bug Detection Rate} = \frac{N_{\text{detected by fuzzer}}}{N_{\text{verified observable in EnCorpus}}}
$$

- $N_{\text{detected}}$：在固定 fuzzing 时长内，fuzzer 找到的、属于 EnCorpus 的 bug 数
- $N_{\text{verified}}$：EnCorpus 中该 CPU 上的可观测 bug 总数

**为什么这么设计**：因为 EnCorpus 的每个 bug 都经过了形式化证明「存在一段指令能触发并传播到体系结构可见位置」，所以漏报（false negative）是 fuzzer 真实能力的指标——能触发的 bug 都没找到，说明 fuzzer 探索能力有限。

### 5.4 假阳性率（fuzzer 报 bug 但不在 EnCorpus 中）

$$
\text{False Positive Rate} = \frac{N_{\text{reported} \setminus \text{in EnCorpus}}}{N_{\text{reported}}}
$$

- $N_{\text{reported}}$：fuzzer 在 fuzzing 期间报告的所有「疑似 bug」
- $\text{reported} \setminus \text{in EnCorpus}$：报告的 bug 中不在 EnCorpus 集合里的部分

**论文中的发现**：差分测试 fuzzer 的误报率不为零——Cascade、DifuzzRTL、ProcessorFuzz 都报告过非 EnCorpus 的「疑似 bug」，其中部分是 Spike 与 DUT 实现差异（非真 bug），部分是同一 EnCorpus bug 的多次发现。

## 7. 创新点

### 创新点 1：把「bug 注入」从玩具集升级为可重复的工业化方法

**已有方法的局限**：此前 CPU fuzzer 的评测要么依赖人工编写的少量「典型 bug」（与真实 bug 分布脱节），要么依赖「看 fuzzer 在真实 DUT 上能发现多少新 bug」（无法对比，因为不同 fuzzer 跑的 DUT 不同，且 DUT 成熟后剩余 bug 数下降导致对比不公平）。

**Encarsia 的突破**：通过对 1,672 个 PR 中 177 个真实软件可观测 bug 的实证调查，归纳出「Signal Mix-ups + Broken Conditionals」二元分类。在 Yosys RTLIL 上做对应的自动注入，每个 CPU 各产生 ~1000+1000 个可控 bug，并通过形式化验证过滤出「确定可触发可观测」的子集——这给出可重复、可扩展、且与真实 bug 分布对齐的评测基准。

### 创新点 2：用形式化验证给 bug 集「背书」

**已有方法的局限**：注入的 bug 经常因为综合器优化、前置逻辑屏蔽等原因永远无法到达体系结构可见状态——传统的「注入 + 跑 fuzz 看输出」方法会把这种「死 bug」混入评测，导致假阴性结论。

**Encarsia 的突破**：用 JasperGold 或开源 Yosys SMT 单独证明每个注入 bug 的「体系结构可观测性」——存在一段指令能触发并传播到 CPU 程序员可见的位置。这是学术界首次把形式化验证作为「bug 集可信度」的核心组件。

### 创新点 3：三大反直觉发现动摇了现有 fuzzer 设计假设

**已有方法的盲点**：DifuzzRTL、ProcessorFuzz 等 fuzzer 在宣传中强调「指令级差分」「结构覆盖率反馈」是其核心优势，但 Encarsia 的实验证明：
- 指令级差分与指令块级差分找到完全相同的 bug 集合——粒度差异无意义；
- 覆盖率反馈开/关找到完全相同的 bug 集合——结构覆盖率指标不提升检出；
- 种子程序才是 bug 检出真正决定性因素——覆盖率反馈甚至在 time-bounded 场景下拖累发现速度。

这些发现**直接动摇了 DifuzzRTL、ProcessorFuzz 等 SOTA fuzzer 的核心宣传点**，迫使整个领域重新审视「什么样的 fuzzer 设计真正有效」。

### 创新点 4：开源复现路径（Yosys 端到端替代 JasperGold）

**已有方法的局限**：形式化验证的商业引擎（JasperGold）许可证昂贵，阻碍了学术团队的复现和扩展。

**Encarsia 的突破**：用 Yosys 内置的 SMT 求解器实现了等价的 assume-guarantee 验证（`-Y` 选项），让不购买 JasperGold 的研究者也能跑完整的 bug 集生成与验证流程。这是 Encarsia 获得 Distinguished Artifact Award 的关键。

### 创新点 5：可扩展的评测框架

**已有方法的局限**：传统 CPU fuzzer 评测只针对一个或两个 CPU 设计做，结论难以跨设计推广。

**Encarsia 的突破**：通过 `EncarsiaConfig` 类对任意新 CPU 进行扩展，文档明确指导如何在 `config.py` 中注册新设计。这一设计使 Encarsia 成为「可以持续加入新 CPU 的活基准」。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
芯片流程                          Encarsia 的位置
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① RTL 设计                       ← ★ Encarsia 的扰动靶点（修改 RTLIL）
② RTL 功能仿真                   ← ★ Encarsia 的可观测性证明在这里
                                       （JasperGold/Yosys 形式化验证 = 
                                        穷举所有可能指令的功能仿真）
⑥ 形式验证                       ← ★ Encarsia 依赖 ⑥ 作为子工具
                                       （但本身不是验证对象）
③ 逻辑综合 ~ ⑰ 芯片到手          ← 完全不涉及
```

**解决的痛点**：硬件 fuzzer 评测长期缺乏公平基线——每个 fuzzer 优化不同的指标、在不同的 CPU 设计上演示、用「发现了多少个新 bug」做对比但这一数字会随 DUT 成熟度下降而下降。Encarsia 提供「可重复 bug 集 + 形式化证明可观测性 + 跨设计统一接口」三件套，第一次让 CPU fuzzer 评测可重复、可对比。

**端到端具体例子**：假设要为 Ibex CPU 注入 30 个 Signal Mix-up bug。

1. **准备 RTL**：从 lowRISC 仓库获取 Ibex RTL。
2. **Yosys 综合**：用 Yosys 把 Ibex RTL 编译为 RTLIL。
3. **RTLIL 注入**：`encarsia.py -d out/EnCorpus -H ibex -p 30`，对 Ibex 注入 30 个 Signal Mix-up。
4. **预过滤**：跑一段简单引导程序，过滤掉让 CPU 无法启动的注入。
5. **形式化验证**：用 `-Y`（Yosys SMT）或 `-V`（JasperGold）证明每个注入 bug 的体系结构可观测性，得到触发指令序列或 VCD 波形。
6. **打包入 EnCorpus_ibex.tar.gz**。
7. **fuzzer 评测**：把 EnCorpus_ibex 解压为 Ibex 设计变体，让 DifuzzRTL/ProcessorFuzz/Cascade 各跑 30 分钟 fuzzing，统计检出率。

### 9.2 「bug 注入能触发」和「fuzzer 找到 bug」之间隔着什么

Encarsia 解决了「bug 注入能触发」的问题，但「fuzzer 是否真能找到」仍是开放问题。这两者之间隔着：

1. **触发序列的可达性**：EnCorpus 给出的触发序列（如「执行 X、Y、Z 指令后 CSR 出现错误」）需要 fuzzer 自己也探索到这条指令序列才能发现 bug。Cascade 等基于程序粒度的 fuzzer 通过「长而复杂的程序」能更快撞上触发序列，但 DifuzzRTL 等基于指令级差分的 fuzzer 受困于「生成的程序过于简单」「覆盖率反馈反而拖慢」等结构性缺陷。
2. **时间预算**：30 分钟 fuzzing（Docker）与 24 小时 fuzzing（原始）的检出率不同。Encarsia 自己也承认 EnCorpus bug 集对「绝对检出能力」敏感——它衡量的是 fuzzer 在固定时间内的相对能力，不是理论上限。
3. **覆盖度天花板**：即使 fuzzer 跑 1 万小时，仍可能有 bug 因为 fuzzer 不覆盖某些指令/CSR 组合而漏掉。Encarsia 的实验证明 fuzzer 远远没有「穷尽」EnCorpus——三家最佳 fuzzer 仍漏掉 60% 的可观测 bug。
4. **可观测性 ≠ 触发概率**：EnCorpus 保证「存在触发序列」，但不保证「随机 fuzzing 高概率撞上」。某些 bug 需要执行数万条精心编排的指令才能触发——这正是 Cascade 长程序设计哲学的优势所在。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **两类 bug 不一定覆盖全部真实 bug 分布**：作者承认「可能还有其他 bug 形态」，但他们调研的 177 个真实 bug 全部落入两类；进一步扩展需要新的 Yosys 注入 pass。
2. **fuzzer 仍远未饱和**：最佳检测率仅 41.67%，作者认为「fuzzer 整体能力距离穷举还有很大空间」。
3. **覆盖率指标「不足以」并非「完全无用」**：作者明确澄清——他们不是说覆盖率完全无用，而是说「目前的结构覆盖率指标不足以提升 bug 检出」，可能需要更好的指标。
4. **硬件复杂度导致覆盖率提升空间有限**：作者推测现代硬件的「复杂、互联、并行」特性使任何输入都能产生高覆盖率，从而让覆盖率作为反馈信号的有效性下降——这是未来工作的开放方向。
5. **不同 fuzzer 在 Docker 与原始 bare-metal 之间存在 3 个已知差异**：论文 README 已注明（Spike/Verilator 版本依赖），但承认这是评测基础设施的小瑕疵。

### 10.2 代码/复现层面的问题

1. **复现等级 R1**：Docker 镜像 + Zenodo 永久归档 + Distinguished Artifact Award，是资料包中可复现性最高的论文之一。研究者只需 `make pull` + `make run` + `python encarsia.py -d out/EnCorpus -H ibex rocket boom -p 30` 即可重现核心数字。
2. **硬件门槛较高**：BOOM 形式化验证需 32 GB/进程；BOOM 注入实验需 512 GB 额外磁盘。对学术团队来说门槛不低。
3. **JasperGold 是闭源商用工具**：若想复现 JasperGold 的验证结果需购买许可证。论文提供开源 Yosys 后端作为替代，但速度较慢。
4. **EncarsiaConfig 扩展需手动适配**：把 Encarsia 移植到新 CPU 需要在 `config.py` 中编写该 CPU 的 RTL 结构、信号约束、初始假设——这一工作对非 comsec-group 研究者来说门槛较高。
5. **EnCorpus tar 包版本绑定**：EnCorpus bug 集与特定 Yosys/JasperGold 版本绑定。当这些工具升级时，注入的 bug 可能因为综合器优化行为变化而失效或被自动修正。

### 10.3 本资料包的批判性分析

1. **「两类 bug 足够」的可推广性受限于 ISA 与设计风格**：Encarsia 的二元分类基于 4 个开源 RISC-V CPU 的 177 个 bug——这些 CPU 都是 Chisel/SystemVerilog 编写、流水线深度 ≤ 7 级、单核结构。若推广到超标量、多核、片上网络（NoC）、或 ARM/x86 复杂乱序 CPU，可能存在新的 bug 形态（如乱序提交错误、缓存一致性协议漏洞）不在两类之内。论文承认这一限制，但未提供扩展其他类别的路线图。

2. **「覆盖率反馈无效」结论的边界条件**：Encarsia 的实验证明在 DifuzzRTL、ProcessorFuzz 现有覆盖率指标（CSR 翻转、控制寄存器、MUX 选择端）下，覆盖率反馈不提升 bug 检出。但这不意味着「覆盖率反馈这个机制」无用——可能是「指标选错」而非「机制无效」。未来工作可能是寻找更好的覆盖率指标（如语义覆盖率、微架构执行路径覆盖率）而非放弃覆盖率反馈。

3. **「种子决定论」容易被误读为「随机种子就够了」**：Encarsia 的发现「种子比覆盖率反馈更重要」是相对而言——种子决定了 fuzzer 能探索的状态空间，但好的种子工程（curated seed corpus）本身是高成本的。Cascade 等程序粒度 fuzzer 在某种意义上用「长而复杂」的程序替代了手工设计的种子库——这正是它们能快速发现 bug 的原因。把「种子重要性」等同于「随便给个种子就够了」会误导 fuzzer 设计。

4. **EnCorpus 与真实 DUT bug 分布的等价性论证不充分**：Encarsia 论证了「EnCorpus 的 bug 与真实 bug 同属两类」，但没有量化「EnCorpus bug 在发现难度分布上是否与真实 bug 一致」。如果 EnCorpus 的 1000 个 Signal Mix-up 中有 800 个是「简单到一眼可见」的、只有 200 个是「需要特定时序才能触发的」，那 fuzzer 的高检测率可能主要来自「捞容易的」而非「真有能力」。

5. **可观测性证明的完备性边界**：形式化验证证明「存在触发序列」，但这只覆盖了 RTL 抽象层——综合后的网表、布局布线后的物理实现、最终的硅片行为仍可能存在 EnCorpus 未覆盖的 bug 模式。Encarsia 是 RTL 阶段的工具，不能取代 ⑪ 后仿真 + ⑫ DRC/LVS + ⑯ 封装测试。

6. **本资料包的「真实 Bug 检出/可信验证」专题需要跨论文联动**：Encarsia 与本资料包的 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md)、[Cascade](../Cascade/论文深度讲解.md) 一起构成「CPU fuzzing 三部曲」：ChipFuzzer 用 LLM 提升 testcase 质量，Cascade 用程序粒度提升覆盖深度，Encarsia 用 bug 注入提供评测基线。三者互补，共同把 CPU fuzzing 从「撞大运」推向「可度量、可重复」。Encarsia 的最大价值不在于注入多少 bug，而在于它揭示的三大反直觉发现——这迫使整个领域重新审视 fuzzer 设计原则。

## 12. 一分钟复述版

Encarsia（ETH comsec-group，USENIX Security 2025，Distinguished Artifact Award）是一个**给 CPU fuzzer 出标准化考卷的评测平台**。核心五招：

1. **真实 bug 二元归类**：审计 1,672 个 PR，筛出 177 个软件可观测 bug，全部归入「信号错连 Signal Mix-ups + 条件错写 Broken Conditionals」两类。这一实证基础使后续注入的 bug 在分布上逼近真实。

2. **Yosys RTLIL 自动注入**：在综合工具的中间表示上做信号 driver 交换 / 多路选择器 case 删除或 don't-care 放宽。每个 CPU 各生成 ~1000 + ~1000 个可控 bug，30 分钟内可启动注入。

3. **形式化可观测性证明**：用 JasperGold（闭源）或 Yosys SMT（开源）单独证明每个注入 bug「存在一段指令能触发并传播到 ISA 可见状态」——这是 EnCorpus bug 集「确定可触发可观测」的基石，也是与传统「注入 + 跑 fuzz」方法的根本区别。

4. **三大反直觉发现**：(a) DifuzzRTL（指令级差分）与 ProcessorFuzz（指令块级差分）找到**完全相同的 bug**——粒度差异无意义；(b) 覆盖率反馈开/关找到**完全相同的 bug**——结构覆盖率指标不提升检出；(c) **种子程序**才是 bug 检出的决定因素，覆盖率反馈反而在时间预算下拖累发现速度。

5. **标准化评测框架**：在 Ibex、Rocket、BOOM 三个 RISC-V CPU 上对比 DifuzzRTL / ProcessorFuzz / Cascade，三家最佳检测率均 ≤41.67%。EncarsiaConfig 可扩展到任意新 CPU。

**边界**：只涉及流程 ①+②（含 ⑥ 形式验证作为子工具），二分类未必覆盖所有真实 bug 分布，覆盖率「无效」是相对「现有指标」而言，硬件门槛较高（BOOM 注入需 512 GB 磁盘）。
