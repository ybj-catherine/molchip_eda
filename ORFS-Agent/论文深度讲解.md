## 1. 一句话定位

**ORFS-Agent 把"调 EDA 工具参数"这件事，从传统贝叶斯优化（BO）手里拿过来，交给一个会调用工具、会读日志、会自己改配置文件的 LLM 智能体。** 它嵌在开源的 OpenROAD-flow-scripts（ORFS）里，每轮并行跑若干组不同参数，读中间指标，再迭代提出新参数，目标是优化布线后的线长（WL）和有效时钟周期（ECP）。

它要回答的问题是：**LLM 能不能像人类工程师那样，读设计日志、凭经验判断下一步该拧哪个旋钮，而不是像贝叶斯优化那样"黑盒盲搜"？**

它和"训练一个专用模型"的路线（ChatEDA、ChipNeMo、JARVIS 都要微调）针锋相对：**ORFS-Agent 不训练任何模型，接上任何现成前沿 LLM 就能用**，论文里就是直接调用 `claude-3-5-sonnet-20241022`，整套实验的 API 花费只有 **48 美元**。

## 2. EDA 阶段映射

按本仓库 [芯片流程.md](../芯片流程.md) 的 17 阶段标准，ORFS-Agent **跑的是完整 RTL-to-GDS 流程，但"调参"只发生在物理设计段**。OpenROAD 会把 RTL 一路做到版图，所以流程上经过①③⑦⑧⑨⑩，但 Agent 实际改动的参数（placement 密度、CTS 聚类、布线层调整）全部落在⑦⑧⑨⑩。

| 阶段 | 是否覆盖 | ORFS-Agent 中的角色 |
|---|:---:|---|
| ① RTL 设计 | ⚠️ 跑但不调 | Verilog 作为输入，Agent 不改 RTL |
| ③ 逻辑综合 | ⚠️ 跑但不调 | Yosys 综合是流程一环，但不属于调参目标 |
| ⑦ Floorplan | ✅ 核心 | Core Utilization（核心利用率）决定 floorplan 密度 |
| ⑧ Placement | ✅ 核心 | TNS End Percent、LB Add On Place Density、Global/Detail Padding、DPO 等直接控制布局 |
| ⑨ CTS | ✅ 核心 | CTS Cluster Size / Diameter 控制时钟树聚类 |
| ⑩ Routing | ✅ 核心 | Pin Layer Adjust、Above Layer Adjust 控制布线资源 |
| ⑪–⑰ | ❌ | 论文不以寄生提取/签核/DRC/LVS 为优化对象，也不产出流片 GDS |

**最容易误读的一点**：ORFS-Agent 不是"从 RTL 生成 GDS 的 Agent"，而是"**给定一份能跑通的流程，自动拧物理设计旋钮让它结果更好**"。它的输入/输出都是"配置"，不是"设计"。

## 3. 输入、输出与任务定义

### 3.1 输入

- **PDK**：两种工艺节点 SKY130HD 和 ASAP7；
- **目标电路**：IBEX（RISC-V 小核）、AES（加密）、JPEG（图像），每种在两个节点上跑，共 6 个设计实例；
- **自然语言指令**：告诉 Agent"优化线长"还是"优化 ECP"，或带约束（见 3.4）；
- **可调参数清单**：4 变量或 12 变量。

### 3.2 目标函数

论文把目标写成加权和：

$$
F = \sum_{i=1}^{n} \alpha_i f_i
$$

其中每个 \(f_i\) 是一个设计指标（如布线线长、最差负裕量），\(\alpha_i\) 是非负权重。单目标就是只保留一项；多目标就是 WL 和 ECP 各归一化后相加。

### 3.3 4 变量 vs 12 变量

| 变量 | 含义 | 取值范围 |
|---|---|---|
| Clock Period | 目标时钟周期（写进 .sdc） | 浮点，(0, ∞) |
| Core Utilization | 核心利用率 % | 整数 [20, 99] |
| TNS End Percent | 要修掉的违例端点百分比 | 整数 [0, 100] |
| LB Add On Place Density | 布局密度附加量 | [0, 1] |

12 变量在上表基础上再加 8 个更细的物理设计旋钮：Global/Detail Padding（全局/详细布局的 cell 间距）、Enable DPO（详细布局优化开关）、Pin Layer Adjust / Above Layer Adjust（金属 2/3 层与 4 层以上布线资源调整）、Density Margin Add-On、Flatten Hierarchy、CTS Cluster Size / Diameter（时钟树每个簇的 sink 数与物理跨度）。

### 3.4 输入可以带"约束式自然语言指令"

人类工程师收到的指令常是："**尽量优化 X，但 A、B、C 不得恶化超过 2%。**" 论文专门验证了这种约束式优化（第 4 节），这是传统 OR-AutoTuner 很难直接表达的——LLM 可以直接把约束读进上下文遵守。

### 3.5 输出

- 优化后的 ORFS 配置文件（`config.mk`）；
- 优化后的 SDC 时序约束文件（`clock period`）；
- 一路的中间日志与指标记录。

## 4. 方法与系统架构

### 4.1 一个迭代循环：RUN → READ → COLLATE → INSPECT → OPTIMIZE → AGGLOM → ALTER

每轮执行 K 个并行 ORFS 作业（论文默认 K=25，JPEG 用 12），每个作业一组不同参数，最多跑 TIMEOUT（30 分钟）。七步如下：

```
RUN（并行跑 K 组参数，直到超时）
 → READ（收集所有 JSON 日志，含"真值"和"CTS 代理值"）
 → COLLATE（合并成一张表：参数 → 各阶段指标）
 → INSPECT（分析分布/相关性；可用函数调用，也可纯推理）
 → OPTIMIZE（用高斯过程等工具提议新参数点）
 → AGGLOMERATE（可选：候选多于 K 个时，按多样性/熵缩减到 K）
 → ALTER（把选中的 K 组参数写回 config.mk 和 SDC）
```

### 4.2 关键设计：CTS 代理值（surrogate）

布线（详细布线）很慢，常常超时，导致"真值线长 WL"拿不到。但 **CTS（时钟树综合）阶段的估算线长 WL′ 几乎总能拿到**。论文的巧妙之处：

- 如果 WL 存在，就用 `WL / WL_baseline` 当损失；
- 如果 WL 缺失但 WL′ 存在，就用 `WL′ / WL′_baseline` 当损失，并在指令里明确告诉 LLM"你现在看到的是强代理信号"。

这是一种典型的多保真度处理：在最终布线指标暂时不可得时，用便宜但粗糙的 CTS 阶段指标维持优化过程，再在可用时回到更精确的布线结果。

### 4.3 三类工具（function-calling）

ORFS-Agent 的核心卖点是**工具调用**，而不是让 LLM 凭感觉报数。工具分三类：

- **INSPECT（观察）**：`AnalyzeManifold`（PCA/TSNE/MDS 看流形）、`AnalyzeLocal`（LOF/DBSCAN 看局部离群）、`InspectDistribution`（看输入输出分布）、`InspectStructure`（看结构并给建模建议）。这些工具**不把原始数据逐 token 塞进上下文**，而是返回压缩后的统计摘要。
- **OPTIMIZE（优化）**：`CreateModel`（建高斯过程）、`CreateKernel`、`ExpectedImprovement`（算 EI 采集函数）、`HandleSurrogate`（合并真值与代理值）、`LatinHypercube`（拉丁超立方采样）。
- **AGGLOM（聚合）**：`SelectPoints`、`HybridSelect`、`EntropySelect`（熵多样性选择）、`GraphSelect`、`CreateQualityScores`。

关键点：**这些工具就是贝叶斯优化那套（GP、EI、拉丁超立方）的封装**。区别在于——**决定"现在该用哪个工具、用什么参数"的是 LLM**，而不是一个写死的 BO 循环。也就是说，LLM 当"决策者"，GP 当"计算器"。

### 4.4 无工具模式 vs 有工具模式

论文故意做了对比：

- **无工具**：LLM 纯靠上下文推理 + JSON 结构化输出，直接报下一轮参数；
- **有工具**：LLM 可以调用上面那些工具做真正的数值分析。

结论是：有工具 > 无工具（6 例中 5 例占优），且**变量维度越高（12 变量）越需要工具**。这印证了"越复杂的优化越不能靠嘴猜"。

## 5. 实验与主要结果

### 5.1 设置

- **模型**：`claude-3-5-sonnet-20241022`，temperature=0.1，关闭 nucleus/top-K 采样，用 JSON Mode（Structured Outputs API）保证输出格式；
- **迭代**：4 变量跑 375 轮，12 变量跑 600 轮；每轮 25 个并行作业；
- **基线**：OR-AutoTuner（基于 METRICS2.1 的贝叶斯优化，跑 1000 轮 12 参数 / 375 轮 4 参数）；
- **成本**：全部实验（含失败）API 费用约 48 美元。

### 5.2 单目标优化

- 相比 **OpenROAD 默认参数**，ORFS-Agent（600 轮 12 参数）平均把线长（或 ECP）改善 **13.2%**；
- 相比 **OR-AutoTuner**，ORFS-Agent 用**少 40% 的迭代**，在 24 个单目标指标里 12 个打平或更优；
- 一个有意思的现象：优化线长时，Agent **不会显著拖垮 ECP**（有时 ECP 还只有 OR-AutoTuner 的 40%）。作者猜测是因为 ECP 也进了上下文窗口，Agent 会主动避免恶化它。

### 5.3 多目标优化

损失设为 `WL/WL_baseline + ECP/ECP_baseline`。结果 ECP 和 WL 同时改善约 11.3% 和 10.5%，**没有任何一个指标相对基线变差**。

### 5.4 约束式优化

"优化 WL，但 Area/Count/Power/PDP 最多恶化 2%/4%"这类指令下，12 参数+工具场景 WL 改善 11.2%~12.1%，同时尊重约束。这在 OR-AutoTuner 里几乎是做不出来的。

### 5.5 消融与稳健性（论文做得很扎实）

- **领域知识消融**：去掉 PDK 信息 → 变差；去掉电路信息 → 变差；两者都去掉 → 明显变差。说明提示里的领域元数据有用；
- **提示敏感性**：删掉"系统角色描述"、删掉"参数引导文本" → 小幅变差；
- **电路混淆**：把 IBEX 改名成 `obfs` 并禁止 grep 原名字，结果仍稳定 → 排除"模型背答案"；
- **统计显著性**：ASAP7-IBEX 上跑 10~20 次，最差值仍优于 OR-AutoTuner；
- **噪声稳健性**：给每个观测乘 ±5% 均匀噪声、给 CTS 代理值乘 ±20% 噪声，结果仍稳定。

## 6. 主要创新点

1. **模型无关（model-agnostic）**：不微调、不训练、不自托管。新模型一出，直接换，零成本受益。这是对"微调派"（ChatEDA/ChipNeMo/JARVIS 每个新 SOTA 都要重新微调、自托管、维护，成本可上万美金）的正面反驳。
2. **把 BO 装进工具调用里**：GP/EI/拉丁超立方等 BO 组件变成 LLM 可选的工具，LLM 决定"何时用、用哪个、用什么超参"。这是"LLM 当决策者 + BO 当计算器"的混合范式。
3. **CTS 代理值做多保真**：布线超时就用 CTS 指标顶上，并显式写进指令，让优化在"部分信息"下也能继续。
4. **可解释的约束式优化**：自然语言约束（"A/B/C 不许恶化 2%"）直接进上下文，比 BO 的显式目标函数灵活得多。
5. **工程上可复现**：完整实验 48 美元、Grok-Mini 上不到 10 美元，极低成本；DEF 文件跨服务器核对保证可复现。

## 7. 关键术语与缩写

| 缩写/术语 | 全称 | 含义 |
|---|---|---|
| ORFS | OpenROAD-flow-scripts | 开源 RTL-to-GDS 流程封装（可编辑的 JSON/Tcl） |
| BO | Bayesian Optimization | 贝叶斯优化，传统调参主力 |
| WL / DRWL | Routed WireLength | 布线后线长（本文核心目标之一） |
| ECP | Effective Clock Period | 有效时钟周期 = 时钟周期 − 最差 slack |
| CTS | Clock Tree Synthesis | 时钟树综合 |
| WL′ / CTSWL | CTS 估算线长 | 早期代理值，布线超时时顶替 WL |
| ECP′ / CTSECP | CTS 阶段 ECP | ECP 的代理值 |
| WNS/TNS | Worst/Total Negative Slack | 最差/总负裕量 |
| PDP | Power Delay Product | 功耗 × ECP，能量指标 |
| GP | Gaussian Process | 高斯过程，OPTIMIZE 工具的建模核心 |
| EI | Expected Improvement | 期望改进，BO 的采集函数 |
| PDK | Process Design Kit | 工艺设计套件 |
| METRICS2.1 | — | OpenROAD 的日志/指标标准，OR-AutoTuner 基于它 |
| Core Utilization | 核心利用率 | floorplan 里逻辑占芯片面积的百分比 |
| function calling | 函数调用 | LLM 调用预定义工具的能力 |

## 8. 与其他工作的关系

| 工作 | 与 ORFS-Agent 的关系 |
|---|---|
| **OR-AutoTuner** [METRICS2.1] | 直接基线（BO 调参）；ORFS-Agent 用更少迭代打平或超越它 |
| **ChatEDA / ChipNeMo / JARVIS** | "微调派"；ORFS-Agent 明确反对其成本与维护负担 |
| **EDA-Copilot / Ask-EDA / ORAssistant** | "RAG 问答派"；不做优化，只答工具用法问题 |
| **Synopsys DSO.ai / Cadence Cerebrus** | 商业 BO 调参工具，同类目标但闭源 |
| **Dr. RTL / ARES**（本仓库） | 同为 LLM 做 EDA 优化，但对象是 RTL 结构，不是流程旋钮 |
| **FluxBench / CLOSER-Bench**（本仓库） | 评测 Agent 的基准；ORFS-Agent 是"方法系统"，可被它们评测 |

## 9. 局限性与风险

1. **范围窄**：只调物理设计参数（placement/CTS/routing 旋钮），不改 RTL、不做综合调参、不做签核。
2. **电路小而老**：IBEX/AES/JPEG 都是中小型开源电路，未在大型 SoC、内存宏、多时钟域上验证。
3. **指标是"流程内"的**：ECP/WL 是 OpenROAD 自报的，未做多角多模、IR/EM、DRC/LVS 等完整签核。
4. **模型版本依赖**：`claude-3-5-sonnet-20241022` 是特定快照，闭源模型行为会变，逐 token 复现困难。
5. **"更优"的判定口径**：论文用"12/24 指标更优、其余打平"这类措辞，需要看原表才能判断到底是不是显著优势。
6. **工具是写死的**：三类工具是预定义的 Python 函数；论文自己也承认未来要让 LLM 动态生成工具。

## 11. 一分钟总结

ORFS-Agent 是把"**调 EDA 流程参数**"交给 LLM 的迭代优化框架：每轮并行跑 25 组参数，读日志（含 CTS 代理值），用**函数调用**去做真正的数值分析（GP、EI、熵选择等），再改写配置进入下一轮。它不训练模型，接哪个前沿 LLM 都行，整套实验 API 花费 48 美元。

在 SKY130HD 和 ASAP7 两个节点、IBEX/AES/JPEG 六个实例上，它比 OpenROAD 默认参数改善约 13%，比贝叶斯优化基线 OR-AutoTuner **少 40% 迭代**还打平或更优，并且能做"不许恶化 2%"这类自然语言约束式优化。

**公开方法学意义**：① 用 CTS 代理布线指标展示了多保真优化如何处理昂贵或超时的最终评价；② 让 LLM 负责工具编排、让数值工具负责计算，比纯语言模型估计或固定优化循环更灵活。
