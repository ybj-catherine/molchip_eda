## 1. 一句话定位

**Fuzzing Hardware Like Software（论文简称 HWFP）是一个把 RTL 翻译成 C++ 软件模型，再用现成软件 fuzzer（AFL）直接 fuzz 这个软件模型的「硬件模糊测试」框架：通过 Verilator 把 SystemVerilog 转 C++ 暴露给 AFL、用一个通用 bus-centric harness + 自定义 3-opcode 语法做协议感知变异、配合只在 DUT 部分插装覆盖追踪 + 在 fork server 中预置 DUT 复位这三项工程优化，达成相对 CRV（Constrained Random Verification）两个数量级加速、相对 RFUZZ 平均 26.70% HDL 行覆盖提升、对 5 个 OpenTitan IP（4 个 Hack@DAC 合成 bug + 1 个真实 bug）实现 10 小时以内全部检出。**

这句话里的 5 个承重点，后面逐一拆解：

1. **把硬件当软件 fuzz — RTL → 软件模型 → 软件 fuzzer** — 论文观察到软件 fuzzer 生态（AFL/libFuzzer/honggfuzz）远比硬件 fuzzer 成熟（覆盖追踪、变异算子、并行化、crash 归因都已工业化），但 RTL 本身不可执行；Verilator 早已把 HDL 编译成 C++ 软件模型，所以「拦截 Verilator 的中间产物、用 Clang++ 编译并插装覆盖追踪」就得到一个 HSB（Hardware Simulation Binary），可以直接喂给 AFL——本质是把硬件设计当作一个普通 C++ 程序 fuzz。
2. **三个核心工程挑战** — 把软件 fuzzer 接到 HSB 上不是直接能用的：(a) HSB 不是单一可执行文件，而是 DUT + testbench + 仿真引擎三个组件的组合，必须决定哪些插装、怎么 reset；(b) 软件输入是一维字节流，硬件是有时序的事务序列，必须把 fuzzer 输出映射到「空间（哪些端口）+ 时间（哪些周期）」两维；(c) 必须设计一个与具体设计无关的 harness，否则对每个 DUT 都要重写 testbench，违背「design-agnostic」的初衷。
3. **Bus-centric harness + 3-opcode 语法** — 论文设计一个 TL-UL（TileLink Uncached Lightweight）总线协议的通用 C++ harness，它把 fuzzer 生成的 `.hwf` 文件解码为「8-bit opcode + 32-bit address + 32-bit data」三条指令（wait/read/write），驱动 DUT 完成 TileLink 总线事务。**关键洞察**：现代 IP 都通过标准总线互联（OpenTitan 全部 TL-UL），只要 harness 按总线协议解析字节流，对总线兼容的任何 DUT 都不需要改 harness——达到 design-agnostic。
4. **三项工程优化决定可部署性** — (a) **只对 DUT 插装覆盖追踪**（不动 testbench 与仿真引擎），实验证明这反而加速覆盖收敛；(b) **fork server 初始化放在 DUT 复位之后**，让 reset 只发生一次而不是每次 fork；(c) **opcode 用 8-bit 表达 + 变长指令帧**，适配 AFL 偏好小 testcase 的特性，让 harness 能解析更长的硬件事务序列。
5. **覆盖追踪的免费搭便车** — 软件覆盖（basic block / 边 / 路径）天然映射到硬件覆盖（line / FSM / functional），因为 Verilator 给每个 Verilog module 生成一个 C++ class、给阻塞和非阻塞赋值都生成 straight-line 代码。论文 §5.4 + §6.1 + Appendix B.3 反复验证：软件覆盖曲线和 HDL 覆盖曲线高度相关，**所以 AFL 自动追踪的 C++ 边覆盖，就是硬件覆盖的代理指标**——这是把硬件 fuzz 问题退化为软件 fuzz 问题的理论根据。

## 2. EDA 阶段映射（①-⑰）

HWFP 是一个**动态验证（dynamic verification）阶段的测试生成与覆盖率反馈工具**。它用软件 fuzzer 替代手写 testbench，但所有行为都发生在 RTL 功能仿真层。它不接触综合、STA、形式验证、后仿真或物理验证——本质上是「用 AFL 替代 cocotb/UVM 的 random stimulus generator」。

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ 部分 | DUT 是已有的 RTL（OpenTitan IP / SiFive blocks / RISC-V Sodor CPUs / FFT）。论文不生成 RTL，但 fuzz 的前提是已有可综合或可仿真的 HDL |
| **② RTL 功能仿真** | ✅ **核心** | HWFP 的全部工作在这里：用 Verilator 把 HDL 翻译成 C++ 软件模型，链接 testbench 与仿真引擎构成 HSB（Hardware Simulation Binary），用 AFL 对 HSB 做覆盖导向模糊测试。所有覆盖追踪、变异生成、crash 检测都发生在仿真执行期间。注意：这里仿真的是软件的「周期精确 C++ 模型」，不是传统事件驱动 Verilog 仿真器（Icarus/VCS），但语义等价 |
| ③ 逻辑综合 | ❌ | 完全不调用 Yosys / DC / Genus。论文假设 RTL 是「可被 Verilator 翻译」的（任意 SystemVerilog），不假设可综合。fuzz 出来的 testcase 是字节流，不是可综合 testbench |
| ④ 门级仿真 | ❌ | 无 SDF 反标，仿真运行在零延迟 C++ 模型上。看不到毛刺、建立/保持违例、X 传播等门延迟相关问题 |
| ⑤ STA | ❌ | 不计算任何路径延迟。覆盖追踪基于代码结构（software edges → HDL lines），不是时序弧 |
| ⑥ 形式验证 | ❌ | **关键区分**：形式验证用 SAT/SMT 求解器做数学证明，覆盖无穷输入空间。HWFP 是仿真驱动 fuzzing，跑有限数量的 testcase（典型 24 小时 ≈ 几千万次执行），靠 AFL 反馈「哪里没覆盖到」来迭代。它无法证明「无 bug」，只能高概率地暴露「存在 bug」。两者互补：形式验证证明正确性，HWFP 在动态空间找 corner case |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF，无 SDF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17**（① 设计阶段的 DUT 已有；② 功能仿真阶段是核心；其余 15 个阶段全部不涉及）。

> ⚠️ **最容易误读的边界**：(1) HWFP **不等价于形式验证**——它跑的是有限 testcase，AFL 反馈的是「软件覆盖」，不能保证「所有硬件 corner case 都覆盖」。(2) HWFP **不保证 DUT 可综合**——它假设的 RTL 是「Verilator 可翻译的 SystemVerilog」，可能包含不可综合的仿真语法（如 force/release、initial 中的任意行为），结果对综合后网表可能无效。(3) HWFP 的「crash」仅指 **invariant 检查失败**（SVA / C++ assert）或 **golden model 失配**——不包含「功能正确但时序违例」「能跑但 PPA 差」「物理上造不出来」这些传统硬件验证问题。(4) HWFP 的覆盖是 HDL 行覆盖，不是断言覆盖（functional coverage）——即使覆盖 100% 行，也不代表所有功能行为被验证。

## 3. 输入 / 输出

### 3.1 输入

HWFP 的输入是面向 RTL fuzzing 的完整工具链 + DUT 上下文：

| 输入项 | 数据类型/格式 | 具体说明 |
|--------|--------------|---------|
| **DUT HDL** | SystemVerilog | 必须能被 Verilator 翻译的 HDL。论文实测覆盖 Chisel / FIRRTL 间接生成的 Verilog、纯 SystemVerilog。OpenTitan IP、SiFive TileLink peripherals、RISC-V Sodor、FFT 都符合 |
| **HSB 组件**：DUT 模型 + testbench + 仿真引擎 | C++ | Verilator 自动为 HDL 模块生成 C++ class，暴露 input/output 公共成员变量 + `eval()` 方法。testbench 由用户写（C++ 或 Python cocotb）。仿真引擎由 Verilator 提供 |
| **软件 fuzzer** | AFL 2.57b | 论文选 AFL（最成熟的 greybox fuzzer）。HWFP 设计为 fuzzer-agnostic——也可接 libFuzzer / honggfuzz |
| **通用 harness** | C++ | Algorithm 1 描述的通用 harness：把 fuzzer 字节流映射到「空间（哪些端口）+ 时间（哪些周期）」两维 |
| **总线协议 grammar** | 8-bit opcode + 32-bit addr + 32-bit data | Table 1 定义三条指令：`wait`（不需 addr/data）/ `read`（需 32-bit addr）/ `write`（需 32-bit addr + 32-bit data）。Appendix B 还比较了 Constant vs Mapped opcode 编码 + Fixed vs Variable 指令帧格式 |
| **DUT 接口映射** | 端口列表 + 类型 | 论文把 IP cores 通过 TL-UL 总线互联，所以 harness 只需懂 TL-UL 协议，不用懂每个 IP 的内部寄存器布局。TL-UL 提供 Get（read）和 PutFullData（write）两种事务 |
| **初始种子** | `.hwf` 二进制文件或空文件 | 论文 §6.2.1 实验：5 个 OpenTitan IP 全用「空文件」做初始种子，1 小时内 4/5 IP 达到 83%+ HDL 行覆盖。**空种子也能跑通**说明 harness 自身提供了合理的协议骨架 |
| **总线兼容的其他 DUT** | SystemVerilog + TL-UL 接口 | 只要 DUT 符合 OpenTitan Comportability Specification（通过 TL-UL 寄存器映射访问），同一 harness 可直接 fuzz，无需修改 |
| **硬件 sanitizer** | SVA / C++ assert | 论文 §6.2.2 在 OpenTitan DUT 中手工注入 SVAs（如 `assert(!unlocked)`）作为「硬件 crash 触发器」。当 SVA 失败，HSB 调用 `abort()`，fuzzer 把它当作软件 crash 记录 |
| **golden model** | 软件参考实现（C/C++） | 论文 §7 提到可与 golden model 差分比对：实现层运行同一字节流，若 DUT 与 reference 输出不一致则 SIGABRT |
| **GCP 基础设施** | Docker + n1-standard-2 VM | 论文 §4.2 设计 HWFP 流水线：Docker 镜像（Ubuntu 20.04 + LLVM 12.0.0 + Verilator 4.0.4 + AFL + DUT + harness），GCP n1-standard-2（2 vCPUs、7.5 GB RAM、50 GB disk）跑 fuzz |

### 3.2 中间产物

**(a) Verilator 生成的 C++ DUT 模型**

例如 OpenTitan AES IP 经过 Verilator 处理后输出约 38k 行 C++ 代码（Table 2），包含：
- AES top module 的 C++ class，公共成员变量为 input/output（key、data、control signals）
- 一个公共 `eval()` 方法，每次调用推进一个时钟边沿（两次调用 = 一个时钟周期：上升沿 + 下降沿）
- `assert()` / SVA 等价物被注入到条件分支里，作为「条件基本块」
- 阻塞和非阻塞赋值都展开为 straight-line C++（不依赖调度事件队列），便于 AFL 追踪 basic block 边

**(b) HSB（Hardware Simulation Binary）**

```
┌────────────────┐
│  DUT Model     │  ← Verilator 生成的 C++ （插装覆盖率追踪）
├────────────────┤
│  Testbench     │  ← 用户写的 C++ harness（接 fuzz 字节流）
├────────────────┤
│  Sim. Engine   │  ← Verilator runtime + main() 入口
└────────────────┘
```

**(c) Hardware Fuzzing Instruction（3-opcode grammar，Figure 4）**

```text
┌──────────┬────────────────┬──────────────┐
│  Opcode  │    Address     │    Data      │
│  8 bits  │    32 bits     │   32 bits    │
└──────────┴────────────────┴──────────────┘
   总宽度：wait = 1 byte / read = 5 bytes / write = 9 bytes（变长）
```

**(d) 覆盖率追踪数据（三种粒度）**

- **软件基本块边覆盖**（AFL 自动追踪）：C++ 软件模型的基本块图，每个边是否被走过
- **HDL 行覆盖**（Verilator 在 fuzz 结束后跑一次）：原始 SystemVerilog 每行是否被执行
- **FSM 覆盖**（用 SVA 测量）：FSM 状态转换是否全部经过

论文 Appendix B.3 验证这三者**高度相关**——软件基本块覆盖曲线和 HDL 行覆盖曲线趋势一致，所以 AFL 的实时反馈 ≈ HDL 覆盖的代理。

**(e) Crash + Bug 报告**

AFL 把 HSB crash（SIGABRT/SIGSEGV）当作软件 crash 记录，包括触发的 SVA 或 assert 的现场。DUT 软件模型异常行为也会触发 crash。

### 4.2 核心模块逐个详解

**（1）Verilator RTL 编译器（步骤 1）**

把 SystemVerilog / Verilog 翻译成 C++ 软件模型。流程：lex (Flex) + parse (Bison) → AST → 多遍优化（常量传播、don't-care 随机化、死代码消除、循环展开） → 生成 C++ class。**关键特性**：每个 Verilog module 生成一个 C++ class，组织结构与 HDL 模块层次一致；为每个顶层 input/output 暴露 public member（`bool` / `uint32_t` / `uint64_t`，宽度对应）；提供一个 public `eval()` 方法——调用两次相当于一个时钟周期（一次上升沿、一次下降沿）。

**（2）afl-clang-fast++ 覆盖插装器（步骤 2）**

论文选择只插装 DUT 的 C++ 代码（testbench 和仿真引擎不插装）。Verilator 把 HSB 的三个组件分到独立 .cpp 文件中，所以可以用不同的编译参数分别处理（论文 footnote 5）。**不插装 TB/sim engine 的两点理由**：
- DUT 是唯一想覆盖的目标，插装 TB 会让 fuzzer 把 fuzzing cycle 浪费在探索 testbench 状态上
- 不插装 TB 让 fuzzer 反馈「粗略但快速」地指向 DUT 行为相关分支（论文引用 Böhme 等的 markov chain 覆盖分析作为理论支撑）

**（3）Generic Harness（Algorithm 1）**

```text
Algorithm 1: 通用硬件 fuzzing harness（testbench）
Input: fuzz_test_file.hwf
1:  dut ← Vtop()                                    // 构造 DUT 软件模型
2:  tf ← open(fuzz_test_file.hwf)                   // 打开 fuzzer 生成的文件
3:  while tf not empty do
4:      foreach port ∈ dut.inputs do                 // 对每个 DUT 输入端口
5:          tf.read((uint_8t*) port, sizeof(port))   // 从文件读一个字节到端口
6:      end
7:      for k ← 1 to 2 do                            // eval() 调用两次 = 一个时钟周期
8:          clock ← (clock + 1) % 2;
9:          dut.eval();
10:     end
11: end
```

**本质**：把 fuzzer 输出的一维字节流展开为两维（空间 = 哪些端口、时间 = 哪些周期）的硬件输入序列。每次 eval() 调用推进半个时钟周期——两次 eval() = 一个完整周期。Algorithm 1 是 **port-level** 的通用 harness，适合无总线接口的 DUT（如数字锁）。

**（4）Bus-Centric Harness + Grammar（§4.1.1 + §4.1.2）**

Algorithm 1 的问题：port 列表在编译期绑定，要支持新 DUT 必须重写 harness。**核心洞察**：现代 SoC 的 IP core 都通过标准总线互联（TileLink / Wishbone / AMBA / Avalon），只要 harness 懂得协议语义，就能用同一份代码驱动任何总线兼容的 DUT。

论文的 bus-centric harness 围绕 **TL-UL（TileLink Uncached Lightweight，32-bit 数据总线）** 实现：

- 把 fuzzer 字节流解码为 **Hardware Fuzzing Instructions**（Figure 4）：8-bit opcode + 32-bit addr + 32-bit data
- opcode 三选一（Table 1）：
  - `wait`：推进一个时钟周期（不需要 addr/data）
  - `read`：TL-UL Get 事务（需要 32-bit addr，不需 data）
  - `write`：TL-UL PutFullData 事务（需要 32-bit addr + 32-bit data）

**为什么必须用 grammar**：bus 协议对事务结构有严格要求（如 write 必须 addr+data、read 必须 ack），但 AFL/libFuzzer/honggfuzz 都是 syntax-blind 变异器，**它们能生成随机字节流但很难凑出有效事务**。grammar 给变异器一个「高层次语义模板」，fuzzer 把字节流「对齐到」合法指令边界，让绝大多数变异后的字节流仍是合法 TL-UL 事务。

**（5）Hardware Fuzzing Pipeline / HWFP（§4.2）**

仿照 Google OSS-Fuzz 设计的端到端 fuzzing 流水线：

1. 构建 Docker 镜像（Ubuntu 20.04 + LLVM 12.0.0 + Verilator 4.0.4 + AFL 2.57b + DUT + harness）
2. 在 GCP n1-standard-2 VM 上启动 container
3. Container 内部依次执行：Verilator 翻译 → Clang++ 编译插装 → AFL 启动（用 `timeout` 设时长）→ fuzzing 期间数据保存到 GCS bucket → 退出后销毁 VM

**设计意图**：让 DV 工程师只需提供 DUT + 可选 seeds，HWFP 自动完成「编译 + 插装 + fuzzing + 覆盖提取」。OSS-Fuzz 已经在软件侧证明这种流水线对持续 fuzzing 工程化是有效的；HWFP 把同样的模式搬到硬件 DV。

**（6）HSB 复位策略（§5.3.2）**

AFL 默认 fork server 流程：在 main() 入口处 fork，所有 fuzzing iteration 共享 fork server 的初始化结果。但 DUT 必须被 reset 才能开始处理输入——传统做法是 testbench 每次都对 DUT 复位，几百~几千次/秒。

论文发现：
- DUT 复位开销在小 DUT 上是瓶颈（小 DUT reset 时间和 testbench 启动时间相当）
- 在 fork server 中**把 DUT 复位放在 main() 之后的某个点**，让 fork server 启动时只 reset 一次，所有 forked child 直接得到「已 reset」的 DUT
- 实验：用 8/16/32/64-state 数字锁对比两种 fork server 位置；8 和 16 state 锁 Mann-Whitney U 检验 p < 0.05（统计显著），32+ state 锁差异不显著但 reset overhead 已不是瓶颈

**（7）Crash 检测机制（§7）**

HWFP 把「硬件 bug」映射为「软件 crash」的两种方式：

- **Invariant 检查**：在 RTL 中插入 SVA（SystemVerilog Assertions）或在 testbench 中插入 C++ `assert()`；当 DUT 违反 invariant，HSB 调用 `abort()` 发 SIGABRT，AFL 当 crash 记录
- **Golden model 差分比对**：同一字节流跑 DUT 软件模型 + 软件参考实现；若输出不一致则 abort

论文强调：硬件 sanitizer 还没有类似 AddressSanitizer / MemorySanitizer 的等价物（不像软件有 ASan/MSan/UBSan 自动检测 OOB/UAF），DV 工程师必须**手工**为 DUT 编写 invariant。这是 HWFP 的工程门槛。

## 5. 关键公式

HWFP 论文以 prose 描述方法学，无编号数学公式。下列公式为对其核心机制的形式化（论文未给出编号公式）。

### 5.1 软件覆盖 → HDL 覆盖的映射（论文 §3.2 + Appendix B.3 论证）

$$
\text{Cov}_{\text{HDL line}} \approx \text{Cov}_{\text{SW basic-block-edge}}
$$

- $\text{Cov}_{\text{HDL line}}$：原始 SystemVerilog 的行覆盖百分比
- $\text{Cov}_{\text{SW basic-block-edge}}$：Verilator 翻译出的 C++ 模型的基本块边覆盖百分比

**工程直觉**：Verilator 给每个 Verilog module 生成一个 C++ class，给阻塞/非阻塞赋值都展开为 straight-line 代码（无控制流汇合），给 SVA 和 Coverage Points 注入条件 basic block。因此**软件模型中两个 basic block 之间的边是否被走过 ≈ HDL 中两条语句之间是否有执行流经过**。论文 Appendix B.3 的 Figure 15 实证：在 4 个 OpenTitan IP 上，软件 line coverage（kcov）、软件 basic block coverage（LLVM）、HDL line coverage（Verilator）三条曲线几乎重合，相关系数极高。

**为什么这么设计**：这就是「用 AFL fuzz 硬件」能成立的理论根据——AFL 自动追踪软件边覆盖，而软件边覆盖 ≈ HDL 覆盖，所以 AFL 的反馈信号天然就是硬件覆盖的代理。**省去了所有 RFUZZ 需要的 RTL 插装、FIRRTL 编译器定制、Chisel 专用工具链**，换来「用现成软件 fuzzer」的便利性。

### 5.2 字节流 → 时空硬件输入的展开（Algorithm 1 形式化）

$$
\forall \text{ byte}_i \in \text{testfile}: \quad \text{byte}_i \mapsto \text{port}_{\pi(i \bmod P)} \text{ at clock } \lfloor i / P \rfloor + \lfloor i / (P \cdot C) \rfloor
$$

- $\text{byte}_i$：测试文件中第 $i$ 个字节（按字典序）
- $P$：DUT 输入端口数
- $C = 2$：每个时钟周期需要的 eval() 调用数（一次上升沿、一次下降沿）
- $\pi(\cdot)$：端口索引映射（Algorithm 1 的 `foreach port` 循环顺序）

**工程直觉**：fuzzer 给的是一维字节流，硬件需要的是两维（哪些端口在哪些时钟周期）。Algorithm 1 的做法是：把字节流切成大小为 $P$ 的块，每块对应一个时刻，每个字节依次喂给对应端口；每个块喂完后调用 `eval()` 两次（一个完整周期）。这是**最朴素的展开方式**——没有协议语义，所以适用于无总线接口的 DUT。

**为什么这么设计**：Algorithm 1 是「最坏情况下的退路」——对于没有标准总线接口的老旧设计（如纯数字锁 FSM），DV 工程师可以让 AFL 直接 fuzz 端口输入字节。Bus-centric harness 则是「对总线兼容 DUT 的优化」。

### 5.3 HDL 行覆盖改进（论文 §6.1 关键结果）

$$
\Delta_{\text{HDL cov}} = \frac{1}{N_{\text{designs}}} \sum_{d=1}^{N_{\text{designs}}} \left( \text{HDL cov}_{\text{HWF},d} - \text{HDL cov}_{\text{RFUZZ},d} \right) = 26.70\%
$$

- $N_{\text{designs}}$：与 RFUZZ 比较的设计数（论文 §6.1：8 个，包括 FFT、3 个 Sodor CPU、I2C/SPI/PWM/UART 四种 TileLink peripheral）
- $\text{HDL cov}_{\text{HWF},d}$：第 $d$ 个设计上 HWFP 方法的 HDL 行覆盖
- $\text{HDL cov}_{\text{RFUZZ},d}$：第 $d$ 个设计上 RFUZZ 方法的 HDL 行覆盖（取 5 次试验中最好结果）
- $\Delta_{\text{HDL cov}}$：平均覆盖改进（论文报告值 26.70%；最小 14.82%，最大 42.64%）

**工程直觉**：HWFP 比 RFUZZ 平均多覆盖 26.70 个百分点的 HDL 行，最差情况下也多 14.82 个百分点（RFUZZ 最好结果 vs HWFP 最差结果，对每个设计各做 5 次 24 小时 fuzz）。论文同时报告 Mann-Whitney U 检验 $p < 0.05$——改进在统计上显著。

**为什么 HWFP 优于 RFUZZ**：(1) HWFP 用 AFL（成熟软件 fuzzer，调度、变异、剪枝算法都经过多年优化），RFUZZ 用 AFL 的 Rust 重写版本 `kfuzz`（功能较弱）；(2) HWFP 插装软件模型，AFL 边覆盖算法在 straight-line 代码上表现最佳；(3) HWFP 用 bus-centric harness 给变异器提供协议骨架，让大多数变异生成合法总线事务，AFL 反馈信号更密集；(4) RFUZZ 的覆盖率指标是 mux toggle coverage（细粒度但搜索空间大），HWFP 用 basic block edge（更粗但反馈更直接）。

### 5.4 Bug 发现时间（论文 §6.2.2，Table 3）

$$
T_{\text{bug}} = \text{首次 crash 时刻} - \text{fuzzing 开始时刻}
$$

- $T_{\text{bug}}$：bug 发现时间，单位秒
- 论文实验在 AFL 用「初始化种子」（配置 DUT 执行其预设任务的指令序列）的前提下报告
- 5 个 bug 的发现时间：5.1 s（RV Timer，最快） / 46.9 s（HMAC） / 65.1 s（AES） / 396.5 s（Alert Handler） / 35548 s（KMAC，最慢且为真实 bug）

**工程直觉**：5 个 bug 中 4 个在 10 分钟内找到（fast tier），1 个在 10 小时内（KMAC 真实 bug，FSM 跳过熵状态刷新需要满足复杂的预条件序列）。论文没有与 RFUZZ 在 bug 发现时间上做 head-to-head 比较，仅与 CRV 范式（手动 testbench）比较——HWFP 的初始 seed 比 OpenTitan 自带 testbench「orders-of-magnitude less complex」（论文 §6.2.2 末段）。

### 5.5 HS 覆盖相对 CRV 的加速（论文 §5.4 + Figure 11）

$$
\text{Accel}_{\text{HWF vs CRV}} = \frac{T_{\text{CRV}}}{T_{\text{HWF}}} > 100
$$

- $T_{\text{CRV}}$：CRV 达到 ≈ full FSM 覆盖所需时间（论文 Figure 11 热力图，20 次试验平均）
- $T_{\text{HWF}}$：HWFP 达到 ≈ full FSM 覆盖所需时间
- 论文报告：medium-to-large 数字锁设计上 HWFP 比 CRV **快两个数量级**；许多 CRV 试验在跑 5 天后被提前终止以节省 GCP 费用

**工程直觉**：CRV 是「随机生成输入序列，碰运气进入新状态」——状态空间爆炸时随机命中关键前缀的概率指数下降。HWFP 用 AFL 反馈信号，每次变异都「有意识地朝未覆盖的代码区域前进」，所以复杂设计的覆盖收敛时间远低于 CRV。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不训练。** HWFP 是一个纯推理时框架——所有能力来自 Verilator、Clang++、AFL 等成熟软件工具，论文不训练任何模型、不微调任何神经网络。LLM 不参与。**这与本资料包其他论文（如 ChipFuzzer）形成鲜明对比**。

### 6.2 实验设置

**Benchmark 分三组**：

**(A) 数字锁 FSM sweep（§5.1-5.4）**
- 480 个数字锁设计，自动用 Rust kaze crate 生成
- 两个可配置维度：(1) 总状态数 $2^N$，由状态寄存器位宽 $N$ 控制；(2) 输入码位宽 $M$
- 状态数从 2 到 64，码宽从 1 bit 到 8 bit

**(B) 与 RFUZZ head-to-head（§6.1，Figure 12）**
- 8 个设计：FFT Small、Sodor1Stage/3Stage/5Stage CPU、TLI2C、TLPWM、TLSPI、TLUART
- 来源：UC Berkeley Architecture Research GitHub（FFT、riscv-sodor）、SiFive Blocks（TileLink peripherals）
- 对比方法：HWFP vs RFUZZ（同样 24 小时，5 次试验）

**(C) OpenTitan 商用 IP fuzzing（§6.2，Table 2/3）**
- 5 个 IP：AES、HMAC、KMAC、RV Timer、Alert Handler
- OpenTitan Root-of-Trust SoC 的关键模块，全部通过 TL-UL 总线访问
- 4 个 Hack@DAC 合成 bug（每个 IP 一个）+ 1 个 GitHub Issue #6408 报告的真实 bug
- 三种 seed 设置：(a) 空文件，(b) 8-12 个手工生成 seed，(c) 针对 DUT 任务的初始化 seed

**评估指标**：
- **HDL 行覆盖**（Verilator 报告，% HDL lines exercised）
- **FSM 覆盖**（通过 SVA 测量 FSM 状态/转换）
- **软件 line coverage**（kcov）/ **基本块边覆盖**（LLVM）/ **基本块路径覆盖**（论文 Appendix B.3 形式化定义）
- **Bug 发现时间**（秒）

**Baseline**：
- **CRV**（Constrained Random Verification）：cocotb 框架 + Verilator，对比时间
- **RFUZZ**（Laeufer et al., ICCAD 2018）：FIRRTL 编译器定制 + kfuzz fuzzer，对比 HDL 行覆盖和 bug 发现
- **DIFUZZRTL**（Hur et al., S&P 2021）：RFUZZ + golden model 差分；论文 §8 讨论性提及，不做头对头

**Mann-Whitney U 检验**：所有对比实验均报告 $p < 0.05$（统计显著）

**硬件配置**：
- GCP n1-standard-2 VM：2 vCPUs、7.5 GB RAM、50 GB disk、Container-Optimized OS
- 每个实验一个 container（隔离 fuzzing 状态）
- 时间预算：主要实验 24 小时；§6.2.1 短实验 1 小时

**（5）Grammar 优化实验（Appendix B.3，Figure 15）**

- opcode 编码：Constant（每个 opcode 唯一值）vs Mapped（opcode 值等距映射到动作）——差异不显著（256 个值 AFL 很快搜索完）

**（7）复位策略实验（§5.3.2，Figure 10）**

- fork server 在 main() 入口 vs 在 DUT reset 之后
- 小 DUT（8/16 states）：Mann-Whitney U $p < 0.05$，reset-after 显著快
- 大 DUT（32/64 states）：差异不显著（DUT 自身复杂度超过 reset overhead）

## 7. 创新点

### 创新点 1：把 RTL 当软件 fuzz 的范式转换（核心创新）

**已有方法的问题**：传统硬件 CDG（Coverage Directed Test Generation）方法（RFUZZ [39]、Coppelia [92]、MicroGP [65]）都试图**把软件测试方法搬到硬件**——它们要么定制 RTL 编译器（FIRRTL pass 注入覆盖追踪硬件）、要么写硬件专用的 fuzzer（kfuzz）、要么为每个 DUT 设计专用 harness。这导致：(1) 与软件 fuzzer 生态（AFL/libFuzzer/honggfuzz 持续优化 10+ 年）脱节；(2) 硬件 DV 工程师必须重新学习专用工具；(3) 部署门槛高——必须熟悉 Chisel/FIRRTL 才能用 RFUZZ。

**HWFP 的突破**：**反向操作，把硬件搬进软件世界**——既然 Verilator 已经在把 HDL 变成 C++ 软件模型，那就**直接在软件模型上跑软件 fuzzer**，享受软件生态的全部红利：
- 不需要定制 RTL 编译器（Verilator 本身是开源成熟的）
- 不需要写专用 fuzzer（直接用 AFL 2.57b）
- 不需要 RTL 插装（用 Clang++ 的覆盖率插装，C++ 模型就是软件）
- 不需要写专用 grammar（用现成 mutational fuzzer + 一个小语法 decoder）

**与 RFUZZ 的关键区别**：RFUZZ 的核心创新是「mux toggle coverage」（细粒度 RTL 覆盖指标），但需要定制 FIRRTL 编译器。HWFP 反过来——**放弃自定义覆盖指标，直接用软件 fuzzer 的成熟指标**。RFUZZ 的细粒度换来适用性窄（仅 FIRRTL 设计）；HWFP 的粗粒度换来适用性广（任何 Verilator 可翻译的 SystemVerilog）。

### 创新点 2：Bus-Centric Harness 实现 Design-Agnostic Fuzzing

**已有方法的问题**：Algorithm 1（port-level harness）虽然通用但每次新 DUT 都要重写——因为端口列表是编译期绑定的。这违背「design-agnostic CDG」的初衷。

**HWFP 的突破**：观察到现代 SoC 设计中 IP core **几乎都通过标准总线互联**（OpenTitan 全部 TL-UL、ARM SoC 用 AMBA/AXI、Lattice/SiFive 用 TileLink/Wishbone、Altera 用 Avalon）。**只要 harness 懂得总线协议语义，就能用同一份代码驱动任何总线兼容的 DUT**。论文以 TL-UL 为例实现：3-opcode grammar（wait/read/write）+ 通用 C++ decoder → 一次写就，所有 TL-UL 兼容 IP 都直接 fuzz。

**真正的 design-agnostic**：这是 RFUZZ 等前作没能做到的——它们仍然依赖 DUT-specific harness（因为用 port-level mapping）。HWFP 在协议层做到 design-agnostic。

**对未来工作的启示**：用户要支持新总线，只需写一个新 decoder（约 380 行 C++，论文 §6.2.2 末段）。HWFP 已经为 TL-UL、Wishbone、AMBA、Avalon 等预留扩展空间（论文 §7）。

### 创新点 3：HSB 组件级插装粒度优化

**已有方法的隐含假设**：软件 fuzzer 的标准做法是「整程序插装」——main 函数及其所有链接的代码都插装覆盖追踪。

**HWFP 的发现**：HSB 由三个组件构成（DUT + testbench + sim engine），**只对 DUT 插装反而最快**。论文用 480 个不同复杂度数字锁做 sweep 实验 + Mann-Whitney U 检验 $p < 0.05$——统计显著。理论解释：fuzzer 反馈信号被「收紧」到 DUT 行为相关分支，不会浪费 fuzzing cycle 在探索 testbench 状态上。

**类似发现**：fork server 初始化位置优化——放在 DUT reset 之后，让 reset 只发生一次（不是每次 fork 都 reset）。这是 AFL fork server API 的标准用法，但**把它与硬件 reset 语义对齐**是 HWFP 的工程洞察。

### 创新点 4：空种子即可达成高覆盖

**已有方法的预期**：传统动态验证通常需要精心设计的初始 seed（如 OpenTitan 自带 cocotb testbench 就很复杂）。HWFP 的预期——「既然 AFL 配合 bus grammar，从空文件开始就能生成合法总线事务」——在 §6.2.1 实验中得到验证：**空种子 + 1 小时 = 5 个 OpenTitan IP 中 4 个达到 83%+ HDL 行覆盖**。

**理论意义**：这意味着 **HWFP 的最低部署门槛只需「Verilator 可翻译的 HDL + 一份 bug invariant」**——DV 工程师不需要为每个新 IP 写 seed 库。这对快速覆盖新型号 IP 有极大价值。

### 创新点 5：跨硬件 fuzzer 生态的「重新解释」

论文不是单独提出新算法，而是**重新解释了硬件和软件模糊测试的等价性**：

| 传统硬件视角 | HWFP 软件视角 |
|------------|--------------|
| RTL 不可执行 | Verilator 已把它变成可执行 C++ |
| 覆盖追踪慢（要 map 回 RTL） | 软件基本块边覆盖天然映射 HDL 行 |
| DUT-specific harness | 总线协议层就 design-agnostic |
| 复杂 seed 库 | 空 seed 即可（grammar 自动生成合法事务） |
| 专用变异器 | AFL 通用变异器（bit flip / arithmetic / splice / dictionary） |
| 商用 simulator license | 仅需开源工具链 |

这种「视角转换」让硬件 DV 立刻能复用软件侧 10+ 年的工程积累（fork server、sanitizer 接口、coverage-guided scheduling、并行 fuzzing、crash corpus minimization），是论文最有启发性的贡献。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
芯片流程                          HWFP 的位置
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① RTL 设计                       ← 部分（接受已有可被 Verilator 翻译的 RTL）
② RTL 功能仿真                   ← ★ HWFP 在这里
    │                              - Verilator 翻译 HDL → C++ 软件模型
    │                              - Clang++ 编译插装 → HSB
    │                              - AFL fuzzing HSB（输入字节流）
    │                              - 软件边覆盖 → HDL 行覆盖代理
    │                              - SVA / assert 失败 → crash
    │                              - 24 小时 fuzzing 循环
    │                              - Verilator 重跑提取最终 HDL 覆盖
③ 逻辑综合 ~ ⑰ 芯片到手           ← 完全不涉及
```

**解决的痛点**：
- 在 ② RTL 功能仿真阶段，传统手写 testbench（UVM/cocotb）需要大量工程师投入（论文引用 Fine & Ziv：硬件开发 70% 时间用于验证）
- CRV 是「随机生成输入序列碰运气」，复杂设计下覆盖收敛极慢（论文 §5.4：medium-large 设计 CRV 跑 5 天仍未收敛，HWFP 数分钟收敛）
- 现有 CDG 方法（RFUZZ）部署门槛高（必须会 FIRRTL、必须会 Chisel）
- HWFP 用「软件 fuzzer + bus harness」模式，让硬件 DV 工程师能复用软件测试基础设施，部署门槛降至「会写 SVA + 会用 Docker」

### 9.2 「仿真通过」和「能流片」之间隔着什么

HWFP 的「crash 没发生」只保证 **HSB 软件模型在 fuzzing budget 内不违反 invariant**。以下维度都不在 HWFP 评估范围内：

1. **覆盖率 ≠ 正确性**：HWFP 追求高 HDL 行覆盖（>83%），但 HDL 行覆盖是「代码被执行过」而非「功能被正确检查过」。一段代码可能被覆盖但内部逻辑错误（如 off-by-one 的状态机跳转），只要 RTL 和某 reference 输出碰巧一致，HWFP 不会报 bug。这是差分测试的固有局限（如果有 golden model 的话）。
2. **无综合检查**：HWFP 不关心 DUT 是否可综合——它只验证 RTL 在 Verilator 模型（仿真语义）下的行为。可能 DUT 包含不可综合的语法（force/release、initial 中的任意行为、real 类型），综合工具会拒绝，但 HWFP 仍能 fuzz。
3. **无时序验证**：HSB 是零延迟 C++ 模型，看不到门延迟、毛刺、建立/保持违例、X 传播、多驱冲突等问题。这些是 ④ 门级仿真和 ⑤ STA 的职责。
4. **无物理验证**：不涉及 DRC、LVS、IR Drop、信号完整性、功耗。HWFP 仿真出来的正确行为在物理上可能完全跑不起来（如时钟频率不满足建立时间）。
5. **Crash 检测依赖手工 invariant**：HWFP 的 crash 检测机制是 SVA 或 C++ assert——DV 工程师必须**事先**为 DUT 编写有意义的不变式。如果 DUT 缺少 invariant，HWFP 即使 fuzzing 出错误行为也不会报 bug。这与软件侧 ASan/MSan/UBSan 自动检测 OOB/UAF/UAF 完全不同。
6. **无侧信道分析**：HWFP 看不到功耗、电磁辐射、时序泄露等侧信道信号——论文 §7 明确指出「In its current implementation, Hardware Fuzzing is not effective against detecting side-channel vulnerabilities that rely on information transmission/leakage through analog domains」。
7. **与形式验证互补而非替代**：HWFP 跑有限 testcase，无法证明「对所有输入行为正确」。完整的验证需要 fuzzing（②）+ 形式验证（⑥）+ STA（⑤）+ 后仿真（⑪）的协同。

## 10. 讨论与局限

### 10.1 论文自述的局限

论文 §7 显式列出的局限：

1. **无硬件 sanitizer**：不像软件侧有 ASan/MSan/UBSan 自动检测 OOB/UAF/UAF，硬件侧 DV 工程师必须**手工编写 SVA/invariant**作为 crash 触发器。这意味着 fuzzing 价值取决于 invariant 质量——若 DUT 缺少 invariant，HWFP 即使触发错误行为也不会报 bug。
2. **无模拟/混合信号支持**：HWFP 只在 RTL 数字域工作，无法检测侧信道漏洞（功耗、电磁辐射、时序泄露）。侧信道是硬件安全的重要攻击面，这一点 HWFP 当前完全无能为力。
3. **仅支持部分总线协议**：当前 harness 仅实现 TL-UL。其他总线（Wishbone、AMBA、AXI、Avalon）需要 DV 工程师自行写新 decoder。论文给出估算：实现一个新协议 decoder 约需 380 行 C++ 代码（含调试代码）。
4. **DUT reset 必须简短**：fork server 把 DUT reset 放在初始化的开销让 AFL 高效 fork；如果 DUT reset 时间过长（多周期），fork overhead 会显著降低 fuzzing 吞吐。论文建议 reset 应在 1-2 个时钟周期内完成。RFUZZ 也有同样问题。

### 10.2 代码/复现层面的问题

1. **Verilator-only 设计约束**：HWFP 依赖 Verilator 把 HDL 翻译成 C++。Verilator 不支持所有 SystemVerilog 特性（如某些 UVM-specific 构造、$random sequence、复杂断言语法）。若 DUT 包含这些特性，HWFP 不能直接 fuzz——需要降级或替换 simulator。论文未量化「Verilator 不支持的设计占工业 HDL 的比例」。
2. **DUT 必须是 TL-UL 兼容才享受 zero-harness-friction**：若 DUT 用自定义总线协议，DV 工程师必须写新 harness（Algorithm 1 的 port-level 模式可用但失去了 design-agnostic 优势）。
3. **初始 seed 仍影响 KMAC 类大型 IP**：对 5 个 OpenTitan IP 中最大的 KMAC（6,996 basic blocks、119k SW LOC），1 小时空种子仅 65%+ 覆盖（其他 4 个 83%+），说明**HWFP 在超大设计上仍需要更好 seed**。论文未深入研究 seed generation 策略。
4. **AFL fork server 在 reset 后的 reset 工程复杂**：论文用注释（`__AFL_INIT` 之类）标记 reset 结束位置。如果 DUT reset 逻辑与 testbench 紧耦合，标注点会不清晰，fork server 优化失效。
5. **缺少与商用 simulator 集成**：HWFP 完全开源（Verilator + AFL + LLVM），但商业 DV 团队通常用 VCS/Xcelium/ModelSim。Verilator 与商业 simulator 的语义差异（如 event ordering、X 传播处理）未在论文中评估。若 DUT 在 Verilator 上 fuzzing 通过但在 VCS 上失败，HWFP 不能保证 bug 检测完整。

### 10.3 本资料包的批判性分析

1. **「软件覆盖 ≈ HDL 覆盖」的相关性强度未量化**：论文 Appendix B.3 给出了「软件 line cov / 边覆盖 / HDL line cov 三者趋势一致」的定性结论（Figure 15），但没有给出皮尔逊相关系数或决定系数 $R^2$。**当相关性不是 100% 时，AFL 的反馈信号会误导 fuzzer**——比如软件侧覆盖上升但 HDL 侧覆盖不变（或反之）。这对工业部署是潜在风险。
2. **数字锁 FSM 的实验可推广性受限**：480 个数字锁是高度可控的 toy benchmark，但工业 DUT 复杂度（OpenTitan KMAC 有 6,996 basic blocks）远超数字锁。HWFP 在 toy 上两个数量级加速，在工业设计上「1 小时 83%」或「10 小时检出 5/5 bug」的指标能否外推到大型 SoC（数十万 basic blocks、跨 IP 交互）未验证。
3. **没有与最新硬件 fuzzer 的对比**：论文（2022 年）只对比了 RFUZZ（2018）和 DIFUZZRTL（2021）。2022-2026 年期间硬件 fuzzing 社区出现多个新工作（如 [HyperFuzzing] 等）。若 HWFP 与这些新基线对比，结果可能不显著。
4. **差分测试的可信度问题**：HWFP 的 bug 检测依赖 SVA/assert 是否被 DUT 触发。论文中 OpenTitan 的 SVAs 是 OpenTitan 项目自己写的，但论文没有审计这些 SVA 的覆盖率（fault coverage）。**SVA 未覆盖的硬件 bug 在 HWFP 中不会被发现**——这是 invariant-driven 测试的根本局限。
5. **「空种子就够」的边界条件**：§6.2.1 用空种子 fuzzing OpenTitan IP 效果好是因为：(a) 总线 harness 本身知道如何生成合法事务；(b) DUT 寄存器地址空间是已知的（OpenTitan 公开）；(c) AFL 从「合法空事务」变异能快速到达有意义的状态。但若 DUT 没有清晰的寄存器接口（如纯组合逻辑电路），空种子可能完全失效——论文未讨论这个边界条件。
6. **与 LLM 驱动 fuzzing 的关系**：本资料包中的 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md) 是 LLM 驱动的硬件 fuzzing，HWFP 是 AFL 驱动的硬件 fuzzing。二者**不是替代关系**而是互补——ChipFuzzer 擅长「定向生成覆盖特定 corner 的 testcase」，HWFP 擅长「不依赖任何先验地暴力探索状态空间」。论文写于 2022 年，未讨论 LLM 时代的硬件 fuzzing 范式。后续工作可以把 HWFP 的 bus harness + grammar 作为「变异算子」，把 ChipFuzzer 的 LLM 作为「种子生成器」，形成 hybrid 框架。

## 12. 一分钟复述版

**HWFP（Trippel 等，USENIX Security 2022）是把硬件当软件 fuzz 的硬件验证框架**。核心五招：

1. **RTL → 软件模型 → 软件 fuzzer**：用 Verilator 把 SystemVerilog 翻译成 C++ 软件模型，用 Clang++ 插装覆盖追踪，用 AFL 直接 fuzz。**软件基本块边覆盖 ≈ HDL 行覆盖**（论文 Appendix B.3 验证），所以 AFL 的反馈信号天然是硬件覆盖的代理——这是把硬件问题退化为软件问题的理论根据。

2. **Bus-centric harness 实现 design-agnostic**：观察现代 SoC 的 IP 都通过标准总线互联（OpenTitan 全部 TL-UL），所以 harness 只需懂总线协议。3-opcode grammar（wait/read/write）+ 变长指令帧（8-bit opcode + 32-bit addr + 32-bit data）+ 通用 C++ decoder——一次写就，所有 TL-UL 兼容 IP 不需改 harness。其他总线（Wishbone/AMBA）需自写 decoder（~380 行 C++）。

3. **三项工程优化决定可部署性**：(a) 只对 DUT 插装覆盖追踪（不插 TB/sim engine）——Mann-Whitney U $p < 0.05$ 验证加速；(b) fork server 初始化放在 DUT reset 之后——reset 只发生一次；(c) opcode 用 8-bit + 变长指令帧——适配 AFL 偏好小 testcase 特性。

4. **空种子就够 + 跨设计可扩展**：5 个 OpenTitan IP（4 个 Hack@DAC 合成 bug + 1 个 GitHub 真实 bug）空种子 1 小时 = 4/5 IP 达到 83%+ HDL 行覆盖；全部 5 bug 10 小时内检出（4 个 10 分钟内，1 个 10 小时）；与 RFUZZ 24 小时对比平均 HDL 行覆盖 +26.70%（最小 +14.82%，最大 +42.64%，$p < 0.05$）；与 CRV 对比数字锁 FSM 中等到大型设计加速 **两个数量级**。

5. **HWFP 不训练的范式**：纯工程框架，不涉及任何神经网络/LLM——和本资料包中 ChipFuzzer（LLM 驱动）形成对照。HWFP 强在「暴力探索 + 协议感知」，ChipFuzzer 强在「语义定向 + 历史先验」。两者是互补关系而非替代。

**边界**：仅覆盖 ② RTL 功能仿真（2/17）。**无门延迟/时序检查**——看不到毛刺、建立保持违例、串扰；**无综合检查**——DUT 可以不可综合但 Verilator 仍可翻译；**无形式验证**——HWFP 是有限 testcase 仿真而非数学证明；**crash 检测依赖手工 invariant**——无硬件 sanitizer 等价物，DV 工程师必须为 DUT 编写 SVA；**不支持侧信道**——功耗/电磁泄露类漏洞完全无法检测。
