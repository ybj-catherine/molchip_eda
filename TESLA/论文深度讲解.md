## 1. 一句话定位

**TESLA 把 "Shift-Left DFT" 这件事拆成两个 7B 的领域微调 LLM（AutoPSS 选扫描单元 + AutoTPI 插测试点），用 SFT 学 RTL 语义到 EDA 反馈的映射、用 DPO 把"测试覆盖率 > 测试向量数 > 数据到达时间"这条工业优先级烧进权重，再让 ChatGPT 当 agent 把 Design Compiler / TetraMAX / Formality 串成闭环 —— 在 RTLLM 上把测试覆盖率提升超过 ChatGPT-4 与启发式+人工专家的组合方案，并在 OpenCores 上击败商用 TetraMAX（如 aes_cipher_top 38.06% vs 24.55%）。**

这句话里有五个技术承重点，后面逐个拆：
1. **多 LLM 分工** → 一个 PSS、一个 TPI，避免"一个 LLM 同时干两件目标互相冲突的事"
2. **SFT + DPO 两阶段微调** → 把 EDA 工具的客观反馈信号变成可学习的偏好
3. **数据增强**：启发式 back-annotation（PSS）+ ChatGPT-4 prompt-engineering（TPI）
4. **ChatGPT Agent 串联 EDA 工具** → 端到端无人化
5. **Shift-Left DFT** → 把门级 DFT 任务推到 RTL 阶段，在综合前评估测试代价

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | TESLA 做了什么 / 为什么没做 |
|------|:---:|---------------------------|
| **① RTL 设计** | ✅ **核心** | AutoPSS / AutoTPI 都直接**修改 RTL Verilog**：AutoPSS 在寄存器上插入 `scan` 注释或等价模板；AutoTPI 在 RTL 中插入 observe / control 测试点（function 或 module instance） |
| ② RTL 功能仿真 | ⚠️ **辅助** | 通过 **Formality 等价性检查** 验证 TPI 修改前后的 RTL 功能等价（不是动态仿真，是形式等价） |
| **③ 逻辑综合** | ✅ **核心** | 用 **Design Compiler** 把修改后的 RTL 综合成 netlist，并产生 timing report（DAT）。**注意**：TESLA 阶段本身不做综合来"找答案"，综合是它的"裁判"——它生成多个候选，DC 综合成功的候选才进入下一轮 |
| ④ 门级仿真 | ❌ | 不跑 SDF 反标 |
| ⑤ STA | ❌ | 不做专门的 STA。但 **DC timing report 中的 DAT（data arrival time）** 被 DPO 当作低优先级偏好信号（详见 §5） |
| ⑥ 形式验证 | ⚠️ **辅助** | **Formality** 被用作 TPI 数据增强阶段的"质量门"——只有功能等价的样本才进入训练集；推理时也用 Formality 验证 PSS+TPI 后 RTL 的功能正确性 |
| ⑦ Floorplan | ❌ | — |
| ⑧ Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | — |
| ⑫ DRC + LVS | ❌ | — |
| ⑬ Signoff | ❌ | — |
| **⑧ DFT** | ✅ **核心** | **PSS（Partial Scan Selection） + TPI（Test Point Insertion）** 是 TESLA 的本职目标，但实现位置是 **① RTL** 而不是传统 ⑧ 门级。这正是 "Shift-Left" 的含义——把 ⑧ 阶段的任务提前到 ① |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：5/17（核心 2 个：①⑧；辅助 3 个：②③⑥）。** TESLA 的核心创新在 **① RTL 阶段** 直接产出 **⑧ DFT 阶段** 的可测试性改造结果，③⑥ 是它的"评分员"。

> ⚠️ 这是理解 TESLA 位置的关键：传统 DFT 在门级做（阶段 ⑧），但 RTL 阶段就引入扫描友好、test point 友好的逻辑，可以**避免对已经按 PPA 优化好的门级网表反复重做**。TESLA 的目标函数由三个 EDA 工具的客观报告决定：
> - **DC timing report** → DAT（数据到达时间）
> - **TetraMAX ATPG report** → TC（测试覆盖率）、PC（测试向量数）
>
> 这三个指标通过 SFT 当 label，通过 DPO 当 preference，构成训练阶段的全部反馈信号。这是 MAGE（纯仿真器反馈）和 TESLA（综合 + ATPG 反馈）的根本分野——TESLA 的反馈成本高得多，但更接近真实生产环境。

## 3. 输入 / 输出举例

### 3.1 输入（两件套）

**(a) RTL Verilog 代码**

```verilog
// Listing 1（论文示例）
module top ( input wire clk, input wire [1:0]
    reset_case, input wire [1:0] data_in1, input wire
     [1:0] data_in2, input wire data_in3, output reg
     [1:0] data_out );
    always @(posedge clk) begin
        case (reset_case)
            2'b00: data_out <= 2'b00;
            2'b01: begin
                data_out <= (data_in1 ^ data_in2) |
                                {1'b0, data_in3}; end
            2'b10: begin
                data_out <= (data_in1 & data_in2) ^ {
                    data_in3, data_in3}; end
            2'b11: begin
                data_out <= (data_in1 | data_in2) &
                                {1'b1, data_in3}; end
        endcase
    end
endmodule
```

**(b) 用户规格（User Specification）**

AutoPSS 的输入是 **"select N scan cells"**（N 个扫描单元）。
AutoTPI 的输入是 **"insert N test points"**（N 个测试点），以及 PSS 阶段选中的非扫描单元名（作为 TPI 的额外上下文）。

### 3.2 AutoPSS 输出

```text
# AutoPSS 输出（自然语言 + 寄存器名列表）
Response: data_out[0]

# 用户规格：select one scan cell
# 含义：把 data_out 这个 2-bit 寄存器的 bit 0 转换为扫描单元，bit 1 保持非扫描
```

### 3.3 AutoTPI 输出（修改后的 RTL）

```verilog
// Listing 2（论文示例，TPI 插入后的 RTL）
module top ( input wire clk, input wire [1:0]
     reset_case, input wire [1:0] data_in1, input wire
      [1:0] data_in2, input wire data_in3, input wire
     cp_en, output reg [1:0] data_out, output
     reset_case_observed_0 );
    function [1:0] InsertTestPointANDType;
        input [1:0] sig_in; input test_in;
        begin
            InsertTestPointANDType = {test_in &
                sig_in[1], sig_in[0]}; end
    endfunction
    InsertTestPointOBType op_reset_case_instance_0 (
        .funcin(reset_case[0]), .tp_out(
        reset_case_observed_0) );
    always @(posedge clk) begin
        case (reset_case)
            2'b00: data_out <= 2'b00;
            2'b01: begin
                data_out <= InsertTestPointANDType((
                    data_in1 ^ data_in2), cp_en) |
                    {1'b0, data_in3}; end
            ... ...
            ... ...
        endcase
    end
endmodule

module InsertTestPointOBType( input wire funcin,
    output wire tp_out );
    assign tp_out = funcin;
endmodule
```

**两类测试点**：
- **Control point**（控制点）：AND 型——`InsertTestPointANDType` 函数把 `cp_en` 和信号 `sig_in[1]` 做与运算，在测试模式下强制该位为 `cp_en` 的值
- **Observe point**（观测点）：OB 型——`InsertTestPointOBType` 模块把内部信号 `reset_case[0]` 引到顶层输出 `reset_case_observed_0`，让 ATPG 可以观测到它

### 3.4 EDA 工具的反馈报告（DPO 的偏好来源）

论文用三个客观指标作为偏好排序的依据：

```text
DC timing report（来自 Design Compiler）：
  data arrival time (DAT) for data_out[0] = 0.27 ns

TetraMAX test report（来自 ATPG）：
  test coverage (TC) = 87.5%
  pattern count (PC) = 14

→ 偏好规则（DPO 阶段使用）：
  TC 高 > TC 低           （测试覆盖率，最高优先级）
  TC 持平时 PC 低 > PC 高 （测试向量数）
  TC PC 都持平时 DAT 短 > DAT 长（数据到达时间，最低优先级）
```

**注意** DAT 是 SFT 训练目标之一，但 DPO 的偏好规则中 DAT 优先级最低。这是因为在实际生产中，**测试覆盖率是硬指标（达不到就要改设计），测试向量数是软指标（影响测试成本），数据到达时间是 PPA 维度（影响性能）**——TESLA 把 DFT 任务放在首位，PPA 优化让位给综合器。

### 3.5 完整运行产物

ChatGPT Agent 协调工具的完整流程：
```text
输入：RTL Verilog + 用户规格（扫描单元数、测试点数）
        │
        ▼
  AutoPSS → 输出：选中的扫描单元列表（如 data_out[0]）
        │
        ▼
  AutoTPI（输入 RTL + 扫描单元列表 + TP 数）
        │
        ▼
  输出：TPI 修改后的 RTL
        │
        ▼
  Design Compiler 综合 → netlist + timing report
        │
        ▼
  Formality 等价性检查（修改前后 RTL 等价？）
        │
        ▼
  TetraMAX ATPG → test coverage + pattern count
        │
        ▼
  报告给用户：
    pass/fail
    TC Imp. = 38.06%（相对非扫描基线的测试覆盖率提升）
    PC = 238（测试向量数）
    DAT = 0.22 ns（关键路径数据到达时间）
```

## 4. 方法与架构

### 4.1 整体框架（三组件）

```text
                    用户输入：RTL Verilog + 用户规格
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   AutoPSS              AutoTPI               ChatGPT Agent
   (LoRA-tuned          (LoRA-tuned           (协调工具调用)
    Qwen2.5-Coder-7B)    Qwen2.5-Coder-7B)        │
        │                     │                     │
        ▼                     ▼                     ▼
   输出：scan cell       输出：TPI 后 RTL      调用 DC / Formality
   列表（如              （含 TP function         / TetraMAX
   data_out[0]）          和 OB module）              │
                              │                     │
                              └────────► 综合 + ATPG 反馈 �────┘
                                        │
                                        ▼
                              pass@5 / TC / PC / DAT
                              返回给用户
```

**关键设计选择**：
- **AutoPSS 和 AutoTPI 是两个独立模型**，不是同一个 LLM 的两次调用。原因：PSS 决策会影响 TPI 的最优策略（被选为非扫描的寄存器周围的 TP 插入位置会不同），需要**专门的优化目标**
- **ChatGPT Agent 不做 DFT 决策**，只做工具编排（类似 ChatEDA [24]）。所有 DFT 决策都在 AutoPSS/AutoTPI 内部完成
- **工具调用闭环**：DC 综合失败 → 反馈给 Agent → Agent 重新调用 AutoTPI → 生成新候选（最多 5 次）

### 4.2 AutoPSS 的数据增强：Netlist → RTL Back-Annotation

```text
GitHub 上的 7842 个 RTL Verilog 单模块样本
                    │
                    ▼
            Design Compiler 综合
                    │
                    ▼
        Netlist（DFFHQX1 标准单元）
        例：DFFHQX1 data_out_reg[0] (.D(N18), .CK(clk), .Q(data_out[0]))
                    │
                    ▼
        启发式 PSS 算法（基于 netlist 环分析和可控性分析）
        输出：data_out_reg[0] 应该转换为扫描单元
                    │
                    ▼
        Back-annotation（基于命名约定）
        规则：RTL 寄存器变量名 + "_reg" 后缀 = 对应 netlist 标准单元
        例：data_out_reg[0] → 映射回 RTL 变量 data_out[0]
                    │
                    ▼
        SFT 训练样本：
          System: "You are an expert in DFT engineering..."
          Instruction: "Please identify the proper single-bit
                       variables of type reg as scan cells..."
          Response: "data_out[0]"
```

**为什么这条路径可行**：Design Compiler 把 RTL 寄存器 `data_out[0]` 综合为 `data_out_reg[0]`，**命名约定是确定性的**。所以 netlist 上的扫描选择可以一对一映射回 RTL。

**为什么 PSS 可以用 back-annotation 但 TPI 不行**：
- **PSS 的对象是寄存器**——寄存器在综合前后是一一对应的（变量名 + "_reg" 后缀）
- **TPI 的对象是组合逻辑表达式或中间线**——综合器会重命名、合并、化简。例如 `(data_in1 ^ data_in2)` 在综合后可能变成 `n18`，无法稳定地映射回 RTL 表达式

论文用一段话精准指出了这个困难：**"back-annotation is particularly challenging because it is difficult to map combinational logic standard cells in the netlist back to RTL variables or expressions"**。这也是 TPI 路径选择 ChatGPT-4 而不是 back-annotation 的根本原因。

### 4.3 AutoTPI 的数据增强：ChatGPT-4 Prompt Engineering

```text
ChatGPT-4（受 DFT 领域 prompt 引导）
        │
        ├─→ System prompt 包含：
        │   • 测试点类型和定义（control / observe）
        │   • SCOAP 可测试性分析启发式规则 [10]
        │   • 部分扫描单元选择结果
        │   • 测试点插入后的 RTL 模板
        │
        ├─→ User instruction：
        │   "Please insert N test points into this RTL..."
        │
        ▼
    ChatGPT-4 输出修改后的 RTL
        │
        ▼
    Design Compiler 综合检查（语法/可综合性）
        │
        ▼
    Formality 等价性检查（功能等价？）
        │
        ▼
    通过的样本 + 人工修正
        │
        ▼
    SFT 训练样本（高质量、可靠）
```

**为什么 TPI 数据集只有 800 个**：ChatGPT-4 调用成本高（每个 RTL 需要一次完整生成 + 一次验证），论文明确说 "due to the high costs, we only applied TPI transformations to 800 carefully selected, more complex RTL Verilog code samples"。相比 PSS 的 7842 个全量样本，TPI 是**精选子集**。

### 4.4 DPO 的偏好对生成（来自 EDA 工具反馈）

```text
        ┌─────┐  ┌─────┐
   AutoTPI 生成 ──→ RTL_A
   SFT 阶段输出 ──→ RTL_B
        │             │
        └──────┬──────┘
               │
               ▼
        DC + Formality + TetraMAX
               │
        ┌──────┴──────┐
        │             │
   RTL_A 通过    RTL_B 通过
   检查          检查
        │             │
        ▼             ▼
        比较 TC / PC / DAT（按规则）
               │
               ▼
        偏好对：(RTL_A, RTL_B) or (RTL_B, RTL_A)
        其中 y+ = 更优者
               │
               ▼
        DPO 训练样本
```

**DPO 偏好规则（论文 Section III-D）**：

| 优先级 | 指标 | 规则 | 含义 |
|:---:|------|------|------|
| 1 | **TC（Test Coverage）** | $\lvert TC_A - TC_B \rvert > 0.1 \times \max(TC_A, TC_B)$ 则选 TC 高者 | 测试覆盖率（最高优先级） |
| 2 | **PC（Pattern Count）** | TC 持平时 $\lvert PC_A - PC_B \rvert > 0.1 \times \max(PC_A, PC_B)$ 则选 PC 低者 | 测试向量数（影响测试成本） |
| 3 | **DAT（Data Arrival Time）** | TC/PC 都持平时选 DAT 短者 | 数据到达时间（影响 PPA） |

**$0.1 \times \max(\cdot)$ 是容差窗口**：避免在指标差异不显著时强行做偏好判断，减少 DPO 训练噪声。

### 4.5 两阶段微调流程（SFT → DPO）

```text
                Qwen2.5-Coder-7B（基座）
                          │
                          ▼
    ═══════════════════════════════════════════════════
    Stage 1  Supervised Fine-Tuning (SFT, 2 epochs)
    ─────────────────────────────────────────────────
      训练样本：(system, instruction, response) 三元组
      AutoPSS：响应 = 扫描单元寄存器名列表
      AutoTPI：响应 = 修改后的 RTL Verilog
      目标：学会 "RTL → DFT 操作" 的映射
      输出：AutoPSS (SFT) / AutoTPI (SFT)
    ═══════════════════════════════════════════════════
                          │
                          ▼
    ═══════════════════════════════════════════════════
    Stage 2  Direct Preference Optimization (DPO, 1 epoch)
    ─────────────────────────────────────────────────
      训练样本：(system, instruction, y+, y-) 四元组
      y+ = EDA 反馈优选的响应
      y- = EDA 反馈劣选的响应
      偏好规则：TC > PC > DAT
      目标：把工业优先级烧进模型权重
      输出：AutoPSS (SFT+DPO) / AutoTPI (SFT+DPO)
    ═══════════════════════════════════════════════════
                          │
                          ▼
              推理时：5 次采样，取最佳
```

**为什么需要两阶段**：SFT 让模型"会做"（从指令到响应），DPO 让模型"做得好"（与工业指标对齐）。SFT+DPO 的组合比单独 SFT 在所有指标上都更好（详见 §6.3）。

## 5. 关键公式

### 公式 (1)：LoRA 的低秩权重更新

$$
\Delta W = A \cdot B, \qquad A \in \mathbb{R}^{d \times r}, \quad B \in \mathbb{R}^{r \times k}, \quad \text{where } r \ll \min(d, k)
$$

- $W_0 \in \mathbb{R}^{d \times k}$：预训练权重矩阵
- $\Delta W \in \mathbb{R}^{d \times k}$：低秩更新
- $A$、$B$：可训练的低秩矩阵
- $r$：秩（远小于 $d$ 和 $k$）

**参数压缩比**：
- 全量微调：$d \times k$ 个可训练参数
- LoRA：$(d + k) \times r$ 个可训练参数
- 当 $r = 8$，$d = k = 4096$ 时，压缩比约为 $\frac{(d+k) \times r}{d \times k} = \frac{2 \times 4096 \times 8}{4096^2} \approx 0.4\%$

TESLA 选 LoRA 的原因：7B 模型在 8×A100 上全量微调显存吃紧，LoRA 把可训练参数压到原模型的 0.4%，可以用更大的 batch size 或更长的训练。

### 公式 (2)：SFT 的指令跟随损失

$$
L_{\text{SFT}}(\theta) = \frac{1}{N} \sum_{i=1}^{N} L\!\left( f_\theta(I_i), R_i \right)
$$

- $f_\theta$：模型（参数 $\theta$）
- $I_i$：第 $i$ 个指令（RTL + 用户规格 + 自然语言要求）
- $R_i$：期望响应（扫描单元名 / 修改后 RTL）
- $L$：交叉熵损失

**这是一个标准的"指令 → 响应"监督学习目标**。TESLA 的 $I_i$ 包含 system prompt（DFT 领域知识）+ instruction（具体任务描述 + RTL 代码 + 用户规格），$R_i$ 是从 back-annotation 或 ChatGPT-4 获得的"标准答案"。

### 公式 (3)：DPO 的偏好对损失

$$
L_{\text{DPO}}(\theta) = -\frac{1}{M} \sum_{i=1}^{M} \log \frac{P_\theta(y_i^+ \mid x_i)}{P_\theta(y_i^+ \mid x_i) + P_\theta(y_i^- \mid x_i)}
$$

- $(x_i, y_i^+, y_i^-)$：第 $i$ 个偏好对，$y_i^+$ 是优选响应，$y_i^-$ 是劣选响应
- $M$：偏好对总数
- $P_\theta(y \mid x)$：模型在输入 $x$ 下生成响应 $y$ 的概率

**DPO 的关键优势**：不需要训练单独的奖励模型（reward model），直接用偏好对优化策略。这避免了 RLHF 中"训练 reward model → PPO 优化"的两阶段不稳定。

**TESLA 的偏好来源是客观 EDA 反馈**（TC/PC/DAT 报告），而不是人类标注。这让 DPO 阶段的"人类偏好"变成了"工业偏好"——比人类标注更稳定、可复现、不疲劳。

### 公式 (4)：DPO 偏好决策规则（TC > PC > DAT）

$$
\begin{aligned}
&\textbf{Step 1 (TC):} \quad \text{if } \lvert TC_A - TC_B \rvert > 0.1 \cdot \max(TC_A, TC_B), \text{ then } y^+ = \arg\max(TC) \\
&\textbf{Step 2 (PC):} \quad \texttext{if } \lvert PC_A - PC_B \rvert > 0.1 \cdot \max(PC_A, PC_B), \text{ then } y^+ = \arg\min(PC) \\
&\textbf{Step 3 (DAT):} \quad y^+ = \arg\min(\text{DAT})
\end{aligned}
$$

**$0.1 \times \max(\cdot)$ 容差窗口的工程含义**：如果两个候选的 TC 差异 < 10%（相对差异），认为它们在这个指标上"无显著差异"，进入下一级比较。这避免了 DPO 在噪声偏好上过拟合。

**为什么 TC > PC > DAT**：
- **TC 是硬约束**——测试覆盖率不达标意味着芯片无法量产。这是 DFT 工程师的"底线"
- **PC 是软约束**——更多测试向量意味着更长的测试时间、更高的测试成本，但只要能覆盖就还能接受
- **DAT 是 PPA 维度**——影响芯片的工作频率，但这本来就是综合阶段该负责的事，DFT Shift-Left 不应过度优化它

### 公式 (5)：Pass@5 无偏估计

$$
\text{pass@}k = \mathbb{E}_{\text{Circuits}} \left[ 1 - \frac{\dbinom{n - c_p}{k}}{\dbinom{n}{k}} \right]
$$

- $n$：每个电路的独立运行次数（TESLA 用 $n = 5$）
- $c_p$：通过次数
- $k = 5$（论文全部报告 Pass@5）

**当 $k = 1$ 时**化简为：
$$
\text{pass@}1 = \mathbb{E}\left[\frac{c_p}{n}\right]
$$

**$k = 5$ 时**意味着"5 次独立运行中至少 1 次通过"的概率。这是一个比 pass@1 更宽松的指标——LLM 偶尔"猜对"也算分。

**TESLA 用 pass@5 而不是 pass@1 的原因**：DFT 任务对结果的精确度要求极高（必须能综合 + ATPG 通过），单次采样难以稳定达到工业可用水平。5 次采样取最佳更符合实际工程流程（多次尝试选最优）。

## 6. 训练与实验设置

### 6.1 是否需要训练

**需要训练，而且做了完整的 SFT + DPO 两阶段微调。**

- 基座模型：**Qwen2.5-Coder-7B**（阿里达摩院开源，7.61B 参数，专门针对代码生成优化）
- 微调方法：**LoRA**（秩 $r = ?$，论文未明确）
- 第一阶段：**SFT（Supervised Fine-Tuning）**，2 epochs
- 第二阶段：**DPO（Direct Preference Optimization）**，1 epoch
- 数据集划分：7 : 2 : 1（train : val : test），PSS 和 TPI 都按这个比例分
- 学习率：$5 \times 10^{-6}$
- Batch size：$8$
- 框架：transformers + trl + PyTorch
- 硬件：**8 × NVIDIA A100 80GB**（通过 NvLink 连接）

**基座选择 Qwen2.5-Coder-7B 的理由**（论文 Section IV-A）：
- 论文评估了 LLaMA 7B 和 Mistral 7B，但 Qwen2.5-Coder-7B 在 Verilog 代码生成上表现最优（论文 [28][29] 报告 Qwen2.5-Coder 在 Verilog 任务上接近 GPT-4）
- 7B 规模在 8 × A100 上可训练（更大模型如 13B/70B 显存/时间都吃不消）

**翻译**：纯 LLM 的 PSS 在 RTL 与综合后 netlist 结构差异大的电路上失效——因为 LLM 学的是 RTL **语义**，而启发式算法分析的是 netlist **图结构**。两者在 "RTL = 几乎即 netlist"（如寄存器、状态机）时等价；在 "RTL ≠ netlist"（如宽加法器、PE 单元）时分歧。

- 论文的隐含主张："Shift-Left 不仅快，而且更准"——因为 RTL TPI 可以利用语义信息（门级 TPI 看不到的）

## 7. 创新点

### 创新点 1：多 LLM 分工（PSS 模型 ≠ TPI 模型）

这是一个看似显然但很少被论文明确拆解的设计选择。

**为什么不能是一个 LLM 同时做 PSS 和 TPI**：
- **目标冲突**：PSS 的目标是"选出对测试最有利的扫描配置"；TPI 的目标是"在最不利的位置插入测试点补偿"。两者优化方向相反
- **上下文冲突**：PSS 输出是"哪些寄存器变扫描"；TPI 输入是"在哪些位置插 TP"。如果一个 LLM 在同一个对话里做这两个任务，第二步会被第一步的中间产物污染
- **数据规模冲突**：PSS 训练数据 7842 个（全量）；TPI 训练数据 800 个（精选）。混合训练会让模型在 PSS 上过拟合、在 TPI 上欠拟合

**TESLA 的处理**：训练两个**完全独立**的 LoRA 适配器（甚至可能是两个独立的微调副本），PSS 模型只学 PSS，TPI 模型只学 TPI。它们通过 **ChatGPT Agent 串联**——AutoPSS 输出扫描单元列表，喂给 AutoTPI 作为额外上下文。

**Table III 的实证**：TESLA 的 pass@5 在两个任务上分别达 95.1% 和 93.75%，证明独立模型没有互相拖累。

### 创新点 2：EDA 反馈驱动的 DPO（不是人类偏好）

DPO 的标准用法（InstructGPT / Anthropic Constitutional AI）是基于**人类标注的偏好对**——A 答案比 B 答案"更好"由人类判断。

**TESLA 的创新点**：偏好判断由 **EDA 工具自动生成**，规则完全确定：
- TC > PC > DAT（工业优先级）
- 容差 $0.1 \times \max(\cdot)$（避免噪声）

**为什么这比人类偏好更好**：
- **可复现**：同样的 RTL + 用户规格，两次跑 DC + TetraMAX 得到相同的偏好对
- **不疲劳**：人类标注员看 1000 对 (RTL_A, RTL_B) 会判断漂移；EDA 工具不会
- **可扩展**：理论上可以无限生成偏好对，没有标注预算限制
- **对齐工业**：偏好规则直接编码了"测试覆盖率 > 测试向量数 > PPA"，这是 DFT 工程师的共识

**Table I 和 Table II 的实证**：SFT+DPO 比单独 SFT 在 TC improvement 上分别提升 +28.3 pp（PSS）和 +16.25 pp（TPI），证明 EDA 反馈偏好有效。

### 创新点 3：两种针对性的数据增强策略

| 任务 | 数据增强方法 | 为什么这样选 |
|------|-------------|------------|
| **PSS** | Netlist → RTL back-annotation（启发式 PSS 结果反标回 RTL） | PSS 的对象是**寄存器**，寄存器在综合前后命名一一对应（`reg foo` → `foo_reg`），back-annotation 可行 |
| **TPI** | ChatGPT-4 prompt-engineering（DFT 知识引导） | TPI 的对象是**组合逻辑表达式**，综合前后命名映射不稳定（`(a^b)` → `n18`），back-annotation 不可行；改用 ChatGPT-4 直接在 RTL 上操作 |

**这个对应关系的精度很高**：
- 寄存器 = 顺序单元 = 综合前后稳定 → back-annotation
- 组合逻辑 = 顺序无关 = 综合后重命名 → 必须用 LLM 在 RTL 上生成

论文在 Section III-C 详细说明了为什么 PSS 可以 back-annotation 而 TPI 不行——这是论文的方法论亮点之一。

### 创新点 4：ChatGPT Agent 串联的端到端无人化

```text
用户输入：RTL + 用户规格
    │
    ▼
ChatGPT Agent（GPT-4）
    │
    ├─→ 决定调 AutoPSS → 得到扫描单元列表
    ├─→ 决定调 AutoTPI → 得到修改后 RTL
    ├─→ 决定调 Design Compiler → 检查能否综合
    ├─→ 决定调 Formality → 检查 TPI 后是否功能等价
    ├─→ 决定调 TetraMAX → 获得 TC/PC
    │
    ▼
如果综合失败：返回 AutoTPI 重新生成（最多 5 次）
    │
    ▼
输出：pass/fail + TC Imp. + PC + DAT
```

**论文明确说**："The entire process can be autonomously executed by a simple agent based on ChatGPT, utilizing prompt engineering to invoke tools or models at each stage, like ChatEDA [24], without the need for human intervention."

**这与 ChatEDA 的关系**：ChatEDA 是更早的工作（TCAD 2024），证明了 LLM agent 可以协调 EDA 工具；TESLA 把这个能力扩展到 Shift-Left DFT，把 AutoPSS/AutoTPI 作为可调用的"领域工具"。

### 创新点 5：首次在 RTL 阶段击败商用 TetraMAX

论文 Table IV 的结果在工业界有直接意义：

| Circuit | TetraMAX（门级 TPI，业界事实标准） | TESLA（RTL TPI，Shift-Left） | 提升 |
|---------|:---:|:---:|:---:|
| aes_cipher_top | 24.55% | **38.06%** | **+13.51 pp** |
| simple_spi_top | 19.95% | **42.28%** | **+22.33 pp** |

**意义**：在 RTL 阶段做的 TPI（TESLA）比传统门级 TPI（TetraMAX）**结果更好**。这反驳了"门级比 RTL 信息更全"的直觉——RTL 的语义信息（控制流、数据流）反而能更好地指导 TP 插入。

**注意事项**：
- TetraMAX 比较的是**门级 TPI**（阶段 ⑧），TESLA 是 **RTL TPI**（阶段 ①）
- 因为机构许可限制，论文用的是 TetraMAX **旧版本的门级 flow**，而非最新版的 RTL TPI 能力
- 但即便如此，TESLA 在 OpenCores 4 个电路中全部优于 TetraMAX 旧版本——这是一个强势结果

## 8. EDA 缩写解释

按文中首次出现顺序，每个都给全称 + 一句实质解释：

| 缩写 | 全称 | 是什么 |
|------|------|--------|
| **DFT** | Design-for-Test（可测试性设计） | 在设计阶段就考虑后续测试成本的方法学。包括 scan、BIST、IJTAG、boundary-scan、TPI 等技术 |
| **Shift-Left** | — | 把传统流程后期才做的事提前到前期做。TESLA 把 ⑧ 门级 DFT 提前到 ① RTL 阶段 |
| **PPAT** | Power-Performance-Area-Testability（功耗-性能-面积-可测试性） | 设计的四维权衡。Shift-Left 试图在 PPA 之外显式优化 T（testability） |
| **TTM** | Time-to-Market（上市时间） | 设计→产品上市的总周期 |
| **PSS** | Partial Scan Selection（部分扫描选择） | 选择一部分寄存器转换为扫描单元（不是全部），平衡测试覆盖率与硬件开销 |
| **TPI** | Test Point Insertion（测试点插入） | 在电路中插入控制点（control point）和观测点（observe point）改善可测试性 |
| **LVP** | Logical Virtual Prototype（逻辑虚拟原型） | 快速综合的 RTL → 简化 netlist，用于早期可测试性分析 |
| **CDFG** | Control Data Flow Graph（控制数据流图） | 从 RTL 提取的图结构，用于概率可测试性分析 |
| **SCOAP** | Sandia Controllability/Observability Analysis Program | 经典的可测试性度量：6 个数（CC0/CC1/CO 对每个节点）评估控制/观测难度 |
| **TP** | Test Point（测试点） | 见 TPI。分 control point（强制信号值）和 observe point（暴露内部信号） |
| **RTL** | Register Transfer Level（寄存器传输级） | 数字设计的抽象层次：描述"每个时钟沿数据从哪到哪"。对应流程阶段 ① |
| **LLM** | Large Language Model（大语言模型） | 本文特指 Qwen2.5-Coder-7B、ChatGPT-4 |
| **LoRA** | Low-Rank Adaptation（低秩适配） | 参数高效微调方法：冻结原权重，只训练低秩增量矩阵 $\Delta W = AB$，$r \ll d, k$ |
| **SFT** | Supervised Fine-Tuning（监督微调） | 用 (输入, 标准答案) 对更新模型权重。TESLA 的 Stage 1 |
| **DPO** | Direct Preference Optimization（直接偏好优化） | 用偏好对 (好答案 > 坏答案) 直接优化策略，绕过显式 reward model。TESLA 的 Stage 2 |
| **trl** | Transformer Reinforcement Learning | HuggingFace 的 RL 库，包含 DPO 实现 |
| **ATPG** | Automatic Test Pattern Generation（自动测试向量生成） | 根据 netlist 自动生成能检测所有故障的测试向量。TetraMAX 是商用 ATPG 工具 |
| **TC** | Test Coverage（测试覆盖率） | 测试向量能检测到的故障占总故障数的比例。TESLA DPO 偏好规则的最高优先级 |
| **PC** | Pattern Count（测试向量数） | ATPG 生成的测试向量数量。影响测试时间成本 |
| **DAT** | Data Arrival Time（数据到达时间） | 数据信号到达目标寄存器的物理时间。来自 DC timing report |
| **netlist** | — | 综合后生成的门级网表，由标准单元（如 DFFHQX1）和它们的连接组成 |
| **DFFHQX1** | — | 一个具体的标准单元类型（带高电平异步复位的 D 触发器）。综合时寄存器被映射到这类单元 |
| **Formality** | — | Synopsys 的形式等价性检查工具。TESLA 用它验证 TPI 前后 RTL 功能等价 |
| **TetraMAX** | — | Synopsys 的商用 ATPG 工具。TESLA 在 OpenCores 上与之比较 |
| **Design Compiler (DC)** | — | Synopsys 的逻辑综合工具。TESLA 用它把 RTL 变成 netlist 并报 timing |
| **RTLLM** | — | RTL 代码生成的 LLM benchmark。TESLA 用它的子集做测试（未参与训练） |
| **OpenCores** | — | 开源硬件 IP 集合（含 AES、SPI、UART 等）。TESLA 用 4 个层次化电路做 scalability 测试 |
| **PE** | Processing Element（处理单元） | 数组处理器的基本单元。论文 Table III 显示 TESLA 在 PE 上失效，因为 RTL 语义与 netlist 偏离大 |

## 9. 与芯片流程的关系

### 9.1 TESLA 在全流程中的位置

```text
  人写规格（自然语言 / RTL）
     │
     ▼
┌─────────────────────────────────┐
│  ① RTL 设计    ←───┐            │  ← TESLA 的核心战场
│        ↓           │            │     AutoPSS: 选扫描单元
│  ② RTL 功能仿真 ───┤            │     AutoTPI: 插测试点

└────────────┬────────┘            │
             │  ⚠️ 交接面：RTL 已含可测试性改造
             ▼
┌─────────────────────────────────┐
│  ③ 逻辑综合 (Design Compiler)   │  ← TESLA 的评分员
│   → netlist + timing report     │     DC 综合失败的 RTL 不通过
└────────────┬────────────────────┘
             ▼
┌─────────────────────────────────┐
│  ⑥ 形式验证 (Formality)         │  ← TESLA 的功能验证
│   → 验证 PSS+TPI 后 RTL 等价    │
└────────────┬────────────────────┘
             ▼
┌─────────────────────────────────┐
│  ⑧ DFT (TetraMAX ATPG)          │  ← TESLA 的最终评分员
│   → test coverage + pattern     │     TC / PC 是 DPO 的偏好信号
│   传统门级 DFT 仍然存在           │
└────────────┬────────────────────┘
             ▼
   ⑨ Floorplan → ⑩ Placement → ⑪ CTS → ⑫ Routing
             ▼
   ⑬ 后仿真 → ⑭ DRC/LVS → ⑮ Signoff → ⑯ 流片 → ⑰ 芯片
```

### 9.2 Shift-Left DFT 改写了什么

**传统 DFT 流程**（门级，阶段 ⑧）：
```text
RTL → 综合 → netlist → DFT 工具插入 scan/TP → ATPG
                                            ↓
                                问题：PPA 已优化好，重做代价大
                                      优化目标冲突（PPA vs Testability）
```

**Shift-Left DFT 流程**（RTL，TESLA）：
```text
RTL → AutoPSS 选 scan → AutoTPI 插 TP → RTL' → 综合 → ATPG
   ↓
  在 RTL 阶段就评估测试代价
  可以迭代多次（不破坏已有 PPA）
  利用语义信息（控制流、数据流）
```

**核心收益**：避免"先按 PPA 优化 RTL → 综合 → 发现测试覆盖率差 → 改 netlist 破坏 PPA → 重新综合"的循环。Shift-Left 把 DFT 决策提前到 RTL，**让 PPA 优化和 Testability 优化可以在同一个 RTL 设计空间内共优化**。

### 9.3 TESLA 用到的工具在全流程中的角色

| 工具 | TESLA 中的用法 | 在真实芯片流程中的地位 |
|------|--------------|----------------------|
| **Design Compiler** | 把 RTL 综合成 netlist + 报 DAT | 阶段 ③ 核心。工业界还会用 Genus（Cadence）等 |
| **Formality** | 验证 PSS+TPI 前后 RTL 功能等价 | 阶段 ⑥ 核心。比动态仿真快但要求 RTL 严格等价 |
| **TetraMAX** | 产生 TC + PC 报告 | 阶段 ⑧ 核心。商用 ATPG 的事实标准 |
| **ChatGPT Agent** | 协调上述工具，决定何时重试 | 类似于把 EDA 工程师的决策流程自动化 |
| **AutoPSS / AutoTPI** | 生成 PSS / TPI 决策 | 把 DFT 工程师的知识蒸馏到 LLM |

### 9.4 Shift-Left 的边界：TESLA 不是替代 ⑧ DFT

论文明确说：
> "This method complements traditional gate-level DFT techniques. ... TESLA can perform high-level functional analysis on early-stage RTL to evaluate and improve testing metrics, while complex mathematical operators are processed at the gate level through traditional DFT tools."

**翻译**：TESLA 是补充，不是替代。对宽加法器、PE 这类 RTL 与 netlist 结构差异大的电路，仍然让传统门级 DFT 工具处理。

**这是一个务实的工程定位**：TESLA 的目标是"在 RTL 阶段尽早处理 80% 的可测试性问题"，剩下 20% 让传统工具兜底。论文 Table III 中 PE、adder_64bit 的失败案例正是这 20%。

## 10. 讨论与局限

### 10.1 最致命的局限：RTL ≠ Netlist 的电路

论文 Table III 的关键反例：

| Circuit | AutoPSS (SFT+DPO) | Heuristic+Expert | 差距 |
|---------|:---:|:---:|:---:|
| **adder_64bit** | 50.98% | **90.96%** | -39.98 pp |
| **pe** | 63.4% | **94.34%** | -30.94 pp |
| multi_16bit | 21.75% | **28.19%** | -6.44 pp |

**论文的原话**：
> "for circuits like wide adders and pe, which consist primarily of a single a*b, the RTL description deviates substantially from the synthesized circuit structure. This poses challenges for LLMs trained purely on semantic representations, leading to inferior PSS performance compared to heuristics that leverage netlist graph analysis."

**根本原因**：
- **宽加法器（64-bit adder）**：RTL 写 `assign sum = a + b;`（一行），综合后变成数百个全加器串成的行波进位加法器（或优化的超前进位）。LLM 看到的"一行加法"和启发式看到的"进位图"完全是两个世界
- **PE（Processing Element）**：RTL 通常是 `result = a * b + c`（一个乘加单元），综合后变成乘法器树 + 加法器树。RTL 语义过于抽象，netlist 结构完全展开
- **多位数乘法器（multi_16bit）**：同理——RTL 的 `*` 操作在 netlist 上变成复杂的 booth 编码或 array multiplier

**对 LLM 的启示**：纯 RTL 语义理解在**结构化算术电路**上失效。需要**额外的电路结构知识**（如 Booth 编码、Wallace 树、进位链）才能弥补这个 gap。论文没有提供这种知识。

### 10.2 训练数据的不对称

| 数据 | PSS | TPI |
|------|:---:|:---:|
| 训练样本数 | 7842 | 800 |
| 来源 | GitHub + back-annotation | ChatGPT-4 prompt-engineering |
| 验证手段 | DC 综合成功 | DC + Formality + 人工修正 |

**TPI 训练数据只有 PSS 的 10%**——这是 ChatGPT-4 API 成本决定的。论文明确说 "due to the high costs, we only applied TPI transformations to 800 carefully selected, more complex RTL Verilog code samples"。

**后果**：
- AutoTPI 的泛化能力不如 AutoPSS（测试集 pass@5 93.75% vs 95.1%）
- TPI 的"复杂电路"覆盖不足——Table III 显示 TPI 在 multi_pipe_4bit 上完全失败（pass@5 = 0）
- 如果 ChatGPT-4 API 成本降低一个数量级，TPI 数据集可以扩展到数千个，性能可能进一步提升

### 10.3 DPO 偏好规则的简化

偏好规则是 TC > PC > DAT 三级瀑布。但工业 DFT 中还有更多维度：

| 维度 | TESLA 考虑了？ | 工业重要性 |
|------|:---:|:---:|
| Test coverage | ✅ | 最高 |
| Pattern count | ✅ | 高 |
| Data arrival time | ✅ | 中（影响 PPA） |
| **Area overhead**（TP 引入的面积开销） | ❌ | 中 |
| **Power overhead**（TP 引入的功耗开销） | ❌ | 中 |
| **Routing congestion**（布线拥塞） | ❌ | 中 |
| **Test point placement**（TP 位置的可布线性） | ❌ | 中 |
| **Fault coverage**（故障覆盖率） | ⚠️ TC 是 proxy | 高 |

**特别说明**：TC 是故障覆盖率的近似，但不等同——TC 还包含其他故障模型（如 transition delay fault、bridge fault）。TESLA 用 TC 作为 proxy 是简化。

### 10.4 ChatGPT Agent 的可靠性

论文把整个流程交给 ChatGPT Agent 串联。但 ChatGPT-4 作为 agent 有自己的失败模式：

- **工具调用失败**：DC/TetraMAX 报错信息有时很长，ChatGPT-4 可能误解错误原因，错误地重新生成 RTL
- **迭代次数限制**：论文说"最多 5 次"重试，但没有给出 5 次的依据。如果最优解需要 6 次重试，整个流程就失败
- **OpenCores 上的特殊处理**：对层次化设计，ChatGPT 需要"根据模块代码长度和寄存器变量数自动分配"非扫描单元和 TP 数——这个分配策略本身是启发式，可能不是最优

论文没有给出 Agent 失败率的数据——这是一个透明度问题。

### 10.5 Benchmark 污染与泛化

- **训练数据 7842 个 RTL 来自 GitHub**——其中很大概率包含与 RTLLM benchmark 重叠的电路（如简单的 adder、counter）
- 论文说 "the circuits of this benchmark did not participate in model training"——但 GitHub 上的公开 RTL 已经被基座 Qwen2.5-Coder-7B 见过（它的训练数据包含 GitHub）
- **结果**：Table III 的 pass@5 可能存在 benchmark 污染效应，绝对数值的"普适性"打折

### 10.6 计算成本不透明

论文没有报告 token 消耗、API 成本、墙钟时间。粗略估算 OpenCores 一个电路的全流程：

```text
1. AutoPSS 5 次采样 × (LLM 调用 + DC 综合) ≈ 5 × (1 LLM + 1 DC)
2. AutoTPI 5 次采样 × (LLM 调用 + DC 综合 + Formality) ≈ 5 × (1 LLM + 1 DC + 1 Formality)
3. TetraMAX ATPG（仅对通过综合的候选）≈ 1
4. ChatGPT Agent 的工具编排开销 ≈ 数次 LLM
──────────────────────────────────────────────────────────────────
约 10+ 次 LLM 调用 + 10+ 次 DC + 5+ 次 Formality + 1 次 TetraMAX
成本：远高于一次 vanilla LLM 调用
```

**对比**：
- **MAGE**（纯 RTL 生成）：~20-50 次 LLM + 20-40 次仿真
- **ChipSeek**（训练时 RL，推理时）：训练一次（昂贵），推理 1 次
- **TESLA**：~10 次 LLM + 10+ 次 EDA 工具调用（每次 EDA 比 LLM 慢得多）

**真正昂贵的不是 LLM，而是 DC + Formality + TetraMAX**——每次调用数十秒到数分钟。

### 10.7 商用 TetraMAX 的对比公平性

论文 Table IV 明确说："we conducted comparison experiments using the previous version's gate-level DFT flow"——因为机构许可限制，没用最新版 TetraMAX（已支持 RTL TPI）。

**这意味着**：
- TESLA (RTL TPI) vs TetraMAX 旧版 (门级 TPI)——技术不对等
- 真正的公平对比应该是 TESLA (RTL TPI) vs TetraMAX 新版 (RTL TPI)
- 论文没有做这个对比，所以"TESLA 击败 TetraMAX"的结论需要谨慎解读

但即便如此，TESLA 在 4 个 OpenCores 电路上全部胜出，是一个强势结果。

### 10.8 与 MAGE / ChipSeek 的范式对照

| 维度 | MAGE（RTL 生成） | ChipSeek（RTL 生成） | **TESLA（RTL DFT）** |
|------|------|------|------|
| **任务** | 写 RTL | 写 RTL | **改 RTL 做 DFT** |
| **流程阶段** | ①② | ①② | **①②③⑥⑧** |
| **基座模型** | Claude 3.5 Sonnet | — | **Qwen2.5-Coder-7B** |
| **微调** | 无（推理时编排） | SFT + CDPO | **SFT + DPO** |
| **反馈信号** | 仿真器 mismatch | EDA 面积/延迟 | **TC/PC/DAT（DC + TetraMAX）** |
| **训练数据** | 无需 | 大规模 RTL 数据 | **7842 PSS + 800 TPI** |
| **EDA 工具依赖** | 轻（仅 iverilog） | 重（综合） | **重（DC + Formality + TetraMAX）** |
| **优化目标** | 功能正确 | 功能正确 + PPA | **测试覆盖率 + 测试成本** |

**三者的关系**：
- **MAGE** 和 **ChipSeek** 是"RTL 生成"的不同方法（推理时 vs 训练时），目标都是把规格变成 RTL
- **TESLA** 是"RTL DFT 增强"——它的输入是**已经存在的 RTL**，目标是修改它提升可测试性
- 三者可以**串联**：用 MAGE 或 ChipSeek 生成 RTL，再用 TESLA 做 Shift-Left DFT。这正是 AI4EDA 全流程自动化的未来方向

## 12. 一分钟复述版

TESLA 是中科院计算所 / CASTEST 发在 ITC 2025 的 Shift-Left DFT 多 LLM 系统，核心思路：**把门级 DFT 任务（PSS + TPI）提前到 RTL 阶段，用两个 7B 领域微调 LLM 完成**。

1. **多 LLM 分工**：AutoPSS 选扫描单元（基于 netlist → RTL back-annotation 数据），AutoTPI 插测试点（基于 ChatGPT-4 prompt-engineering 数据）。两者通过 ChatGPT Agent 串联
2. **两阶段微调**：SFT（2 epochs）让模型学会 "RTL → DFT 操作"，DPO（1 epoch）让模型对齐工业优先级 TC > PC > DAT（偏好信号来自 DC + TetraMAX 的客观报告）
3. **数据增强双策略**：PSS 用启发式 back-annotation（寄存器在综合前后命名稳定），TPI 用 ChatGPT-4 引导（组合逻辑表达式无法稳定 back-annotation）
4. **结果**：AutoPSS pass@5=95.1%，AutoTPI pass@5=93.75%，OpenCores 上击败商用 TetraMAX（aes_cipher_top 38.06% vs 24.55%）

**边界**：
- 只在阶段 ①②③⑥⑧ 活跃（5/17），核心是 ①⑧
- **RTL ≠ Netlist 的电路失效**：宽加法器、PE 上 LLM 输给启发式（RTL 语义与 netlist 结构偏离大）
- **TPI 数据集小**：只有 800 个（ChatGPT-4 成本限制），泛化能力受限
- **商用 TetraMAX 对比用旧版门级 flow**，未与最新版 RTL TPI 公平对比
- **缺商用 EDA 许可难以复现**，代码未公开

**与 MAGE / ChipSeek 的关系**：TESLA 不是"RTL 生成器"（MAGE/ChipSeek 是），而是"RTL 改造器"——输入已有 RTL，输出 PSS+TPI 增强后的 RTL。三者可以串联：MAGE/ChipSeek 生成 → TESLA 增强 DFT → 综合 → 流片。
