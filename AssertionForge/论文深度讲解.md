## 1. 一句话定位

**AssertionForge 把自然语言 spec 和 RTL 代码同时建模为「硬件知识图谱（KG）」，再用 GraphRAG-style 多分辨率上下文合成生成 SystemVerilog Assertions（SVA）**：相比仅基于 spec 的 AssertLLM，在五个开源 IP 设计（apb / ethmac / openMSP430 / sockit / uart）上 SVA 通过 Jasper 形式验证的「proven」数量全面领先——ethmac 从 15 个提升到 208 个（+193），openMSP430 从 55 提升到 327 个（+272），apb 条件/分支/功能/翻转四类覆盖率达 100%，uart 翻转覆盖 90.41%（vs AssertLLM 的 63.01%）。

这句话里的五个承重点，后面逐一拆解：

1. **「Spec + RTL 双源融合」的 KG** — 此前 LLM-for-SVA 工作（如 AssertLLM）只看 spec，导致断言漏掉 RTL 内部的信号交互。AssertionForge 用硬件专用 schema 把 spec 抽取的 KG 与 PyVerilog 从 RTL 抽取的信号/控制流融合为一张图，是「结构性 mental model」思想在硬件验证的落地。
2. **硬件专用 schema 定制** — 实体类型（module/signal/port/register/clock/design_specification 等）和关系类型（hasSection/contains/defines/connectsTo/operatesAt）基于 OpenCores 等真实 spec 抽取后人工 review。论文明示：通用 GraphRAG 的 schema 直接搬到硬件上效果很差。
3. **多分辨率上下文合成** — 三层生成器从同一张 KG 中抽取不同粒度的上下文：(a) 全局摘要（设计意图概述）、(b) SSR（RAG，信号级局部片段）、(c) GRW-AS（KG 路径游走，信号到关键模块的最短路径）。再用一个 LLM-as-Pruner 过滤冗余上下文，控制 prompt 大小。
4. **GRW-AS 是断言级别的"路径搜索器"** — 从目标 architectural signal 出发做带偏置的随机游走（α·局部重要性 + β·目标方向 + γ·访问新颖性），找到通向关键信号的最相关路径。该路径直接喂给 SVA 生成 LLM，作为「需要监控哪条信号链」的结构化线索。
5. **「proven SVA 数」+「覆盖率」双指标** — 论文把「能通过形式验证的 SVA 数」作为第一指标——这是比"生成的 SVA 数"更严肃的评价。大量 SVA 听起来很美，但只有被形式证明器接受才算贡献。

## 2. EDA 阶段映射（①-⑰）

AssertionForge 处于 **② RTL 功能仿真**（生成 SVA 作为仿真断言）→ **⑥ 形式验证**（Jasper 证明 SVA 不被违反） 的交叉地带。它的输入是 spec+RTL，输出是经过形式验证的 SVA 库。

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ❌ | 不修改 RTL；只读 RTL 抽取信号、控制流、模块实例 |
| **② RTL 功能仿真** | ✅ **核心** | AssertionForge 生成的 SVA 可直接放进仿真 testbench 中作为运行时断言；但论文主要在 Jasper 形式验证平台上跑 SVA |
| ③ 逻辑综合 | ❌ | 不调用综合工具 |
| ④ 门级仿真 | ❌ | 无 SDF 反标 |
| ⑤ STA | ❌ | 不做时序分析 |
| **⑥ 形式验证** | ✅ **核心** | AssertionForge 用 Cadence Jasper 2023.12 做形式验证，证明生成的 SVA 在所有可达状态下不被违反；论文 Table II 报告 #Proven 数量 |
| ⑦ 布局规划 | ❌ | — |
| ⑧ 标准单元摆放 | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17。** AssertionForge 同时占据 **② RTL 功能仿真**（生成仿真断言）与 **⑥ 形式验证**（用 Jasper 证明 SVA 正确性），是少见的「形式化验证 + LLM」交叉工作。

> ⚠️ **最容易误读的边界**：(1) AssertionForge 不"验证 DUT 是否正确"——它生成 SVA，再用形式验证器证明 SVA 不会被违反。如果 SVA 本身写错了（覆盖了不该覆盖的信号），Jasper 仍会显示 "proven"，但这个证明是「错题得分高」。论文没有引入 reference model 校验 SVA 的语义正确性。(2) 论文核心指标 #Proven 是「通过形式验证的 SVA 数」，不代表「找出的 bug 数」。SVA 多 = 监控的范围广，但「监控范围广 ≠ 找到真 bug」。

## 3. 输入 / 输出

### 3.1 输入

| 输入项 | 数据类型/格式 | 具体说明 |
|--------|--------------|---------|
| **自然语言 spec** | PDF 或纯文本 | OpenCores / AssertLLM 数据集来源；范围 2,634~34,133 tokens；论文实验涉及 apb / ethmac / openMSP430 / sockit / uart 五个设计 |
| **RTL 代码** | SystemVerilog / Verilog | PyVerilog 解析，范围 1,116~116,093 tokens |
| **目标 architectural signals** | 设计者选定 | 用于驱动 GRW-AS 路径游走的「锚点信号」；一般选顶层 IO 或关键状态信号 |
| **LLM** | API 调用 | 论文用 GPT-4o；不做微调 |
| **PyVerilog** | 工具 | RTL 解析器，提取 modules/ports/signals/control flow/assignments/FSM |
| **形式验证器** | Jasper 2023.12 | Cadence 商业形式验证平台，输出 SVA 是否被证明的判定 + COI 覆盖 |

### 3.2 中间产物

**(a) 初始 KG（来自 spec）**

用 GraphRAG（Microsoft）+ 硬件专用 schema 抽取：

```
节点: design_specification（spec 章节）, module（设计模块）, signal, port, register, clock
边: hasSection, contains, defines, connectsTo, operatesAt
节点属性: type, description, source ID, level, degree
边属性: weight, description, source IDs
```

**(b) 精炼 KG（融合 RTL 后）**

PyVerilog 提取内部信号、控制流节点、模块实例、FSM；通过精确匹配 + 模糊匹配（缩写词典、大小写归一、active-low 信号模式、Levenshtein 距离 ≥ 0.6）与 spec 节点合并。

**(c) 三类上下文**

| 类型 | 来源 | 粒度 | 论文示例 |
|------|------|------|---------|
| Global Summarization | LLM 全局摘要 | 设计意图级 | "openMSP430 is a 16-bit microcontroller core..." |
| SSR (Signal-Specific Retrieval) | RAG over spec/RTL chunks | 信号级 | "uart_tx block transfers data when tx_busy=1..." |
| GRW-AS | KG 随机游走 | 路径级 | "tx_busy → uart_tx → uart_top → new_tx_data → data_stability" |

**(d) LLM prompt（每信号最多 3 个 prompt）**

prompt 内容：自然语言计划 + 上下文 + 信号列表 → LLM 输出 SVA 代码。

**(e) SVA 候选**

```systemverilog
// openMSP430 DMA 地址边界
property dma_addr_bound;
    @(posedge clk) disable iff (!PRESETn)
        (dma_addr inside {[16'h0000:16'hFFFF]});
endproperty
assert property (dma_addr_bound);

// uart TX 忙状态连续性
property tx_busy_lift;
    @(posedge clk) disable iff (!PRESETn)
        (!tx_busy && new_tx_data) |-> ##1 tx_busy;
endproperty
assert property (tx_busy_lift);

// ethmac 复位行为
property reset_byte_cnt;
    @(posedge clk) disable iff (!PRESETn)
        (ResetByteCnt == 1 && TxReset == 1) |-> 
            (ByteCnt == 0 && TxFlow == 0);
endproperty
assert property (reset_byte_cnt);
```

### 4.2 核心模块逐个详解

**(1) KG Schema 发现（LLM 驱动 + 人工 review）**

从代表性 spec 摘录中让 LLM 推断硬件专用实体/关系类型，再由人工合并冗余概念。论文 schema 包含 37 个实体类型 + 31 个关系类型（全文未在正文列出，仅附录示意）。

**(2) PyVerilog RTL 精炼**

| 抽取对象 | 方法 | 用途 |
|---------|------|------|
| 模块 / 端口 | 直接解析 | 建立模块-端口连接边 |
| 内部信号 | always 块 / assign 提取 | 增加 signal 节点 |
| 控制流节点 | if / case / for | 增加 control flow 节点 |
| 模块实例化 | submodule 调用 | 跨模块依赖 |
| FSM | 时钟 always + case 模式 | 状态机节点与转换边 |
| Spec-RTL 对应 | 精确 + 模糊匹配（缩写、active-low、Levenshtein ≥ 0.6） | 把 spec 节点与 RTL 节点合并 |

**(3) 多分辨率上下文生成**

| 生成器 | 来源 | 输出 | 论文示例参数 |
|--------|------|------|------------|
| Global Summarization | LLM | 设计意图概述 | 高层抽象 |
| SSR | RAG over chunks | 信号级局部文本 | 多尺度 chunk 50/100/200/800/3200 tokens，overlap 0.2/0.4；top 20 chunks；TF-IDF + Sentence Transformer |
| GRW-AS | KG 随机游走 | 信号间路径 | 70 walks/signal，100 step budget；α=0.3 / β=0.5 / γ=0.2 |

**(4) LLM-as-Pruner**

按相关性、多样性、验证潜力过滤候选上下文。每类型最多 50 条，总数 ≤ 100。

**(5) Prompt 组装 + SVA 生成**

每个 architectural signal 最多 3 个动态 prompt；LLM 先输出自然语言 plan，再合成 SVA 代码。

**(6) Jasper 形式验证**

SVA 进入 Jasper 后报告：(a) 语法正确（SynC）、(b) 形式证明（Proven）、(c) COI 覆盖（Statement / Branch / Functional / Toggle）。

## 5. 关键公式

论文未给独立编号公式。以下对核心机制做形式化表达。

### 5.1 KG 定义（论文 Section 3.A）

$$
\mathcal{G} = (\mathcal{V}, \mathcal{E}), \quad \mathcal{G} = \mathcal{F}(\mathcal{S}, \mathcal{R})
$$

- $\mathcal{G}$：硬件知识图谱
- $\mathcal{V}$：节点集合（实体：design_specification / module / signal / port / register / clock …）
- $\mathcal{E}$：边集合（关系：hasSection / contains / defines / connectsTo / operatesAt …）
- $\mathcal{F}$：融合函数（spec KG + RTL 精炼 + 模糊匹配）
- $\mathcal{S}$：自然语言 spec
- $\mathcal{R}$：RTL 代码

**工程直觉**：KG 不是把 spec 和 RTL 拼接成长上下文，而是把"设计意图"与"实现细节"显式建边——`signal A connectsTo module B` 这种关系能让 LLM 推理"为什么 A 的行为会影响 B"。

### 5.2 GRW-AS 游走偏置（论文 Section 3.E）

$$
P(c) = \alpha \cdot I(c) + \beta \cdot D(c) + \gamma \cdot N(c), \quad \alpha + \beta + \gamma = 1
$$

- $P(c)$：候选邻居 $c$ 的转移概率
- $I(c)$：局部节点重要性
- $D(c)$：目标方向性
- $N(c)$：探索新颖性
- $\alpha, \beta, \gamma$：论文实验取 $\alpha=0.3, \beta=0.5, \gamma=0.2$

**局部重要性**：

$$
I(n) = 0.4 \cdot \frac{\deg(n)}{\max_{v \in \mathcal{V}} \deg(v)} + 0.6 \cdot T(n)
$$

- $\deg(n)$：节点 $n$ 的度
- $T(n)$：节点类型权重（论文用 uniform weights）

**方向性**：

$$
D(c) = \frac{\sum_{s \in \mathcal{S}_{\text{arch}}} \mathbb{1}[c \text{ is next hop to } s]}{|\mathcal{S}_{\text{arch}}|}
$$

- $\mathcal{S}_{\text{arch}}$：architectural signals 集合
- $\mathbb{1}[\cdot]$：指示函数

**探索新颖性**：

$$
N(c) = \begin{cases} 1.0, & \text{if } c \text{ 未被访问} \\ 0.0, & \text{otherwise} \end{cases}
$$

**工程直觉**：GRW-AS 不是盲目随机游走，而是"以目标信号为终点，沿 KG 中已有的最短路径引导"。当游走从 `tx_busy` 出发想到达 `data_stability`，会偏向走 `tx_busy → uart_tx → uart_top → new_tx_data → data_stability` 这条预计算的最短路径附近，而非随机乱走。β=0.5 表明"目标方向"是主导因素。

### 5.3 SVA 质量评估指标（论文 Section 4.D）

$$
\text{SVA Quality} = f(N_{\text{SVA}}, N_{\text{SynC}}, N_{\text{Proven}}, \text{COI}_{\text{stmt/br/func/tog}})
$$

- $N_{\text{SVA}}$：生成的总 SVA 数
- $N_{\text{SynC}}$：Jasper 接受（语法正确）数
- $N_{\text{Proven}}$：Jasper 形式证明（无违例）数
- $\text{COI}_{\text{stmt/br/func/tog}}$：Statement / Branch / Functional / Toggle 四类覆盖率

**工程直觉**：单纯追求 $N_{\text{SVA}}$ 大数是「凑指标」——大量 SVA 可能语法错、与 DUT 无关。$N_{\text{Proven}}$ 是更严肃的指标，因为它要求"形式证明这个属性在所有可达状态下不被违反"。

**工程直觉**：Jasper 形式验证才是瓶颈（占 57-90%），LLM 调用和 KG 构建加起来 < 15%。这意味着**减少 LLM 调用的优化对总时间影响有限**，形式验证器本身才是改进重点。

## 7. 创新点

### 创新点 1：把 spec 与 RTL 同时建模为硬件知识图谱

**已有方法的问题**：AssertLLM 等 LLM-based SVA 生成方法只读 spec，不读 RTL。但很多 spec 不会写出"复位时内部状态机的行为"——这些信息只能从 RTL 推导。

**AssertionForge 的突破**：(1) 用硬件专用 schema（37 实体 + 31 关系）建立 KG；3) 用 PyVerilog 从 RTL 抽取内部信号、控制流、模块实例并合并到 KG；3) 用模糊匹配对齐 spec 节点与 RTL 节点。spec-RTL 融合让"语义"和"实现"在同一张图上对齐，LLM 不再需要自己跨语料推理。

**关键证据**：ethmac 上 #Proven 从 15（AssertLLM）跃升到 208（+193 个），openMSP430 上从 55 跃升到 327（+272 个）——单纯加 spec 信息不可能带来这个量级提升，必须有 RTL 内部信号的贡献。

### 创新点 2：硬件专用 schema 定制 + GraphRAG 适配

**已有方法的问题**：通用 GraphRAG（Microsoft）的 schema 是"实体-关系"的通用 NLP 抽象，搬到硬件 spec 上识别效果差——会把 "uart" 识别为地名或姓名，把 "TX" 识别为缩写。

**AssertionForge 的突破**：基于 OpenCores / AssertLLM 数据集反复迭代 + 人工 review，提出 37 个硬件专用实体类型与 31 个关系类型。论文强调：**通用 schema 直接搬用效果差**（Table II 中 "AssertionForge Orig KG" 一行的数据明显差于 Full AssertionForge）。

### 创新点 3：多分辨率上下文合成（Global / SSR / GRW-AS）

**已有方法的问题**：单分辨率 RAG 在长 spec + RTL 上要么粒度太粗（找不到细节信号），要么粒度太细（找不到全局意图）。

**AssertionForge 的突破**：三层互补——
- **全局摘要**：让 LLM 建立"这是 16 位微控制器核"的心理模型；
- **SSR（信号级 RAG）**：让 LLM 看到"uart_tx block transfers data when tx_busy=1"这样的局部细节；
- **GRW-AS（KG 路径游走）**：让 LLM 看到"tx_busy → uart_tx → uart_top → new_tx_data → data_stability"这样的跨模块信号链。

这种「金字塔结构」让 LLM 既见森林又见树木。

### 创新点 4：GRW-AS 带偏置的随机游走

**已有方法的问题**：直接随机游走 KG 容易陷入局部噪声，找不到通向关键信号的路径。

**AssertionForge 的突破**：把"目标方向性"作为游走偏置的主导（β=0.5）——游走偏向于朝目标 architectural signal 收敛。这种设计把"无目的探索"变成"有目的路径检索"。

### 创新点 5：「#Proven」作为严肃评价指标

**已有方法的姿态**：很多 LLM-for-EDA 工作报告"生成的代码数"或"通过编译的代码数"。

**AssertionForge 的姿态**：用 Jasper 形式验证器证明每个 SVA 在所有可达状态下不被违反，统计 **#Proven**。这是比 "compiled successfully" 更严格的标准——它要求 SVA 在数学上正确。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
芯片流程                              AssertionForge 的位置
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① RTL 设计                           ← 不参与（不修改 RTL）
② RTL 功能仿真                       ← ★ 生成的 SVA 可直接放进仿真 testbench
    │                                   - SVA 作为运行时断言监控 DUT 行为
    │                                   - 但论文主要在 ⑥ 而非 ② 评估
    ▼
⑥ 形式验证                           ← ★ 主战场
    │                                   - SVA 进入 Jasper 形式验证器
    │                                   - 输出 #SynC / #Proven / COI
    │                                   - KG 自身可重用于 code gen、design understanding
③ 逻辑综合 ~ ⑰ 芯片到手              ← 完全不涉及
```

**解决的痛点**：在 ⑥ 形式验证阶段，传统手工写 SVA 极其耗时（一个复杂 IP 可能需上千条 SVA），且容易遗漏内部信号交互。AssertionForge 用 KG + LLM 把"读 spec → 读 RTL → 写 SVA"自动化。

**端到端具体例子**（ethmac 的 reset behavior）：

- **传统手工**：工程师读 102 页 spec，找到"复位后 ByteCnt 必须为 0、TxFlow 必须为 0"这一条；再去 RTL 找 ByteCnt、TxFlow 信号；写 SVA：`ResetByteCnt && TxReset |-> ByteCnt == 0 && TxFlow == 0`；提交给 Jasper；Jasper 跑数小时证明该 SVA 无违例。
- **AssertLLM**：只读 spec，可能写出"复位后所有寄存器清零"这样**过于宽泛**的 SVA（RTL 内部信号交互缺失），Jasper 验证通过覆盖率仅 50% 左右。
- **AssertionForge**：spec + RTL 同步建 KG → `ResetByteCnt connectsTo module ethmac / defines ByteCnt / defines TxFlow` → GRW-AS 找到这条信号链 → LLM 输出精确 SVA → Jasper 形式证明 #Proven 208 个。

### 9.2 「SVA 通过形式验证」和「DUT 正确」之间隔着什么

AssertionForge 的 "#Proven SVA 数提升" 只证明**生成的断言在 Jasper 中形式无违例**。以下维度都不在评估范围内：

1. **SVA 语义正确性 vs DUT 正确性**：如果 SVA 写错了（监控了不该监控的信号，或属性写反），Jasper 仍会显示 "proven"——错的命题永远为真。AssertionForge 没有引入 reference model 校验 SVA 语义。
2. **覆盖率 ≠ bug 检出**：openMSP430 Functional 覆盖 90.09%、uart Functional 88.82%——仍有未覆盖的功能点。**未覆盖 = 未监控 ≠ 无 bug**。SVA 监控不到的功能区，DUT 可能有 bug 但 AssertionForge 不会发现。
3. **KG 构建的隐含错误**：模糊匹配阈值 0.6 可能在某些 spec-RTL 信号名上产生误合并（如把"address"和"addr"误对齐到不相关的信号），导致 KG 拓扑错误，LLM 据此生成的 SVA 偏离真实意图。
4. **Schema 的人工 review 不可规模化**：37 个实体 + 31 个关系需要人工合并冗余——这是**一次性成本**，但每遇到一个新设计领域（汽车 / 通信 / 航天），可能需要重做 schema。
5. **形式验证器自身的局限**：Jasper 用 SAT/SMT，对超大状态空间的设计（百万门以上）会遇到容量问题。论文实验设计最大为 openMSP430（4,636 节点），还远小于工业 IP。
6. **未涉及 RTL 修改 / bug 修复**：论文不"修 DUT"——它只生成 SVA。即使 SVA 显示有违例（counterexample），论文不做根因分析（是 RTL bug 还是 SVA 写错？），留给"future work"。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **覆盖率仍非 100%**：openMSP430 Functional 覆盖 90.09%、uart Functional 88.82%，仍有未覆盖的功能点。
2. **假设 golden RTL**：论文假设 RTL 本身是"golden implementation"，但 Jasper 的 counterexample 可能是 RTL bug 而非 SVA 错误——根因分析留 future work。
3. **Jasper 验证主导运行时间**：57-90% 时间花在 Jasper 上（论文 Appendix B），LLM 调用和 KG 构建只占 < 15%。这意味着**优化 LLM 端收益有限**。
4. **Prompt 数非单调**：ℬ=3 → ℬ=9 时 Functional 覆盖度先降后升（88.82 → 83.93 → 89.14），说明上下文选择存在复杂交互。
5. **Pruner prompt 未公开**：论文注明"due to space constraints"——影响可复现性。

### 10.2 代码/复现层面的问题

1. **代码未开源**：论文未提供公开仓库，与 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md) 的匿名审稿链接和 [HAVEN](../HAVEN/论文深度讲解.md) 的"未开源"一致。复现等级 R3（仅描述方法，未公开实现）。
2. **Jasper 是商业闭源工具**：依赖 Cadence 商业 license，复现需要显著成本。论文未开源也部分因为 Jasper 不易获取。
3. **GPT-4o 行为可能漂移**：OpenAI 模型持续迭代，复现时可能因模型下架而无法对齐论文数字。
4. **Pruner prompt 缺失**：直接影响消融实验的可复现性。

### 10.3 本资料包的批判性分析

1. **「Proven SVA 数」不等于「找到的 bug 数」**：论文把 #Proven 作为主要指标，但 **#Proven 高 = 监控范围广，不等于找到 bug**。要让 SVA 找 bug，需要 SVA **被违例**——即 Jasper 给出反例。这与 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md) 用 Spike golden model 做差分检测的思路形成对比：ChipFuzzer 的「bug 检出率」是仿真时的实际违例，AssertionForge 的「#Proven」是静态形式证明。要做完整评价，应该同时报告「#Violated SVA 数」（被 Jasper 拒绝的 SVA）和对应的 RTL 根因。
2. **KG 拓扑错误会污染下游 SVA**：模糊匹配阈值 0.6 是经验值，可能把同名信号误合并（如不同模块里的同名 `valid`）。这种 KG 错误无法被 Jasper 检测——Jasper 只能验证 SVA 是否被违例，无法验证 SVA 监控的信号是否真的是用户想监控的。需要人工 spot-check。
3. **Spec-RTL 关系建模的天花板**：当 spec 不充分（许多工业 spec 只描述接口不描述内部状态）或 RTL 是高度优化过的（寄存器被重命名、状态被重编码）时，KG 的"语义对齐"假设崩塌。论文在 5 个 OpenCores 设计上工作良好，但这些设计的 spec 与 RTL 都相对完整、自洽——与真实工业 IP（往往 spec 滞后于 RTL 多版迭代）有差距。
4. **与 [HAVEN](../HAVEN/论文深度讲解.md) 的方法论对照**：HAVEN（arXiv 2604.27643）的"LLM 不写 HDL、只做 spec→JSON 提取"原则与 AssertionForge 形成对照。AssertionForge 让 LLM 写 SVA（一种 HDL 子集），HAVEN 让 LLM 完全不写 HDL。**后者更激进但更适合 LLM 弱项场景**。
5. **与 [STG](../STG/论文深度讲解.md) 的方法论对照**：STG（arXiv 2606.12983）的"结构化确定性"思想也与 AssertionForge 形成对照。STG 完全不用 LLM 生成 testbench，用确定性模板引擎，0.13 秒生成全 testbench；AssertionForge 全程 LLM 生成 SVA，Jasper 验证占数小时。**确定性 vs 生成式** 是两个路线的根本差异。
6. **缺乏端到端 bug 检出演示**：论文没有用 AssertionForge 在一个已知有 bug 的 RTL 上证明它"找到了这个 bug"。这是与 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md)（Encarsia 90-bug benchmark，61.1% 检出率）的关键差距——**AssertionForge 在公开 bug 集上的检出能力未知**。

## 12. 一分钟复述版

AssertionForge（NVIDIA，LAD 2025）是 **SVA 自动生成 + 形式验证** 的 LLM 框架。核心五招：

1. **Spec + RTL 双源融合为 KG**：用硬件专用 schema（37 实体 + 31 关系）把 spec 抽取为 KG，再用 PyVerilog 把 RTL 的内部信号/控制流/FSM 节点合并进来。spec-RTL 节点通过精确 + 模糊匹配（Levenshtein ≥ 0.6）合并到同一张图。

2. **多分辨率上下文合成**：全局摘要（设计意图）+ SSR（信号级 RAG，top 20 chunks）+ GRW-AS（KG 偏置随机游走，β=0.5 主导目标方向性），再用 LLM-as-Pruner 过滤冗余。

3. **GRW-AS 是断言级"路径搜索器"**：从目标 architectural signal 出发，沿预计算的最短路径附近做游走，找到通向关键信号的路径。论文示例：`tx_busy → uart_tx → uart_top → new_tx_data → data_stability` 直接喂给 SVA 生成器。

4. **严肃评价指标 #Proven**：用 Cadence Jasper 2023.12 做形式验证，统计通过证明的 SVA 数（不是"生成的 SVA 数"）。ethmac 从 15 → 208，openMSP430 从 55 → 327，apb 四类覆盖全 100%。

5. **诚实消融**：去掉 GRW-AS 后 Functional 覆盖降 5 pp，去掉 Summaries 后语法正确性腰斩（132 → 76），朴素 spec+RTL 拼接在所有指标上最差。

**边界**：只覆盖流程阶段 ② + ⑥（2/17）；Jasper 是商业闭源；论文未开源代码；**#Proven 高 ≠ 找到 bug 数高**——没有 RTL 根因分析；缺乏公开 bug 集上的端到端检出率（如 [ChipFuzzer](../ChipFuzzer/论文深度讲解.md) 的 Encarsia 90-bug）；OpenCores / AssertLLM 5 个设计偏教学级，外推工业 IP 有风险。同期/后续的 [HAVEN](../HAVEN/论文深度讲解.md)（LLM 不写 HDL）和 [STG](../STG/论文深度讲解.md)（完全确定性无 LLM 生成 testbench）代表了"更激进分工"的两个方向。
