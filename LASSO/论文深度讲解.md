## 1. 一句话定位

**LASSO（University of Florida，MLCAD 2025）是一个面向总线型 SoC 的 LLM + RAG 安全属性/SVA 自动生成框架——它把规格/RAG 检索出来的设计语义喂给 LLM 生成时序逻辑层面的安全属性（含 k-shot 注入 9 条 vacuity 定理自动剔除空泛属性），再翻译成 SystemVerilog Assertions、用 Cadence JasperGold 做 FPV 反馈和 Formal/Stimuli/Checker 三类覆盖率分析、未达 80% 阈值则迭代精炼 prompt；在 CEP（MIT-LL，5 个 IP）与 OpenTitan（3 个 IP）共 8 个 IP 上覆盖率达 ~88%，并在 Hack@DAC'24 漏洞版 OpenTitan 上检出 5 个真实 bug。**

这句话里的五个承重点，后面逐一拆解：

1. **"Oracle-first" 路线** — 与偏向"生成大量 testcase 看是否触发 bug"的 fuzzing 路线（如同期 ChipFuzzer、VerilogCoder）相反，LASSO 走的是"先生成高质量安全属性 → 形式工具穷举状态空间 → 反例即 bug"的 *oracle-first* 路线：先造 oracle（属性/SVA），再用 FPV 引擎在数学上穷举所有可能输入。这等价于把"找 bug"问题转化为"找反例"问题——这是一个根本性的方法论分野。
2. **RAG + JSON SPEC_FILE 共同解决 LLM 上下文瓶颈** — LLM 的上下文窗口有限，无法直接塞下整个 SoC。LASSO 用结构化 JSON 规格（SoC 名称、总线类型、IP 列表、资产列表……）替代自然语言 prompt，再用 RAG 从 IP 手册/数据表中按需检索信号语义（信号名、端口、位宽、功能、互联、必备断言信息、微架构），把检索结果注入 prompt。这让 LLM 能在 token 预算内"按需取阅"大规模 SoC 文档，是"接得住真实工业 SoC"的关键。
3. **9 条 vacuity 定理做非空泛（non-vacuous）过滤** — LLM 生成的属性常见问题是"前件永远为假"导致"空泛满足"（vacuous satisfaction）。LASSO 把 Kupferman & Vardi、Beer 等的 9 条 vacuity 定理作为 k-shot 示例注入 prompt，让 LLM 自我评估每条属性是否符合非空泛条件；任一定理不满足即丢弃。这是"LLM 幻觉 + 形式化过滤"的协作范式。
4. **Cadence JasperGold 做 FPV 与覆盖率闭环** — 翻译出的 SVA 写入 `.sva` 文件、配套 TCL 脚本自动跑 JasperGold；JasperGold 不仅报 proved/failed/cex（counterexample），还输出 Formal、Stimuli、Checker 三类覆盖率（每类再细分为 COI 和 Proof Core）。覆盖率 < 80% 触发"prompt 库 + 反馈循环"再次生成属性/SVA——这是标准的"形式验证 → 覆盖率 → 精炼"闭环。
5. **Hack@DAC'24 真实漏洞检出** — 不是只在干净 design 上玩，LASSO 把同一框架套到 Hack@DAC'24 故意植入 bug 的 OpenTitan 上，发现 5 个独立 bug（UART 奇偶校验、prim_subreg_arb 写端口赋值、OTP 字溢出、HMAC 密钥泄漏、prim_subreg_shadow 错误检测逻辑），三个 bug 涉及安全敏感路径（密钥/OTP/错误检测）。这类"安全验证"工作通常被视为上半年的旗舰案例。

## 2. EDA 阶段映射（①-⑰）

LASSO 是一个**面向 SoC 安全验证的 assertion/generation + 形式验证**框架。它不写综合代码、不做仿真跑 testbench、不评估 PPA；它的工作是"为已有 RTL 写安全属性，并在 FPV 引擎上验证这些属性"。

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ⚠️ **消费侧** | LASSO 不生成/修改 RTL，但其工作对象是 RTL（SystemVerilog/Verilog）。它阅读 RTL 模块层级结构、子模块接口、信号名以辅助 RAG/属性生成。是"RTL 的消费者"而非"RTL 的作者" |
| ② RTL 功能仿真 | ❌ | LASSO 不跑动态仿真。验证手段是形式验证（⑥），不是 testbench 仿真 |
| **⑥ 形式验证** | ✅ **核心** | LASSO 的核心引擎。Cadence JasperGold 2020.12 跑 SVA，做 proof core / COI / Formal / Stimuli / Checker 覆盖率统计；模型检查器对每条 SVA 给出 proved / failed / cex 三种结果之一。failed/cex 是潜在 bug 信号 |
| ③ 逻辑综合 | ❌ | 不调用 Yosys/Design Compiler。LASSO 工作在 RTL+FPV 层面，不关心综合后网表 |
| ④ 门级仿真 | ❌ | 无 SDF 反标，不跑门级仿真 |
| ⑤ STA | ❌ | 不计算路径延迟。LASSO 的"覆盖率"是形式验证的 COI/Proof Core/Code coverage，与时序无关 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17（⑥ 形式验证 ✅ 核心；① RTL 设计 ⚠️ 消费侧）。** LASSO 是典型的 **EDA 验证侧工具**——专注于设计早期、纯数学意义上的安全性验证，与制造/物理层完全解耦。

> ⚠️ **最容易误读的边界：LASSO 的"formal verification"在 ⑥，而不是 ②。** 形式验证（⑥）用 SAT/SMT 求解器穷举所有可能输入（数学上），不跑 testbench——LASSO 通过 JasperGold 做的正是这件事。② 仿真验证（动态 testbench）则是 LASSO 完全不涉及的领域。Fuzzing 类工作（如 ChipFuzzer）属于 ②，而 LASSO 属于 ⑥。**两者的"找 bug"思路截然不同**：fuzzing 是"用大量 testcase 碰运气"，LASSO/FPV 是"先写对属性，再用证明器穷举"。另外，LASSO 的"功能正确"由 FPV 证明器对设计的逻辑等价性与安全性属性来度量——没有 golden model（这是 FPV 区别于差分测试 / 仿真的关键），但 BUG 检出能力取决于"生成的属性是否覆盖了关键安全行为"——若 LLM 漏写某个安全属性，对应的 bug 就检测不到。

### 3.2 中间产物

**(a) 时序逻辑形式的安全属性**

LLM 生成的属性形式（论文示例，包括 vacuous 与 non-vacuous 例子）：

```systemverilog
// 经典 vacuity 例子（论文 Listing 2，被丢弃）
property p_validCounter_decrement;
  @(posedge clk) disable iff (rst)
  (validCounter > 1) |=> (validCounter == $past(validCounter) - 1);
endproperty
assert property (p_validCounter_decrement);
```

— 论文明确指出 "the antecedent `validCounter > 1` is never true if validCounter is stuck at 1 or 0"，违反 vacuity 定理，应被丢弃。

**(b) SVA 翻译（论文 Listing 3 节选）**

```systemverilog
// 例子：DES3 上 CEX 暴露的语义错误 SVA
property p_k_update;
  @(posedge clk) disable iff (reset)
  (!$stable(roundSel)) |=> (K !== $past(K));
endproperty
assert property (p_k_update);
```

— JasperGold 模型检查器生成 CEX 表明此属性违反设计行为，标记为"语义不正确的 SVA"。

**(c) JasperGold 报告**：每条 SVA 的结果状态（proved / failed / cex）+ 覆盖率报告（Formal/Stimuli/Checker × COI/Proof Core/Code coverage）。

**(d) prompt_database（论文 Listing 4）**

```yaml
prompt_database:
  - "Enhance coverage by adding reset conditions."
  - "Add corner case assertions for boundary values."
  - "Include sequential behavior checks."
  - "Cover unreachable states if any."
  - "Extend assertions to multi-cycle paths."
```

LASSA 把这些 hint 字符串作为"补丁 prompt"在覆盖率不足时注入生成循环。

### 4.2 核心模块逐个详解

**（1）RAG 与高层抽象化（Stage 1）**

LASSO 面对的最大问题是 LLM 上下文限制——一个完整 SoC 可能有几十万行 Verilog，远超任何 LLM 的 200K token 窗口。LASSO 用三层策略解决：

- **高层抽象化**：把 RTL 拆为模块/子模块/组件，每个单元的描述塞进 prompt；
- **RAG 检索**：从 IP 手册/数据表按需抽取 7 项信号信息（检索粒度定义在 Prompt 7）；
- **SPEC_FILE + RAG 联合**：JSON 模板给结构化骨架（SoC 名称、总线、IP 列表、资产列表），RAG 给信号级别的语义补充。

**为什么需要 RAG**：纯自然语言 prompt 无法容纳上千个信号的定义；纯 verbatim RTL 又会让 LLM 看不清"设计意图"。RAG 把"工程文档"和"RTL 代码"映射起来，让 LLM 看到"信号 X 是一个 192-bit 密钥，输入到 AES_192_top 的 key_in 端口，应该在 reset 之后保持"这种带语义的结构化信息。

**（2）安全属性生成 + k-shot vacuity 注入（Stage 2）**

LLM 输出时序逻辑形式的安全属性。论文 Prompt 2 直接把 9 条 vacuity 定理作为 k-shot 注入 prompt：*"Here are the 9 vacuity checking rules you need to memorize. Utilize these 9 theorems to generate valid and non-vacuous properties for the <module/sub-module>."*

论文 Prompt 3 进一步要求 LLM 自我评估：*"A property must fail at least one vacuity condition among the 9 theorems to be non-vacuous."*

**为什么需要 vacuity 检查**：LLM 生成的属性常见问题是"前件永远为假"。例如 `if (validCounter > 1) then ...`——如果 validCounter 实际上总是 0 或 1，这个属性永远成立（vacuously true），等于没验证。**形式化过滤是应对 LLM 幻觉的关键**——不能完全信任 LLM 的"语义合理性"。

**（3）SVA 翻译 + 错误修正（Stage 3）**

LLM 直接把属性翻译为 SVA，加入 reset/clock/假设。语法错误（如 `syntax error near <>` VERI-1137）触发 re-prompt（Prompt 4、5）。论文指出：*LLM often produces SVAs that are "syntactically valid but semantically incorrect"*——非布尔表达式进 implication、信号作用域错误、reset 行为违例。**这类语法正确但语义错误的情况只有 JasperGold 模型检查器能抓到**——这是 LLM→SVA 翻译流水线的"最后一道关卡"。

**（4）JasperGold FPV + 三类覆盖率（Stage 4）**

JasperGold 不只跑"proved/failed/cex"——它报告三类覆盖率：

- **Stimuli Coverage**：输入条件对 DUT 的覆盖程度 = code coverage（branch/statement/expression/toggle）+ functional coverage（covergroups）。
- **Checker Coverage**：形式断言的完整度 = COI coverage（影响某断言的逻辑路径覆盖）+ Proof Core coverage（断言真值所必需的最少设计元素）。
- **Formal Coverage**：上述两类的复合度量。

**为什么需要这三类**：单看"断言 proved/failed"无法判断"验证是否充分"——可能 100% 断言都 proved 但 DUT 关键路径实际上没经过任何断言。COI 告诉你"哪些逻辑路径影响断言"，Proof Core 告诉你"哪些信号是断言成立的最小必要集"——把这两类与代码覆盖/功能覆盖配对，才能判断"验证完整度"。

**（5）迭代精炼（Stage 5）**

如果 Formal Coverage 低于阈值（论文实验 80%），触发反馈循环：从 prompt_database 注入"补丁 prompt"（如"加入 reset 条件"、"加入边界值"、"加入多周期路径"），重新生成属性/SVA。**这是一个标准的"measure → diagnose → remediate"覆盖率闭环**。

**（6）Bug 检出：把 FPV 失败映射到设计缺陷**

把 LASSO 套到 Hack@DAC'24 故意植入 bug 的 OpenTitan 上，跑同样的流水线。LLM 此时被告知目标："针对 security-critical 资产（HMAC key、OTP 字、UART 校验路径、shadow register 错误检测）生成针对性 SVA"。JasperGold 跑出 cex → 即潜在 bug 信号。论文在 5 个 bug 上给出对应 SVA（详见 §3.3 输出(3)）。

## 5. 关键公式

LASSO 论文的"形式化"较薄——只有 1 个核心公式（vacuity 定义），主线由 9 条 vacuity 定理 + 5 个工程阶段构成。下面把核心的形式/概念整理为公式。

### 5.1 经典 vacuity 例子（论文 Eq. 1）

$$
\varphi = G(p \rightarrow F q)
$$

- $\varphi$：时序逻辑公式（"Always, if p holds, then eventually q holds"）
- $G$：globally 算子（所有未来时刻）
- $F$：finally 算子（最终/未来某时刻）
- $p$：前件（antecedent）
- $q$：后件（consequent）

**工程直觉**：这是一个标准的"响应性"（responsiveness）安全属性——"只要请求 p 发生，迟早会得到响应 q"。如果 $p$ 永远不发生，$\varphi$ 自动满足（空泛满足）——这就是 vacuity。

**为什么这么设计**：用最简洁的 LTL 表达式展示"空泛满足"问题。论文同时引用另一例 $AG(req \rightarrow AF grant)$（"every request is eventually followed by a grant"）——若系统从不发请求，$\varphi$ 也 vacuously true。LASSO 通过 9 条定理自动过滤这种"前件永远为假"的属性。

### 5.2 Vacuity 定义（论文 §II-B）

$$
M \models_{\text{vacuous}} \varphi \iff M \models \varphi \;\wedge\; \exists \psi \in \text{sub}(\varphi): \psi \text{ does not affect } \varphi \text{ in } M
$$

- $M$：系统（Kripke 结构 / RTL 设计）
- $\models$：满足关系
- $\varphi$：待验证的时序逻辑公式
- $\psi$：$\varphi$ 的某个子公式
- "$\psi$ does not affect $\varphi$ in $M$"：存在某个子公式 $\psi$ 的真值对 $\varphi$ 在 $M$ 中的真值无影响

**工程直觉**：一个属性 $\varphi$ 在 $M$ 中 "vacuous" 当且仅当 (1) $M$ 满足 $\varphi$，(2) 但存在某个 $\psi$ 在 $\varphi$ 中其实"形同虚设"——无论 $\psi$ 真值如何，$\varphi$ 都成立。**典型情况**：$\varphi$ 的前件永远为假。

### 5.3 9 条 Vacuity 定理（LASSO 注入 LLM 的 k-shot 内容）

LASSO 把 Kupferman & Vardi [16] 与 Beer et al. [17] 的 9 条 vacuity 定理作为 k-shot 示例注入 Prompt 2。形式化摘要（论文正文）：

**定理 1（高效 vacuity 检查）**：

$$
\psi \text{ doesn't affect } \varphi \text{ in } M \iff M \models \varphi[\psi \leftarrow \text{true}] \iff M \models \varphi[\psi \leftarrow \text{false}]
$$

**工程直觉**：检查某个子公式 $\psi$ 是否影响 $\varphi$，等价于把 $\psi$ 强制为 true 和 false 各检查一次 $\varphi$——若两次 $\varphi$ 都满足，则 $\psi$ 在 $M$ 中对 $\varphi$ 无影响（vacuous）。

**定理 2（多项式时间）**：

$$
\text{Vacuity checking time} = O(C_M(|\varphi|) \cdot |\varphi|)
$$

- $C_M(|\varphi|)$：模型检查 $\varphi$ 在 $M$ 上的代价
- $|\varphi|$：公式长度

**工程直觉**：虽然有时候 vacuity 检查需要多次模型检查（定理 1），但整体仍是 $|\varphi|$ 的多项式复杂度——是工业可接受的代价。

**定理 3（CTL vacuity 复杂度）**：对 CTL 公式 $\varphi$、多次出现的子公式 $\psi$、系统 $M$，判定 $\psi$ 是否不影响 $\varphi$ 在 $M$ 中——co-NP-complete。

**定理 4（线性可证伪 CTL 复杂度）**：判定 CTL 公式 $\varphi$ 是否"线性可证"（linearly witnessable）——在 $O(2^{2^{p(n)}})$（2EXPTIME）内，EXPTIME-hard。

$$
C_{\text{lin-witness}} = O(2^{2^{p(n)}})
$$

- $p(n)$：多项式函数

**定理 5（线性可反驳）**：分支时序逻辑 $\varphi$ 线性可反驳 iff $\neg \varphi$ 线性可证。

**定理 6（分支时序）**：$M \not\models A\varphi^d$ iff 存在路径 $\pi$ 使 $\pi \not\models \varphi$。

- $A$：all paths 算子
- $\varphi^d$：去"all"算子后的公式

**定理 7（CTL\* 线性可证伪）**：判定 $\varphi$ 在 $M$ 中线性可证伪——PSPACE-complete（多项式内存）。

**定理 8（反例）**：$\varphi$、$M$ 情形下，$\neg \text{witness}(\varphi)$ 在 $M$ 中的反例即 $\varphi$ 在 $M$ 中的"有趣证"（interesting witness）。

**定理 9（有趣证生成）**：LTL 或 CTL\* 公式 $\varphi$ 在 $M$ 中的 interesting witness 可在多项式空间生成；存在性判定是 PSPACE-complete。

**这些定理的工程作用**：LASSO 把这 9 条作为"判定 vacuity 的形式化清单"灌给 LLM——Prompt 3 要求 LLM 自我评估每条属性是否违反这 9 条之一，违反则丢弃。

**为什么选这 9 条**：覆盖 CTL/CTL\*/LTL 三大分支/线性时序逻辑；复杂度从多项式到 PSPACE-complete 都覆盖；既有结构性判据（定理 1）也有生成性证据（定理 9）。这是"形式化方法教科书级"的最小完备子集。

### 5.4 覆盖率定义（论文 §II-C）

**Stimuli Coverage**：

$$
\text{StimCov} = f(\text{branch},\; \text{statement},\; \text{expression},\; \text{toggle},\; \text{covergroups})
$$

- 包含 code coverage（branch/statement/expression/toggle）+ functional coverage（用户自定义 covergroups）
- 衡量"输入条件对 DUT 的覆盖程度"

**Checker Coverage**：

$$
\text{ChkCov} = f(\text{COI},\; \text{ProofCore})
$$

- COI（Cone of Influence）：影响某断言的逻辑路径覆盖
- Proof Core：断言真值所必需的最少设计元素
- 衡量"形式断言的完整度"

**Formal Coverage**：

$$
\text{FormalCov} = \text{StimCov} \cup \text{ChkCov}
$$

- FormCov 是 StimCov 与 ChkCov 的复合度量

**工程直觉**：单看"所有断言都 proved"无法判断"验证充分"——可能 100 条断言都 proved，但 DUT 关键路径其实没被任何断言"罩住"。Checker Coverage 的 COI/Proof Core 解决"哪些逻辑路径对断言有影响"的问题；Stimuli Coverage 解决"输入条件是否覆盖"的问题；两者并起来才是"验证完整度"的真正度量。

### 5.5 迭代精炼的覆盖率阈值（论文 §III-E）

$$
\text{FormalCov} < \theta_{\text{cov}} \implies \text{触发 prompt 反馈循环}
$$

- $\theta_{\text{cov}}$：论文实验设为 80%（可配置）
- 反馈循环：从 prompt_database 选相关 hint 注入生成，重新生成属性/SVA

**工程直觉**：80% 不是"完全覆盖"，而是"工业上可接受 + 进一步提升边际成本高"的实用阈值。论文把这设成可调参数——商业项目中通常会更严（95%+）。

## 7. 创新点

### 创新点 1：把 RAG + spec-driven prompt 引入 SoC 安全验证

**已有方法的问题**：早期 LLM 验证工作（如 AssertLLM、ChatAssert）把整个 RTL 塞进 prompt，受限于 LLM 上下文窗口；或者直接从 RTL 抽取"特征"（LASP 模式），但抽取后丢失了设计意图。这些工作没有一个能"按需取阅"IP 手册/数据表。

**LASSO/LASA 的突破**：用 JSON 结构的 `<SPEC_FILE>` + RAG 检索共同构造"上下文感知 prompt"。SPEC_FILE 给出 SoC 骨架（SoC_General、BUS_INTERFACE、IP_n、Assets），RAG 检索填充每个信号的 7 项信息。这让 LLM 能在 token 预算内"按需取阅"大规模 SoC 文档。

**与 LASP 的关键区别**：LASP（MLCAD 2024，UF 同一团队的姊妹工作）也用 LLM 生成安全属性，但 *直接从 RTL 抽取关键特征 + 安全资产*，没有 RAG、没有 SPEC_FILE 模板、没有 9 条 vacuity 过滤、没有覆盖率闭环。LASSO/LASA 是 LASP 的"完整版本"。

### 创新点 2：9 条 vacuity 定理的 k-shot 注入 + 非空泛过滤

**已有方法的问题**：LLM 生成的安全属性常见 ~30%~50% 是 vacuous（"前件永远为假"）。这个问题在 ChatAssert、AssertLLM 里都没有专门处理。

**LASSO/LASA 的突破**：把 Kupferman & Vardi、Beer et al. 的 9 条 vacuity 定理作为 k-shot 注入 prompt（Prompt 2），并在 Prompt 3 要求 LLM 自我评估每条属性是否违反这 9 条。**这是"LLM 能力 + 形式化过滤"的协作范式**——LLM 负责生成形式化候选，形式化清单负责判定质量。

**工程意义**：Final 报告里 Non-vacuous / Correct 比例 ≥ 80%——说明"9 条定理 + LLM 自我评估"这条组合拳有效。

### 创新点 3：Cadence JasperGold FPV + Formal/Stimuli/Checker 三类覆盖率闭环

**已有方法的问题**：以往 LLM 验证工作只做"生成 SVA → 跑 SIMULATION"或者"做 functional verification"，没有把 FPV 引擎作"反馈源"。

**LASSO/LASA 的突破**：把 JasperGold 的三类覆盖率（Formal = Stimuli ∪ Checker；Stimuli = code coverage + functional coverage；Checker = COI + Proof Core）作为"验证完整度"的标准度量。低于 80% 阈值触发 prompt 精炼——这是标准的"measure → diagnose → remediate"闭环。

**工程意义**：这是"工业级 FPV 工具 + LLM 创意生成"的协作范式。LLM 不是替换 FPV，而是为 FPV 提供"高质量种子属性"。

### 创新点 4：Hack@DAC'24 真实 bug 检出

**已有方法的问题**：很多 LLM 验证工作只在干净 design 上玩（生成 SVA、统计通过了多少），没在故意植入 bug 的版本上检验"是否能真的找到 bug"。

**LASSO/LASA 的突破**：在 Hack@DAC'24 buggy OpenTitan 上检出 5 个真实 bug（UART 奇偶校验、prim_subreg_arb 写端口、OTP 字溢出、HMAC 密钥泄漏、prim_subreg_shadow 错误检测）。其中 3 个涉及安全敏感路径（HMAC 密钥、OTP 字、错误检测）。

**工程意义**：这是"AI for security verification"从"演示"走向"真实 bug 检出"的实证。同期的 LAMBDA（IEEE 2025）也在同一 OpenTitan 上检出 8 个 bug——印证"spec/RAG + FPV 闭环"路径的可行性。

### 创新点 5：与 LASP 的纵向对比体现"完整化"

LASP（MLCAD 2024，UF 团队）只做 LLM 生成安全属性；LASSO（MLCAD 2025）补齐了：

- RAG 检索信号上下文
- 9 条 vacuity 形式化过滤
- JasperGold 翻译 + FPV 自动化
- Formal/Stimuli/Checker 三类覆盖率
- 阈值触发的迭代精炼
- Hack@DAC'24 真实 bug 检出

**LASSO 是 LASP 的"完整版本"**——同一团队，方法学一脉相承，但工程化程度有数量级提升。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
芯片流程                          LASSO 的位置
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① RTL 设计                       ← ⚠️ 消费侧：阅读 RTL、子模块、信号、
                                   配合 SPEC_FILE/RAG 抽取设计意图
                                   不生成/修改 RTL 本身
② RTL 功能仿真                   ← ❌ 不跑动态仿真
③ 逻辑综合 ~ ⑤ STA               ← ❌ 与物理实现完全解耦
                                   ★ LASSO 在这里
                                   - RAG 检索 + LLM 生成 non-vacuous 安全属性
                                   - LLM 翻译为 SVA → re-prompt 修正语法
                                   - Cadence JasperGold FPV 跑 SVA
                                   - 三类覆盖率（Formal/Stimuli/Checker）反馈
                                   - 覆盖率 < 80% 触发 prompt 精炼
                                   - FPV 反例即潜在 bug 信号
⑦ 布局规划 → ⑬ 签核            ← ❌
⑭-⑰ 流片→制造→封装测试→芯片    ← ❌
```

**解决的痛点**：在 ⑥ 形式验证阶段，传统安全验证需要安全专家手工写 SVA——耗时、易错、专家稀缺。LASSO 用 LLM 把"专家写 SVA"自动化：用 RAG 降低 LLM 的上下文负担，用 vacuity 过滤保证属性质量，用 JasperGold FPV 提供工业级证明引擎。

**端到端具体例子**：以 OpenTitan HMAC 密钥泄漏（Bug #4）为例：

1. LASSO 拿到 OpenTitan 的 `hmac_reg_top.sv` + IP 手册 + SPEC_FILE；
2. RAG 检索到 HMAC 有 `reg_rdata_next` 寄存器、`[8]/[9]` 地址段对应 secret key 寄存器；
3. LLM 生成安全属性"`(addr_hit[8] || addr_hit[9]) |-> reg_rdata_next == 0`"——即"读密钥寄存器时必须返回 0"；
4. vacuity 检查：前件 "addr_hit[8] || addr_hit[9]" 在合理实现中会触发，非空泛；
5. LLM 翻译为 SVA `p_hmac_key_read_blocked`，加入 reset 条件；
6. JasperGold 跑 cex：发现 `reg_rdata_next` 实际未被打断——证实 bug 存在；
7. 报告：Hack@DAC'24 Bug #4，HMAC 哈希密钥通过 `reg_rdata_next` 泄漏。

### 9.2 「FPV 通过」和「能流片」之间隔着什么

LASSO 的"FPV 通过 + 覆盖 80%"只保证**在已生成安全属性覆盖的范围内** RTL 在数学上满足这些属性。以下维度都不在 LASSO 评估范围内：

1. **属性覆盖率不等于设计正确性**：LASSO 追求 80%+ Formal Coverage，但这个覆盖率是"已生成属性 + 形式引擎能证明的"范围内的覆盖率。LLM 漏写某个安全属性（如不熟悉某个寄存器读路径语义），对应的 bug 就检测不到。LASSO 的"安全"上限受限于"LLM 看过的类似 IP"和"RAG 检索到的文档完整度"。
2. **不做动态仿真**：LASSO 完全不跑 testbench，无法发现时序相关 bug（毛刺、建立/保持违例、X 传播）。形式验证只关心"逻辑等价"，不关心"时间"。
3. **无物理验证**：不涉及门级仿真、STA、DRC、LVS、IR Drop、信号完整性等物理层面。
4. **依赖 LLM 推理质量**：LLM 可能幻觉硬件语义，尤其对自定义 CSR 或厂商私有扩展。论文未做"out-of-distribution IP"的鲁棒性测试。
5. **依赖 FPV 引擎的 scalability**：JasperGold 对状态空间爆炸敏感。论文实验的 IP 都是中等规模（AES/DES/I2C 等）；超大 IP（如 GPU、视频解码）的 scalability 未验证。
6. **无综合检查**：不验证综合是否改坏逻辑（那是 ⑥ 形式验证的另一面——等价性检查 EC）。
7. **与差分测试、fuzzing 互补而非替代**：LASSO 不能替代仿真验证（②）、等价性检查（⑥ EC）、门级仿真（④）、后仿真（⑪）。完整的验证流程需要 LASSO + 仿真 + 形式 EC + STA + 后仿真的协同。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **依赖 RAG 检索质量**：LASSO 的"信号语义"完全依赖 RAG 从 IP 手册/数据表抽取。如果文档不全、错位（或 IP 是闭源无文档），RAG 检索效果退化，LLM 生成的属性质量下降。
2. **未公开 LLM ablation**：论文 Fig. 2 只给出三种 LLM 的最终排名（GPT-4o > Gemini-1.5 > Llama-3.1），没有详细分析每个 LLM 在不同 IP、不同 vacuity 定理上的差异。读者无法判断 GPT-4o 是"全面优势"还是"某些定理上特别强"。
3. **依赖商业 FPV 工具**：Cadence JasperGold 2020.12 是商业闭源。论文未讨论是否可迁移到 Synopsys Formality/Conformal、Siemens EDA（以前 Mentor）的 Questa Formal 等替代 FPV 工具。
4. **特定 IP 集合**：8 个 IP（CEP 5 个 + OpenTitan 3 个）都是中等规模的开源 SoC。未在大规模商业 IP（如某 GPU 核、多核 CPU）上验证 scalability。
5. **scale 限制**：未给出 FPV 跑通每条 SVA 的 wall-clock 时间，也未给出完整一遍迭代精炼的总体时长。论文只给出"硬件配置 + 内存"。
6. **属性生成数量的"质量-数量"权衡未量化**：论文 Table II 显示 GPS 生成 108 个属性（93 个 non-vacuous），但 DES3 只有 37 个——这种数量差异对覆盖率贡献多大？未单独分析。

### 10.2 代码/复现层面的问题

1. **代码未开源**：论文及 arXiv LASA 版本均未给出代码仓库链接。无法独立核验 prompt 模板、vacuity 过滤逻辑、SPEC_FILE 模板、prompt_database 内容。
2. **arXiv PDF 抓取不稳定**：本资料包尝试下载 arXiv:2506.17865v1 PDF 时多次 timeout（>200s），最终未能完整下载。本节内容基于 arXiv HTML 渲染版 + Semantic Scholar 摘要 + 多源叙述交叉核对，与 IEEE 论文正式版可能有微小差异。
3. **IEEE Xplore pdf 受限**：DOI 10.1109/MLCAD65511.2025.11189178 在 WebFetch 抓取中受限，无法直接获取正式 PDF。
4. **prompt 细节依赖人工复现**：Prompt 1~7 的完整文本未在论文正文给出（仅在附录 -A），复现需要审稿版本的完整附录。
5. **复现门槛**：(a) Cadence JasperGold 商业 license（昂贵）；(b) GPT-4o API 账户；(c) 8 个 IP 的 RTL（CEP 需要 MIT-LL 许可，OpenTitan 公开）；(d) Submodule 级别的设计规格文档。

### 10.3 本资料包的批判性分析

1. **"非空泛"≠"有意义"**：LASSO 的 vacuity 过滤只能保证"前件不为假"。但一个属性可能前件真但描述了一个无关紧要的信号行为（如"复位时所有寄存器为 0"——技术上 non-vacuous，但几乎没有安全意义）。需要领域专家额外评估"生成的属性是否对应真实威胁模型"。
2. **GPT-4o 商业依赖**：选 GPT-4o 作为主 LLM 意味着复现成本高（API 费用 + 速率限制）。Llama-3.1 等开源 LLM 性能差距未量化，无法判断本地化部署是否可行。
3. **scale 评估不足**：state explosion 问题是 FPV 的根本挑战。论文只测了中等规模 IP。对超过 1M latches 的工业 SoC，LASSO 的"覆盖率 80%"目标是否可达成？JasperGold 的求解时间是否 exponential？未讨论。
4. **闭环上限**：LASSO 的反馈循环是"覆盖率 < 80% → 重新生成"。但如果 LLM 反复生成的都是同一类属性（"模型模式坍缩"），反馈循环就无法提升。论文未给出"反馈循环迭代次数"上限与"哪种 prompt_database hint 失效最快"的统计。
5. **与 ATLAS、TAS+ 等后续工作的潜在差异**：同期 / 后续工作（如 ATLAS [Tashdid et al., 2025]）也在做类似 spec-to-assertion 学习，可能在"威胁模型注入"或"fine-tuned LLM"上超越 LASSO 的纯 prompt 路线。LASSO 框架目前还是"通用 LLM + 形式化过滤"，未涉及 fine-tuning。
6. **RAG 的"知识库"运维代价**：PRODUCTION 部署里，RAG 的知识库需要持续更新（IP 改版、手册更新）。LASSO 未讨论知识库的版本管理、自动同步。
7. **未结合 diffusion / GNN 等结构化 IP 表示**：IP 在 LLM 看来是"扁平文本"。AST/AIG/DDG 等结构化表示理论上能让 LLM 推理更准。但 LASSO 完全依赖纯文本 RTL + RAG，没用结构化 IP 表示。

## 12. 一分钟复述版

LASSO（University of Florida，MLCAD 2025）是一个**不训练模型、用 LLM + RAG + JasperGold 形式验证做 SoC 安全验证自动化**的 oracle-first 框架。核心五招：

1. **RAG + JSON SPEC_FILE 喂上下文**：把 SoC 规格结构化为 JSON（SoC 名称、总线、IP 列表、资产），再用 RAG 从 IP 手册按 7 项信号信息（name/port/desc/func/interconnect/assert-hints/uarch）检索信号语义，注入 prompt——让 LLM 在 token 预算内"按需取阅"大规模 SoC 文档。

2. **9 条 vacuity 定理 k-shot 注入**：Kupferman & Vardi、Beer 的 9 条 vacuity 形式化定理作为 k-shot 喂给 LLM，Prompt 3 要求 LLM 自我评估每条属性是否违反任一定理——非空泛过滤让 LASSO 生成的属性"前件永远为假"的比例大幅下降。

3. **Cadence JasperGold FPV + 三类覆盖率**：翻译出的 SVA 跑 JasperGold 2020.12，输出 Formal/Stimuli/Checker 三类覆盖率（每类再细分为 COI / Proof Core），加 code coverage（branch/statement/expression/toggle）。80% 阈值未达则触发 prompt 精炼——是 measure → diagnose → remediate 闭环。

4. **8 个开源 IP 验证**：CEP（MIT-LL）的 AES-192、DES3、GPS、FIR、IIR + OpenTitan 的 i2c、adc_ctrl、kmac，各 IP 生成 30~108 条属性，Non-vacuous / Correct 比例 ≥ 80%，覆盖率达 ~88%。GPT-4o > Gemini-1.5 > Llama-3.1（按 proved+failed 占比）。

5. **Hack@DAC'24 真实 bug 检出**：在故意植入 bug 的 OpenTitan 上检出 5 个独立 bug——UART 奇偶校验、prim_subreg_arb 写端口、OTP 字溢出、HMAC 密钥泄漏、prim_subreg_shadow 错误检测。3 个涉及安全敏感路径。

**方法学定位**：LASSO 走的是"oracle-first"路线（先写好属性 → FPV 穷举验证 → 反例即 bug），与 fuzzing 类工作（生成大量 testcase 碰运气）形成**根本性对比**。形式验证（⑥）vs 仿真（②）的区别：LASSO 用 SAT/SMT 求解器穷举数学可能输入，fuzzing 跑仿真跑 testbench。

**边界**：流程阶段 2/17（① 消费侧 + ⑥ 核心），依赖 JasperGold 商业 FPV 引擎 + GPT-4o API，代码未开源，scale 仅测中等规模开源 IP（8 个），RAG 质量依赖 IP 文档完整度，对超大 IP（>1M latches）的 scalability 未验证。

**与 LASP 的关系**：LASP（MLCAD 2024）是 LASSO 的前身，由 UF 同一团队出品。LASSO 是 LASP 的"完整版"——补齐 RAG、vacuity 过滤、覆盖率闭环、bug 检出。
