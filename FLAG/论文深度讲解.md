# FLAG 论文深度讲解

> **FLAG: Finding Line Anomalies (in RTL code) with Generative AI**  
> 作者：Baleegh Ahmad, Joey Ah-Kiow, Benjamin Tan, Ramesh Karri, Hammond Pearce  
> 期刊：ACM Transactions on Design Automation of Electronic Systems，30(6)，Article 103，2025  
> DOI：<https://doi.org/10.1145/3736411>

---

## 1. 一句话定位

FLAG 是一种 **不依赖 testbench、仿真或形式属性** 的 RTL 行级 fault localization 方法：先用静态规则缩小候选行，再让 LLM 分别进行 token-level 或 line-level 生成，通过原代码与生成结果的差异、模型置信度和代码上下文对可疑行排序。ACM 正式版报告，line-level 分析在 120 个 real-world bugs 中 Top-5 定位 38 个，token-level 分析在 81 个 synthetic bugs 中 Top-5 定位 32 个。

它的作用是给工程师提供“优先检查哪些行”的排序，不是证明某行一定有 bug，也不负责生成能暴露该 bug 的 stimulus。

## 3. 输入 / 输出

### 输入

- 一个 Verilog 或 SystemVerilog 设计文件；
- 源码的语法结构与上下文；
- 可调用的代码生成 LLM。

不需要输入：

- testbench、waveform 或 coverage；
- golden RTL；
- security property 或 functional assertion；
- 可综合、可编译的完整工程。

### 输出

- 经过 generic localization 筛选的候选代码行；
- token-level 与 line-level 生成特征；
- 每行 anomaly / suspiciousness 排名；
- 供工程师检查的 Top-1、Top-5 或 Top-10 可疑位置。

下面是概念性接口，用于说明 FLAG 返回的是排序而非 bug 判定；它不是论文仓库中的真实输出格式：

```text
input : Verilog/SystemVerilog source
output: [(line_number, suspiciousness_score), ...]  # descending rank
```

## 4. 方法与架构

```text
RTL 源文件
   │
   ▼
Generic Localization
   │  静态规则先排除不适合分析的行
   ▼
候选 RTL 行
   ├───────────────┐
   ▼               ▼
Token-level      Line-level
逐 token 生成     整行重生成
   │               │
   └───────┬───────┘
           ▼
差异与上下文特征
Levenshtein distance / log probability /
distance from comments / 其他分类特征
           │
           ▼
行级排序 → Top-K 可疑位置
```

### Generic Localization

这一步用语法和代码结构先减少候选范围。ACM 页面描述其通常可把需要继续分析的代码行减少约 30%–50%，降低 LLM 调用和误报压力。

### Token-level 与 line-level

- **Token-level**：逐 token 观察模型生成与原始 token 的差异及置信度。
- **Line-level**：让模型生成完整代码行，再把生成行与原始行比较。

两条路径评估的数据类型不同，因此不能把“38/120 real-world”与“32/81 synthetic”相加成一个总检出率。

## 5. 关键公式与指标

Levenshtein distance 用最少编辑操作数衡量两个字符串的差异：

$$
d(i,j)=\min
\begin{cases}
d(i-1,j)+1,\\
d(i,j-1)+1,\\
d(i-1,j-1)+\mathbb{1}[x_i\neq y_j]
\end{cases}
$$

- $x$：原始 RTL 行的 token 或字符序列；
- $y$：LLM 生成序列；
- $d(i,j)$：两个前缀之间的最小插入、删除、替换代价；
- $\mathbb{1}[x_i\neq y_j]$：两个位置不同时取 1，否则取 0。

论文还使用 LLM confidence / log probability、distance from comment 等特征。旧讲解把一个未证实的“ed ∈ [-1,1] 相似度”当作核心公式，这是错误的；正式版的可靠表述是 **Levenshtein distance（ld）及相关分类特征**。

正式版摘要给出的关键 Top-5 结果：

| 分析方式 | 数据 | Top-5 定位结果 |
|---|---:|---:|
| Line-level | 120 个 real-world bugs | 38 / 120 |
| Token-level | 81 个 synthetic bugs | 32 / 81 |

论文评估的目标是 fault localization：真实缺陷行是否进入 FLAG 输出的 Top-K，而不是生成代码是否通过仿真。

---

## 7. 创新点

1. **Test-free、specification-free 的 RTL 定位**：在完整验证环境尚未建立时也能给出可疑行。
2. **生成式自比较**：不只用模型直接回答“哪里有 bug”，而是比较原代码与模型生成替代内容。
3. **token / line 两个粒度**：允许分析局部 token 异常和整行语义异常。
4. **先静态筛选再调用 LLM**：Generic Localization 控制候选规模和成本。

## 9. 与芯片流程的关系

FLAG 位于 RTL 编写后的早期审查阶段。它可以在仿真环境、checker 或形式属性尚未完成时给工程师一个检查顺序；后续仍需要 testbench、assertion、formal verification 或其他 oracle 来确认可疑行是否真正导致功能错误。

与 [BluesFL](../BluesFL/论文深度讲解.md) 相比，FLAG 更轻量且不需要运行处理器；BluesFL 结合 instruction path、processor state 和 waveform，把定位扩展到大规模处理器项目。与 [MulFetFL](../MulFetFL/论文深度讲解.md) 相比，FLAG 依赖生成式语言模型，后者融合 AST、signal 和 timing 图特征。

## 10. 讨论与局限

- **Anomaly 不等于 bug**：LLM 不喜欢某种代码写法，不代表该行功能错误。
- **不使用动态证据**：缺少 waveform、failing test 和 propagation trace，难以区分语法罕见与真实行为错误。
- **Top-5 仍需人工确认**：real-world 集上 38/120 表明多数缺陷没有进入前五。
- **模型与代码分布敏感**：训练语料较少的 RTL 风格、宏、参数化代码可能提高误报。
- **跨文件和时序 bug 更难**：单行排名不天然表达多模块状态、协议序列或跨周期依赖。

因此 FLAG 更适合作为 triage 工具，而不是 verification signoff 工具。

## 12. 一分钟复述版

FLAG 用 LLM 对 RTL 原代码做生成式自比较，再把差异、置信度和上下文特征转换成行级可疑排名。它不需要 testbench、仿真或形式属性，因此适合早期 triage。ACM 正式版报告：line-level 方法在 120 个真实 bug 中 Top-5 定位 38 个，token-level 方法在 81 个合成 bug 中 Top-5 定位 32 个。它能减少人工搜索范围，但不能证明可疑行真的有 bug，也不能替代动态或形式验证。
