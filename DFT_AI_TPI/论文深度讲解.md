## 1. 一句话定位

**FT-Pilot 不训练任何模型，它把"自动给 RTL 做软错误加固"这件事拆成"GNN 在 RTL 级找出该保护的寄存器 + LLM 选策略并重写代码 + 多级验证自动修复"三段闭环——把 GNN+TMRG 的平均面积开销从 +112% 压到 +71%（同等可靠性），同时把加固全流程从"人工四步"变成"零人工全自动"。**

这句话里有三个承重点，后面逐个拆：

1. **不训练** → 收益全部来自推理时编排（GNN 预测 + LLM 重写 + 自动修复）
2. **GNN 引导** → 解决"哪些寄存器该保护"的问题（uniform TMR 之所以贵，是因为它不加选择地保护所有寄存器）
3. **双知识库 RAG + 多级验证自动修复** → 解决"LLM 在硬件领域缺乏领域知识 + 容易幻觉"的问题

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。FT-Pilot 是一个**可靠性（reliability）维度的纵向工具**，它和传统正向设计流程正交：

| 阶段 | 覆盖 | FT-Pilot 做了什么 / 为什么没做 |
|------|:---:|---------------------------|
| **① RTL 设计** | ✅ **核心** | RTL Rewriter 读取原始 RTL，根据 GNN 给出的 vulnerable register 列表 + RTL Analyzer 给出的 strategy 分配 + 双知识库 RAG 检索的模板，生成加固后的 Verilog 代码 `module fsm_ft(...)` |
| **② RTL 功能仿真** | ✅ **核心** | Auto-Repair 用 iverilog 语法检查 + ModelSim 跑原始 benchmark TB 做功能比对（"reuse original testbench to preserve behavioral equivalence"），保证加固后功能等价 |
| ③ 逻辑综合 | ✅ **次要** | 用 Yosys + Nangate45 开源工艺库综合，统计面积/延迟 overhead（论文 Table V）。**不是核心优化目标**，是评价指标 |
| ④ 门级仿真 | ❌ | 不做 SDF 反标、亚稳态、毛刺分析。加固目标是 SEU 软错误（register-level），不涉及 setup/hold 违例 |
| ⑤ STA（Static Timing Analysis） | 部分 | 只报综合后的 critical-path delay（论文 Table V），不做静态时序违例分析 |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明。功能等价靠"原始 TB 跑过"近似——比形式验证弱得多 |
| ⑦-⑩ 后端物理设计 | ❌ | 不涉及 |
| ⑪ 后仿真 | ❌ | — |
| ⑫-⑬ 物理验证 & 签核 | ❌ | — |
| ⑭-⑰ 流片→制造→封测→芯片 | ❌ | — |

**覆盖率：2.5/17（核心 2 个 + 综合作为评价工具）。** FT-Pilot 在阶段 ① 的 RTL 重写子任务里来回迭代（Analyzer → Rewriter → 语法/接口/功能验证 → Auto-Repair → 再 Rewriter），直到多级验证全部通过。

> ⚠️ **可靠性是横切关注点（cross-cutting concern）**：传统流程按 ①→⑰ 顺序串行，可靠性加固是在 RTL 阶段做的额外 transform，不改变主流程的几何顺序。但加固后的 RTL 必须能通过后续所有阶段的检查，所以"加固可综合 + 功能等价"是硬约束——这是 §9.3 展开的核心论点。

## 3. 输入 / 输出举例

### 3.1 输入（三件套）

以论文 Fig. 2 用例 `module fsm`（一个简单的 FSM）为例：

**(a) 原始 RTL（Unhardened）**
```verilog
module fsm(
    input  IN,
    input  CLK, RST,
    output MATCH
);
    reg [2:0] ST_cr, ST_nt;     // ← GNN 标记为 critical
    // ... 组合 + 时序逻辑
endmodule
```

**(b) GNN 输出的脆弱性报告（vulnerability report，结构化 JSON）**
```json
{
  "critical_registers": [
    {
      "asset_id": "A1",
      "asset_type": "fsm_state",
      "signals": ["ST_cr", "ST_nt"],
      "risk": "high",
      "strategy_candidates": ["fsm_hamming", "tmr_state"]
    },
    {
      "asset_id": "A2",
      "asset_type": "counter_reg",
      "signals": ["cnt"],
      "risk": "high",
      "strategy_candidates": ["tmr_reg", "ecc"]
    }
  ]
}
```

**(c) 原始 benchmark testbench（用于功能验证）**
```verilog
// 来自 RTLLM / OpenCores / GitHub 的标准 TB
// 加固后用同一个 TB 跑，验证功能等价
```

### 3.2 中间产物

**Stage 1 — GNN Vulnerability Analysis 的产出**：
- 每个 register 的 AVF（Architectural Vulnerability Factor）预测
- 加固目标列表（vulnerable registers + types）

**Stage 2 — RTL Analyzer 的产出（plan.json）**：
```json
{
  "asset_id": "A1",
  "asset_type": "fsm_state",
  "signals": ["cur_state"],
  "risk": "high",
  "strategy_candidates": ["tmr_state"],
  "query_terms": ["fsm state register protection", "tmr state encoding"]
}
```

经过 Plan Builder 三道校验（static structure check 去伪 register、deduplication 合并同物理 register、strategy compliance check 对照 eligibility table）后，发给 RTL Rewriter。

**Stage 3 — RTL Rewriter 的产出**：
- 加固后的 RTL `module fsm_ft(...)`，内含三模冗余 / Hamming 编码 / ECC 等具体实现
- 通过语法 → 综合 → 接口 → 功能仿真 → 故障注入五道关卡
- 失败的尝试进入 **Strategy Failure KB**（失败经验库）累积

### 3.3 输出

**最终加固 RTL（FT-Pilot 输出的 fsm1 加固版本）**：
```verilog
module fsm_ft(
    input  IN,
    input  CLK, RST,
    output MATCH,
    // ... 可能新增的接口信号（Hamming 需要额外 encode/decode 端口）
);
// 原始 FSM 逻辑保留
// 但 ST_cr/ST_nt 被三模冗余或 Hamming 保护
endmodule
```

**伴随产物**：
- 加固前后 AVF 对比（验证可靠性提升）
- 面积/延迟 overhead 报告
- 完整的 Auto-Repair 轨迹（哪些尝试失败、为什么失败）
- Strategy Failure KB（跨设计累积的错误知识）

| 知识库 | 内容 | 解决的问题 |

- 让 LLM 预先规避同类错误——这是跨 run / 跨设计的知识迁移

## 5. 关键公式（LaTeX）

### 公式 (1)：节点特征向量（静态 + 动态拼接）

$$
\mathbf{x}_i = [\mathbf{x}_i^{(s)} \| \mathbf{x}_i^{(d)}]
$$

- $\mathbf{x}_i^{(s)}$：**静态拓扑特征**——节点类型 one-hot（PI / PO / 逻辑门 / FF）、fan-in / fan-out 数、forward / backward logic depth、一阶邻居类型分布
- $\mathbf{x}_i^{(d)}$：**动态行为特征**——toggle rate（仿真期间信号翻转次数）、signal probability（信号为高的时间占比）、coverage（信号是否同时取过 0/1）

**为什么要分静态和动态**：
- **只看静态**：FSM 状态寄存器的位置重要，但一个被反复采样的 control register 也可能同样脆弱
- **只看动态**：toggle 高的节点可能只是被时钟扇出（toggle 来自下游），未必自身关键
- **拼接**：拓扑位置 × 运行时活跃度 = 综合判据（论文 Sec III-B 的核心论断）

**与 Lu et al. [12] 的关键区别**：[12] 的 GNN 用 netlist-level 拓扑 + 时序仿真特征，需要**post-synthesis netlist**。FT-Pilot 用 RTL-level AIG graph + 同一份 workload 的 RTL 仿真，**不需要做综合**，shift left 到 RTL 设计阶段。

### 公式 (2)：AVF（Architectural Vulnerability Factor）

$$
\text{AVF}(r_i) = \frac{N_i^{\text{err}}}{N_i^{\text{inj}}}
$$

- $N_i^{\text{inj}}$：对寄存器 $r_i$ 注入 SEU 故障的总次数
- $N_i^{\text{err}}$：导致 primary output 错误的注入次数

**AVF 是 GNN 的训练标签**：
- 跑 Z01X fault injection，对每个寄存器随机时刻注入单 bit-flip
- 比对故障输出与 golden reference，统计出错概率
- 按设计的 AVF 分布设阈值（"predefine a per-design AVF threshold"）→ 1 表示 vulnerable，0 表示 non-vulnerable
- 转成 **binary classification** 问题

### 公式 (3)：GraphSAGE 邻居聚合（k-th layer）

$$
\mathbf{h}_v^{(k)} = \sigma\left( \mathbf{W}^{(k)} \cdot \text{AGG}\left( \mathbf{h}_v^{(k-1)},\ \{ \mathbf{h}_u^{(k-1)},\ \forall u \in \mathcal{N}(v) \} \right) \right)
$$

- $\text{AGG}(\cdot)$：聚合函数（论文用 **mean aggregation**）
- $\mathcal{N}(v)$：节点 $v$ 的邻居集合
- $\mathbf{W}^{(k)}$：第 $k$ 层的可学习权重矩阵
- $\sigma$：ReLU 激活

**为什么用 GraphSAGE 而不是 GCN**：
- GCN 是 transductive（全图卷积），需要整个图一起训练
- GraphSAGE 是 inductive（邻居采样 + 聚合），对**未见过的图节点**也能推理
- 对大规模电路（mriscv 9 个子模块、上千个 register）扩展性更好

**网络结构**（论文 Sec III-B.4）：
- 3 层 SAGEConv：input dim=19 → hidden=64 → output=2
- 每层后接 BatchNorm + ReLU + Dropout
- 类加权 cross-entropy 处理类别不平衡

### 公式 (4)：类加权交叉熵损失

$$
L = -\frac{1}{N} \sum_{i=1}^{N} \left[ w_{y_i}^{(i)} y_i \log(\hat{p}_1^{(i)}) + (1 - y_i) \log(1 - \hat{p}_1^{(i)}) \right]
$$

- $w_{y_i}^{(i)}$：类权重（vulnerable 类权重高，缓解非脆弱寄存器远多于脆弱寄存器的 imbalance）
- $\hat{p}_1^{(i)}$：节点 $i$ 被预测为 vulnerable 的 Softmax 概率

### 公式 (5)：Pass@k 无偏估计（Codex/HumanEval 标准）

$$
\text{pass@}k = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n - c_p}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个设计的独立候选生成数（论文 $n=10$）
- $c_p$：其中通过功能验证的候选数
- $k$：抽取的样本数

当 $k=1$ 时化简为 $\text{pass@}1 = \mathbb{E}[c_p / n]$，即每题期望通过率。

论文采样配置：$T=0.8$，$\text{top\_p}=0.95$，$n=10$。同时报告 pass@1（单次成功率）和 pass@3（最多 3 次重试的成功率）。

## 6. 训练与实验设置

### 6.1 是否需要训练

**部分训练**。FT-Pilot 不是纯推理时编排——GNN 部分需要训练，LLM 部分不训练。

**GNN 训练**：
- 用 PyTorch Geometric 实现 GraphSAGE
- 标签生成：Synopsys Z01X fault injection（每个 register 注入 SEU，计算 AVF → 二分类）
- 数据集：4 个 medium-to-large 设计（mriscv、SPI、I2C、XGE-MAC），每个 split 70%/30%
- **per-design basis**：每个新设计需要重做 fault injection 生成标签（论文 Sec V-B 明说 "for each new, previously unseen design, fault-injection simulation is still required"）

**LLM 训练**：
- **不训练**——直接调用现成的 Claude Opus 4.6 / GPT-5.3 / GLM-5 / Qwen-3.6 Plus
- 也不做 SFT / RLHF / DPO
- 收益全部来自 prompt engineering + RAG + Auto-Repair

**对比 MAGE**：MAGE 是纯推理时编排；FT-Pilot 是"GNN 训练 + LLM 推理时编排"的混合范式。GNN 的训练数据来自 Z01X 仿真（**不是用 LLM 生成的数据**），保留了 ground truth 标签。

**评估指标**：
1. **GNN 阶段**：Accuracy / Precision / Recall / F1
2. **LLM 重写阶段**：
   - **pass@k**（Codex/HumanEval 标准）
   - **面积 overhead**（Yosys + Nangate45 综合，µm²）
   - **延迟 overhead**（critical-path delay, ns）
   - **错误率**（SEU fault injection 下的 error rate, %）
3. **自动化程度**（Table VI）：五个环节是否需要人工

**基线方法（Table V）**：

| 系统 | 描述 |
|------|------|
| **Unhardened** | 原始 RTL，不做任何保护——area / reliability baseline |
| **Full TMR** | 对**所有**寄存器三模冗余 + 多数投票——upper bound on reliability, lower bound on efficiency |
| **GNN+TMRG** | 用 GNN 找 vulnerable register，再用开源 TMRG 工具插入 TMR——state-of-the-art 选择性加固 |
| **FT-Pilot（本文）** | GNN 找 vulnerable register + LLM 选多策略（Hamming / TMR / ECC / ABFT）+ 自动修复 |

**基线覆盖范围**：
- Full TMR 和 GNN+TMRG 在 11 个设计上评估（fifo / memory / gemm 这三个 storage/matrix 设计被排除——TMR 对存储类设计几乎无意义）

**LLM 配置**：
- 主实验：**Claude Opus 4.6**（Anthropic）
- 消融实验：GPT-5.3、GLM-5、Qwen-3.6 Plus

## 7. 创新点

### 创新点 1：RTL-level 脆弱性预测（不依赖 post-synthesis netlist）

**这是 FT-Pilot 最硬的一个洞察**。

传统 GNN 脆弱性预测（Lu et al. [12]）需要 **post-synthesis gate-level netlist**：
- 必须先跑综合（Design Compiler / Yosys + tech mapping）
- 预测模型和具体工艺库耦合
- 换工艺库要重新训练
- 整个流程只能跑在综合之后——违反"shift-left"

**FT-Pilot 的做法**：
- RTL → Yosys 翻译 → **AIG graph**（technology-independent）
- 在 AIG graph 上跑 GraphSAGE，预测每个 register 的脆弱性
- 由于 AIG 不绑定工艺库，**模型可移植**，**分析提前到 RTL 阶段**

**Table IV 的证据**：
- mriscv：fault injection 3 小时 → GNN 19 秒（**540 倍加速**）
- I2C：fault injection 1.5 小时 → GNN 10 秒（**540 倍加速**）
- **同等或更高的 accuracy**（mriscv 98.84% vs [12] 98.67%，XGE-MAC 96.73% vs 96.67%）

**这是 shift-left reliability optimization 的第一个可工程化的实例**。

### 创新点 2：GNN + LLM 的"分工"范式（gating 互补）

**这不是简单的"两个工具串起来"**：

| 维度 | GNN | LLM |
|------|-----|-----|
| **擅长** | 拓扑感知的结构脆弱性 | 代码语义理解与代码生成 |
| **不擅长** | 写代码 | 判断电路拓扑 |
| **训练** | 需要 Z01X 标签（per-design） | 不训练 |
| **泛化** | 在**结构相似**的设计间 | 在**自然语言描述相似**的代码模式间 |

**两者互补性**：GNN 找出"哪些寄存器该保护"，LLM 决定"用什么策略保护 + 怎么写代码"。没有 GNN，LLM 会过度保护；没有 LLM，GNN 只能指导 TMRG 这种单一策略（Table V 显示 GNN+TMRG 的 +112% vs FT-Pilot 的 +71%）。

**论文 Sec V-A 的反思**：这种范式的上限取决于 LLM 能力（GLM-5 pass@1 47.86% vs Claude Opus 4.6 85.00%）。随着 LLM 进步，FT-Pilot 会自动受益——**这是推理时编排的复利效应**。

### 创新点 3：Strategy Eligibility Table —— 把 LLM 的"随机性"压回约束内

LLM 的天然随机性会让它在策略选择时乱来（"model may deviate from the Strategy Eligibility Table or assign multiple strategies to the same asset"）。FT-Pilot 用一张显式的 **Strategy Eligibility Table**（Table I）做硬约束：

| Asset 类型 | 适用策略 |
|-----------|---------|
| fsm state | ✓ tmr_state, ✓ fsm_hamming, ◦ one_hot, ◦ illegal_detect, ◦ parity |
| counter reg | ✓ tmr_reg, ✓ hamming, ◦ cnt_comp, ◦ secded, ◦ parity |
| datapath reg | ✓ tmr_reg, ✓ hamming, ◦ secded, ◦ parity, ◦ parity_byte |
| control reg | ✓ tmr_reg, ◦ parity, ◦ watchdog |
| memory | ✓ ecc_fifo, ✓ sram_ecc, ◦ scrubbing, ◦ gray_ptr, ◦ parity_byte |
| matrix unit | ✓ abft_sec, ✓ abft, ◦ checksum |

✓ = 推荐（可纠错）；◦ = 替代（仅检错或高开销）

**Plan Builder 的三道校验**（论文 Sec III-C.1）：
1. **Static structure check**：解析 always 敏感列表，剔除只在组合逻辑中赋值的信号（伪 register，硬化无意义）
2. **Deduplication**：合并指向同一物理 register 的多个 asset（避免重复保护）
3. **Strategy compliance**：对照 eligibility table，违规的自动替换为该 asset 类型的推荐策略

**这是用确定性规则约束 LLM 的一个干净例子**——避免"过度硬化 + 冗余保护 + prompt 膨胀"。

### 创新点 4：双知识库 RAG（语义 + 实例）

**单知识库不够**：
- 只有策略描述 → LLM 知道"该用 TMR"但写不出 voter
- 只有代码模板 → LLM 不知道"什么场景该用哪个模板"

**FT-Pilot 的双 KB 设计**（论文 Sec III-C.2）：

| 知识库 | 存储 | 检索触发 |
|--------|------|---------|
| **Semantic KB** | 29 个 fault-tolerance 策略的形式描述：适用场景、实现原理、接口约束、overhead 估算 | Query Constructor 提取 (asset, strategy, module context) |
| **Examples KB** | 经人工 check 的 RTL 重写模板代码片段 | 从 Semantic KB 检索到的 strategy identifier 二次定位 |

**消融证据（Table VII）**：去掉 RAG 后 pass@1 从 85% 降到 74%，mriscv 直接从 30% 降到 0%——RAG 是 FT-Pilot 整个 LLM 引擎能用的前提。

**比 MAGE 的 LlamaIndex RAG 更垂直**：MAGE 用通用 RAG 做 Verilog 知识检索，FT-Pilot 把 RAG 专门化到 fault-tolerance 领域，且 Semantic/Examples 严格对齐——这是 hardware-specific RAG 的一个示范。

### 创新点 5：Strategy Failure KB —— 跨 run 错误累积

**LLM 在这个领域的典型失败模式**（论文 Sec IV-D 列出）：
- TMR voter 实现不完整
- 对陈旧寄存器值投票（时序错位）
- Hamming 校验位错位
- 端口不匹配（新增 encode/decode 接口）
- 多驱动冲突

**FT-Pilot 的解法**：把这些失败模式分类、用 `(strategy, error_type)` 索引入 KB。下次同样策略被选时，**主动检索历史失败模式，作为 warning 注入 prompt**——让 LLM 预先规避。

**这是一个"negative RAG"**：传统 RAG 检索正面知识（怎么写对），Failure KB 检索负面知识（不要这样写）。两者结合显著提升重写鲁棒性。

### 创新点 6：多级验证自动修复闭环

**5 道验证关卡**（论文 Sec III-C.2）：
1. **语法检查**（iverilog）
2. **可综合性**（Yosys synth）
3. **接口一致性**（端口匹配）
4. **功能仿真**（ModelSim + 原始 TB——"reuse original testbench to preserve behavioral equivalence"）
5. **可靠性验证**（Z01X fault injection）

**修复机制**：错误分类 → 修复 prompt（包含原 RTL + 错误版 + 分类错误 + 精简 RAG）→ 下一轮 LLM（≤3 轮）。失败案例入 Failure KB。

**为什么 ≤3 轮**：3 轮是 success rate 和 compute cost 的平衡点——再多轮性价比下降（论文 Sec III-C.2）。

**对比 MAGE**：MAGE 的 Judge Agent 只做"功能仿真 mismatch 计数"（pass/fail），FT-Pilot 的多级验证做"语法 + 综合 + 接口 + 功能 + 可靠性"五道关卡。**后者把"修复目标"从 1 维（功能正确）扩展到 5 维（语法 + 综合 + 接口 + 功能 + 可靠性）**——这是 fault-tolerant RTL 任务的内在需求决定的。

### 9.2 FT-Pilot 与 MAGE 的范式对照

FT-Pilot 和本资料包中的 MAGE 是 **AI4EDA 的两个互补方向**——一个在 RTL 生成，一个在 RTL 加固：

| 维度 | FT-Pilot | MAGE |
|------|----------|------|
| **任务** | 把 RTL 改成 RTL（加固变换） | 把自然语言改成 RTL（生成） |
| **优化目标** | 可靠性（vulnerability 降低）+ 面积最优 | 功能正确（$s(r)=1$） |
| **使用模型** | GNN + LLM | 仅 LLM |
| **是否需要训练** | GNN 部分需要 Z01X 标签 | 不训练 |
| **闭环反馈** | 5 级（语法 / 综合 / 接口 / 功能 / 可靠性） | 1 级（功能仿真 mismatch） |
| **EDA 工具** | Yosys + iverilog + ModelSim + Z01X | iverilog |
| **主要约束** | 加固必须保留功能（"preserve behavioral equivalence"） | 生成必须功能正确 |
| **Benchmark** | 14 个 RTLLM/OpenCores 设计 | VerilogEval-Human/V2 |
| **可比指标** | pass@1 = 85%（Claude Opus 4.6） | pass@1 = 94.8%（Claude 3.5 Sonnet 高温） |
| **EDA 阶段** | ① + ② + ③ | ① + ② |

**为什么两者互补**：
- **MAGE 解决"如何自动写 RTL"**——benchmark 里 51% → 95% 的提升来自推理时多 Agent 编排
- **FT-Pilot 解决"如何在 RTL 上做可靠性优化"**——把全人工 + 高开销的加固流程变成自动 + 选择性
- **理想组合**：MAGE 生成的 RTL → FT-Pilot 自动化加固 → 加固后的 RTL 进入综合和后端。这是 RTL 设计的"全自动 + 自动加固"完整链路。

### 9.3 "加固通过验证" ≠ "硅片上可靠"

和 MAGE 一样，FT-Pilot 的多级验证通过≠芯片能可靠工作。列出加固可能仍失败的情形：

**在 ② RTL 仿真被拦下的**：
- 时序竞争（race condition）：加固引入的额外组合路径在 RTL 仿真无延迟，看不出来
- X 传播：如果原始电路有未初始化的寄存器，加固版本可能放大 X 传播

**在 ③ 综合被拦下的**：
- **不可综合结构**：`initial` 块、latch 推断、组合环——加固代码若用这些，仿真通过但综合报 warning/error
- **面积异常**：Table V 显示 fsm1 加固后面积从 30.1 → 72.4（+140.53%），因为这个电路太小，所有 register 都被 GNN 标为 critical

**在 ④ 门级仿真被拦下的**：
- **TMR voter 的建立/保持违例**：投票器在三路寄存器之后，如果路径延迟差异大，门级仿真会报时序违例
- **跨时钟域未同步**：加固后跨时钟域路径变多，CDC 问题加剧

**在 ⑤ STA 被拦下的**：
- **关键路径延迟增加**：Table V 显示 mriscv 延迟从 1.236 ns → 1.694 ns（+37%），uart 从 0.730 ns → 0.840 ns（+15%）
- **时钟偏斜**：TMR 三个副本可能因布局差异引入 skew

**结论**：FT-Pilot 的 5 级验证是**必要条件而非充分条件**。它把"人工四步加固"变成"自动多级验证加固"，但"从 RTL 加固到能流片"这段路它只走了一半——综合、STA、布局后的可靠性仍需传统 EDA 工具兜底。

## 10. 讨论与局限

### 10.1 GNN 模型的 per-design 训练限制

论文 Sec V-B 明说："The current GNN predictor is trained on a per-design basis, meaning that for each new, previously unseen design, fault-injection simulation is still required to generate training labels, cross-design generalization has not yet been achieved."

**这意味着**：GNN 不能"零成本迁移到新设计"。每个新设计需要先跑 Z01X 生成标签、再训练 GraphSAGE——这是 **per-design 的固定开销**。

**对比 Lu et al. [12]**：[12] 的 GNN 也是 per-design 训练，所以这不是 FT-Pilot 的倒退，而是该方向的开放问题。

**可能的突破方向**：
- **预训练 + 微调**：用大量小设计的 GNN 数据做预训练（自监督），新设计只微调
- **跨设计特征工程**：让节点特征包含"asset type one-hot"，靠 asset 类型跨设计共享（FSM 状态寄存器在哪都脆弱）
- **在线学习**：加固过程中产生的新数据回灌 GNN

### 10.2 上下文窗口限制（最大 mriscv 2665 行）

论文 Sec V-C："Designs with significantly larger register counts, such as XGE-MAC, already exceed the practical context limits of current LLMs."

**这意味着**：FT-Pilot 当前**只能处理中小规模 RTL**（论文最大 2665 行、9 个子模块）。

**论文建议的扩展路径**：
- **按模块层次分解**：把大设计拆成子模块，逐个加固，保留接口一致性
- **自动从论文/规格提取策略**：减少人工维护的 Semantic KB / Examples KB

**对比 MAGE**：MAGE 在 VerilogEval 上也是单模块（single-file），同样撞上下文墙。两个系统的下一步都需要解决"多模块 / 长上下文"问题。

### 10.3 Fault Model 局限：只考虑 SEU

论文 Sec V-B 指出当前实验**只考虑 SEU（单事件翻转）**——即每个寄存器被翻转 1 bit。但随着工艺缩小：

- **MBU（Multi-Bit Upset）**：单粒子击中导致多位翻转
- **SET（Single Event Transient）**：组合逻辑中产生毛刺被寄存器捕获
- **SEFI（Single Event Functional Interrupt）**：影响整个模块功能

论文明说："As technology nodes continue to shrink, the probability of multi-bit upsets (MBUs) increases, and existing fault-tolerance strategies such as Hamming(7,4) encoding and standard TMR may no longer provide adequate protection."

**这意味着**：Hamming(7,4) 假设单 bit 错，标准 TMR 假设 3 副本中至多 1 副本错——MBU 会让这两条假设同时失效。需要 2-bit 检错 + Hamming 扩展码或更复杂的策略。

### 10.4 LLM 能力的上限依赖

论文 Sec V-A："The overall effectiveness of the proposed framework is, to a considerable extent, bounded by the current capability of large language models."

Table VIII 的数据是直白的：
- Claude Opus 4.6 pass@1 = 85.00%
- GPT-5.3 pass@1 = 75.00%
- Qwen-3.6 Plus pass@1 = 60.71%
- GLM-5 pass@1 = 47.86%

**模型差距高达 37 个百分点**——FT-Pilot 的收益强烈依赖 LLM 选型。

**比 MAGE 的 LLM 依赖更严重**：MAGE 只做 RTL 生成，LLM 写错可以靠高温采样 + Debug 修复；FT-Pilot 做加固变换，写错的代码可能**功能等价但保护逻辑失效**——这种错误仿真看不出来，只有 fault injection 才能发现。这让 LLM 能力差距的影响更隐蔽。

**好消息**：论文 Sec V-A 的判断——"as LLMs continue to advance in code generation, such progress is expected to directly translate into higher rewriting quality within the framework without requiring architectural modifications"——这是一个**复利**效应：未来 Claude/GPT 更强，FT-Pilot 自动更强。

### 10.5 Knowledge Base 的人工维护成本

论文 Sec V-C："the strategy entries in the current knowledge base are manually curated, and incorporating new fault-tolerance techniques requires ongoing human effort."

**Semantic KB 的 29 个策略**：
- 寄存器保护、FSM 加固、数据路径编码、存储 ECC、系统级监控
- 每条包含：适用场景、实现原理、接口约束、overhead 估算

**Examples KB 的 RTL 模板**：
- 每个策略对应经人工 check 的代码片段
- 新增策略需要写策略描述 + 写代码模板 + 检查可用性

**这是 FT-Pilot 的扩展性瓶颈**：加一种新策略 = 人工写两条 KB 条目。对研究系统可接受，对工业部署是大坑。

**论文建议的解决**：自动从论文 / 设计规格提取策略知识（用 LLM 反向工程）。但这又依赖 LLM 能力——回到 10.4 的循环依赖。

### 10.6 验证机制的盲区

**5 级验证没有覆盖的**：

1. **功能等价的形式化证明**：ModelSim 跑 TB 通过 ≠ 两个 RTL 行为等价。TB 覆盖率有限，可能漏掉 corner case。
   - 应该做 ⑥ 形式验证（等价性检查 EC / 模型检查 MC），但论文不做。
   - 后果：加固后的 RTL 在原 TB 上仿真通过，但换一个 TB 可能 fail

2. **可靠性提升的形式化证明**：Z01X fault injection 是统计性的（随机注入 N 次算 error rate），不是 100% 的覆盖。
   - 论文 mriscv 报 ERR=1.46%，这意味着 100 次注入中还有约 1.5 次出错。
   - 工业级标准（如 ISO 26262 ASIL-D）可能要求更严格的证明。

3. **功耗影响**：Table V 没报功耗。TMR/Hamming 都增加 toggle 概率 → 动态功耗上升。
   - 对电池供电或低功耗设计，这可能是 deal-breaker

4. **可测试性影响**：加固后寄存器变成 3 倍（TMR），scan chain 长度增加 → DFT 复杂度上升
   - 论文未涉及 DFT 影响

### 10.7 自动化程度的真实评估

论文 Table VI 把流程分为 5 个环节：

| Flow | Vulnerability Id. | Strategy | Rewrite | Verification |
|------|-------------------|----------|---------|--------------|
| Manual | Manual | Manual | Manual | Manual |
| TMRG | Manual | TMR only | Semi-Auto | Manual |
| GNN+TMRG | GNN | TMR only | Semi-Auto | Manual |
| **FT-Pilot** | **GNN** | **Multi-strategy** | **LLM** | **Auto** |

**这看起来"全自动"**，但有几个隐藏的人工环节：

1. **GNN 训练标签**：Z01X fault injection 仍然要人准备 workload TB + 跑 Z01X
2. **Semantic KB / Examples KB 维护**：新增策略要人写 KB 条目
3. **Auto-Repair 的 3 轮上限**：超过 3 轮仍 fail 时需要人介入（论文没说介入方式）
4. **原始 TB 的存在**：依赖每个设计都有可跑的 TB——这是 benchmark 假设，不是工业现实

**真实自动化程度**：FT-Pilot 把"加固策略选择 + 代码重写 + 多级验证"自动化了，但"生成训练数据 + 维护知识库 + 处理边缘案例"仍需人工。**对 benchmark 上的中小规模设计，它接近全自动；对工业设计，它是一个半自动工具**。

### 10.8 值得追问的开放问题

1. **Plan Builder 的合规检查是否过严？** 论文说"automatically replaces any non-compliant assignment with the preferred strategy for that asset type"。如果 LLM 给出了一个合理的非标准策略（如 FSM 状态用 parity），会被强制改成 tmr_state——可能浪费 LLM 的推理能力。

2. **RAG 的 top-k=3 是否最优？** 论文没给消融。top-k=1 可能漏掉有用知识，top-k=5 可能让 prompt 过长稀释关键信息。

3. **Auto-Repair 的 3 轮上限是否够？** mriscv pass@1 只有 30%，意味着 70% 的尝试要靠 Auto-Repair。3 轮内修复率是多少？论文没给。

4. **Failure KB 多久"失效"？** 累积的失败模式可能误导后续尝试（如某种错误在新设计上不存在，但 KB 仍注入 warning）。需要遗忘机制。

5. **能否集成 PPA 优化？** 当前 FT-Pilot 只优化 reliability + area。如果把 timing closure 或 power optimization 加进 LLM 目标函数，框架就成了"可靠性 + PPA 联合优化"——这是更完整的设计空间探索。

6. **能否处理层次化设计的加固？** 当前假设单模块或小规模多模块。工业设计几十个模块，每个有自己的加固需求——需要模块级加固 + 全局一致性检查。

## 12. 一分钟复述版

FT-Pilot 是中科院计算所发在 arXiv 的 GNN + LLM RTL 软错误加固框架，**GNN 部分需要训练，LLM 部分不训练**。核心四招：

1. **RTL 级 GNN 脆弱性预测**——RTL → Yosys → AIG graph → GraphSAGE 分类（mriscv 上 F1 = 99.26%），**比传统 fault injection 快 100-500 倍**，且**不依赖 post-synthesis netlist**，shift-left 到 RTL 阶段。
2. **GNN + LLM 的分工范式**——GNN 找"哪些寄存器该保护"，LLM 选"用什么策略 + 怎么写代码"。消融证明没 GNN 时 LLM 会过度保护低风险寄存器（crc 错误率 0.16% → 9.71%）。
3. **双知识库 RAG + Strategy Eligibility Table**——Semantic KB（29 策略描述）+ Examples KB（RTL 模板）做检索增强；eligibility table 做硬约束避免 LLM 乱选策略。消融证明没 RAG 时 mriscv pass@1 从 30% 跌到 0%。
4. **5 级验证自动修复闭环**——语法（iverilog）+ 综合（Yosys）+ 接口 + 功能仿真（ModelSim）+ 可靠性（Z01X）。失败分类后入 Failure KB 累积跨设计错误知识，≤3 轮重试。

主结果（Claude Opus 4.6）：14 个 benchmark 上面积开销平均 **+71%**（vs Full TMR +176%、GNN+TMRG +112%），同等可靠性（fifo / memory / crc / uart 错误率 < 0.2%）。

**边界**：核心覆盖流程 ① + ② + 部分 ③（综合作为评价工具）。GNN 训练 per-design 不可零成本迁移；最大设计 2665 行（mriscv 9 个子模块）；只考虑 SEU 故障模型；LLM 选型影响极大（GLM-5 pass@1 = 47.86% vs Claude Opus 4.6 = 85.00%）；Knowledge Base 需人工维护；功能等价靠"原 TB 跑过"近似（非形式验证）。

**与 MAGE 的关系**：MAGE 是"自然语言 → RTL"（生成），FT-Pilot 是"RTL → 加固 RTL"（变换）。两者在 AI4EDA 中互补——MAGE 解决 RTL 生成正确性，FT-Pilot 解决生成后的可靠性优化。
