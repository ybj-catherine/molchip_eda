# Dr. RTL：用商业 EDA 工具反馈驱动的自主 RTL PPA 优化

> 论文：**Dr. RTL: Autonomous Agentic RTL Optimization through Tool-Grounded Self-Improvement**

> 代码：<https://github.com/hkust-zhiyao/Dr_RTL>

## 1. 一句话定位

**Dr. RTL 把 Claude Code 当作总控宿主，让多个专职 Agent 反复读取 Synopsys Design Compiler 的综合/静态时序结果、改写已经由人写好的 RTL，再用商业形式等价检查过滤错误候选，并把成功与失败的局部改写沉淀成可复用 skill，从而在不训练新模型的情况下做推理时 PPA 优化。**

它与“让 LLM 从自然语言生成一份能通过仿真的 Verilog”不是同一个问题。Dr. RTL 的起点是**已有、可综合、功能正确的 RTL**，目标是在保持时序等价的前提下，找到商业综合器常规优化之外仍有价值的结构级改写，例如条件预计算、进位选择式算术结构、寄存器复制和高扇出信号复制。

这篇论文与“是否有人直接用 Codex、Claude Code 等闭源工具做 EDA，而不是魔改一个开源 Agent 仓库”的问题高度相关，原因有三点：

1. **Agent 宿主就是现成的 Claude Code CLI。** 论文没有重新造一套 React 前端，也没有把主要贡献包装成一个自研通用 Agent 框架；公开仓库用 `CLAUDE.md`、`.claude/agents/` 与 `.claude/skill/rtl-opt/` 组织工作流。
2. **真正的环境反馈来自工业 EDA。** 核心闭环调用 Synopsys Design Compiler 做综合和 STA，并调用 Cadence JasperGold／Synopsys Formality 一类商业形式工具做顺序等价检查（SEC）。LLM 不是凭语言直觉猜 PPA。
3. **贡献落在工作流与可积累经验上。** 多 Agent 分工、候选并行搜索、同组相对比较和 skill library 才是核心；基础模型可替换，论文还比较了 Claude 系列、OpenAI GPT-5.3 与 Qwen Coder 8B。

但也要准确区分：论文所说的 skill 是项目内可读、可检索、可迭代的 RTL 优化经验库，虽然其目录形式与 Claude Code skill 接近，却不应自动等同于 Codex 官方技能规范或某个跨宿主标准。Dr. RTL 证明的是“**闭源 coding-agent 宿主 + 工业 EDA 工具 + 项目内 skill memory**”这条路线可行，不是证明所有 Agent Skill 格式天然互通。

## 2. EDA 阶段映射

按照本仓库 [芯片流程.md](../芯片流程.md) 的 17 阶段标准，Dr. RTL 的**核心闭环覆盖 4/17：① RTL 设计、③ 逻辑综合、⑤ 静态时序分析、⑥ 形式验证**。论文还用 Innovus 做过布局布线后的迁移性实验，但后端流程不是 Agent 的主要搜索环，因此下面标为“辅助评估”，不计入核心 4/17。

| 阶段 | 是否覆盖 | Dr. RTL 中的具体角色 |
|---|:---:|---|
| ① RTL 设计 | ✅ 核心 | Agent 读取并改写已有 Verilog/SystemVerilog，实现条件预计算、逻辑重构、复制等结构优化 |
| ② 功能仿真 | ❌ | 核心正确性守门依赖形式等价，不以 testbench 仿真或覆盖率闭合为主 |
| ③ 逻辑综合 | ✅ 核心 | Synopsys Design Compiler 将每个 RTL 候选综合到门级，提供面积与时序基础数据 |
| ④ DFT/扫描插入 | ❌ | 未讨论 scan、ATPG、MBIST 或可测试性约束 |
| ⑤ 静态时序分析 | ✅ 核心 | 提取 WNS、TNS、关键路径、起止点、逻辑层级和扇出，直接驱动下一轮修改 |
| ⑥ 形式验证 | ✅ 核心 | 用 SEC 过滤功能不等价候选；只有 SEC 通过者才有资格晋级 |
| ⑦ Floorplan | ⚠️ 辅助 | post-P&R 实验需后端环境，但 Agent 核心方法不搜索 floorplan |
| ⑧ Placement | ⚠️ 辅助 | Innovus 实验用于观察综合期 RTL 优化在后端是否仍保留收益 |
| ⑨ CTS | ⚠️ 辅助 | 后端验证流程可能经过时钟树，但论文没有提出 CTS Agent 或专项优化 |
| ⑩ Routing | ⚠️ 辅助 | 用于 post-route PPA 观察，不是闭环中的候选生成阶段 |
| ⑪ 寄生参数提取 | ❌ | 未给出 signoff RC extraction 方法或多角提取设置 |
| ⑫ 功耗分析 | ❌ | 目标函数主要用 WNS、TNS、面积；没有以活动率驱动的功耗签核 |
| ⑬ IR Drop | ❌ | 未涉及电源完整性 |
| ⑭ EM | ❌ | 未涉及电迁移 |
| ⑮ DRC | ❌ | 未以版图 DRC 为闭环约束 |
| ⑯ LVS | ❌ | 未涉及版图与原理图一致性检查 |
| ⑰ Tapeout/GDS | ❌ | 不产出可流片 GDS，也没有完整 signoff 结论 |

这里最容易被误读的是“RTL-to-PPA”。Dr. RTL 的主闭环并不是完整 RTL-to-GDS 自动设计系统，而是**以综合后 PPA 为主要奖励信号的 RTL 级局部搜索**。Innovus 结果能说明部分收益可传递到后端，却不能把覆盖率直接算成 10/17，更不能等价为完成了物理签核。

## 3. 输入、输出与任务定义

### 3.1 输入

一次优化任务至少需要以下输入：

- 一份原始、可综合并被视为功能基准的 RTL 设计；
- 时钟、I/O delay、library 等综合和时序约束；
- 能运行综合、STA 与 SEC 的脚本和工具环境；
- 当前轮基准候选及其 WNS、TNS、面积、关键路径等结构化记录；
- 历史 skill library，包括推荐模式、适用条件、风险和应避免的改写；
- coding-agent 宿主的工程指令，例如仓库中的 `CLAUDE.md` 和专职 Agent 提示文件。

论文处理的不是故意打坏的 toy RTL。20 个设计平均约 812 行 RTL、3 个模块、6230 个门和 760 个寄存器，最小约 128 行，最大约 4615 行。作者把时钟周期设成很激进的 0.1 ns，使综合后普遍存在负 slack，目的是给优化器制造足够明显的时序压力。

### 3.2 一个典型改写长什么样

论文图 7 给出“条件预计算”类 skill。下面是按照其结构重写的示意，而不是仓库源码逐字摘录。

```systemverilog
// 改写前：多个分支重复执行相同的宽比较，容易形成重复逻辑和较深控制路径
always_comb begin
  next_state = state;
  if ((src_id == dst_id) && (opcode == OP_A)) begin
    next_state = S_A;
  end else if ((src_id == dst_id) && (opcode == OP_B)) begin
    next_state = S_B;
  end
end
```

候选改写把重复条件显式抽出，让综合器更容易共享逻辑，也让后续 Agent 能定位关键控制信号：

```systemverilog
logic same_id;
logic is_op_a, is_op_b;

assign same_id = (src_id == dst_id);
assign is_op_a  = (opcode == OP_A);
assign is_op_b  = (opcode == OP_B);

always_comb begin
  next_state = state;
  if (same_id && is_op_a) begin
    next_state = S_A;
  end else if (same_id && is_op_b) begin
    next_state = S_B;
  end
end
```

这种改写并不保证每次都好。商业综合器可能已经做过公共子表达式消除，显式拆分也可能改变扇出和映射结果。因此 Dr. RTL 不把语言模型的解释当结论，而是对每个候选重新综合、重新 STA、重新 SEC。

### 3.3 中间工件

公开仓库采用结构化文件保存每轮结果。字段可抽象成下面这种记录：

```json
{
  "iteration": 4,
  "parent": "iter_03_best",
  "candidate": "cand_02",
  "strategy": "replicate_high_fanout_control",
  "wns": -0.041,
  "tns": -3.27,
  "area": 18432.8,
  "sec_pass": true,
  "score": -0.163,
  "critical_paths": ["u_ctrl/state_reg -> u_alu/result_reg"]
}
```

结构化状态有两个用途：一是让总控在上下文窗口之外仍能恢复搜索轨迹；二是让 skill 学习 Agent 对“同一个父设计、同一套工具条件、同一轮生成的多个候选”做可比的归因，而不是把跨设计、跨约束的绝对 PPA 数字硬拼在一起。

### 3.4 输出

最终输出不是一句建议，而是一组可验证工件：

1. 经过若干轮改写后的最佳 RTL；
2. 与原始 RTL 的 SEC 通过结果；
3. 最佳候选及各轮候选的 WNS、TNS、面积与综合报告；
4. 关键路径诊断和修改日志；
5. 更新后的 skill library，包含高/中/低置信度技能及 avoid list；
6. 可供下一设计复用的 Agent 配置与工具脚本。

所以它的任务可以概括为：**在功能等价约束下，在可综合 RTL 的等价变换空间里搜索更好的 PPA 点，同时把搜索过程中可迁移的因果模式压缩成显式技能。**

## 4. 方法与系统架构

### 4.1 总体闭环

```text
原始 RTL + 约束
       │
       ▼
商业综合/STA ──► Timing Analysis Agent ──► 关键路径与结构诊断
       ▲                                      │
       │                                      ▼
Evaluation Agent ◄── N 个候选 RTL ◄── RTL Optimization Agent
       │                 ▲                    │
       │                 └──── Skill Library ┘
       ▼
SEC 过滤 + PPA 评分
       │
       ├── 选出本轮最佳候选，进入下一轮
       └── Skill Learning Agent 比较同组成功/失败候选并更新技能
```

系统通常执行 10 个大轮次，每轮并行产生 5 个候选，也就是每个设计最多约 50 次尝试。候选可以并行跑 EDA，因此墙钟时间更接近“轮数 × 一次 EDA 评估时间”，而不是“轮数 × 候选数 × EDA 时间”。

### 4.2 Orchestrator：用 Claude Code 做现成总控

Claude Code 负责调用专职 Agent、读写文件、发起工具脚本和维护当前最优状态。它不是一个只输出单次 patch 的聊天机器人，而是一个长时任务执行器：

- 把每轮的父设计、候选目录、报告路径和分数写入共享 JSON；
- 在上下文过长时依靠文件状态恢复，而不是只靠对话记忆；
- 控制候选并行和 EDA 作业提交；
- 只把 SEC 通过且综合成功的候选送入排名；
- 将最低 score 的合法候选晋升为下一轮基线；
- 在 10 轮后汇总最佳 RTL 与 skill 更新。

这一选择很有现实意义：研究者没有为了论文重新实现一套 IDE、Agent runtime 或网页界面，而是把研究创新集中到 EDA 闭环与记忆机制上。代价是系统会受到 Claude Code 版本、模型服务、计费与接口行为变化影响。

### 4.3 Timing Analysis Agent：把报告转成可修改原因

综合报告本身往往只告诉工程师某条路径很慢。Timing Analysis Agent 继续完成四步：

1. 找出 top-k 关键路径的 startpoint、endpoint、逻辑层级、cell delay 和 fanout；
2. 把网表级路径映射回 RTL 模块、寄存器和表达式；
3. 判断瓶颈属于组合深度过大、高扇出、控制/数据耦合、重汇聚逻辑或算术链；
4. 输出一份可执行的修改假设，而不是泛泛地说“优化时序”。

论文消融显示，去掉细粒度寄存器 slack 反馈后，平均 WNS/TNS/面积收益从约 21%/17%/6% 降到约 9%/9%/3%。这说明 coding agent 真正需要的是**贴近工具语义、可以定位到代码位置的反馈**，不是把一整份几万行报告塞进 prompt。

### 4.4 RTL Optimization Agent：并行探索而不是单一路径贪心

优化 Agent 根据诊断生成 5 个相互有差异的候选。它先检索 skill library：如果当前结构与已有模式匹配，就套用带条件的策略；如果没有，就提出新假设。

并行候选非常关键。RTL 等价变换具有强烈的非单调性：看似相似的两个重写可能因映射、扇出或优先级语义而得到完全不同的综合结果。单次生成会把偶然失败误判成策略无效，也会把偶然成功误判成普遍规律。同父候选提供了一个小型“受控实验组”。

### 4.5 Evaluation Agent：只报告证据，不参与自我说服

Evaluation Agent 的职责被刻意限制为：

- 检查 RTL 是否能被工具解析和综合；
- 运行 SEC；
- 采集 WNS、TNS、面积等指标；
- 按固定公式计算 score；
- 返回原始报告路径和状态。

它不负责替候选辩护，也不根据自然语言解释修改评分。这种角色隔离减轻了“生成者自己给自己打分”的偏差。特别是 SEC 是硬门槛：一个 PPA 再好的候选，只要等价检查失败，就不能晋级。

### 4.6 Skill Learning Agent：从同组相对结果提炼经验

Skill Learning Agent 不只收集成功 patch，而是比较同一父设计下的候选组：

- 哪些候选改变了同一种结构；
- 哪些通过 SEC，哪些破坏了状态、位宽、符号或优先级语义；
- 哪些让 WNS/TNS 变好但面积恶化；
- 成功是否能由明确的结构条件解释；
- 该策略应进入高、中、低置信度还是 avoid 类别。

论文最终得到 47 项技能：12 项高置信度、16 项中置信度、6 项低置信度和 13 项 avoid。高置信度例子包括条件预计算、carry-select adder transformation、寄存器或信号复制；中置信度包括 mux-select 与无条件计算、mux-before-adder、公共子表达式消除；avoid 中既有综合器通常已经会做的低收益重写，也有经常恶化时序或破坏等价性的重写。

这里的关键不是“把所有过去 patch 拼进上下文”，而是把经验压缩为**模式、适用条件、动作、预期收益、风险和反例**。这比无边界的聊天记忆更接近工程知识库。

### 4.7 三层搜索轨迹

论文把轨迹分成三层：

- **iteration 层**：当前最佳设计如何沿 10 轮逐步演化；
- **candidate 层**：同一轮 5 个候选之间的相对表现；
- **critical-path 层**：每个候选具体针对哪条路径、哪类结构和哪项工具反馈。

这三层分别回答“搜索往哪里走”“这轮哪个动作更好”“为什么可能更好”。只有 patch，没有父子关系与工具报告，就无法可靠提炼 skill。

## 5. 核心公式与评分机制

### 5.1 带功能等价约束的优化目标

设原始 RTL 为 \(D_0\)，允许的 RTL 变换集合为 \(\mathcal{T}(D_0)\)，PPA 目标函数为 \(f_{PPA}\)，则论文问题可写成：

$$
D^{*}=\arg\min_{D\in\mathcal{T}(D_0)} f_{PPA}(D)
$$

同时满足：

$$
\operatorname{Equiv}(D,D_0)=1
$$

`Equiv=1` 是硬约束，不是分数中的一个软权重。它防止 Agent 用删逻辑、改状态机行为或缩短运算位宽等方式“作弊”。

### 5.2 一轮中的候选生成

第 \(t\) 轮从当前父设计 \(D_t\) 生成 \(N\) 个候选：

$$
D_t\rightarrow\left\{D_t^{(i)}\right\}_{i=1}^{N}\rightarrow D_{t+1}
$$

论文默认 \(N=5\)。这些候选共享父 RTL、约束和工具设置，因此适合做组内相对比较。

### 5.3 多目标分数

公开实现按照基准设计对三项指标归一化。对 WNS 和 TNS 使用基准绝对值作为分母，可避免负 slack 造成方向混淆：

$$
\operatorname{WNS}_{i}^{norm}=\frac{\operatorname{WNS}_{i}-\operatorname{WNS}_{base}}{\left|\operatorname{WNS}_{base}\right|}
$$

$$
\operatorname{TNS}_{i}^{norm}=\frac{\operatorname{TNS}_{i}-\operatorname{TNS}_{base}}{\left|\operatorname{TNS}_{base}\right|}
$$

$$
\operatorname{Area}_{i}^{norm}=\frac{\operatorname{Area}_{i}-\operatorname{Area}_{base}}{\operatorname{Area}_{base}}
$$

候选综合分数为：

$$
\operatorname{Score}_{i}=\alpha\operatorname{WNS}_{i}^{norm}+\beta\operatorname{TNS}_{i}^{norm}+\gamma\operatorname{Area}_{i}^{norm}+\operatorname{penalty}_{i}
$$

实现中权重为 \(\alpha=0.50\)、\(\beta=0.35\)、\(\gamma=0.15\)。当候选面积相对基准增加超过 10% 时，再加 0.5 的惩罚。代码采用“分数越低越好”的约定；SEC 失败者直接失去晋级资格。

下一轮父设计选择为：

$$
D_{t+1}=\arg\min_{D_t^{(i)}}\operatorname{Score}_{i},\quad \text{subject to }\operatorname{SEC}_{i}=1
$$

这个目标把 WNS 和 TNS 同时纳入，会更偏向修复最坏路径并减少整体违例，但二者并非统计独立，权重也不是技术节点无关的普适常数。迁移到其他团队时，权重、面积阈值和时序目标都应重新校准。

### 5.4 组内相对优势

对第 \(t\) 轮候选分数，设均值为 \(\mu_t\)、标准差为 \(\sigma_t\)，论文使用类似标准分数的组内相对量：

$$
A_t^{i}=\frac{\operatorname{Score}_{i}-\mu_t}{\sigma_t}
$$

因为 score 越低越好，所以更负的 \(A_t^i\) 表示候选相对同组更强。组内比较可部分抵消不同设计规模、不同绝对 slack 与不同迭代基线之间的不可比性，但候选数只有 5 时估计仍然很噪，不能把一次极端值直接升级为高置信度技能。

### 5.5 并行后的墙钟时间

若每轮 \(N\) 个候选并行运行，轮数为 \(K\)，一次完整 EDA 评估耗时为 \(T_{EDA}\)，理想墙钟时间近似为：

$$
T_{wall}\approx K\times T_{EDA}
$$

实际还会受到许可证 token、作业队列、最慢候选、远程传输和 Agent 推理影响。论文报告 EDA 执行是主要瓶颈，而非 LLM token。

## 6. 训练、实验与主要结果

### 6.1 没有参数训练，只有推理时搜索与 skill 学习

Dr. RTL 不微调 Claude，也不训练专门的 RTL policy 或 reward model。所谓 self-improvement 指的是：

1. 在当前设计上通过工具反馈搜索；
2. 从候选相对结果中提炼显式 skill；
3. 在后续轮次和未见设计中检索这些 skill；
4. 继续用 SEC 与 PPA 证据修订技能置信度。

因此它更像“有实验记录和工程手册的自动化优化团队”，而不是传统强化学习训练。

### 6.2 数据集与工具设置

| 项目 | 设置 |
|---|---|
| 设计数 | 20 个 RTL 设计 |
| RTL 规模 | 平均约 812 LoC；范围约 128–4615 LoC |
| 结构规模 | 平均约 3 个模块、6230 个门、760 个寄存器 |
| 工艺库 | NanGate 45 nm |
| 时钟 | 0.1 ns，刻意制造强时序压力 |
| 搜索预算 | 10 轮 × 每轮 5 候选，约 50 次尝试/设计 |
| 主 Agent 模型 | Claude Opus，Claude Code CLI 编排 |
| 核心 EDA | Synopsys Design Compiler + 商业 SEC 工具 |
| 泛化评估 | 4-fold cross-validation；每折 15 个设计学 skill，5 个未见设计测试 |

四折交叉验证很重要：每折都会重置 skill library，测试设计的 prompt 与示例不泄漏到训练折。这比“先在全部 20 个设计上总结经验，再在同一批设计上展示效果”更能支持技能迁移结论，但样本量仍然有限。

### 6.3 总体结果

20 个设计的平均结果为：

- WNS 改善 **21.3%**；
- TNS 改善 **16.9%**；
- 面积降低 **5.8%**；
- SEC 平均通过率 **86%**；
- 20/20 设计的时序均有改善；
- 9/20 同时获得时序与面积的 Pareto 改善；
- 8/20 的面积代价低于 5%；
- 3/20 出现较明显面积增长。

代表性个案如下：

| 设计 | WNS 改善 | TNS 改善 | 面积变化 | SEC 通过率 | 解读 |
|---|---:|---:|---:|---:|---|
| cpu_pipe | 71.1% | 88.4% | -11.8% | 90% | 时序和面积同时显著改善 |
| pcie | 44.3% | 17.1% | -33.9% | 100% | 强 Pareto 改善，所有候选均等价 |
| lstm | 25.3% | 30.3% | -67.9% | 83% | 面积收益极大，说明原 RTL 有较多可重构空间 |
| vending | 66.7% | 51.0% | +0.2% | 77% | 以几乎零面积代价换取显著时序收益 |
| controller | 有改善 | 有改善 | +18% 左右 | — | 暴露固定权重下的面积权衡问题 |

百分比改善不等于 timing closure。基线与结果都可能仍是负 slack；在 0.1 ns 这种极端约束下，从 -0.10 ns 改到 -0.08 ns 可以记作约 20% 改善，但设计依旧违例。阅读结果时必须同时看绝对 WNS/TNS。

### 6.4 与基线比较

论文表 3 的平均变化如下；负号表示对应违例或面积相对基线减少：

| 方法 | WNS 变化 | TNS 变化 | 面积变化 |
|---|---:|---:|---:|
| Single-shot Claude Opus | -2.4% | -2.8% | -0.7% |
| Single-shot GPT-5.3 | -1.2% | +0.3% | +0.6% |
| RTLRewriter | -4.9% | -6.3% | -3.1% |
| SymRTLo | -7.1% | -5.7% | -1.4% |
| **Dr. RTL** | **-21.3%** | **-16.9%** | **-5.8%** |

这里最有力的结论不是“Claude 比某模型强”，而是**带工具反馈的多轮搜索远强于一次性 prompt**。单次 Opus 和 GPT-5.3 都只获得小幅改进；Dr. RTL 的增益来自可定位反馈、并行候选、硬验证和跨轮记忆的组合。

### 6.5 消融实验

| 配置 | WNS 改善 | TNS 改善 | 面积降低 | SEC 通过率 |
|---|---:|---:|---:|---:|
| 完整系统 | 约 21% | 约 17% | 约 6% | 86% |
| 去掉寄存器级 slack 反馈 | 约 9% | 约 9% | 约 3% | — |
| 去掉多 Agent 分工 | 约 10% | 约 7% | 约 2% | — |
| 去掉 learned skills | 约 14% | 约 11% | 约 7% | 78% |

没有 skill 时面积平均值反而略好，但时序收益和 SEC 通过率下降。这提示 skill library 的主要价值可能不是最大化单一面积指标，而是提高**有方向的探索效率与正确候选比例**。它仍需更长预算或更多设计来证明是否能持续复利。

### 6.6 基础模型规模

| 模型 | WNS 改善 | TNS 改善 | 面积降低 | SEC 通过率 |
|---|---:|---:|---:|---:|
| Qwen Coder 8B | 约 1% | 约 0% | 约 0% | 22% |
| Claude Haiku | 约 3% | 约 2% | 约 3% | 57% |
| Claude Sonnet | 约 12% | 约 9% | 约 2% | 73% |
| Claude Opus | 约 21% | 约 17% | 约 6% | 86% |

系统并不是“接上任何便宜小模型都会自动变强”。较弱模型首先在语义保持上失败，SEC 通过率低会让搜索预算大量浪费。对 Codex 路线的启示是：宿主能否调用 skill 只是基础条件，模型能否理解跨模块 RTL、位宽、时序与状态语义同样决定上限。

### 6.7 不同 EDA 阶段的迁移

论文还比较了不同工具设置：Design Compiler 综合后评估约有 21%/17%/6% 的 WNS/TNS/面积收益；Yosys 综合后时序收益约 29%/28%，面积约 2%；Innovus 布局布线后仍保留约 14%/13% 的时序收益和约 4% 面积收益。单纯调 DC flow 选项的结果接近零，说明改 RTL 结构与调工具旋钮不是同一层次。

不过这些是影响研究，不代表 Agent 在 Yosys 或 Innovus 中完整闭环搜索。尤其 post-P&R 数字只说明迁移趋势，不能替代多角多模 signoff。

### 6.8 成本

作者报告 20 个设计约运行一周，LLM 使用费用约 50 美元，主要时间消耗来自综合与等价检查。这个数字不能直接理解成“复现实验只需 50 美元”：它不包含商业 EDA license、算力服务器、队列等待和工程环境搭建成本，也会随模型价格与缓存策略变化。

## 7. 主要创新点

### 7.1 把现成 coding agent 变成 EDA 实验总控

Dr. RTL 最贴近用户关注点的创新，是没有从零实现通用 Agent runtime，而是在 Claude Code 的工程工作流上叠加专职 Agent、EDA 脚本和 skill。它展示了闭源 coding agent 可以承担论文系统的主控制面，而研究者把精力放在领域反馈、搜索与知识沉淀上。

### 7.2 工具 grounded，而非文字 self-critique

许多 LLM RTL 工作用编译错误或 testbench pass/fail 作反馈。Dr. RTL 把工业综合、STA 和 SEC 同时接入：优化方向由关键路径和 PPA 决定，正确性由形式工具决定。Agent 的自然语言分析只是提出假设，EDA 报告才是证据。

### 7.3 同父候选的组内相对学习

不同设计的面积、slack 与结构规模相差很大，直接比较绝对指标会产生大量伪规律。Dr. RTL 只在相同父设计、相同约束下比较并行候选，再提炼技能，近似构造低成本对照实验。它比只存“最佳 patch”更能识别失败边界。

### 7.4 同时维护正向 skill 与 avoid list

失败不是简单丢弃。系统记录“综合器本来就会做”“经常恶化时序”“容易破坏等价性”的模式，避免后续设计重复消耗昂贵 EDA 预算。对于自动研究或自动优化系统，**知道不该试什么**与知道该试什么同样重要。

### 7.5 把经验写成可读工件

skills 是人可审查、可版本控制的文本与模板，而不是隐藏在新一轮模型权重里。这使工程师能够删除错误经验、调整适用条件、追踪技能来源，并把知识库作为项目资产交接。

## 8. 关键术语与缩写

| 缩写/术语 | 全称 | 在本文中的含义 |
|---|---|---|
| RTL | Register-Transfer Level | 寄存器传输级硬件描述，是 Agent 直接修改的对象 |
| PPA | Power, Performance, Area | 功耗、性能、面积；本文实际评分重心是时序与面积，未做完整功耗闭环 |
| WNS | Worst Negative Slack | 最差负裕量；越接近 0 或转正越好 |
| TNS | Total Negative Slack | 所有违例路径负裕量之和；越接近 0 越好 |
| STA | Static Timing Analysis | 无需输入向量的静态时序分析，用于关键路径反馈 |
| SEC | Sequential Equivalence Checking | 顺序等价检查，验证改写前后跨时序状态行为是否等价 |
| DC | Design Compiler | Synopsys 商业逻辑综合工具 |
| JasperGold | Cadence JasperGold | 商业形式验证平台，可承担等价或属性验证 |
| Formality | Synopsys Formality | Synopsys 商业等价检查工具；公开工程环境中可作为 SEC 后端 |
| Innovus | Cadence Innovus | 物理设计工具，论文用来观察 post-P&R 收益 |
| QoR | Quality of Results | EDA 结果质量，通常包括时序、面积、功耗等 |
| Critical Path | 关键路径 | 限制时钟频率或产生最坏 slack 的路径 |
| High Fanout | 高扇出 | 一个信号驱动大量负载，可能造成缓冲、延迟与拥塞问题 |
| Skill Library | 技能库 | 带适用条件、动作、证据和风险的 RTL 优化经验集合 |
| Avoid List | 避免清单 | 已知低收益、高风险或综合器会自动完成的变换集合 |
| Group-relative | 组内相对 | 只比较同一父设计、同一轮、同一工具条件下的候选 |
| Tool-grounded | 工具落地/工具校准 | 结论由真实 EDA 执行结果支持，而非只由 LLM 自评 |
| LoC | Lines of Code | RTL 代码行数 |
| Pareto improvement | 帕累托改善 | 至少一项目标变好且其他目标不变坏；文中常指时序和面积同时更优 |

## 9. 与芯片流程及本仓库其他工作的关系

### 9.1 它位于“前端 RTL—综合—时序—形式”闭环

Dr. RTL 的核心价值链是：

```text
RTL 结构修改（①）
   → 逻辑综合获得门级映射与面积（③）
   → STA 暴露关键路径和违例（⑤）
   → SEC 保证行为不变（⑥）
   → 反馈到下一轮 RTL 修改（①）
```

这个闭环比只跑 lint/编译更接近真实前端优化，也比直接让 Agent 操作完整后端更容易控制变量。它正好占据架构设计完成、RTL 已可用，但综合 QoR 仍需工程师手工打磨的阶段。

### 9.2 与 ARES 的关系

[ARES](../ARES/论文深度讲解.md) 同样关注 Agent 驱动的 PPA 优化，但更强调成本感知与搜索预算。Dr. RTL 的辨识度在于 Claude Code 宿主、专职 Agent、同组相对 skill 学习，以及商业综合/SEC 的明确闭环。两者可以放在同一条“工具反馈式 EDA Agent”研究线上比较。

### 9.3 与 FluxBench 的关系

[FluxBench](../FluxBench/论文深度讲解.md) 主要回答“RTL-to-GDS Agent 应该怎样评测”，覆盖流程更广；Dr. RTL 回答“在 RTL PPA 优化这个窄而深的问题上，怎样真正搜索并积累经验”。前者偏 benchmark，后者偏方法系统。Dr. RTL 不能因为做了 post-P&R 实验就被视作完整 RTL-to-GDS Agent。

### 9.4 与 VPR-Evolve 的关系

[VPR-Evolve](../VPR-Evolve/论文深度讲解.md) 也体现让 Agent 在真实工具环境中迭代的范式，但工具栈、目标对象和搜索空间不同。把三者并列阅读，可以分辨“通用 Agent 框架创新”“领域工具接入”“记忆/技能机制”各自贡献了什么。

### 9.5 对 Codex skill 路线的直接启示

如果把 Dr. RTL 的思想迁移到 Codex，最自然的架构不是重写一个庞大 Agent 应用，而是：

- 用一个项目级 skill 定义 RTL 优化 SOP、硬约束和报告格式；
- 用 MCP 或稳定的命令封装综合、STA、SEC 和作业队列；
- 由 Codex 工作流按路径分析、候选生成、独立评估、技能提炼分工；
- 把所有候选、工具版本、约束摘要和父子关系落盘；
- 只有工具结果能升级技能置信度，LLM 自评不能；
- 对商业工具保留 license、远端环境和安全边界，不把工具凭据写入 skill。

这正是该论文能形成研究 idea 的地方：论文已经证明“闭源 coding agent 做 EDA”不是空想，后续问题应转向**怎样让技能跨模型宿主、跨 EDA 工具、跨设计可靠迁移，以及怎样用可审计协议避免经验污染**。

## 10. 局限性与风险

### 10.1 极端时钟下的百分比容易被放大

0.1 ns 时钟会制造大量负 slack，有利于观察相对变化，却不一定代表实际设计约束。若 WNS 从很差变成稍差，百分比可很好看，但仍未 closure。论文应同时报告绝对 slack、目标频率与路径数量，使用者也不应只看相对百分比。

### 10.2 20 个设计仍不足以证明通用 RTL 优化

四折交叉验证比同集评测严格，但 20 个设计无法覆盖大型 SoC 的协议、低功耗结构、时钟域、多周期/false path、内存宏、黑盒 IP 和复杂 reset 语义。平均 3 个模块与真实工业层次仍有明显差距。

### 10.3 商业 EDA 使复现门槛很高

公开代码不等于实验完全开放。完整复现需要 Design Compiler、Formality 或 JasperGold、可能还需要 Innovus，以及正确的 license、库、远端机器和队列配置。没有这些条件，只能审计 Agent 逻辑或替换成开源工具，后者又无法严格复现论文数字。

### 10.4 SEC 结果依赖建模边界

形式等价是强守门员，但它不是无条件真理。reset 假设、X 语义、memory/blackbox 模型、时钟 gating、multicycle 约束和未定义行为都会影响等价结论。SEC pass 需要和完整工具设置一起存档，不能只存一个布尔值。

### 10.5 固定加权分数隐藏多目标偏好

WNS、TNS 与面积权重固定为 0.50/0.35/0.15，并对面积增长超过 10% 设置跳变惩罚。这个偏好可能适合论文实验，却未必适合功耗敏感、面积上限严格或必须 timing closure 的项目。WNS 与 TNS 也存在相关性，双重计权会改变搜索方向。

### 10.6 skill 归因仍可能受到幸存者偏差

同父候选比跨设计绝对比较更可靠，但每组只有 5 个样本。某候选变好可能来自综合器随机性、多个同时改动或路径迁移，而不是被总结的单一策略。高置信度技能最好要求跨设计、跨 seed、跨工具重复验证，并保留反例。

### 10.7 coding-agent 宿主是外部依赖

Claude Code 与 Claude 模型是闭源服务。模型版本、系统提示、工具调用策略和上下文行为升级后，论文轨迹可能无法逐 token 重现。LLM 费用约 50 美元也只是特定时间点和计价规则下的结果。

### 10.8 没有完整功耗与物理签核

论文标题使用 PPA，但评分主要是 performance 与 area。没有活动率驱动功耗、IR/EM、DRC/LVS、OCV/多角多模等完整 signoff。综合期面积下降也不保证布线拥塞、功耗或可制造性同步变好。

### 10.9 与综合器能力高度耦合

一些 skill 在 DC 上有效，在 Yosys 或另一版本/另一库上可能无效，甚至被工具自动抵消。论文的跨工具结果是积极信号，但真正可迁移的经验应描述“结构条件 + 工具条件 + 约束条件”，而不是只写一个通用 RTL 招式。

### 11.4 建议的分级复现路径

**R1 静态审计**：核对 prompt、Agent 角色、score 实现、skill schema、候选晋级逻辑和工具命令，不执行 EDA。

**R2 开源冒烟**：选 1–2 个小设计，用 Yosys + OpenSTA + EQY/SymbiYosys 替代商业工具，跑 2 轮 × 2 候选。该结果只能验证工作流，不能宣称复现论文 PPA。

**R3 单设计商业闭环**：固定 DC/SEC 版本、library、时钟约束、模型版本和随机设置，在一个设计上跑完整 10×5，并核对 SEC 通过率、候选晋级与报告。

**R4 全量复现**：按四折隔离 skill library，在 20 个设计上复跑；记录绝对与相对 PPA、每项 skill 的来源候选、商业工具版本、失败原因和总成本。

### 11.5 最小审计清单

- [ ] 所有结果是否绑定 commit、模型版本、EDA 版本与 library checksum？
- [ ] 每个候选是否有明确父设计，避免把不同约束的结果混组？
- [ ] SEC 失败、综合失败、超时是否都保留而非静默删除？

## 12. 一分钟总结

Dr. RTL 是一个很直接的“闭源 coding agent 做 EDA”案例：研究者把 **Claude Code** 当作总控，用多个专职 Agent 分析关键路径、提出并行 RTL 候选、运行商业综合/STA/SEC，并把同组候选中的成功与失败归纳成可复用 **skill library**。它不是改造 React 仓库做一个看起来像 Agent 的壳，也不是只让 LLM 自己评价代码。

方法在 20 个设计、10 轮 × 5 候选、NanGate45 和激进 0.1 ns 时钟设置下，平均改善 WNS 21.3%、TNS 16.9%，面积降低 5.8%，SEC 通过率 86%；相比 single-shot LLM 和已有 RTL 优化基线提升明显。消融表明寄存器级时序反馈、多 Agent 分工与 learned skills 都有贡献。

它的最佳启示是：**EDA Agent 的核心不是再造一个通用 Agent 框架，而是把真实工具反馈、硬正确性门槛、可比较的搜索实验和可审计的技能记忆接好。** 它的主要局限也同样清楚：商业工具和闭源模型提高复现门槛，20 个中小设计不足以代表大型 SoC，0.1 ns 下的相对收益不等于 timing closure，PPA 中也缺少完整功耗与物理签核。

对本项目而言，Dr. RTL 最适合与 ARES、VPR-Evolve 和 FluxBench 放在同一研究簇：它为“在 Codex/Claude Code 工作流里接入 EDA 工具，并让 skill 随真实结果进化”提供了已发表的近邻证据和一套足够具体的工程参照。
