# ChipModeler 论文深度讲解

> **ChipModeler（底稿 arXiv 名 ChatModel）: Automating Reference Model Design and Verification with LLMs**
> 东南大学 · DAC 2026（63rd Design Automation Conference，RESEARCH2319 / sess166）
> 底稿：[ChatModel](https://arxiv.org/abs/2506.15066)（arXiv:2506.15066）
> 原文：[2506.15066_ChatModel.pdf](./2506.15066_ChatModel.pdf)（13 页，本地已下载）
> 代码：截至核验时未核实公开仓库

> ⚠️ **定位提示**：这篇属于 reference model 生成方向，解决如何让 LLM 自动写出可用参考模型，终点是模型本身的质量和生成效率。标题中的 verification 指验证生成模型是否正确，不是直接验证 RTL 或检出 RTL 缺陷。

---

## 1. 一句话定位

**ChipModeler 是首个基于多智能体 LLM 的参考模型（reference model）自动化设计与验证平台——它把一份复杂的硬件规格自动拆成模块级中间表示（Design IR），再用 7 个分工明确的 Agent 分层生成 SystemC 参考模型，通过功能块分轮生成（AMG）+ 等价性自检 + RAG 调试器逐级纠错，在 300 个设计上把参考模型的「功能通过率（FP）」从 31.72%（Zero-Shot）拉到 86.74%，功能通过率峰值相对基线提升 55.02%，生成容量扩大 9.18×。**

四个承重点，逐一拆：

1. **7 个 Agent、两个 Phase**——Phase 1 把规格「标准化」成结构化的 Design IR（3 个 Agent），Phase 2 分层「敏捷建模」成 SystemC 代码（4 个 Agent）。分工不是装饰，而是把「理解规格」「等价自检」「划分功能块」「生成代码」「调试修复」拆给不同的 LLM 角色，避免一个脑子又出题又判卷。
2. **Design IR（DSL + DAG）**——核心数据载体：每份规格先被翻译成标准化的模块 IR（端口、实现细节、子模块清单），再组织成 DAG（节点=模块，边=父子端口连接）。LLM 不直接啃原始规格，而是啃这份结构化中间表示，幻觉和 token 溢出大幅下降。
3. **HAP（后序遍历规划）+ AMG（按功能块分轮生成）**——两个算法解决「先生成谁」「一轮生成多少」两个工程死穴：HAP 保证子模块先于父模块就绪（依赖先于依赖者），AMG 保证每轮 LLM 只专注生成一个功能块（不因 token 限制截断或幻觉）。
4. **300 设计 benchmark**——VerilogEval 156 + RTLLM2.0 50 + 自研 ModelEval 94，按规模分小/中/大三档，最大代码 1800 行、21 个子模块。这是「reference model 生成」方向目前最大的公开评测之一。

## 2. EDA 阶段映射（①-⑰）

ChipModeler 是**验证基础设施生成**工具，处在阶段 ② 的「上游准备」位置——它生成的是「判卷用的标准答案」，本身不跑仿真、不碰 DUT、不涉及后端。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ❌ | 不生成 RTL、不改 RTL。它生成的是 SystemC **参考模型**，与被测 RTL 是两个东西 |
| **② RTL 功能仿真** | 辅助（准备侧） | 生成的参考模型是模型驱动验证（MDV）的「黄金参照」，将来要和 DUT 在同激励下比对输出。但 ChipModeler 自身不搭 testbench、不驱动仿真器 |
| ③~⑰ 全部 | ❌ | 与综合/门级/STA/形式/物理设计完全无关 |

**覆盖率：0.5/17（仅作为阶段 ② 的输入准备）。**

> **最容易误读的边界**：ChipModeler 生成的是参考模型，它是验证流程里的判卷标准，不是被测对象。论文的终点停在模型生成与测试用例验证，没有继续评估该模型发现未知 RTL 缺陷的能力。

## 3. 输入 / 输出

### 3.1 输入

| 输入项 | 必需 | 格式 | 说明 |
|--------|:---:|------|------|
| 硬件规格 | 是 | 自然语言文本 | 描述模块行为的文档（端口、功能点、时序关系），是唯一依据 |
| 测试用例 | 是（评测用） | — | 判断「生成的模型对不对」的外部判卷，论文用 benchmark 自带 testbench |

### 3.2 中间产物（核心）

**Design IR** 是这篇论文的命脉，分两层：

```text
Design IR
├── 模块 IR（module IR）  每个模块一份，标准化描述：
│     ├── 端口信号（port signals）
│     ├── 实现细节（implementation details）
│     └── 子模块清单（submodule list）
└── DAG（Design Architecture Graph）
      ├── 节点 = 模块
      ├── 边   = 父子模块间的端口连接关系
      └── 结构 = 多个「深度 2」子树（每棵子树刻画父子端口对齐）
```

生成方向是**自顶向下**（先顶层 IR，再逐层子模块 IR），建模方向是**自底向上**（先子模块后顶层）。

### 3.3 输出

**SystemC 参考模型**——一个可执行、周期/行为精确的「标准答案」。论文评价它「好不好」用两个指标：

- **SP（Syntax Pass rate，语法通过率）**：生成的模型能编译通过。
- **FP（Functional Pass rate，功能通过率）**：生成的模型跑测试用例结果正确。

## 4. 方法与架构

### 4.1 整体 Pipeline（7 Agent / 2 Phase）

```text
                    输入：硬件规格（自然语言）
                                │
   ┌────────────────────────────┼────────────────────────────┐
   │ Phase 1：Design Specification Standardization（规格标准化） │
   │  A1 模块级 IR 生成器：切片规格 → 提取端口/实现/子模块 → 模块 IR │
   │  A2 IR 等价性检查器：比对模块 IR vs 原始规格，丢失则报错回 A1   │
   │  A3 DAG 构造器：分析父子端口数据流 → 构建设计架构图            │
   └────────────────────────────┼────────────────────────────┘
                                │  Design IR（模块 IR + DAG）
   ┌────────────────────────────┼────────────────────────────┐
   │ Phase 2：Hierarchical Agile Modeling（层级敏捷建模）          │
   │  A4 功能块划分：CoT 分析功能点 → 聚成 fblocks                │
   │  A5 SystemC 代码生成：先类声明 → 逐功能块多轮生成函数实现      │
   │  A6 完整性检查：验证功能/端口/等价性                          │
   │  A7 调试器：RAG（Chroma 向量库）修复语法+功能错误             │
   └────────────────────────────┼────────────────────────────┘
                                │
                                ▼
                    输出：SystemC 参考模型（SP / FP 评测）
```

### 4.2 两个关键算法

**HAP（Hierarchical Adaptive Planning，层级自适应规划）**——决定「先生成哪个模块」：

1. 遍历 DAG，提取所有 (父 P, 子 C) 对，装入设计树；
2. 找根节点；
3. **后序遍历**（post-order）：先递归访问所有子节点，回溯后再处理当前节点——保证「依赖模块先就绪」，子系统生成过程中即可被验证，不必等整个设计完成；
4. **节点名规范化**：硬件里常见「多个功能相同但实例名不同的模块」（相似子树），规范化后跳过冗余，省 token。

**AMG（Agile Model Generator，敏捷模型生成器）**——决定「一轮生成多少」：

- A4 把功能点聚成功能块集合 f_blocks，**每个功能块 = 一轮生成对话**；
- 每轮只让 LLM 专注一个功能块 → 最小化 token 截断和幻觉；
- 生成函数实现前先产**伪代码**作中间步骤；
- 循环直到 A6 等价性检查通过。

### 4.3 Agent 职责矩阵

| Agent | 阶段 | 输入 → 输出 | 作用 |
|---|---|---|---|
| A1 模块 IR 生成器 | P1 | 规格切片 → 模块 IR | 把自然语言翻译成结构化 IR |
| A2 IR 等价性检查器 | P1 | 模块 IR + 原始规格 → 通过/报错 | 防「翻译丢信息」 |
| A3 DAG 构造器 | P1 | 模块 IR → 架构图 | 刻画父子端口连接 |
| A4 功能块划分 | P2 | IR + DAG → fblocks | 用 CoT 把功能点聚类 |
| A5 SystemC 生成器 | P2 | fblocks → SystemC 代码 | 分轮生成 |
| A6 完整性检查器 | P2 | 代码 + IR → 通过/报错 | 查端口/功能/等价 |
| A7 调试器 | P2 | 报错 → 补丁 | RAG 查历史错误修 bug |

## 5. 关键公式

论文没有像 GoGoTB 那样给出成体系的公式，核心评价指标是两个通过率：

$$
\text{SP} = \frac{\text{语法可编译的模型数}}{\text{总模型数}},\qquad
\text{FP} = \frac{\text{测试用例通过的模型数}}{\text{总模型数}}
$$

论文用 **Pass@k**（k 次生成中至少一次成功）报告，主表取 **Pass@5、温度 0.3、调试迭代上限 6**。

**工程直觉**：SP 高只说明“能编译”，FP 高才说明“行为对”。类比来说，SP 是作文没有错别字，FP 是作文切题且结论正确。一个编译通过但行为错误的参考模型会在 MDV 中把正确 RTL 误判为错，因此参考模型不仅要独立于 DUT，自身也必须经过充分验证。

## 6. 训练与实验设置

**不需要训练。** 直接调用底座 LLM（主实验 GPT-4o，消融换 Claude 3.5-Sonnet、DeepSeek-R1），无微调。

**Benchmark（300 设计）**：

| 来源 | 数量 | 特点 |
|---|---|---|
| VerilogEval（NVIDIA） | 156 | 简单逻辑到 FSM，含 interface/spec/reference/testbench 四件套 |
| RTLLM2.0（HKUST） | 50 | 算术 19 / 存储 7 / 控制 6 / 杂项 18 |
| ModelEval（自研） | 94 | 高复杂度：DSP、图像缩放、3D 加速器、通信总线、RISC-V 组件；20–1800 行、1–21 子模块 |

按规模三档：Small（<100 行）/ Medium（单模块 100–400 行，或多模块 <300 行）/ Large（更大）。

**主表结果（Pass@5，GPT-4o）**：

| 方法 | 平均 SP/% | 平均 FP/% |
|---|---|---|
| Zero-Shot | 59.62 | 31.72 |
| Few-Shot | 65.65 | 36.03 |
| CoT | 66.26 | 38.55 |
| CoT+Few-Shot | 71.45 | 41.79 |
| Multi-Agent | 76.18 | 47.53 |
| Best-Choice | 79.58 | 44.23 |
| **ChatModel** | **95.44** | **86.74** |

**关键数字**：

- FP 峰值相对 baseline 提升 **55.02%**（Pass@1 提升 51.62%，Pass@5 提升 55.02%）；
- 三 benchmark 上 SP 达 99.32% / 94.74% / 89.36%，FP 达 91.20% / 83.29% / 81.17%；
- 相对第二名 Multi-Agent，小/中/大三档分别提升 **1.37× / 2.68× / 10.23×**；
- 生成容量扩大 **9.18×**（能生成 >1800 行复杂设计）；
- 相对无 LLM 工程师，效率提升 **5.90×**（3.94×–6.27×）；
- 消融：Design IR → +HAP → +AMG → +Debugger 逐级提升；Debugger 平均 2 次迭代修复；
- 换底座：Claude 3.5-Sonnet 下 FP 提升 48.81%，DeepSeek-R1 下 37.01% → 框架具通用性。

## 7. 创新点

1. **Design IR（面向参考模型生成的 DSL）**：把「复杂自然语言规格」转成「模块 IR + DAG」的结构化中间表示，让 LLM 不直接啃原文。这跟 GoGoTB 的 Design Profile 是同一思路的两种实现——都承认「直接喂原始规格，LLM 会幻觉」。
2. **HAP 后序遍历规划**：用树的后序遍历保证依赖先就绪，同时靠节点名规范化跳过冗余子树。是「任务调度」层面的确定性约束，不依赖 LLM 决策。
3. **AMG 功能块分轮生成**：把「一次生成整个模块」拆成「每轮一个功能块」，直接对抗 token 限制导致的截断/幻觉。这是本篇最实用的工程技巧。
4. **ModelEval benchmark**：自研 94 个高复杂度设计的评测集，补上「LLM 生成参考模型」方向的评测缺口。

## 8. EDA 缩写表

| 缩写 | 全称 | 一句话解释 |
|------|------|-----------|
| MDV | Model-Driven Verification | 模型驱动验证：用一个独立参考模型与 DUT 对照判对错 |
| DUT | Design Under Test | 被测设计（这里指待验证的 RTL，不是参考模型） |
| IR | Intermediate Representation | 中间表示，把规格转成结构化数据 |
| DAG | Directed Acyclic Graph | 有向无环图，这里表模块层级 |
| DSL | Domain-Specific Language | 面向特定领域的专用语言 |
| HAP | Hierarchical Adaptive Planning | 层级自适应规划（后序遍历调度） |
| AMG | Agile Model Generator | 敏捷模型生成器（按功能块分轮生成） |
| RAG | Retrieval-Augmented Generation | 检索增强生成，用向量库查历史错误 |
| SystemC | — | 用 C++ 类描述的硬件系统级建模语言 |
| SP / FP | Syntax / Functional Pass rate | 语法通过率 / 功能通过率 |
| CoT | Chain of Thought | 思维链，让 LLM 先推理再作答 |

## 9. 与芯片流程和相关工作的关系

ChipModeler 的直接产物是 SystemC 参考模型，而不是被测 RTL 或缺陷报告。它位于“规格理解与参考模型准备”这一侧，可为后续模型驱动验证提供输入，但论文本身的实验终点仍是参考模型的语法与功能通过率。

与直接生成 RTL 的工作相比，ChipModeler 更强调规格分解、分层规划和模型自检；与 RTL 验证工作相比，它没有继续评估参考模型能否稳定发现未知 RTL 缺陷。因此，引用本文时应区分“参考模型生成质量”和“下游验证检出能力”两个问题。

## 10. 讨论与局限

论文自述（Appendix E）：

1. **受底座 LLM 能力制约**：换弱模型，复杂任务仍难；
2. **无法彻底消除幻觉**：任务分割、自验证、CoT、输出模板都只是缓解；
3. **FP 的完备性取决于测试用例质量**：测试用例不够强时，错误模型也可能通过，形成 false-pass；
4. 未来：微调专用小模型、冲击乱序多处理器级超大设计。

**本资料包的批判性补充**：

5. **代码未核实公开**，SP/FP 数字无法独立复现；
6. **ModelEval 自研**，评测集作者自建，存在「同源模板」风险；
7. **评价的是模型生成质量，不是下游验证质量**：FP 86.74% 的“正确”是相对测试用例而言，不代表模型能在真实 MDV 中稳定充当参考标准。

## 12. 一分钟复述版

1. **做什么**：给定硬件规格，自动生成 SystemC 参考模型（验证用的「标准答案」）。
2. **为什么难**：复杂规格超 LLM 上下文窗口 → 幻觉；一次输出装不下大设计 → 截断；同输入不同输出 → 错误累积。
3. **怎么解决**：规格先翻译成结构化 Design IR（模块 IR + DAG），再用 7 个 Agent 分两阶段（标准化 → 敏捷建模），HAP 后序遍历定顺序、AMG 按功能块分轮生成、RAG 调试器修错。
4. **效果**：FP 从 31.72% 拉到 86.74%，峰值提升 55.02%，容量 9.18×，速度 5.90×。
5. **不做什么**：不碰 DUT、不找 RTL 的 bug——它只负责把「判卷标准」造出来，判卷本身是下游 MDV 的事。
6. **研究定位**：它是参考模型自动生成的重要工作，但没有覆盖使用独立参考模型发现未知 RTL 缺陷的下游环节。
7. **一句话**：ChipModeler 证明了 LLM 能自动生成基本可用的参考模型，但模型自身仍可能出错；“生成参考模型”和“用参考模型发现 RTL 缺陷”应作为两个独立问题评价。
