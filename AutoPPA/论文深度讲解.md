## 1. 一句话定位

**AutoPPA 的目标是回答一个根本问题：能不能不靠人总结优化经验，而是自动从海量开源 RTL 代码里"挖"出一个 PPA 优化规则库，再用它去优化目标电路？**

先看清它要取代的两类老路线：

1. **反馈派**（ChipGPT、VeriPPA）：把综合后的 PPA 数字直接喂给 LLM，让它"看着数字改"。问题：**LLM 根本不理解"电路结构"和"PPA 数字"之间的因果关系**，改起来效率低。
2. **知识派**（RTLRewriter、SymRTLO）：靠人手总结优化规则（"常见子表达式可以消除""条件可以预计算"之类）。问题：**规则库靠人写，规模上不去、覆盖不了那么多电路花样**——连 Synopsys 官方指南都只有几十条例子。

AutoPPA 走第三条路：**让 LLM 当"代码采样器"生成海量功能等价的改写对，再用 EDA 工具验证这些改写对里"谁更优"，最后从"优 vs 差"的对比里自动归纳出优化规则**。这套流程叫 **E²I = Explore → Evaluate → Induce**（探索 → 评估 → 归纳）。

---

## 2. EDA 阶段映射

AutoPPA 的优化发生在 RTL 层，评估靠综合。

| 阶段 | 是否覆盖 | AutoPPA 中的角色 |
|---|:---:|---|
| ① RTL 设计 | ✅ 核心 | 输入是 RTL，输出是优化后的 RTL（保持功能等价） |
| ② 功能仿真 | ✅ 核心 | 自动生成 testbench 验证等价性（100% 行覆盖） |
| ③ 逻辑综合 | ✅ 核心 | Yosys（粗筛）+ SiliconCompiler（Yosys+OpenSTA 精测）给 PPA 标签 |
| ⑥ 形式验证 | ⚠️ 近似 | 用自动 testbench 仿真做等价检查，不是形式等价（SEC） |
| ⑦–⑰ | ❌ | 不碰物理设计/签核 |

**注意**：AutoPPA 的"等价性"靠的是**自动生成的 testbench 随机仿真**（100% 行/分支覆盖），不是 Dr. RTL 那种形式等价检查（SEC）。这是两者的一个重要差别，也决定了 AutoPPA 的等价性保证更弱一些。

## 3. 输入、输出与任务定义

### 3.1 输入

- 一段待优化的 RTL 代码；
- 一个优化目标：**面积** 或 **延迟**（论文也报功耗，但主攻面积/延迟）；
- 一个自动学到的规则库（见第 4 节）。

### 3.2 输出

- 功能等价、PPA 更优的 RTL 改写；
- 评估报告（面积 / 延迟 / 动态功耗）。

### 3.3 评分口径

- 合成总单元面积（μm²）、周期延迟（ns）、动态功耗（mW），FreePDK 45nm；
- 改善率：`Impr = 1 − PPA_opt / PPA_original`；不等价或变差的记为 0；
- 为了和"采样 N 次"的 baseline LLM 公平比，提出 **Impr@k**：从 n 次采样里按组合公式估计"取最好 k 个"的期望改善（借 Pass@k 的思路）。

## 4. 方法与关键设计

### 4.1 阶段一：规则库学习（E²I 三段式）

#### Explore（探索）：LLM 当"变异采样器"

- 从 GitHub 爬 ~13 万份 Verilog；
- Yosys 轻量过滤掉不可综合/不自洽的；
- SiliconCompiler 精测 PPA，存下代码 + PPA；
- 取 **10 万份面积居中的设计**，每份用 **Qwen2.5-Coder-7B-Instruct 改写 N=50 次**，得到 **500 万+ 对**功能可能等价的代码对。

**关键洞察**：通用 LLM 虽然不懂电路优化的专业知识，但它"生成大量五花八门代码"的能力极强。AutoPPA 正是利用这个能力做**穷举式探索**。

#### Evaluate（评估）：EDA 工具当"裁判"

- **PPA 评估**：和上一步同样设置综合；
- **等价性评估**：难点是没法给花样繁多的电路写 testbench。AutoPPA 用 Yosys 自动提取 top module、端口、时钟、复位，**自动生成 testbench**，施加多组长随机激励，比较原电路和改写电路的输出（100% 行覆盖）；
- **香农熵量化多样性**：对每个设计的功能等价版本算 PPA 分布的香农熵，熵越高说明"能挖出的优化花样越多"；按熵排序取 top 25%；
- 每个入选设计只保留"相对 PPA 差异 > 5%"的等价对，记为 (C_non, C_opt)。

#### Induce（归纳）：从"差 vs 优"的对比里提炼规则

每条规则是一个三元组 **`(snippet, condition, action)`**：

- **snippet**：低效 RTL 代码片段（优化对象）；
- **condition**：泛化的适用条件（什么时候能用）；
- **action**：具体怎么改。

对每对 (C_non, C_opt)，LLM 生成 n=2 条候选规则，然后**每条规则拿回原电路重新应用、多次尝试**，用下面的式子打分：

$$
s_i = \mathbf{1}_{\text{eq}}(i)\cdot \text{clip}_{[0,1]}\Big(\alpha + \beta\,\frac{PPA_n - PPA_i}{PPA_n - PPA_o}\Big)
$$

- \(\mathbf{1}_{eq}\)：不等价直接 0 分（硬门槛）；
- 等价但没改善 → 0.25 分；等价且达到 C_opt 的改善 → 0.75 分；
- 每条规则多次尝试取平均，**平均 > 0.7 的才算高质量规则**，进库。

最终得到 **101,987 条规则**（对比：工程师 16 小时只总结出 12 条）。这就是"自动挖规则"的规模优势。

### 4.2 阶段二：自适应规则优化（ARAO + 束搜索）

光有规则库还不够——规则是"抽象描述"，具体电路是"具体代码"，两者有鸿沟（Challenge 3）。

#### ARAO（Adaptive Retrieval Augmented Optimization）四步

1. **Speculate（猜测）**：LLM 先为目标代码总结一条规则 `(snippet_t, condition_t, action_t)`；
2. **Retrieve（检索）**：用 condition_t、action_t 的 embedding 余弦相似度，从库中**检索最像的 3 条规则**；
3. **Adapt（适配）**：用 LLM 把检索到的规则"翻译"成贴合目标电路、去掉源设计特有噪声的版本；
4. **Optimize（优化）**：目标代码 + 适配后的规则喂给 LLM，生成优化变体，再验证等价 + 综合评 PPA。

**为什么要"先猜再检索"？** 因为直接按语义 embedding 检索会引入噪声，而且规则里可能残留"源代码对"的描述，会污染当前电路的优化上下文。用 LLM 先总结出目标电路自己的规则，再拿它当"检索键"，能更精准。

#### 多步束搜索（Rule-based Enhanced Searching）

单步 ARAO 不够，PPA 优化需要多步搜索。用束搜索（beam search）：

- 每轮选 top-k 候选（束宽 k）；
- 每个候选经 ARAO 扩展出 m 个变体；
- 下一轮候选池 = 所有新变体 + 当前 top 候选，最多 s 轮；

候选评分函数：

$$
Score = \omega \cdot Score_{diversity} + (1-\omega) \cdot Score_{ppa}
$$

- \(Score_{diversity}\) 用 TF-IDF 相似度量化"和父代码的差异"，鼓励探索不同策略；
- \(Score_{ppa}\) 综合功能等价 + 相对 PPA；
- \(\omega = 0.25\)（75% 权重压 PPA，25% 鼓励多样性）。

搜索规模有 4 档配置（2-3-3 → 5-10-5），对应采样 15 → 210 份 RTL。

## 5. 实验与主要结果

### 5.1 设置

- **基准**：RTLRewriter 基准（54 个设计 + 3 个实用大设计拆成 6 模块 = 60 个设计）；
- **基线**：RTLRewriter、SymRTLO、一位 2 年经验 Verilog 工程师（给 16 小时）、以及 HaVen / CodeV / DS-R1-Dist / Qwen-Coder / DeepSeek-V3 等 LLM；
- **主模型**：DeepSeek-V3-0324（685B）或 Qwen2.5-7B 系列；
- **嵌入模型**：gte_Qwen2-7B-instruct；温度 0.6。

### 5.2 面积优化（表 3、4）

- 11 个代表电路上，AutoPPA 平均改善**面积 20.45%**，**超过人工优化 19.25%、超过 RTLRewriter 7.56%**；
- 对 SymRTLO 自报结果的复杂电路（spmv/subexp_elim/adder_architecture 等），AutoPPA 面积改善 18.12%（12nm）/ 18.93%（65nm），略超 SymRTLO 的 17.58%；
- 60 电路全量：面积最高改善 **15.31%**，延迟最高 **11.28%**。

### 5.3 与裸 LLM 采样对比（表 5）

- 面积优化 Impr@210：AutoPPA-DS 15.31% vs 裸 DeepSeek-V3 11.20%（高 4.11 个百分点）；
- 延迟优化 Impr@210：AutoPPA-Qw 11.28% vs 裸 Qwen-Coder 7.74%；
- 关键：**AutoPPA 随采样预算增加，改善率持续上升且斜率更陡**——规则库让"每多采一个样本"更值钱。

### 5.4 规则库 vs 人工规则库（表 6）

同样的搜索设置，只换规则库：**自动 E²I 规则（101,987 条）→ 面积 8.83%**；**人工规则（12 条）→ 6.56%**。规模碾压，效果也更优。

### 5.5 消融（表 7）

| 设置 | 面积 Impr@50 |
|---|---|
| 完整 AutoPPA | 8.83% |
| 去掉搜索（单步） | 7.83% |
| 去掉 Adapt | 6.96% |
| 去掉 Retrieve + Adapt | 5.34% |
| 去掉 Speculate + Retrieve + Adapt | 6.39% |

每一步都有贡献，**检索 + 适配（Retrieve/Adapt）最关键**。

### 5.6 一个反直觉发现

- 延迟优化时，**小模型 Qwen2.5-7B 反而比 DeepSeek-V3 好**——因为 Qwen 在延迟优化上的基线能力更强，规则库只是"放大器"；
- 专门的 RTL 生成模型（HaVen、CodeV）在"优化"任务上反而垫底——说明**生成 ≠ 优化**，多任务微调才重要。

## 6. 主要创新点

1. **规则库全自动**：E²I 把"人总结经验"换成"机器从 13 万份代码、500 万改写对里自动挖"，得到 10 万+ 条规则，规模上碾压人工；
2. **对比式规则学习**：核心是从"功能等价但 PPA 有差异"的代码对（contrastive code pairs）里归纳规则，而不是从单一好代码里硬总结；
3. **香农熵筛数据**：用 PPA 分布的熵量化"这个设计能挖出多少优化花样"，只对高熵设计深挖，省算力；
4. **ARAO 的"先猜再检索再适配"**：解决"抽象规则 ↔ 具体设计"的鸿沟和检索噪声；
5. **规则增强的束搜索**：把规则检索嵌进多步搜索，兼顾 PPA 收益和多样性；
6. **跨工具跨工艺验证**：首个在 SiliconCompiler + 商业工具、12nm/45nm/65nm 三个节点上都评测的 LLM RTL 优化工作。

## 9. 局限性与风险

1. **等价性靠随机仿真，不是形式证明**：自动 testbench 100% 行覆盖 ≠ 时序等价，可能漏掉边角情形的功能偏差（对比 Dr. RTL 用 SEC 更硬）。
2. **PPA 标签是综合级的**：面积/延迟/功耗来自综合，不保证布局布线后趋势一致；也未做签核。
3. **规则库可能过拟合到 45nm/FreePDK**：规则是在特定工艺/工具下"挖"出来的，换节点未必迁移。
4. **对 SymRTLO 的比较不完全公平**：SymRTLO 没开源代码/脚本，AutoPPA 只能拿其自报数字对比，工艺节点和脚本不一致（论文自己坦承）。
5. **搜索成本**：动辄采样 210 份 RTL、每次都要综合，算力开销不小；论文没重点报告成本。
6. **规则质量依赖 LLM 归纳能力**：Induce 阶段用 LLM 从代码对提炼规则，可能引入幻觉；虽然用打分（>0.7）过滤，但规则仍可能"看起来对、实际不通用"。

## 11. 一分钟总结

AutoPPA 要解决的痛点是：**"知识派"的 PPA 优化规则靠人写，规模上不去**。它用 E²I 三段式——先让 LLM 把 10 万份开源 RTL 各改写 50 次（Explore），再用自动 testbench + 综合工具筛选出"功能等价且 PPA 差异 >5%"的代码对（Evaluate），最后从"差 vs 优"的对比里归纳出 `(片段, 条件, 动作)` 三元规则（Induce）——**全自动挖出 10 万+ 条规则库**。

优化时用 ARAO（先猜→检索→适配→优化）+ 束搜索，把最贴合的规则喂给 LLM 改写目标电路。结果在 60 个电路上面积最高改善 15.31%、延迟 11.28%，超过人工优化 19.25%、RTLRewriter 7.56%、SymRTLO 约 1 个百分点，且消融证明"检索 + 适配"是最大功臣。

**公开方法学意义**：早期预测与优化知识可以从大规模代码对比中自动归纳，而不必完全依赖人工规则；这为从候选优劣对中提炼可复用优化规律提供了实例。
