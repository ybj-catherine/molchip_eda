## 1. 一句话定位

**ASIC-Agent 把大语言模型从“只能写一段 Verilog”的生成器，升级为能跑完整数字 ASIC 设计闭环的自主多 Agent 系统。** 它以 OpenHands 和 CodeAct 的软件 Agent 基础设施为基础，在 Docker 沙箱里挂载 Icarus Verilog、Verilator、Yosys、OpenLane、KLayout 等 EDA 工具，并用主 RTL Agent、Verification Agent、Hardening Agent、Caravel Integration Agent 四个角色切分设计流程。系统还用向量数据库保存 OpenLane/Caravel/cocotb 文档、IP 仓库和社区排错知识，通过 RAG 在出错时检索解决方案。对应评测集 ASIC-Agent-Bench 以自然语言开放任务、checkpoint 部分分和 Gemini 2.5 Pro 裁判评估 Agent 全流程能力；在 20 个任务上，Claude 4 Sonnet 平均得分 88%，GPT-4.1 为 60.8%，Gemini 2.5 Pro 为 71.45%。

这句话里的四个承重点：

1. **完整 ASIC 流程，而不只是 RTL 生成** — 系统同时承担 RTL 编写、cocotb 功能验证、OpenLane RTL-to-GDSII hardening 和 Caravel SoC 集成。
2. **Agent 与真实 EDA 工具之间用 ACI 连接** — 工具不是通过自然语言假装执行，而是通过结构化 Action/Observation 接口执行 lint、仿真、OpenLane、KLayout 和文档查询。
3. **外部知识库承担“领域记忆”** — 向量数据库保存文档、错误模式、社区讨论和开源 IP 信息，补足基础 LLM 缺乏长期记忆和工具私有知识的问题。
4. **评测用开放任务和 checkpoint 部分分** — 不规定模块名、文件布局或固定 testbench，Agent 可以自行规划；裁判按可观察产物给部分分，并用固定 Gemini 2.5 Pro 保证一致性。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ✅ **核心** | Main Agent 从自然语言规格生成 Verilog 模块，并做 lint/静态分析。 |
| ② RTL 功能仿真 | ✅ **核心** | Verification Agent 使用 cocotb 写 Python testbench 并跑 Icarus Verilog/Verilator 仿真。 |
| ③ 逻辑综合 | ✅ | Hardening Agent 调用 OpenLane，流程内部使用 Yosys 做逻辑综合。 |
| ④ 门级仿真 | ❌ | 论文没有把门级 SDF/后仿作为独立评测里程碑。 |
| ⑤ STA | ✅ | Hardening Agent 查看 OpenLane timing metrics，并迭代修复 timing violations。 |
| ⑥ 形式验证 | ❌ | 没有明确使用 SAT、属性检查或形式等价工具。 |
| ⑦ 布局规划 | ✅ | OpenLane 自动执行 floorplanning 与宏摆放。 |
| ⑧ 标准单元摆放 | ✅ | OpenLane 的 placement 阶段属于 hardening 闭环。 |
| ⑨ 时钟树综合 | ✅ | OpenLane 自动完成 CTS。 |
| ⑩ 布线 | ✅ | OpenLane 自动完成 routing，Agent 监控并处理报错。 |
| ⑪ 后仿真 | ❌ | 论文未给出 parasitic-aware 后仿真结果。 |
| ⑫ 物理验证 | ✅ | Agent 分析并迭代消除 timing、antenna、DRC 和 LVS violations。 |
| ⑬ 签核 | ⚠️ 部分 | Agent 查看 PPA/DRC/LVS 指标，但没有工业级 signoff 报告或 MPW 实测闭环。 |
| ⑭-⑰ 流片到芯片到手 | ❌ | 只产出 GDSII 或 Caravel 集成件，不包含 mask、晶圆制造、封装测试。 |

**覆盖率：10/17。** ASIC-Agent 把 ① 到 ⑫ 的主要实现环节串起来，⑬ 只覆盖到 OpenLane 指标层面，制造与测试不在范围内。

> ⚠️ ASIC-Agent 的“成功 hardened”不等于“工业可制造”。OpenLane 使用开源 PDK 和简化流程，缺少完整 DFM、IR-drop、ESD、可靠性、封装测试及量产良率信息。

## 3. 输入 / 输出

### 3.1 输入

输入是自然语言任务文件，例如附录中的四比特流水线乘法器：

```text
Task: Four-Bit Pipelined Multiplier Implementation

1. Design and implement a four-bit pipelined multiplier in Verilog.
2. Create a verification environment and verify functional correctness.
3. Use the OpenLane flow to harden the verified design.
4. Report timing, area, power, DRC and LVS results.
```

用户只给目标和不完整的约束，没有规定模块名、testbench 文件名、OpenLane 参数或最终文件布局。Agent 需要在开放环境里自行完成“设计、验证、硬化、检查”的完整链条。

### 3.2 中间产物

Agent 会依次产生 Verilog、Python/cocotb testbench 和 OpenLane 配置：

```verilog
module pipelined_multiplier (
    input  wire        clk,
    input  wire        rst_n,
    input  wire [3:0]  a,
    input  wire [3:0]  b,
    output wire [7:0]  product
);
  // Pipeline registers, partial-product generation and accumulation.
endmodule
```

```json
{
  "DESIGN_NAME": "pipelined_multiplier",
  "VERILOG_FILES": "dir::src/pipelined_multiplier.v",
  "CLOCK_PERIOD": 10,
  "DIE_AREA": "0 0 50 50",
  "FP_PDN_CORE_RING": 0
}
```

OpenLane 运行后会生成 `runs/<tag>/results/final/verilog/gl/`、`gds/`、`metrics.csv` 等产物。Verification Agent 也会把失败原因回传给 Main Agent，构成 `edit -> lint -> simulate -> debug` 的闭环。

### 3.3 输出

最终交付物包括：

1. `pipelined_multiplier.v` 等 RTL 源码；
2. `tb_pipelined_multiplier.py` 等 cocotb testbench；
3. `config.json` 或等价 OpenLane 配置；
4. `pipelined_multiplier.gds` 最终版图；
5. OpenLane 报告中的 `tns`、`wns`、area、power、DRC/LVS 状态。

例如附录轨迹的最终摘要为：实现完成、全部测试通过、OpenLane 成功运行并产生 GDSII，然后 Agent 检查 timing/area/power/DRC/LVS，确认没有 critical errors。

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
 User natural-language task
          │
          ▼
 ┌──────────────────────────── ASIC-Agent ────────────────────────────┐
 │ Main Agent (RTL generation, lint, planning)                         │
 │        │                                                           │
 │        ▼                                                           │
 │ Verification Agent (cocotb testbench, simulation, root-cause)      │
 │        │ pass / debug feedback                                     │
 │        ▼                                                           │
 │ Hardening Agent (OpenLane config, RTL-to-GDSII, PPA/DRC fixing)    │
 │        │                                                           │
 │        ▼                                                           │
 │ Caravel Integration Agent (wrapper, Wishbone, memory-mapped CSR)   │
 └────────────────────────────────────────────────────────────────────┘
          │
          ▼
 Execution Environment: Docker + ACI tools
 Icarus Verilog / Verilator / Yosys / OpenLane / KLayout / cocotb
          │
          ▼
 Deliverables: RTL, testbenches, config files, GDSII, reports
```

### 4.2 核心模块逐个详解

#### Main RTL Agent

该模块解决“规格到可综合 RTL”的问题。它维护项目全局状态、设计约束和进度，生成带合适接口、信号声明与行为逻辑的 Verilog，并调用 Verilator/iverilog lint 做静态检查。若后续验证或硬化失败，它会根据反馈修改设计。

#### Verification Agent

该模块解决“RTL 是否满足任务要求”的问题。论文选择 cocotb/Python 而不是纯 Verilog testbench，原因是 LLM 写 Python 更稳，而且可以用 Python 方便实现矩阵乘法、神经网络参考模型等复杂行为。Agent 检测失败后做 root-cause analysis，并把建议修复传回 Main Agent。

#### Hardening Agent

该模块解决“功能正确到物理版图”的问题。它生成 OpenLane 配置文件，按设计约束选择 `CLOCK_PERIOD`、`DIE_AREA`、`CORE_UTILIZATION` 等参数，运行 RTL-to-GDSII 流程并读取 metrics。关键工具是专用 OpenLane 日志分析器：当 flow 出错时，它检查每一步的输出和错误日志，把复杂报错转成结构化原因。

#### Caravel Integration Agent

该模块解决“独立 IP 到可投片 SoC harness”的问题。它了解 Caravel 的接口、memory map、pin assignment 和集成要求，生成 wrapper、interconnect、时钟域与复位同步逻辑，并在需要时通过 Wishbone 实现控制和状态寄存器。

#### Runtime Environment, ACI 与 Knowledge Base

所有 Agent 运行在隔离 Docker 容器中，预装 Icarus Verilog、Verilator、Yosys、OpenLane 等工具。硬件专用 Agent-Computer Interface 提供 `lint_verilog`、`simulate_verilog`、`parse_verilog`、`run_openlane`、`view_openlane_metrics`、`query_opensource_ips`、`query_docs` 等能力。外部知识库用向量数据库保存：

- OpenLane、Caravel、cocotb 文档和 API reference；
- 从 Open Source Silicon Design Community 讨论中抽取的错误模式和解决方案；
- 由 IPM 索引的开源 IP 块；
- 面向硬件工作流的 multi-hop RAG 检索逻辑。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|---|---|---|---|---|
| Main RTL Agent | 自然语言任务 | Verilog 源码、lint 报告 | 基础 LLM、Verilator、iverilog | 否 |
| Verification Agent | RTL、任务规格 | cocotb testbench、仿真结果、修复建议 | 基础 LLM、cocotb、Icarus Verilog、Verilator | 否 |
| Hardening Agent | 已验证 RTL | OpenLane config、GDSII、PPA/DRC/LVS 指标 | OpenLane、Yosys、KLayout、专用日志分析器 | 否 |
| Caravel Integration Agent | hardened IP | wrapper、Wishbone CSR、集成验证 | Caravel、cocotb | 否 |
| Knowledge Base | 查询文本 | 文档、错误模式、IP 检索结果 | 向量数据库、RAG、IPM | 否 |
| Judge Agent | workspace、checkpoints | 任务得分 | Gemini 2.5 Pro | 否 |

## 5. 关键公式

论文没有为评分函数给出编号公式，但它明确说最终分数是各个 milestone score 的加权和。下面是对该描述的形式化，不是论文原式。

### 5.1 Checkpoint 的二元判定

$$
c_j=\mathbb{1}\left[\text{checkpoint } j \text{ is satisfied}\right]
$$

- $c_j$：第 $j$ 个 checkpoint 是否满足。
- $\mathbb{1}[\cdot]$：indicator function，条件成立为 1，否则为 0。
- $j$：checkpoint 编号。

### 5.2 加权总分

$$
S=\frac{100\%}{\sum_{j=1}^{K} w_j}\sum_{j=1}^{K} w_j c_j
$$

- $S$：最终百分比得分。
- $K$：任务定义的 checkpoint 总数。
- $w_j$：第 $j$ 个 checkpoint 的权重，按其对总目标的重要程度设置。
- $c_j$：第 $j$ 个 checkpoint 的二元结果。

**工程直觉**：这个评分让 Agent 即使没有完成 GDSII，也能因“写好 RTL”“通过仿真”“生成 config.json”等中间产物获得部分分，而不是只给 0 或 100。

**为什么这么设计**：ASIC 任务是长 horizon 开放任务，只有最终 GDSII 不足以区分“卡在语法错误”和“只剩 DRC 修复”两种失败。checkpoint 把连续设计进度离散成可验证步骤，更适合 LLM 裁判。

## 6. 训练与实验设置

### 6.1 是否需要训练

ASIC-Agent 不训练或微调基础模型。三个被测 backbone 分别是 Claude 4 Sonnet、GPT-4.1 和 Gemini 2.5 Pro，系统通过 prompt、工具调用、记忆和 Agent 编排在推理时增强模型。

### 6.2 实验设置

- 评测集：20 个开放任务，覆盖组合逻辑、序列逻辑、处理器核心、加密、浮点、debug、Caravel 集成与 OpenLane hardening。
- 指标：percentage score、steps、cost in USD。
- Judge：固定 Gemini 2.5 Pro，通过 checkpoint 和 workspace/GDSII 检查给分。
- 每个模型运行 Agent 后，用相同 Judge 评分。
- 复杂度按是否包含顺序逻辑、数据处理/控制复杂度、流水线/多级架构深度、是否集成 Caravel/OpenLane 分类。

- Agent 在 OpenLane、lint 和 Caravel 问题卡住时，会主动查询向量数据库和 RAG。

## 7. 创新点

### 创新点 1：把软件 Agent 基础设施改造成数字 ASIC 全流程 Agent

已有硬件 Agent 大多只覆盖单文件 RTL 或 testbench。ASIC-Agent 复用 OpenHands/CodeAct 的执行与 Agent 架构，但扩展出针对 RTL、验证、OpenLane 和 Caravel 的专用工具和知识库，使模型能持续执行从 RTL 到 GDSII 的工具链。

### 创新点 2：用 ACI 把 EDA 工具变成 Agent 可操作接口

论文不是让模型输出一串看似正确的命令，而是提供硬件专用 Action/Observation 接口。`lint_verilog`、`simulate_verilog`、`parse_verilog`、`run_openlane`、`view_openlane_metrics` 等函数把工具执行、日志解析和结构反馈都标准化，降低模型误用工具的概率。

### 创新点 3：首次提出面向硬件 Agent 的 ASIC-Agent-Bench

VerilogEval、RTLLM 等评测主要看固定 testbench 下的单文件 RTL 生成；ASIC-Agent-Bench 允许开放文件结构、自主工具使用、反复调试、Caravel 集成和 OpenLane 硬化，并用 checkpoint 部分分与 LLM Judge 评测 Agent 系统。

### 创新点 4：社区错误知识库和 IP 检索作为领域记忆

系统把 Open Source Silicon Design Community 的错误讨论抽取成向量数据库，并用 IPM 检索开源 IP，使 Agent 拥有基础模型参数之外、可以跨任务复用的硬件领域经验。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

ASIC-Agent 接手工件是自然语言规格，交付件是经过功能验证和 OpenLane 硬化的 GDSII，或进一步集成到 Caravel 的 SoC 项目。它把传统上由前端设计、验证、综合、后端实现和 SoC 集成工程师分别完成的步骤，交给一组共享 workspace 的 Agent 连续执行。

### 9.2 从“OpenLane 成功”到“能做成芯片”之间隔着什么

OpenLane 成功代表开源流程能在指定 PDK 上生成版图并通过基础 DRC/LVS。距离真实量产还缺：

- 工业 signoff timing、SI、IR-drop、EM、ESD、DFM 和可靠性检查；
- 多工艺角、多电压域和温度覆盖；
- 封装、bonding、测试与量产良率分析；
- 高质量模拟/IO 单元与第三方 IP 许可；
- 符合 MPW 项目规则的完整 Caravel 顶层和约束检查。

因此论文结论应理解为“自主完成开源 ASIC 流程中的主要工程步骤”，而不是“无需人工即可量产芯片”。

## 10. 讨论与局限

### 10.1 论文自述的局限

- 没有给出真实 MPW 投片或封装测试结果，制造端未验证。
- 20 个任务的规模仍然有限，尤其是高级处理器、复杂 SoC 和超大规模设计覆盖不足。
- LLM Judge 虽有 human review，但主观开放任务评分仍可能受到 Judge 偏好和 prompt 设计影响。

### 10.2 代码/复现层面的问题

- 仓库使用 Docker、OpenLane、Caravel 及商业 LLM API，完整复现需要网络、算力和较长 runtime。
- 论文表内成本、步数和分数受模型版本与 API 价格影响，日期较旧，无法直接复现到当前模型。
- 只归档论文本身，未在本仓库运行完整 Docker 流程；代码细节、env 版本和 OpenLane PDK 配置需要另行核对。

### 10.3 本资料包的批判性分析

该工作最值得肯定的是把 RTL Agent 扩展到了物理实现和 SoC 集成，并给出开放任务评测。但从学术证据看，20 个任务中很多简单任务都能到 100%，区分度主要来自少数复杂任务；Claude 平均分 88% 也需要和成本一起解释。向量数据库和 IP 检索的实际贡献没有单独消融，不能把收益都归因于多 Agent 分工。若要作为“加速 ASIC 工作流”的证据，还需要大型工业设计、独立工程师对照和端到端 tape-out 闭环。

## 12. 一分钟复述版

1. 单模型只能生成 Verilog，无法自己执行、调试、综合和做版图。
2. ASIC-Agent 用 OpenHands/CodeAct 基础设施，加上 RTL、验证、hardening 和 Caravel 四个 Agent。
3. Docker 沙箱提供 Icarus Verilog、Verilator、Yosys、OpenLane 等真实工具。
4. ACI 把工具执行和日志反馈结构化，向量数据库提供文档、错误和 IP 知识。
5. Verification 用 cocotb/Python，Hardening 用 OpenLane，集成用 Caravel/Wishbone。
6. ASIC-Agent-Bench 用开放任务、checkpoint 部分分和 Gemini 2.5 Pro Judge 评测 Agent。
7. 20 个任务上，Claude 4 Sonnet 平均 88%，GPT-4.1 为 60.8%，Gemini 2.5 Pro 为 71.45%。
8. Claude 在难任务强，但平均成本最高；GPT-4.1 便宜但精度低；Gemini 在简单任务接近 Claude。
9. 系统能修复 lint、testbench、timing、antenna、DRC 等错误，并自动产出 GDSII。
10. 当前证据仍是开源流程级成功，没有真实量产良率、工业 signoff 和封装测试闭环。
