# DAC 2026 LBR Verification Gap 论文深度讲解

> **The Verification Gap — Why Compile Success Fails as a Correctness Proxy for LLM-Generated Hardware Verification Collateral**  
> 作者：Vikash Kumar（ARM）  
> 出处：DAC 2026 Late Breaking Results，Work-in-Progress Poster，WIP3164  
> 公开页面：<https://63dac.conference-program.com/presentation/?id=WIP3164&sess=sess306>  
> 证据边界：公开页面提供摘要和实验数字，未提供独立 PDF、公式全文、代码或数据集。

---

## 1. 一句话定位

这项 DAC 2026 LBR 工作指出：LLM 生成的 UVM 验证代码即使成功编译，也可能在协议功能上严重错误。作者在 AHB2APB bridge 案例中用 **Repair Efficiency Score（RES）**、**Verification Gap（VG）** 和 **Specification Coverage Ratio（SCR）** 描述“编译通过”与“功能正确”之间的差距；自动修复循环在 15 次调用中解决 37 个编译错误，但最终仍有 **VG = 0.80**，即 80% 的功能失败对编译器不可见。

核心不是“又做了一个 testbench 生成器”，而是提醒评测者：compile success 只能证明语法和部分 elaboration 条件成立，不能代理协议级 checker、stimulus、时序和功能正确性。

## 3. 输入 / 输出

### 输入

- AHB2APB bridge RTL 与协议规格；
- LLM 生成的 UVM testbench；
- 编译器和仿真器反馈；
- agentic repair loop 的每次调用与修复记录。

### 输出

- 编译错误修复统计：37 个错误、15 次调用；
- RES、VG、SCR 三类度量；
- 8 类 protocol-level failure modes 的 taxonomy；
- 一个额外发现：功能修正后的 testbench 暴露了 bridge registered pipeline logic 中此前未知的 RTL race condition。

公开摘要没有给出 8 类 failure mode 的逐项名称，也没有公布三项指标的完整数学定义，因此不应从缩写自行扩写公式或构造不存在的数据表。

下面只是帮助理解输入/输出边界的概念性接口，不代表作者公开了这种文件格式：

```text
input : bridge RTL + protocol specification + generated UVM testbench
output: compile-repair statistics + RES/VG/SCR + protocol-failure taxonomy
```

## 4. 方法与架构

```text
LLM 生成 UVM testbench
        │
        ▼
编译驱动的 agentic repair loop
        │  37 compile errors / 15 calls
        ▼
“能够编译”的 verification collateral
        │
        ▼
协议级功能检查与规格覆盖分析
        │
        ├── RES：修复循环效率
        ├── VG：编译器看不见的功能失败比例
        └── SCR：相对规格的覆盖程度
        ▼
8 类协议失败模式 + AHB2APB 案例结论
```

这个流程刻意把两个 gate 分开：

1. **Compile gate**：验证代码是否能够编译、展开并进入仿真。
2. **Functional gate**：验证 stimulus、checker、协议时序和规格覆盖是否真正正确。

论文的主要反例是：前一个 gate 可以被自动修复得很好，后一个 gate 仍然很差。

---

## 5. 关键公式与指标

公开摘要只允许可靠恢复 RES 的案例计算：

$$
\mathrm{RES}_{\mathrm{case}} = \frac{37\ \text{resolved compile errors}}{15\ \text{LLM calls}} = 2.47
$$

- $37$：repair loop 解决的编译错误数；
- $15$：LLM 调用次数；
- $2.47$：公开页面报告的 RES。

另一个公开数字为：

$$
\mathrm{VG}=0.80
$$

- $\mathrm{VG}$：Verification Gap；
- $0.80$：80% 的 functional failures 对编译器不可见。

公开页面没有给出 VG 和 SCR 的完整分子、分母与聚合公式。本讲解因此不把 VG 写成“1 − requirement hit rate”，也不把 SCR 写成“unique requirements / stimuli”；这些曾经出现过的定义没有公开来源支持。

## 7. 创新点

1. **把 compile success 从“最终指标”降为“前置 gate”**：明确指出它与 protocol-level functional correctness 接近不相关。
2. **提出三项互补度量**：分别观察修复循环、验证缺口和规格覆盖，而不是只报“生成代码能否编译”。
3. **用功能修正后的 testbench 发现真实 RTL 问题**：说明验证 collateral 的价值最终必须由可观察的功能错误来证明。

## 9. 与芯片流程的关系

该工作位于 RTL 验证入口：LLM 先生成 UVM collateral，repair loop 让它通过 compile gate，再由仿真与协议判据检查 functional gate。它不替代 assertion coverage、formal verification、功能覆盖闭合或 signoff；它提供的是一个评测警告和度量框架。

与本资料包中的 [Verification-Gap-Detection](../Verification-Gap-Detection/论文深度讲解.md) 不同：后者关注 missing checker 的识别方法，本工作关注“可编译但不正确”的验证产物及其度量。

## 10. 讨论与局限

- 公开材料只有会议页面摘要，三项指标的完整定义与统计细节不可核查。
- 只有一个 AHB2APB bridge 案例，不能据此推断对所有协议、设计规模或模型都成立。
- 8 类 failure mode 的名称和判定规则未在公开摘要中展开。
- 发现 race condition 说明 testbench 有效，但公开页面不足以独立复现触发序列。
- RES 数值高只说明编译错误修复效率，不能说明功能正确性。

最重要的引用边界是：可以引用 37/15、RES=2.47、VG=0.80 和“80% functional failures invisible to compiler”；不能引用旧文档中没有来源的相关系数、SCR 中位数、具体 failure-mode 列表或自拟公式。
