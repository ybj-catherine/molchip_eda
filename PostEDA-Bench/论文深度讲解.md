## 1. 一句话定位

**PostEDA-Bench 把 LLM Agent 在 EDA 工具跑完之后的“最后一公里”拆成可机器判定的 145 个任务，专门评测两件旧 benchmark 没测的事：修复 residual DRC violation，以及把 PPA 推到目标点。** 它从 RTLLM v2、VerilogEval-Human 和 OpenCores 筛选设计，映射到 ASAP7 PDK，再构造 DRC-Essential、DRC-Reasoning、PPA-Mono、PPA-Multi 四个层级分支。八个商用和开源 LLM 在多种 Agent scaffold 下评测后发现：合成 DRC-Essential 最好只有 85.50% SR，单目标 PPA-Mono 最好只有 64.56% SR；更贴近现实的 DRC-Reasoning 最好只有 36.66%，PPA-Multi 最好只有 20.00%。视觉增强对 DRC 普遍有利，而 PPA-Multi 的主要瓶颈不是不知道 knob，而是不会在多个 PPA 指标之间做 trade-off。

这句话里的五个承重点：

1. **评测对象是 post-EDA closure，不是 NLP-to-script** — 旧 benchmark 大多只让 LLM 生成 EDA 脚本，PostEDA-Bench 要求 Agent 在已有 OpenROAD/GDS 工程上完成目标驱动的修复或优化。
2. **DRC-Bench 与 PPA-Bench 是两个维度** — DRC-Bench 测版图制造规则修复，PPA-Bench 测功耗/性能/面积目标收敛；两者使用不同工具面、输入和判分函数。
3. **层级化能定位“哪一类能力不会”** — DRC 分 synthetic/practical，PPA 分 single/multi-objective，再按 knob 数量或 Pareto 维度分 L1/L2/L3，避免只看平均分。
4. **SR、VRR、NIS 三个指标分开看** — SR 表示完全达标，VRR/NIS 表示部分进展；有些模型能改进很多 violations 但无法 DRC-clean，有些能朝目标移动但停在阈值前。
5. **真实瓶颈不是规则记忆，而是几何规划和权衡推理** — DRC-Essential L1/L2 可到 92–96%，但多步几何修复和多目标 PPA 迅速崩到 0–20%。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ⚠️ 部分 | PPA-Mono Performance L3 允许修改 RTL/微架构，但常规任务不是生成式 RTL 设计。 |
| ② RTL 功能仿真 | ✅ | PPA-Bench 用 testbench 检查修改后 RTL 与原设计的功能等价。 |
| ③ 逻辑综合 | ✅ | Agent 通过 OpenROAD-flow-scripts 重跑综合到布局布线的完整流程。 |
| ④ 门级仿真 | ❌ | 不做 SDF 后仿真，只做原始/修改 RTL 的功能等价 sanity check。 |
| ⑤ STA | ✅ | PPA-Bench 的 performance 指标以 effective period 为主，直接依赖静态时序分析。 |
| ⑥ 形式验证 | ❌ | 不执行属性检查或形式等价，只有 testbench-based 功能等价。 |
| ⑦ 布局规划 | ✅ | OpenROAD flow 重跑覆盖 floorplanning。 |
| ⑧ 标准单元摆放 | ✅ | PPA 优化可编辑 placement 相关参数，OpenROAD 完成 placement。 |
| ⑨ 时钟树综合 | ✅ | OpenROAD flow 重跑覆盖 CTS。 |
| ⑩ 布线 | ✅ | OpenROAD flow 重跑覆盖 routing；DRC-Reasoning 的 violation 来自 post-route。 |
| ⑪ 后仿真 | ❌ | 不使用寄生提取后仿真。 |
| ⑫ 物理验证 | ✅ **核心** | DRC-Bench 直接评测 sign-off DRC repair，KLayout 重跑 DRC deck 给最终标签。 |
| ⑬ 签核 | ✅ 部分 | PPA-Bench 的目标是 post-tool PPA convergence，但不是完整工业多 PVT/reliability signoff。 |
| ⑭-⑰ 流片到芯片到手 | ❌ | 无 mask、制造、封装和测试。 |

**覆盖率：9/17（① 为部分，⑬ 为部分指标）。** PostEDA-Bench 的核心落点是 ⑫ DRC 修复和 ⑤/⑬ PPA 收敛，OpenROAD 重跑使 ③、⑦-⑩ 作为支持阶段被触达。

> ⚠️ DRC-clean 只针对 ASAP7 deck 和 KLayout 版本；PPA 达标只针对论文定义的 effective period、total power、die area 阈值。它不等于工业 signoff 或制造 ready。

## 3. 输入 / 输出

### 3.1 输入

DRC-Bench 每个任务给一个 target GDS 和一条自然语言 prompt。prompt 列出初始 sign-off DRC violations，包括 rule ID、描述、几何类型和坐标：

```text
The input gds file is ./top_cell.gds
Top Cell: aes_cipher_top
=======================================
--- V0.M1.AUX.3 | cell: aes_cipher_top
[0] {
  'category': 'V0.M1.AUX.3',
  'description': V0 must exactly be the same width as M1 along the Direction ...
}
```

PPA-Bench 每个任务给一个自包含 OpenROAD 工程，含 `src/`、`config/`、`logs/`、`reports/`、`objects/`、`results/`。prompt 总结当前 PPA、目标阈值、constraint floor，并指向 `FlowVariables.md`：

```text
The design has completed the OpenROAD flow, but effective period is not met.
Current effective_period: 212.2 ps
Target effective_period: <= 210.0 ps
Analyze any available files and optimize design configuration or timing constraints in config/*.mk
```

### 3.2 中间产物

DRC-Bench 的 Agent 可以用文本或图像查询 violation 上下文，然后编辑 GDS 并重跑 DRC。工具返回 KLayout 版图区域的 JPEG、Base64 data URI，或结构化 violation 列表：

```text
DRC report after edit:
  V0.M1.AUX.3: 1 residual violation
  coordinate: (x=..., y=...)
  rule description: V0/M1 width extension mismatch
```

PPA-Bench 的 Agent 主要改 `config.mk`、`constraints.sdc` 或 RTL，然后调用 `run_openroad`，最终读取 `report_ppa()` 的 effective period、total power 和 die area。

### 3.3 输出

- DRC-Bench：最终 `top_cell.gds` 必须通过 KLayout sign-off DRC；否则最多按 violation 减少数量得 VRR 部分分。
- PPA-Bench：最终工程必须同时满足所有目标阈值，并且修改后的 RTL 通过 testbench-based 功能等价 sanity check；否则按 NIS 给部分分。

例如，一个有效 DRC 结果可以是 `query_drc_report()` 返回 `remaining_violations=0`；一个有效 PPA 结果可以是 `report_ppa()` 返回 `effective_period=208.1 ps`, `total_power=...`, `die_area=...` 且所有目标均满足。

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
 Source RTL: RTLLM v2 / VerilogEval-Human / OpenCores
          │ filter: parse + synthesis + std-cells > 300
          │ dedup + license/audit eligibility
          ▼
 Constructed Task Pool
          ├─ DRC-Bench
          │    ├─ DRC-Essential L1/L2/L3 (synthetic)
          │    └─ DRC-Reasoning L1/L2/L3 (post-flow residual)
          └─ PPA-Bench
               ├─ PPA-Mono Performance/Power/Area L1/L2, Perf L3
               └─ PPA-Multi 2D/3D Pareto targets L1/L2
          │
          ▼
 Agent Evaluation
   ReAct / Proposer-Critic / ORFS-Agent / Reflexion / ToT
   DRC tools: query, vision_query, add_shape, change_shape,
              move_cell, query_drc_report
   PPA tools: read_file, edit_file, run_openroad, report_ppa
          │
          ▼
 Machine-checkable scoring
   DRC: KLayout sign-off DRC + VRR
   PPA: OpenROAD report parser + SR/NIS + functional-equivalence check
```

### 4.2 核心模块逐个详解

#### Source Design Curation

这个模块解决“设计从哪里来、能不能公开复现”。候选设计必须：

1. 有合法顶层模块、语法正确，并能成功做 gate-level synthesis；
2. 综合后标准单元数大于 300；
3. 通过 top-module name、port signature、post-synthesis structural similarity 做跨来源去重，门级重叠超过 90% 即合并；
4. 具备 provenance、license、selected top module 和 derived artifacts 的发布审计条件。

论文报告的源设计统计为 min 301、avg 16,505、max 95,061 个标准单元。因为公开 RTL 可能出现在 LLM 训练语料中，评测刻意转向下游 tool interaction、benchmark-specific target 和生成 EDA artifact，而不是源代码回忆。

#### DRC-Bench

DRC-Essential 用合成 violation 隔离规则知识、上下文抗干扰和连续修复能力：

- L1：原子单规则，case 只包含制造 violation 所需的最小 shapes；
- L2：把一个 L1 风格 violation 放进真实 layout context，模型需要从杂乱几何中过滤相关 shapes；
- L3：注入 5–15 个同时出现的 L1 风格 violation，修复一个可能触发或消除另一个。

DRC-Reasoning 用完整 EDA flow 和 Innovus built-in repair 后仍残留的 violation，按最少编辑步数分 L1/L2；L3 是真实 post-flow GDS 中多个 violations 的联合调试。

#### PPA-Bench

PPA-Mono 分别测 performance、power、area 的单目标优化：

- L1：扰动一个 knob；
- L2：联合扰动多个 knob，通常 2–3 个；
- L3 只用于 Performance：需要 pipeline、retiming、datapath 或 SDC 等源码级重构。

PPA-Multi 把 target 设置在 Pareto front 上，起点位于 front 内部，要求 Agent 同时满足非目标指标的 constraint floor。L1 是两目标 Pareto，L2 是三目标 Pareto。

#### Machine-Checkable Scoring

DRC 由 KLayout 使用 ASAP7 DRC deck 重跑并确定是否 clean；PPA 由 OpenROAD report parser 读 effective period、total power、die area。PPA 还要通过功能等价 sanity check，防止 Agent 通过偷偷简化逻辑或破坏功能来“达到 PPA”。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的工具/方法 | 是否需训练 |
|---|---|---|---|---|
| Source curation | 公开 RTL | 筛后 design pool | DC、OpenROAD、license audit | 否 |
| DRC construction | DRC-clean GDS | violation-injected tasks | OpenROAD/DC+Innovus、KLayout、专家修复 | 否 |
| PPA construction | 筛后 design | PPA target tasks | OpenROAD-flow-scripts grid sweep、Pareto front | 否 |
| DRC Agent tools | 当前 GDS | GDS edits、violation reports | KLayout、image rendering | 否 |
| PPA Agent tools | OpenROAD project | modified config/RTL、PPA reports | OpenROAD-flow-scripts、sandbox shell | 否 |
| Scoring | final artifacts | SR/VRR/NIS、functional-equivalence verdict | KLayout、OpenROAD parser、testbench | 否 |

## 5. 关键公式

### 5.1 Violation Reduction Rate

论文公式 (1) 定义 DRC 部分进展：

$$
\mathrm{VRR}=\frac{\max(0,E_{\mathrm{initial}}-E_{\mathrm{final}})}{E_{\mathrm{initial}}}\times 100\%
$$

- $\mathrm{VRR}$：violation reduction rate，违规数减少比例。
- $E_{\mathrm{initial}}$：Agent 编辑前的总 violation 数。
- $E_{\mathrm{final}}$：Agent 编辑后的总 violation 数。
- $\max(0,\cdot)$：如果违规数反而增加，VRR 截断到 0。

### 5.2 Per-Metric Normalized Score

论文公式 (2) 定义每个 PPA 指标的单指标进展：

$$
s_i=
\begin{cases}
\min\left(1,r_i\right), & i\in A,\\
1, & i\in B \text{ and } M_i^{\mathrm{fin}}\leq M_i^{\mathrm{tgt}},\\
1-r_i, & i\in B \text{ and } M_i^{\mathrm{fin}}>M_i^{\mathrm{tgt}},
\end{cases}
$$

$$
r_i=\frac{M_i^{\mathrm{fin}}-M_i^{\mathrm{init}}}{M_i^{\mathrm{tgt}}-M_i^{\mathrm{init}}}
$$

- $s_i$：第 $i$ 个 metric 的归一化得分。
- $i$：PPA metric 索引，如 effective period、total power、die area。
- $A$：需要改善的 violated metrics，即 $M_i^{\mathrm{init}}>M_i^{\mathrm{tgt}}$。
- $B$：不能 regress 的 constraint metrics，即 $M_i^{\mathrm{init}}\leq M_i^{\mathrm{tgt}}$。
- $M_i^{\mathrm{init}}$、$M_i^{\mathrm{fin}}$、$M_i^{\mathrm{tgt}}$：metric $i$ 的初始值、最终值和目标值。
- $r_i$：相对目标的进展比例；所有 PPA 指标都是 lower-is-better。

### 5.3 Normalized Improvement Score

论文公式 (3) 聚合多指标得分为 NIS：

$$
\mathrm{NIS}=
\begin{cases}
0, & A\neq\emptyset \text{ and } M_i^{\mathrm{fin}}\geq M_i^{\mathrm{init}}\ \forall i\in A,\\
\dfrac{1}{|M|}\sum_{i\in M}s_i, & \text{otherwise}.
\end{cases}
$$

- $\mathrm{NIS}$：normalized improvement score。
- $M$：该任务涉及的全部 PPA metric 集合。
- $|M|$：metric 数量。
- $s_i$：公式 (2) 的单 metric score。
- $A$：仍被违反且没有改善的 metric 集合。

**工程直觉**：VRR/NIS 区分“完成目标”和“只往前走了一步”。在 PPA-Multi 中，负数 NIS 表示 Agent 为追一个目标而牺牲其他约束，说明它不会做 trade-off。

**为什么这么设计**：SR 对长流程任务过于稀疏，部分分能定位能力缺口。公式 (3) 的 zero-floor 防止 Agent 只优化本来已满足的 constraint metric 来刷分。

## 6. 训练与实验设置

### 6.1 是否需要训练

PostEDA-Bench 不训练 Agent。论文评测 3 个商业模型和 5 个开源模型，在 ReAct、Proposer-Critic、adapted ORFS-Agent 等 scaffold 下执行。ORFS-Agent 只用于 PPA。

### 6.2 实验设置

- 模型：GPT-5、GPT-5-mini、Gemini-3-Flash-preview、DeepSeek-V3.2、Qwen3.5-122B-A10B、Qwen3.5-27B、Gemma-4-31B-it、Qwen3.5-9B。
- 框架：ReAct、Proposer-Critic、ORFS-Agent；另有 Reflexion 和 ToT 用于 PPA 侧 wrapper/ablation。
- 协议：每任务 5 次 temperature=0 run；ReAct 和 Proposer-Critic 使用 8 DRC / 16 PPA action cap；ORFS-Agent 使用 18 次 OpenROAD run/task。
- 工具栈：DRC 为 ASAP7 + KLayout v0.30.3；PPA 为 ASAP7 + OpenROAD-flow-scripts commit `a2bb042b6`。
- 评测脚本：`eval_drc_sr.sh`、`eval_ppa_sr.sh`、`ppa_score.py`。

**DRC per-level 核心发现：**

- DRC-Essential L1/L2 对代表性 ReAct backbone 可达 92–96% SR，说明原子规则记忆和上下文过滤基本解决。

- PPA-Performance L3 的 SR 只有 8–20%，NIS 只有 20–27%，说明需要 retiming/pipelining 等微架构改造时模型明显失效。

论文还报告视觉增强：增加 layout image channel 对 DRC-Bench 从未有害，能在文本-only baseline 较弱时带来一致 SR/VRR 提升。

## 7. 创新点

### 创新点 1：首次把 DRC fixing 纳入 EDA-LLM benchmark

Table 1 显示现有 EDA-LLM benchmark 都不测 DRC repair。PostEDA-Bench 让 Agent 必须真正读 GDS、理解 rule、编辑几何并反复调用 KLayout，填补 sign-off physical verification 的评测空白。

### 创新点 2：用四维层次结构定位能力缺口

DRC-Essential 与 DRC-Reasoning 区分 synthetic/practical；PPA-Mono 与 PPA-Multi 区分 single/multi-objective；每个分支再按 knob 数量、edit step 或 Pareto 维度分层。这样能明确说“模型不会的是编辑交互建模，还是多目标约束追踪”。

### 创新点 3：同时覆盖开源和商业工具链的构造路径

DRC-Bench 使用 OpenROAD-flow-scripts 与 Synopsys DC + Cadence Innovus 生成 post-flow layout，虽然最终 sign-off scoring 由开源 KLayout 完成；PPA-Bench 当前以 OpenROAD 为主。这个设计让 benchmark 具有工业 residual violation 的语义，又不牺牲外部复现性。

### 创新点 4：用机器可检查的 SR/VRR/NIS 分开完成和部分进展

相比只报 success/failure，VRR/NIS 可以捕捉“靠近目标但未达标”。功能等价 sanity check 又防止 Agent 通过破坏功能换取 PPA 分数。

| ToT | Tree of Thoughts | 树状思考搜索。 |
| ECO | Engineering Change Order | 工程变更单，用于修复局部设计问题。 |

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

PostEDA-Bench 接手工件是“工具已经跑完但还没有 closed”的结果：DRC-Bench 是 post-route GDS 上残余 rule violations，PPA-Bench 是 OpenROAD 已完成但未满足目标阈值的工程。它对应工程师在 ⑫ 物理验证和 ⑬ 签核之间反复修 DRC/调 PPA 的 last-mile 工作。

### 9.2 从“benchmark 通过”到“能做成芯片”之间隔着什么

DRC-clean 只证明对 ASAP7 + KLayout deck 通过，不等于先进工艺、Calibre/ICV 或其他 foundry deck 通过。PPA 达标只针对 period/power/area 三个摘要指标，仍缺 timing margin、IR drop、EM、SI、DFM、可靠性、多 PVT、封装和测试数据。功能等价 sanity check 是 testbench 级检查，也不是形式等价。

## 10. 讨论与局限

### 10.1 论文自述的局限

- DRC-Bench 只用 ASAP7 单 PDK，尚未推广到 commercial advanced-node deck 和当前 Calibre release。
- DRC-Reasoning step-count labels 由单一物理设计工程师标注，未来计划补充多 annotator 和 kappa 一致性。
- PPA-Bench 当前只用 OpenROAD，计划扩展 commercial flow。
- `run_openroad` 一次完整 flow 需要分钟到数十分钟 wall-clock，大规模模型对比成本高。

### 10.2 代码/复现层面的问题

- DRC-Reasoning 的一部分任务需要 Innovus/DC 生成；发布包若仅保留最终 GDS、prompt、report 和 KLayout setup，外部可在不重新生成 commercial artifact 的前提下评测，但完整再生成仍需商业工具。
- 开源模型通过 vLLM 在本地 GPU cluster 服务，商业模型调用 API，具体结果会受版本和部署环境影响。
- 论文说任务、工具和日志在 acceptance 后 release，本仓库仅归档 PDF/text，没有本地跑 benchmark。

### 10.3 本资料包的批判性分析

PostEDA-Bench 的层级设计是它最实用的贡献，能把“会背 DRC rule”和“会做几何修复”分开。但 benchmark 的 PPA 目标来自同一 grid sweep 的 Pareto front，模型可通过大量重复实验逼近而不是真正理解设计。ORFS-Agent 的结果也提示搜索空间先验非常重要；如果不把 LLM 推断 knobs 与 Bayesian optimizer 的结构讲清楚，20.00% SR 很难直接归因于 Agent 的 trade-off 推理能力。

## 12. 一分钟复述版

1. 旧 EDA-LLM benchmark 大多考生成脚本，不考 DRC fixing，也用 flat hierarchy。
2. PostEDA-Bench 从公开 RTL 构造 145 个 post-EDA 任务。
3. DRC-Bench 分 DRC-Essential 和 DRC-Reasoning，PPA-Bench 分 PPA-Mono 和 PPA-Multi。
4. DRC 输入是 GDS 和 violation prompt，输出要 KLayout DRC-clean。
5. PPA 输入是 OpenROAD 工程，输出要满足目标阈值且保持功能等价。
6. SR 看完全达标，VRR 看 DRC 部分进展，NIS 看 PPA 部分进展。
7. 最好成绩：DRC-Essential 85.50%，DRC-Reasoning 36.66%，PPA-Mono 64.56%，PPA-Multi 20.00%。
8. DRC 原子规则和单目标优化已较可，但 cascaded fix、多步几何推理和多目标 trade-off 仍很弱。
9. 视觉增强对 DRC 有帮助，ORFS Bayesian optimization 可改善部分 PPA-Multi 结果。
10. 局限是单 PDK、OpenROAD-only PPA、单 annotator、商业工具生成依赖和 full-flow 运行成本高。
