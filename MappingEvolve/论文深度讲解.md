## 1. 一句话定位

**MappingEvolve 是首个直接用 LLM 演化 technology mapping 核心 C++ 算法代码的框架**：论文从 mockturtle 映射实现中抽象出 `MatchPhase`、`MatchPhaseExact`、`MatchDropPhase` 三个可演化算子，并用 Planner → Evolver → Evaluator 的分层架构把“选哪个算子优化、用什么策略、改成什么”分开；每个改动只在 `EVOLVE-BLOCK` 安全区域内进行，并经编译、ABC `cec` 等价检查、QoR 评估三级验证。相比 ABC 面积降低 10.04%，相比 mockturtle 降低 7.93%，EPFL 上相对 mockturtle 的 $S_{\mathrm{overall}}$ 提升 46.6%–96.0%，代价是 4.46%–6.50% 的延迟增加。

这句话里的四个承重点：

1. **演化对象是 mapper 核心算法，不是综合脚本** — 现有 ChatLS/LLSM 让 LLM 写优化脚本或调参；MappingEvolve 直接修改 mockturtle 的匹配/相位优化逻辑。
2. **抽象出三个小而完整的算子** — 每个算子对应 delay/area-flow、exact-area、phase unification 三种优化动作，保证 LLM 改动区域可隔离、可回滚、可量化。
3. **Planner 与 Evolver 解耦** — Planner 根据历史演化、停滞信号和算子使用频率决定“下一步改哪个算子”，Evolver 只负责在受限代码区域做 plan-conditioned mutation。
4. **功能安全不是事后补丁** — 每个候选都要编译、组合等价检查、QoR 测量；错误代码收到强负奖励，从而让演化长期保持 `e=0.00`。

## 3. 输入 / 输出

### 3.1 输入

演化输入是逻辑网络和标准单元库。论文以 AIG 为 technology-independent network，以 ASAP7 为映射目标：

```text
Input:
  G : logic network (typically AIG)
  L : standard cell library (ASAP7)
  O = {MatchPhase, MatchPhaseExact, MatchDropPhase}
  S = {area-opt, delay-opt, balanced}
```

对 Evolver 而言，具体编辑入口是 mockturtle C++ 中的 `EVOLVE-BLOCK` 安全区域：

```cpp
// EVOLVE-BLOCK: MatchPhase cost selection
// LLM 只能改下面这段优化启发式，不能改函数签名/API/数据结构
if (alpha_r * T + (1.0 - alpha_r) * F < best_cost) {
    best_cost = alpha_r * T + (1.0 - alpha_r) * F;
    best_cut = c;
    best_gate = g;
}
// EVOLVE-END
```

### 3.2 中间产物

演化中间产物是“完整 mapper 候选程序”，由被改动的算子和未改动的其余算子合并而来；随后经过编译产物、等价检查结果、QoR metrics 三层记录：

```text
iteration_29:
  selected_operator: MatchDropPhase
  strategy: delay-opt
  compilation: pass
  equivalence_failure_rate_e: 0.00
  S_area: 0.xx
  S_delay: -0.xx
  S_overall: 0.298
  accepted: true
```

### 3.3 输出

最终输出是演化后的 mapper 程序和 mapped netlist：

```text
evolved mapper:
  mockturtle source with evolved MatchPhase / MatchPhaseExact / MatchDropPhase

mapped netlist metric:
  circuit: hyp
  area: 15296.85
  delay: 198729.45
  equivalence: cec pass
```

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
  Evolution History H_i
  (S_area, S_delay, S_overall, e, operator, strategy)
        │
        ▼
  Planner                        Evolver                      Evaluator
  ┌─────────────────────┐        ┌──────────────────────┐     ┌──────────────────────┐
  │ objective hint      │        │ plan-conditioned     │     │ merge + compile       │
  │ diversity pressure  │  plan  │ population evolution │code │ ABC cec equivalence   │
  │ delay stagnation    │───────>│ OpenEvolve islands   │────>│ QoR on ISCAS85/EPFL   │
  │ operator usage      │        │ EVOLVE-BLOCK bounds  │     │ reward R              │
  └─────────────────────┘        └──────────────────────┘     └──────────┬───────────┘
                                                                          │
  ┌───────────────────────────────────────────────────────────────────────┘
  ▼
  accept/reject -> update H_{i+1}, code C_{i+1}
```

### 4.2 核心模块逐个详解

#### 模块 1：Planner

Planner 处理最近 $w=5$ 轮演化历史，计算 objective hint、diversity pressure、delay stagnation 和 operator usage。它输出计划 $\pi_i=(o_i,s_i,m_i)$，其中 $o_i$ 是待演化算子，$s_i$ 是 area-opt/delay-opt/balanced，$m_i$ 描述代码区域、实现方法和预期影响。

#### 模块 2：Evolver

Evolver 以 OpenEvolve 为底层，但把普通 population-based code evolution 改为 plan-conditioned：只允许修改 $o_i$ 的 `EVOLVE-BLOCK`，并且 mutation 要遵循 $s_i$ 的算法提示。这样能把搜索空间从全代码 $X_{\mathrm{all}}$ 收窄到 $X_{o_i,s_i}$。

#### 模块 3：Evaluator

Evaluator 合并改动后的算子与未改代码，先编译，再用 ABC `cec` 做组合等价检查，最后在 benchmark suite 上测量面积/延迟并计算 $S_{\mathrm{area}}$、$S_{\mathrm{delay}}$、$S_{\mathrm{overall}}$。Reward 对编译失败给最严厉惩罚，对等价失败给负惩罚，对有效但回归的代码封顶在 `r_equiv`，允许临时探索。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|---|---|---|---|---|
| Planner | 最近 $w$ 轮 H、C、adaptive signals | evolution plan $\pi_i$ | LLM | 否 |
| Evolver | $\pi_i$、当前算子代码 | evolved code | OpenEvolve、LLM | 否 |
| Evaluator | evolved mapper | R、$S_{\mathrm{area}}$、$S_{\mathrm{delay}}$、$e$ | 编译器、ABC `cec`、mockturtle | 否 |
| Acceptance | evaluation record | accept/reject | 规则 | 否 |

## 5. 关键公式

### 5.1 Mapping 面积与延迟

$$
A(M)=\sum_{v\in V} \mathrm{area}(M(v))
$$

$$
D(M)=\max_{p \in \mathrm{Paths}(G)} \sum_{v\in p} \mathrm{delay}(M(v))
$$

- $G=(V,E)$：technology-independent 逻辑网络，典型为 AIG。
- $M:V\to L$：节点到标准单元库的映射。
- $M(v)$：节点 $v$ 映射到的单元。
- $\mathrm{area}(\cdot)$：单元面积。
- $\mathrm{delay}(\cdot)$：单元最大 pin-to-output 延迟。
- $\mathrm{Paths}(G)$：网络中路径集合。

### 5.2 DelayFlow / AreaFlow / ExactArea

$$
T(v,c,g)=\mathrm{delay}(g)+\max_{l\in c} T(l,\phi_l)
$$

$$
F(v,c,g)=\mathrm{area}(g)+\sum_{l\in c} \frac{F(l,\phi_l)}{\mathrm{fo}(l)}
$$

$$
E(v,c,g)=\mathrm{area}(g)+\sum_{\substack{l\in c\\ \rho(l,\phi_l)=0}} E(l,\phi_l)
$$

- $c$：cut。
- $g$：与 cut 匹配的 library gate。
- $\phi_l\in\{0,1\}$：leaf $l$ 被 gate 输入相位要求确定的输出相位。
- $\mathrm{fo}(l)$：leaf 的估计 fanout 数。
- $\rho(l,\phi_l)$：leaf 在相位 $\phi_l$ 上的当前 reference count。

### 5.3 MatchPhase 的候选代价

$$
C(c,g)=\alpha_r\cdot T(v,c,g)+(1-\alpha_r)\cdot F(v,c,g)
$$

- $\alpha_r\in[0,1]$：第 $r$ 轮 delay/area-flow 的优先级权重。
- delay 轮 $\alpha_r$ 接近 1，area-flow 轮逐渐降低。

### 5.4 演化指标

$$
S_{\mathrm{area}}(M')=\frac{A(M)-A(M')}{A(M)}
$$

$$
S_{\mathrm{delay}}(M')=\frac{D(M)-D(M')}{D(M)}
$$

$$
S_{\mathrm{overall}}(M')=\alpha S_{\mathrm{area}}(M')+(1-\alpha)S_{\mathrm{delay}}(M')
$$

- $M$：原始 mapper。
- $M'$：演化 mapper。
- $\alpha$：实验设为 0.5。
- $S_{\mathrm{overall}}$ 越大越好，但必须同时满足等价失败率 $e(M')=0$。

### 5.5 Objective Hint

$$
h_{\mathrm{obj}}=
\begin{cases}
\text{area}, & n_{\mathrm{area}}>0 \wedge \bar{\Delta}_{\mathrm{delay}}\ge 0,\\
\text{delay}, & n_{\mathrm{delay}}>0 \wedge \bar{\Delta}_{\mathrm{area}}\ge 0,\\
\text{balanced}, & \text{otherwise}.
\end{cases}
$$

- $n_{\mathrm{area}}$：历史中面积改善的轮数。
- $n_{\mathrm{delay}}$：历史中延迟改善的轮数。
- $\bar{\Delta}_{\mathrm{area}}$：面积指标平均变化。
- $\bar{\Delta}_{\mathrm{delay}}$：延迟指标平均变化。

### 5.6 Reward

$$
R=
\begin{cases}
r_{\mathrm{compile}}, & \text{compilation fails},\\
r_{\mathrm{equiv}}-\beta e, & \text{equivalence fails, } e>0,\\
\max(r_{\mathrm{equiv}}, S_{\mathrm{overall}}), & S_{\mathrm{overall}}<0,\\
\dfrac{S_{\mathrm{overall}}}{1+S_{\mathrm{overall}}}, & S_{\mathrm{overall}}\ge0.
\end{cases}
$$

- $r_{\mathrm{compile}}=-0.5$：编译失败惩罚。
- $r_{\mathrm{equiv}}=-0.4$：有效但回归时的封顶值。
- $\beta=0.1$：等价失败率惩罚系数。
- $e$：非等价 circuit 占比。

## 6. 训练与实验设置

### 6.1 是否需要训练

MappingEvolve 不训练或微调 LLM，属于 inference-time 多智能体演化。实验使用 DeepSeek-V3、Qwen3-Max、GPT-5 作为 base LLM。

### 6.2 实验设置

- 硬件：Ubuntu 22.04、Intel Xeon Gold 6226R、256 GB RAM。
- 外层 30 个 MappingEvolve iteration，每个 iteration 内部 3 次 OpenEvolve mutation/selection，合计 90 次 LLM 代码演化调用。
- Ablation 在 ISCAS85 的 11 个 circuit 上做；性能对比在 EPFL benchmark 上、以 ASAP7 为标准单元库。
- 输入 AIG 先用 ABC `compress2` 优化，再调用演化 mapper。
- 等价验证用 ABC `cec`。
- 超参：$\alpha=0.5$、$\tau=-0.1$、$\gamma=0.8$、$w=5$、$r_{\mathrm{equiv}}=-0.4$、$\beta=0.1$、$r_{\mathrm{compile}}=-0.5$。
- 成本：约 100 万 tokens（约 10 美元）与约 1.5 小时完成一次演化流程。

### 6.3 关键实验结果

**Table 1：ISCAS85 上 MappingEvolve 与直接 OpenEvolve 对比**

| Method | Model | Operator | $S_{\mathrm{overall}}$ | $e$ |
|---|---|---|---:|---:|
| OpenEvolve | DeepSeek-V3 | MatchPhase | 0.00 | 0.00 |
| OpenEvolve | DeepSeek-V3 | MatchPhaseExact | 0.00 | 0.00 |
| OpenEvolve | DeepSeek-V3 | MatchDropPhase | 0.02 | 0.09 |
| **MappingEvolve** | DeepSeek-V3 | 三个算子协同 | **0.23** | **0.00** |
| MappingEvolve | Qwen3-Max | 三个算子协同 | 0.18 | 0.00 |
| MappingEvolve | GPT-5 | 三个算子协同 | 0.30 | 0.00 |

该表说明：直接让 LLM 演化单个算子的收益很低，且 `MatchDropPhase` 会产生等价错误；Planner 跨算子调度后，DeepSeek-V3 取得 11.5× 相对提升，且保持零等价失败。

**EPFL/ASAP7 汇总（Table 2 与论文结论）**

| 口径 | ABC | mockturtle | MappingEvolve |
|---|---:|---:|---:|
| Area normalized ratio | 1.0000 | 0.9771 | 0.8996 |
| Delay ratio | 1.0000 | 0.9926 | 1.0369–1.0571 |
| $S_{\mathrm{overall}}$ | 0 | 0.0174 | 0.0255–0.0341 |

论文最终结论：

- 相对 ABC 面积降低 10.04%。
- 相对 mockturtle 面积降低 7.93%。
- 延迟增加 4.46%–6.50%，属于论文明确接受的 area-delay trade-off。
- $S_{\mathrm{overall}}$ 相对 mockturtle 提升 46.6%–96.0%。
- 所有 netlist 都通过 ABC `cec`。

## 7. 创新点

### 创新点 1：把 mapping 核心算法抽象为三个可演化算子

论文不是让 LLM 改整个 mapper，而是识别出 delay/area-flow、exact-area、phase unification 三个高频核心逻辑；`EVOLVE-BLOCK` 给出语义边界，使演化既自由又可验证。

### 创新点 2：Planner 将“战略”从“实现”中解耦

Planner 依据历史指标选择算子与策略，Evolver 才写代码。相比直接 OpenEvolve，跨算子调度避免了反复修改同一算子造成的局部收敛，并能在 area 优化伤害 delay 时自动切到 delay-opt。

### 创新点 3：Reward 保留有效回归与延迟改进

对等价但暂时变差的候选，Reward 封顶在负值而不是无限惩罚；对 delay 改善但 overall 略差的候选，接受条件允许 $\gamma=0.8$ 比例保留。这使演化不会过早丢掉有潜力的局部改动。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

Technology mapping 位于 ③ 逻辑综合内部：输入是优化后的逻辑网络，输出是标准单元网表。MappingEvolve 直接增强该阶段的 mapper，因此下游门级仿真、STA、形式验证和物理设计都会接收新的网表。

### 9.2 从“mapped area 变小”到“能做成芯片”之间隔着什么

论文比较的是 ASAP7 单元库映射后的 area/delay，不包含 floorplan、placement、CTS、routing 引起的单元面积利用、时钟 skew 与互连延迟。此外，延迟增长 4.46%–6.50% 可能在一些设计上超出用户时序预算；等价只保证组合功能，不考虑异步/时序/测试结构等物理实现问题。

## 10. 讨论与局限

### 10.1 论文自述局限

作者明确列出 delay-oriented optimization 是未来方向，说明当前演化主要获得面积收益，delay 指标不是其主要强项；后续需扩展更多 EDA 工具与目标。

### 10.2 代码/复现层面问题

- 完整复现依赖 mockturtle、ABC、ASAP7、OpenEvolve 与闭源/托管 LLM API。
- 演化成本约 100 万 tokens 与 1.5 小时在单轮实验内可控，但扩展到更多 benchmark 或工具会快速放大成本。
- Table 2 排版的表头在 PDF 中跨页，逐列核对时容易把 DeepSeek-V3 与 GPT-5 列错位；本讲解只引用论文结论与可在文本中交叉验证的平均值。

### 10.3 本资料包的批判性分析

该方法把技术映射改进从人工启发式扩展为 LLM 搜索，但仍受三个约束：一是演化训练集只有 ISCAS85，EPFL 泛化未必能覆盖新电路族；二是面积优化可能来自对 benchmark 特性的过拟合，而不是真正发现普适算子；三是 reward 主要基于 mapped area/delay，未考虑功耗和后续物理实现。该方向的关键成功标准应是演化出的代码在公开多 benchmark 上稳定优于人工 mapper，而不只是单个训练/验证集。

## 12. 一分钟复述版

1. Technology mapping 是逻辑综合内把 AIG/逻辑网络映到标准单元库的关键阶段。
2. 已有 LLM 工作主要写综合脚本或调参，不直接改 mapper 核心逻辑。
3. MappingEvolve 从 mockturtle 抽出 MatchPhase、MatchPhaseExact、MatchDropPhase。
4. Planner 决定演化目标和策略，Evolver 在 EVOLVE-BLOCK 内改代码。
5. Evaluator 用编译、ABC `cec`、QoR 三层把关。
6. 直接 OpenEvolve 最好只有 $S_{\mathrm{overall}}=0.02$ 且有等价错误；MappingEvolve 可达 0.23–0.30、$e=0$。
7. EPFL 上相对 ABC 面积降 10.04%，相对 mockturtle 降 7.93%。
8. 代价是延迟增加 4.46%–6.50%，属于明确的 area-delay 权衡。
9. 相对 mockturtle 的 $S_{\mathrm{overall}}$ 提升 46.6%–96.0%。
10. 局限是演化主要面向面积，且真实流片还需要物理设计阶段验证。
