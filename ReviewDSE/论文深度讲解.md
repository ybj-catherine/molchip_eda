## 1. 一句话定位

**ReviewDSE 把开源 EDA 的 DSE 从“搜索公开命令参数”推进到“搜索有保护的源码级 mechanism”**：它把 OpenROAD legalization、DPO 与二者 handoff 中的源码逻辑作为搜索空间，但通过 protected evaluator 固定输入、测量路径、合法性检查和 runtime gate；Level 1 在 calibration designs 上建立 method evidence 与 source-start branches，Level 2 用 Teacher 分配、Student 改写、完整候选重新编译运行并做 full-flow review。在 9 个 target task 上，ReviewDSE 在 2× runtime gate 内平均降低 post-DPL HPWL 1.78%，而公开旋钮 BO-DSE 只降低 0.38%；runtime-aware 选择仍保留 1.68% 改善并把平均 runtime 从 1.34× 降到 1.11×。

这句话里的五个承重点：

1. **搜索单元从 whole patch 变为 reviewed mechanism evidence** — 不是只记住“赢的 diff”或“输的 diff”，而是记录某 mechanism 在哪个 stage、是否被激活、为何被接受或拒绝、是否和下游组合失败。
2. **完整候选仍然必须重新构建和运行** — ReviewDSE 不直接拼接独立插件；每个搜索点是完整源码 workspace $O+\Delta$，避免代码对象与真实 build/evaluator 脱节。
3. **Protected evaluator 是可信边界** — benchmark 输入、设计状态、命令序列、合法性检查、metric parser、runtime gate、比较器和无关工具组件都被固定，候选不能通过改 eval 路径作弊。
4. **Level 1 用 calibration 建立可复用先验** — 不是每个 target 都从空 prompt 随机生成源码修改；先在不同压力/合成设计上识别 promising、fragile、expensive、inactive、non-composable 路线。
5. **应用点是 OpenROAD detailed placement** — legalization、DPO、handoff 是天然有 stage 接口的复杂优化器，适合展示“stage-local 优但不一定能过完整 downstream flow”的问题。

## 3. 输入 / 输出

### 3.1 输入

ReviewDSE 的输入分为三层：

1. target design 状态，例如 incoming global placement、网表和 benchmark collateral；
2. OpenROAD/OpenROAD-flow-scripts 固定 checkout 与 protected evaluator；
3. Level 1 已冻结的 method evidence 和 source-start branches。

```text
target_design:
  name: JPEG
  node: Nangate45
  incoming_global_placement_state: def/lef/collateral

protected_evaluator:
  command_sequence: fixed
  legality_checker: OpenROAD + check_placement
  metric_parser: fixed
  runtime_gate: 2.0
  reference_comparison: default Diamond detailed-placement flow
```

### 3.2 中间产物

Level 1 输出两类 warm-start product：

```json
{
  "method_evidence": {
    "route": "Diamond-sourceTopK",
    "scope": "legalization-DPO handoff",
    "observed_on": ["AES_UTIL70", "JPEG_UTIL90", "SWERV_UTIL60"],
    "verdict": "promising under target patterns"
  },
  "source_start": {
    "branch": "Diamond-sourceTopK-branch",
    "editable_scope": ["legalizer", "DPO", "handoff"],
    "source_anchor": "OpenROAD detailed-placement source"
  }
}
```

### 3.3 输出

Level 2 每次返回完整源码候选及其评测证据：

```text
candidate:
  source_workspace: O + Delta
  build: pass
  strict_legality: pass
  liveness_evidence: present
  full_flow_trajectory:
    H_g: <after global placement>
    H_lg: <after legalization>
    H_ip: <after improve-placement>
    H_f: <final post-DPL>
  runtime: 1.11x_default
  review_outcome: parent_promotion / mechanism_evidence / rejection
```

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
 Level 1: Calibration Warm-Start Construction
 ┌────────────────────────────────────────────────────────────┐
 │ calibration designs (N45, constructed pressure cases)      │
 │ -> parallel methodology exploration + source-start build   │
 │ -> protected evaluator -> method evidence + source branches│
 └────────────────────────────────────────────────────────────┘
                              │ fixed warm-start material
                              ▼
 Level 2: Target-Specific Exploration
 ┌────────────────────────────────────────────────────────────┐
 │ Teacher plans routes / reviews full flow                    │
 │ Student 1..4 in private OpenROAD source workspaces          │
 │ -> build complete O+Delta -> protected evaluator on target  │
 │ -> full-stage metrics/logs/liveness/legality/runtime        │
 │ -> Teacher: promote / evidence / repair lead / reject       │
 └────────────────────────────────────────────────────────────┘
```

### 4.2 核心模块逐个详解

#### 模块 1：Protected Evaluation Contract

该模块解决“源码改写为什么可信”的问题。它固定 benchmark 输入、设计状态、命令、基线 harness、合法性检查、metric parser、参考比较、runtime gate、evaluator 脚本和无关组件。候选不能改测量路径；缺少 canonical metrics、无 liveness、超 runtime gate 或 stale binary 都会失败。

#### 模块 2：Calibration Warm-Start Construction

Level 1 不用 target 本身来预训练搜索。它在校准设计上暴露 stage-local damage、downstream recoverability、constraint pressure、runtime pressure、stage-interface incompatibility，把观察变成 mechanism hypotheses 和完整 source branches。Level 2 只把 Level 1 产物当固定先验，不在 target 搜索中更新全局 warm-start。

#### 模块 3：Target-Case Source Exploration Loop

Level 2 为每个 target 建立独立 local record：baseline、候选、源码引用、diff、Student knowledge cards、Teacher review、peer-learning packet、clean parent。Teacher 在第一轮匹配 target 特征与 Level 1 evidence；之后每个 Student 在私有 workspace 中扩展/切换/重实现机制，并提交完整候选。

#### 模块 4：Teacher Review Decisions

Teacher 不是只看最终 score，而是区分 parent promotion、mechanism evidence、repair lead、negative evidence 和 candidate rejection。一个 mechanism 可能在 stage 层面有帮助但最终 score 丢失，此时它仍作为 evidence 保留；不可激活、太贵或不组合的 mechanism 成为后续搜索约束。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|---|---|---|---|---|
| Protected evaluator | target + source candidate | canonical metrics/logs/liveness/legality | OpenROAD、OpenROAD-flow-scripts | 否 |
| Level 1 methodology exploration | papers/source/domain knowledge | mechanism hypotheses | LLM agents | 否 |
| Level 1 source-start build | mechanism ideas | complete source branches | LLM + build | 否 |
| Level 2 Teacher | local record + Level 1 evidence | routes and review decisions | GPT-5.5 xhigh | 否 |
| Level 2 Students | route + source start | complete $O+\Delta$ candidate | GPT-5.4 xhigh ×4 | 否 |
| Review DB | evaluated candidates | mechanism evidence | Teacher | 否 |

## 5. 关键公式

### 5.1 Stage/Interface Scope 的候选机制池

$$
\mathcal{M}_c=\{p_{c,1},\ldots,p_{c,n_c}\}
$$

- $\mathcal{M}_c$：scope $c$ 中候选 mechanism 池。
- $c\in\mathcal{C}$：一个 stage scope 或两个相邻 stage 的 handoff scope。
- $p_{c,j}$：该 scope 中的一个源码级 mechanism。
- $n_c$：scope $c$ 的候选数量。

### 5.2 候选源码编辑的机制内容

$$
\mathrm{mech}(\Delta)=\bigcup_{c\in\mathcal{C}}\left\{(c,p_{c,j},\theta_{c,j})\mid p_{c,j}\in\mathcal{M}_c(\Delta)\right\}
$$

- $\Delta$：可编辑源码表面上的 admissible edit。
- $\mathcal{M}_c(\Delta)$：候选 $\Delta$ 在 scope $c$ 中实际实现的机制集合。
- $\theta_{c,j}$：机制激活参数，例如权重、阈值、预算、seed、fallback 或 early-stop。
- 该式表示候选的机制内容，不代表论文把 mechanism 做成可独立装配的插件。

### 5.3 Protected Evaluator 记录完整轨迹

$$
E(O+\Delta,d)=\left\{H_g,H_{lg},H_{ip},H_f,L,A,M,T,\tau\right\}
$$

- $E$：protected evaluator。
- $O$：固定 staged optimizer 实现。
- $d$：target design。
- $H_g,H_{lg},H_{ip},H_f$：global placement、legalization、improve-placement、final post-DPL 后的 HPWL。
- $L$：strict legality 结果。
- $A,M$：平均与最大 displacement。
- $T$：runtime。
- $\tau$：traces、liveness counters 与 diagnostics。

### 5.4 Runtime-Aware Selection Score

论文用 higher-is-better 的 runtime-aware score 选择低开销候选：

$$
G_{\mathrm{HR}}=100\cdot\frac{H_f^{\mathrm{Default}}-H_f}{H_f^{\mathrm{Default}}}-P\left(\frac{T}{T^{\mathrm{Default}}}\right)
$$

$$
P(r)=
\begin{cases}
0, & r\le 1.10,\\
\dfrac{\sqrt{r}-\sqrt{1.10}}{\sqrt{2}-\sqrt{1.10}}, & r>1.10.
\end{cases}
$$

- $H_f^{\mathrm{Default}}$：默认 flow 的 post-DPL HPWL。
- $T^{\mathrm{Default}}$：默认 flow 的 runtime。
- $r$：归一化 runtime。
- $P(r)$：对超过 1.10× 的 runtime 施加惩罚；2× runtime 需要约 1 个百分点 HPWL 改善来补偿。

## 6. 训练与实验设置

### 6.1 是否需要训练

ReviewDSE 不训练或微调 LLM。它使用 1 个 Teacher agent（GPT-5.5 xhigh）和 4 个并行 Student agent（GPT-5.4 xhigh），运行 10 个 review iterations。

### 6.2 实验设置

- 工具：固定 OpenROAD/OpenROAD-flow-scripts checkout。
- Target tasks：AES、Ariane133、Ibex、JPEG、SWERV，分别用 ASAP7 与 Nangate45，共 9 个。
- Baseline：public-knob BO-DSE，用 Optuna TPE，每 case 400 trials、4 路并行。
- 比较口径：post-DPL HPWL $\Delta H_f$ 与 normalized runtime 相对默认 Diamond detailed-placement flow。
- 报告只接受能编译、strict legality、完整 protected metrics、source/binary/metric 一致、有 liveness 且在 2× runtime gate 内的候选。
- Level 1 calibration cases 为 JPEG UTIL=90、AES UTIL=70、SWERV wrapper UTIL=60，与 target 分离。

### 6.3 关键实验结果

**Table 4：9-case DSE 结果**

| Design | Default HPWL/runtime | BO $\Delta H_f$/runtime | ReviewDSE-HPWL $\Delta H_f$/runtime | ReviewDSE-GHR $\Delta H_f$/runtime |
|---|---:|---:|---:|---:|
| AES ASAP7 | 42.2k / 5.3s | -0.98% / 1.47× | -1.91% / 1.91× | -1.40% / 1.38× |
| AES N45 | 176.8k / 6.0s | -1.20% / 1.38× | -3.67% / 1.86× | -3.67% / 1.86× |
| Ariane133 N45 | 5.78M / 151s | -0.06% / 0.92× | -5.50% / 0.56× | -5.50% / 0.56× |
| Ibex ASAP7 | 63.3k / 6.9s | -0.10% / 1.10× | -0.60% / 1.17× | -0.60% / 1.17× |
| Ibex N45 | 200.1k / 5.1s | -0.09% / 1.00× | -0.99% / 2.00× | -0.56% / 1.08× |
| JPEG ASAP7 | 134.6k / 23s | -0.63% / 1.39× | -0.94% / 1.00× | -0.94% / 1.02× |
| JPEG N45 | 467.2k / 33s | -0.23% / 1.13× | -1.63% / 0.56× | -1.63% / 0.77× |
| SWERV ASAP7 | 913.9k / 57s | -0.04% / 1.08× | -0.33% / 1.90× | -0.30% / 1.09× |
| SWERV N45 | 3.27M / 34s | -0.09% / 1.08× | -0.49% / 1.07× | -0.49% / 1.07× |
| Mean | — | **-0.38% / 1.17×** | **-1.78% / 1.34×** | **-1.68% / 1.11×** |

表中 $i\#$ 迭代信息与 token 预算在原文单独列出；本表保留主要 QoR/runtime 结果。AES N45 与 Ariane133 N45 分别达到 3.67% 和 5.50% HPWL reduction，且在相当或更低 runtime 上优于 BO-DSE 的可达前沿。

**Full-flow review counterexample：**

- AES dense N45：某 stage-local 更优 legalizer 把 legalization HPWL 降低 0.76%，但 final post-DPL HPWL 反而上升 1.48%。
- JPEG dense N45：最明显，selected legalizer 降低 $H_{lg}$ 14.96%，但经 DPO 与 mirroring 后最终 $H_f$ 恶化 20.96%。
- SWERV dense N45：$H_{lg}$ 降低 0.12%，最终 $H_f$ 仅恶化 0.02%。

这说明只按 stage-local HPWL 接受候选会误导优化。

**Hard cut-row repair：**

- 在 9 个 fragmented row/cut-row stress pattern 上，固定 Diamond/Negotiation route 出现 legality fail 或 7200s timeout。
- ReviewDSE 均恢复 strict legal placement。
- Ariane133/SWERV 中部分 case 还有可用的 legal fixed-source reference，ReviewDSE 同时改善 HPWL 与 runtime。
- BPQUAD 固定 route 全部失败或超时，ReviewDSE 在 563.6–1085.0s 内通过 legality。

## 7. 创新点

### 创新点 1：Protected White-Box DSE 的正式化

论文把源码改写纳入 DSE，但通过 protected evaluator 防止工具重写变成“改测试和 parser 刷分”。它让 source-level search 与外部 flow metrics 保持同一条可信测量路径。

### 创新点 2：Mechanism-Level Evidence 而非 Winning Patch

已有 coding evolution 通常只保留完整 diff；ReviewDSE 保留 mechanism 的 scope、source anchor、liveness、full-flow outcome 与 Teacher decision，因此失败候选仍能贡献可复用负面证据或 repair lead。

### 创新点 3：Teacher-Student 与两级 warm-start

Level 1 calibration 把可迁移方法假设与源码起点先物化，Level 2 再按 target 局部记录演化；Teacher 负责战略，Student 负责具体代码编辑，避免单一 agent 在几十万行 EDA 代码中无方向搜索。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

ReviewDSE 接收已完成 global placement 的 design 状态，进入 ⑧ 标准单元摆放中的 legalization 和 DPO。它交棒的是 post-DPL placement；后续 CTS、routing 和 signoff 仍按原 OpenROAD flow 继续。

### 9.2 从“post-DPL HPWL 变好”到“能做成芯片”之间隔着什么

论文只报告 HPWL、runtime、displacement 与 strict legality。post-DPL HPWL 改善可能不会转换为 routed wirelength 或 timing 改善；候选源码修改也未经过 P&R 后 timing、congestion、power 与 signoff 检查。

## 10. 讨论与局限

### 10.1 论文自述局限

- 当前 protected metrics 覆盖有限，timing、congestion、power、signoff 需要额外评估。
- 搜索成本高：每个 target 平均 2.15B logged tokens 与 0.10B active uncached-input-plus-output tokens，适合高价值设计/硬失败，而非日常批量优化。
- ReviewDSE 做 target-specific specialization，不声称产生普适的 OpenROAD 优化器替换。

### 10.2 代码/复现层面问题

- 论文声明固定 checkout、evaluator scripts 与候选 artifact 被记录，但未在 arXiv 摘要/正文给出公开仓库 URL。
- 实验依赖 GPT-5.5/GPT-5.4、OpenROAD 源码、OpenROAD-flow-scripts 和构造 stress cases，端到端复现门槛较高。
- 同一 target 的 LLM 搜索随机性、API 版本与 token budget 可能影响最佳结果。

### 10.3 本资料包的批判性分析

该工作最有价值的是把“源码级 DSE”做成有可信边界的搜索，但它用 benchmark family 与 target 同源的任务来展示，仍需警惕设计过拟合。源码 specialization 到特定 AES/JPEG/SWERV 实例，可能只在对应 row pattern 与 density 条件下有效；是否推广到未知大型 design 是未来核心问题。另外，当前搜索成本可能超过人工专家针对单个设计做定向源码修改的成本，仍需更好的 evidence reuse 度量。

## 12. 一分钟复述版

1. 普通 DSE 把 EDA 工具当固定可执行文件，只搜索 public knobs。
2. ReviewDSE 让 DSE 进入 OpenROAD 源码中的 bounded mechanisms。
3. 源码修改必须作为完整候选重新编译、运行和评测。
4. Protected evaluator 固定 benchmark、测量路径、合法性、runtime gate。
5. Level 1 用 calibration designs 建立 method evidence 与 source starts。
6. Level 2 用 Teacher + Student 在 target design 上做源码级搜索。
7. 搜索知识是 mechanism evidence，不是单纯 winning patch。
8. 9 个 target 上平均 HPWL 降 1.78%，公开旋钮 BO 只降 0.38%。
9. Runtime-aware 选择保留 1.68% 改善，平均 runtime 1.11×。
10. 局限是成本高、未覆盖 timing/congestion/power/signoff，且目标是 design-specific specialization。
