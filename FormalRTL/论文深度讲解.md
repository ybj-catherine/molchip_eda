# FormalRTL 论文深度讲解

> **FormalRTL: Verified RTL Synthesis at Scale**
> 香港中文大学 + 东南大学 + 华为 · arXiv 预印本（2026-02-25，arXiv:2603.08738v1，未见会议录用信息）
> 原文：[2603.08738_FormalRTL.pdf](./2603.08738_FormalRTL.pdf)（8 页，本地已下载并全文核对）
> 代码：论文承诺开源框架与 benchmark 套件，截至核验时未核实公开仓库

> ⚠️ **定位提示**：这是一项 RTL 生成工作，目标是自动写出 RTL 并用形式方法证明其正确，而不是直接扫描既有 RTL。其核心闭环是“C 参考模型作为可执行规格 + C-RTL 等价性检查 + 反例引导修复”。

---

## 1. 一句话定位

**FormalRTL 把 C/C++ 软件参考模型当作「可执行的形式化规格」来锚定 LLM 的 RTL 生成：先用 Clang 编译器对 C 模型做 AST 静态分析，把设计确定性地拆成子模块并按拓扑序自底向上生成，每个子模块生成后立即用 hw-cbmc 做软硬件形式等价性检查（EC），失败则把 EC 反例喂给 LLM 引导修复——在 Berkeley SoftFloat FP16 与华为昇腾 HiFloat8 等工业级数据通路上（最难一例总依赖代码 1129.95 行）做到高最终成功率，而纯规格驱动的单体基线在最大设计上成功率 0%。**

四个承重点，逐一拆：

1. **参考模型升格为形式化规格**——不再依赖可能含糊的自然语言规格做规划，而是直接从 C 模型的函数依赖结构（AST）出发分解任务。「架构写在 C 代码里」，比写在文档里精确。这呼应工业传统：Synopsys HECTOR、Cadence Jasper C2RTL 本来就拿 C 模型做高层等价性检查，LLM 时代此前却没人用上这份资源。
2. **静态分析分解 + 拓扑序自底向上验证**——分解是编译器（Clang）干的确定性活，不是 LLM 拍脑袋；每个子模块先于其使用者被形式化验证，写顶层时所有依赖已是「已证正确」，顶层负担大减（反直觉结果：顶层 ISR 反而高于 leaf/mid）。
3. **timeframe 的双重角色**——时序逻辑的验证 harness 需声明「硬件几个周期出结果」，这个参数既触发 transactional equivalence checking，又是流水线深度的设计旋钮。
4. **反例引导调试（counterexample-guided debugging）**——EC 工具保证任何等价失败都产出一个反例（分歧输入）；bug locator 给语法错抽取错误行上下文、CE simplifier 给反例只留问题函数与 mismatch 信号，LLM 修复从「盲猜」变「有据」。消融显示去掉反例引导后 FSR 从 95% 掉到 55%——这是全系统的命脉部件。

## 2. EDA 阶段映射（①-⑰）

FormalRTL 是少有的**同时落在 ① 和 ②** 的工作：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅（主业） | LLM 生成 RTL 代码，且是 1000+ 行规模的工业级数据通路 |
| **② 功能验证** | ✅（形式化路线） | 不写传统 testbench，用 hw-cbmc 做 C-RTL 形式等价性检查；harness 自动生成 |
| ③~⑰ 其余 | ❌ | QoR 评估用到 Yosys 综合 + OpenROAD 布局布线，但只是评价手段，不介入流程 |

**覆盖率：约 1.5/17（阶段 ① 主业 + 阶段 ② 形式等价验证）。**

> **边界提醒**：它的「验证」是**验证生成物**（证明 LLM 写的 RTL ≡ 可信 C 模型），不是**验证既有设计**（抓别人 RTL 里的 bug）。同一套 EC 机器，输出是「修复」还是「报告」，就是生成方向与验证方向的分界。

## 3. 输入 / 输出

### 3.1 输入

| 输入项 | 必需 | 格式 | 说明 |
|--------|:---:|------|------|
| C/C++ 软件参考模型 | 是 | 可编译 C 代码 | **trusted**——被预设为正确的「可执行黄金规格」，是整个流程的锚 |
| 设计规格 | 是 | 自然语言（工业风格） | 含特殊情形处理、时序需求；benchmark 里由作者按工业惯例撰写 |

### 3.2 中间产物

- **子模块目标规格**：LLM 把主规格按 C 子函数重写成每个子模块一份；
- **初始 RTL + verification harness**：harness 假设 C 与 RTL 输入相同、断言输出等价；
- **EC 反馈**：语法错误（带行号）或反例（分歧输入与 mismatch 信号值）。

### 3.3 输出

**经形式化验证的 RTL**（C-RTL EC 通过）。附带 QoR 数据（Yosys + Nangate45 + OpenROAD 综合/布局布线的面积与延迟）。

## 4. 方法与架构

### 4.1 三 Agent 流水线

```text
输入：C 参考模型 + Spec
            │
┌───────────┴──────────────┐
│ Planning Agent（GPT-4.1）  │
│  Clang AST 静态分析：        │
│   每个 C 函数 + 依赖打包      │
│   （宏/枚举/常量）           │
│  LLM 重写子模块级规格        │
│  定拓扑序（依赖先于使用者）    │
└───────────┬──────────────┘
            │  按拓扑序逐个 submodule
┌───────────┴──────────────┐
│ Initializing Agent（GPT-5）│
│  输入：该子模块 C 参考 +      │
│        所有已验证依赖 RTL     │
│  输出：初始 RTL + harness    │
│  时序逻辑 → 定 timeframe     │
└───────────┬──────────────┘
            │
        Soft-Hard EC（hw-cbmc）
        ├─ pass → 下一子模块 / 全部完成则合并
        └─ fail ─┐
┌───────────────┴──────────┐
│ Debugging Agent            │
│ （GPT-4.1，5 轮未修复升级 GPT-5）│
│  语法错 → Bug Locator：      │
│    抽取错误行周围代码          │
│  反例 → CE Simplifier：      │
│    只留问题函数 + mismatch 信号│
│  LLM 产出「定位 + 补丁」→ 应用 │
└───────────────────────────┘
```

### 4.2 分解策略的三个收益（论文原述）

1. 基于 C 函数层次的规划比纯规格规划**可靠**；
2. 分解把每次 EC 的规模**控制在可行范围**，工具反馈快；
3. **自底向上验证哲学**：每个子模块对它的 C 函数做形式化等价检查，依赖先证对，顶层调试负担小。

### 4.3 反例长什么样（Fig. 3 实例）

```text
CE Simplifier 输出（hifloat8_mul）：
  input for function hifloat8: ...
  mismatched values:
    C reference model      Verilog implementation
    status_c = 0           c = 1
    z_c = 128              z_c = 127
```

一个具体输入，两边输出逐信号对照——这就是「bug 的完整案发现场」。LLM 拿着这个去定位补丁，远比拿一句「FAIL」有效。

## 5. 关键公式

$$
\text{ISR} = \frac{N_{\text{pass}}}{N_{\text{total}}}\times 100\%
\quad(\text{首次生成即通过 EC，相当于 pass@1；}N_{\text{total}}=20)
$$

$$
I'_j = \begin{cases} I_j & \text{run } j \text{ 通过}~(I_j \le I_{\text{limit}})\\ 2\times I_{\text{limit}} & \text{run } j \text{ 失败（罚分）}\end{cases}
\quad(I_{\text{limit}}=20)
$$

再取 $I_{\text{avg}}$、$I_{\text{std}}$；**FSR** = 在迭代上限内修复成功的运行占比。

与单体基线对比用的总工作量：

$$
I^{\text{module}}_{\text{total}} = I^{\text{module}}_{\text{avg}} + \sum_{i\in\text{dependencies}} I^i_{\text{avg}}
$$

设计级 FSR = top 模块 FSR × 所有依赖子模块 FSR 之积。

**工程直觉**：失败罚分（记 2×limit）防止「失败运行不占迭代预算」的统计假象；设计级 FSR 用连乘，意味着**一个子模块崩了整个设计归零**——这是自底向上策略必须每个子模块都硬的数学原因。

## 6. 训练与实验设置

**不需要训练**，直接调商用 LLM（Langchain 搭建）：

| Agent | 模型 | 理由 |
|---|---|---|
| Planning | GPT-4.1 | 按 C 子函数细化规格，中等推理即可 |
| Initializing | GPT-5 | 生成高质量 RTL，需要强推理 |
| Debugging | GPT-4.1 → GPT-5 | 先快修，5 轮不愈再升级强模型 |

静态分析用 **Clang**；等价性检查用学术工具 **hw-cbmc**（DAC 2017）。

### 6.1 Benchmark

| 类别 | 案例 | 准备过程 |
|---|---|---|
| 学术 | Berkeley SoftFloat FP16 算子（f16_add/sub/mul/le/roundToInt 等，IEEE 754） | Clang 合并散落的子函数到单文件 → 人工清理至可独立编译 → 作者撰写工业风格规格 |
| 工业 | 华为昇腾 Ascend **HiFloat8** 乘法/加法（8 位浮点，AI 芯片专用格式） | 作者手写 C 参考模型 + 参照 IEEE 754 写详细规格 |

共 23 行子模块结果（含 2 个时序版变体）；**最难一例 f16_add 总依赖代码 1129.95 行**。

### 6.2 主表（Table 1）关键数字

| 模块 | 类型 | ISR | I_avg | FSR | 总行数 |
|---|---|---|---|---|---|
| f16_add | top | 65% | 1.00 | 100% | 1129.95 |
| subMagsF16 | mid | **5%** | 9.25 | 95% | 700.25 |
| f16_mul | top | 15% | 7.30 | 95% | 565.75 |
| hifloat8_mul | top | **95%** | 0.05 | 100% | 684.35 |
| hifloat8_add（sequential） | top | 20% | 16.00 | 70% | 981.99 |
| hifloat8_mul（sequential） | top | 60% | 9.65 | 80% | 757.35 |

**读法**：ISR 普遍不高（5%–95%）说明商用 LLM 一次写对工业级模块很难；但 FSR 几乎全在 85%+ → **调试闭环才是把活干成的部件**。时序版本明显更难（ISR/FSR 双降）。

### 6.3 规划方法消融（Fig. 4）

基线 = 模拟现有 spec-only 范式（C 模型仅作为非结构化文本塞进规格，整个设计单体生成+调试，迭代预算对齐 $I_{\text{total}}$）：

| 设计 | 总行数 | 总修复迭代（Ours/Baseline） | FSR（Ours/Baseline） |
|---|---|---|---|
| f16_roundToInt | 210 | 5 / **0.6** | 100% / 100% |
| hifloat8_mul | 685 | 22.4 / 24.2 | 95% / 65% |
| hifloat8_add | 818 | 23.9 / 34.1 | 95% / 40% |
| f16_add | 1130 | 28 / 60 | **81% / 0%** |

小设计基线占优（一轮能顺手修全部子模块）；**规模一大基线崩塌——最大设计成功率 0%**，而 FormalRTL 仍保持 81%。这是「分解 + 自底向上」的规模化证据。

### 6.4 调试部件消融（Table 2，normalize 模块）

| 配置 | 平均迭代 | FSR |
|---|---|---|
| **FormalRTL 完整** | **6.40** | **95%** |
| 去掉 bug locator | 14.15 | 80% |
| 去掉 CE simplifier | 9.55 | 90% |
| 去掉反例引导调试 | 21.30 | **55%** |

反例引导是生死部件；两个「降噪工具」（locator/simplifier）各砍约一半迭代。

### 6.5 QoR（Table 3，vs 工程师手工优化版）

| 模块 | FormalRTL 面积/延迟 | 工程师 面积/延迟 |
|---|---|---|
| hifloat8_mul | 1015 μm² / 3.29 ns | 743 μm² / 1.78 ns |
| f16_mul | 1629 μm² / 3.54 ns | 1343 μm² / 2.50 ns |

面积落后约 20–37%、延迟约 1.4–1.9×。论文立场：先保**形式化正确**，PPA 迭代留给后续（且有一个被证明正确的基线 + 稳定黄金参考，PPA 优化才敢放手做）。

## 7. 创新点

1. **首个把软件参考模型系统性升格为 LLM-RTL 合成「形式化锚」的方法学**——此前 LLM 生成工作只用自然语言规格，浪费了工业界早已依赖的可执行黄金规格；
2. **编译器静态分析驱动的规划**——分解是 Clang 的确定性输出，可复现、不随 LLM 抽风；规划可靠性高于 spec-only；
3. **自底向上形式化验证**——依赖先证对再往上盖，顶层 ISR 反超 leaf/mid 的反直觉收益；
4. **timeframe 双重角色**——一个参数同时是「transactional EC 的触发条件」和「流水线深度旋钮」，把验证需求与设计微架构显式打通；
5. **工业级 benchmark（规格 + C 参考成对）**——SoftFloat + HiFloat8，承诺开源，补上「工业级 RTL 生成」评测缺口。

## 8. EDA 缩写表

| 缩写 | 全称 | 一句话解释 |
|------|------|-----------|
| EC | Equivalence Checking | 等价性检查：证明两个实现（这里是 C 与 RTL）功能等价 |
| hw-cbmc | Hardware CBMC | 学术 C-RTL 等价性检查工具（DAC 2017），基于有界模型检查 |
| BMC | Bounded Model Checking | 有界模型检查：在有限步数内穷举搜索反例 |
| transactional EC | — | 事务级等价：不逐周期比，按「事务」（timeframe 个周期）比输入输出 |
| timeframe | — | harness 声明的硬件出结果周期数；既是 EC 参数又是流水线设计旋钮 |
| AST | Abstract Syntax Tree | 抽象语法树，Clang 用来做函数依赖分析 |
| ISR / FSR | Initial / Final Success Rate | 首次通过率（pass@1）/ 迭代上限内最终修复率 |
| QoR | Quality of Result | 综合后面积/延迟等物理结果质量 |
| PPA | Power, Performance, Area | 功耗/性能/面积，芯片设计三指标 |
| HECTOR | Synopsys HECTOR | 商用高层等价性检查工具（C vs RTL） |
| Jasper C2RTL | Cadence Jasper C Apps | 商用 C-RTL 形式等价验证 |
| SoftFloat | Berkeley SoftFloat | IEEE 754 浮点运算的 C 参考实现库 |
| HiFloat8 | Ascend HiFloat8 | 华为昇腾 AI 芯片的 8 位浮点格式 |
| HLS | High-Level Synthesis | 高层综合（C→RTL），FormalRTL 与之对照：不综合，由 LLM 写 |

## 9. 与芯片流程和相关工作的关系

FormalRTL 位于规格到 RTL 的生成与形式验证闭环：C 参考模型既提供生成锚点，也提供 C-RTL 等价检查的形式化规格。hw-cbmc 返回的反例被送给调试 Agent，形成“生成—证明—修复”的闭环。

这套方法说明 C 参考模型与等价检查可以扩展到千行级算术数据通路，但它预设参考模型可信，并主要覆盖 bit-exact 的数值计算设计。控制密集、协议驱动或允许数值容差的设计仍需要额外的比较策略；论文也没有评估自然历史缺陷上的检出率。

## 10. 讨论与局限

论文自述三条未来工作 + 本资料包批判性补充：

1. **规模仍有差距**：验证到 1000+ 行，距真正工业 IP（万行级）还远；分解策略是路径但未被大规模证实；
2. **依赖模型读懂反例的能力**：计划训练专用小模型做反例修复，说明当前靠 GPT-5 硬扛成本高；
3. **开源 C-RTL EC 工具稀缺且年久失修**（hw-cbmc 是 2017 年的）——社区需要支持现代 RTL 语法的新工具，复现这条路线前必须先解决形式化后端兼容性；
4. （批判）对象清一色 bit-exact 算术通路，控制逻辑/协议类设计的 EC 可扩展性未知；
5. （批判）QoR 落后人工 20–40% 面积、近 2× 延迟——「验证过的正确」≠「可流片的优秀」；
6. （批判）benchmark 的规格与 HiFloat8 C 参考均为作者手写——**「参考模型自身正确」这条信任链未被独立验证**，与 ChipModeler 的 FP≠100% 是同一个坑；
7. （批判）hw-cbmc 是**有界**模型检查，timeframe/bound 的选择本身是人为决定，完备性不等于数学完备。

## 12. 一分钟复述版

1. **做什么**：给可信 C 参考模型 + 规格，LLM 自动写 RTL，并用形式等价性检查**证明** C ≡ RTL。
2. **怎么写**：Clang AST 拆模块 → 拓扑序自底向上 → 生成子模块 + harness → hw-cbmc 等价检查 → 失败用反例引导 LLM 修复。
3. **关键数字**：最难设计 1129.95 行，单体基线 0% vs FormalRTL 81%；去掉反例引导 FSR 95% → 55%；时序逻辑是硬骨头。
4. **为什么重要**：首次把工业界惯用的「C 模型当形式规格」系统性接进 LLM 生成闭环，且规模到工业级数据通路。
5. **不做什么**：不给既有 RTL 找 bug、不解决「C 模型从哪来/错了怎么办」、对象限于 bit-exact 算术通路。
6. **研究延伸**：同一套 EC 机制也可用于报告 C 与既有 RTL 的分歧，但这属于论文没有直接评估的扩展方向。
7. **一句话**：FormalRTL 证明有可信 C 参考模型时，LLM 可以生成 RTL，并通过等价检查与反例反馈持续修正。
