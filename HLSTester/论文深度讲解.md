## 1. 一句话定位

**HLSTester 自动改造 C/C++ testbench，用 backward slicing 找关键变量、让 GPT-4o 生成输入并结合 8 类动态变异，比较软件执行与 Vitis HLS/FPGA 行为；在 10 个任务上，完整系统相对基础随机测试把不一致检测速度提升 2.71 倍。**

这里的目标不是验证任意 C 程序，而是找出软件语义与 HLS 后实现语义之间的不一致，例如定宽整数溢出、截断、静态数组越界或流水线数据依赖造成的差异。LLM 负责理解代码和提出候选输入，运行时谱与变异反馈负责把搜索集中到更可能触发差异的边界区域。

## 3. 输入 / 输出

### 3.1 输入

输入是 HLS C/C++ kernel、原 testbench 和目标综合环境。下例在普通 `int` 和 HLS 定宽整数间可能产生不同溢出解释：

```cpp
#include <ap_int.h>
ap_int<8> mac(ap_int<8> a, ap_int<8> b, ap_int<8> c) {
  ap_int<8> y = a * b + c;
  return y;
}
```

HLSTester 改造 testbench，使输入可由生成器注入、结果可分别从软件路径与 HLS 路径收集：

```text
candidate = {a: 127, b: 2, c: 1}
software_reference(int): 255
HLS_ap_int<8>:           -1
status: inconsistency exposed
```

### 3.2 中间产物

Backward slicing 从待比较输出反向追踪影响变量，减少交给 LLM 的无关代码。LLM 在切片上下文中给出初始测试；仪器化程序记录关键变量和值域，动态变异器根据哪些变异曾成功触发新行为来更新 8 类 operator 的概率。

八类变异为 size、dimension、zero、order、element、type、bit 和 byte。初始测试约 30% 由 LLM 直接产生，其余通过动态变异扩展。冗余过滤器再移除相似或无法带来新覆盖/差异的候选，减少昂贵的 HLS 调用。

### 3.3 输出

输出是能稳定重现差异的测试输入、两条执行路径的输出以及触发位置，例如：

```json
{
  "kernel": "mac",
  "input": {"a": 127, "b": 2, "c": 1},
  "software_output": 255,
  "hls_output": -1,
  "mismatch": true,
  "suspected_cause": "8-bit truncation/overflow"
}
```

它不是补丁生成器；工程师需判定期望语义，并修改类型、边界检查、pragma 或参考模型。

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
HLS C/C++ + original testbench
              |
              v
      adapt testbench for automated injection
              |
              v
 backward slicing -> LLM-guided instrumentation
              |
              v
  GPT-4o initial tests (30%) + dynamic mutations (70%)
              |
              v
 software run <-> Vitis HLS / FPGA behavior comparison
              |
              v
    feedback update + redundant-test filtering
              |
              v
       minimal mismatch-triggering tests
```

### 4.2 Testbench 改造与切片

原始 benchmark 往往把输入写死或混有文件 IO。第一步统一输入接口和输出采集。随后从目标输出做 backward slicing，只保留能影响结果的变量与语句；这既缩短 LLM 上下文，也让运行时 instrumentation 更聚焦。

### 4.3 LLM 推理与动态变异

LLM 根据类型、数组维度、循环和边界条件提出种子输入，并允许最多 5 轮逐步修正。动态变异不是均匀随机：某类 operator 一旦找到有效新测试，其选择概率增加，其他 operator 略减。这样保留 LLM 的语义启发，同时避免每次都支付一次生成调用。

### 4.4 模块职责矩阵

| 模块 | 输入 | 输出 | 工具/模型 | 是否训练 |
|---|---|---|---|:---:|
| TB adapter | 原 testbench | 可注入测试环境 | 规则 + LLM 辅助 | 否 |
| Slicer | HLS C/C++、目标输出 | 相关语句/变量 | backward slicing | 否 |
| Initial generator | 切片代码、提示 | 语义种子 | GPT-4o | 仅闭源模型推理 |
| Mutator | 种子、历史反馈 | 新输入 | 8 类动态变异 | 在线概率更新 |
| Executor | 测试输入 | 双路径输出 | C simulation、Vitis HLS | 否 |
| Filter | 测试与执行谱 | 去冗余测试集 | 相似性/新颖性判据 | 否 |

## 5. 关键公式与判据

### 5.1 变异 operator 的初始概率

$$
P_m^{(0)}=\frac{1}{l}=\frac{1}{8}=0.125
$$

- $P_m^{(0)}$：第 $m$ 类变异的初始选择概率
- $l$：变异类别数，论文设置为 8

初始均匀分布不预设哪种错误更常见，让反馈自行调整。

### 5.2 成功变异后的概率更新

$$
P_m^{(t+1)}=P_m^{(t)}+\alpha
$$

- $P_m^{(t)}$：第 $t$ 轮时成功 operator 的概率
- $\alpha$：更新步长，论文设置为 0.04

$$
P_j^{(t+1)}=P_j^{(t)}-\frac{\alpha}{l-1},\quad j\ne m
$$

- $P_j^{(t)}$：其他 operator 的当前概率
- $j$：任一未在本轮成功的变异类别
- $l$：operator 总数

一增多减保持概率总量不变。实际实现还需要边界裁剪或归一化，避免多轮后出现负概率；公开正文对该工程细节描述有限。

### 5.3 检测加速比

$$
S=\frac{T_{\mathrm{baseline}}}{T_{\mathrm{method}}}
$$

- $S$：检测速度提升倍数
- $T_{\mathrm{baseline}}$：基础测试找到不一致所需时间
- $T_{\mathrm{method}}$：HLSTester 找到同类不一致所需时间

速度倍数必须结合重复次数和工具环境理解，不能直接当作覆盖率或准确率。

## 6. 训练与实验设置

### 6.1 是否需要训练

作者没有训练专用模型，使用 GPT-4o 推理。实验以 AMD Vitis HLS 和 Xilinx Virtex UltraScale+ XCVU9P-FLGA2104I 为 HLS/FPGA 环境，主机为 Intel Xeon Silver 4314。每个任务重复 15 次，LLM progressive correction 最多 5 轮。

### 6.2 Benchmark

10 个任务为 genetic algorithm、depth-first search、AES、KNN、graph coloring、median filter、DNN、edge detection、QR decomposition 和 breadth-first search，覆盖数组、图、密码、线性代数与图像 kernel。比较基础输入生成、TB 改造、LLM 推理、动态变异和过滤等组件。

### 6.3 关键结果

| 组件/完整方法 | 论文报告的收益 |
|---|---:|
| testbench modification | 检测能力提高 20.67% |
| LLM progressive reasoning | 检测速度 1.81× |
| dynamic mutation | 检测速度 2.28× |
| redundancy-aware filtering | 检测能力提高 15.73% |
| **完整 HLSTester** | **相对 baseline 2.71× 检测速度** |

这些数字来自不同组件实验，不能简单相乘。论文强调的是在相同任务上更快触发差异，而不是证明全部可能的不一致都被覆盖。

## 7. 创新点

### 7.1 把 LLM 放在“理解边界条件”而非直接判正确性的位置

LLM 提出高价值输入与 instrumentation，最终 mismatch 仍由可执行的两条路径比较。这比让模型凭代码文本猜 bug 更可审计。

### 7.2 语义种子与反馈变异结合

LLM 只贡献约 30% 初始输入，后续用便宜的动态 mutation 扩展。概率更新让搜索适应当前 kernel 的差异类型。

### 7.3 针对 HLS 接缝组织完整测试流程

方法不仅生成数值，还处理 testbench 适配、切片、仪器化、执行和冗余过滤，针对 HLS 工具调用昂贵这一现实约束优化总流程。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

上游是算法工程师写好的 HLS C/C++ 和测试；HLSTester 在软件语义与 HLS 结果之间寻找反例；下游是修订 C/C++ 类型/边界/pragma，并再次跑 C simulation、C/RTL co-simulation、综合与实现。它可在 RTL 大规模验证前发现高层语义断裂，减少后续调试成本。

### 9.2 “找到不一致”距离“能做成芯片”还有什么

不一致需要先归因：软件参考是否使用相同定宽语义，越界是否本就未定义，HLS pragma 是否允许该调度。修复后还要验证协议接口、延迟、吞吐、资源、时序、功耗以及 FPGA/ASIC 后端。论文的成功指标不包含 PPA 或 signoff。

## 10. 讨论与局限

### 10.1 证据边界

实验只有 10 个任务，且以单一商业 HLS 工具和一款 FPGA 为主要环境。结果不自动外推到 Intel HLS、Catapult、Bambu 或 ASIC HLS。差异 oracle 若没有统一定宽类型，也可能把预期的语义差异当成缺陷。

### 10.2 代码与工具门槛

截至整理日未核验到稳定官方代码仓库。GPT-4o 和 AMD Vitis HLS 都带来版本、费用与许可依赖；论文没有提供足够证据证明换用其他 LLM 或开源 HLS 能保留 2.71×。本地只完成原文归档与事实核对，未重跑实验。

### 10.3 本资料包的判断

可发表的延伸不应只替换 LLM。更有价值的是建立开源、跨 HLS 工具的差分 oracle，区分未定义 C 行为、合法定宽语义、调度错误和真正的工具缺陷，并报告每类 bug 的 detection latency、有效测试率和 HLS 调用成本。

## 12. 一分钟复述版

HLSTester 找 C/C++ 软件执行和 HLS/FPGA 结果之间的不一致。它先改造 testbench，再从输出做 backward slicing，把关键代码交给 GPT-4o 生成初始测试并指导 instrumentation。约 30% 输入来自 LLM，其余由 size、dimension、zero、type、bit、byte 等 8 类动态变异产生；成功 operator 的概率按步长 0.04 增加。系统执行软件与 Vitis HLS 两条路径，过滤重复输入并保留 mismatch。10 个任务、15 次重复实验中，完整方法相对 baseline 报告 2.71× 检测速度。它属于 HLS 前端验证，不涉及后端 PPA 或芯片安全；代码未确认公开，商业工具与闭源模型使独立复现受限。
